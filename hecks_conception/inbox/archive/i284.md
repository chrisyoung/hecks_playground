# i284 — strict bare-name dispatch ambiguity check — runtime errors when a bare command name resolves to multiple aggregates

strict bare-name dispatch ambiguity check — runtime errors when a bare command name resolves to multiple aggregates

i155 (commit 63b9a870) lifted per-aggregate command-name uniqueness so the natural UL verbs (Plan / Apply / Revert) coexist on Layout AND Move. The corresponding runtime resolve() change — error on bare-name ambiguity instead of first-match-wins — was REVERTED in the same commit because it surfaced 15 cross-bluebook collisions in the corpus :

  - Express : Conversation + Mood
  - many heartbeat / mood / boot / domain_cell tests use bare setups that silently rely on first-match-wins via the merged corpus

Today's resolve() keeps first-match-wins. UL is unblocked (Restructure works), but cross-bluebook bare-name dispatch can silently target the wrong aggregate.

The proper fix has three parts :

  1. Validator extension — check the FULL LOADED corpus for cross-bluebook command-name collisions (today's validator only sees one bluebook). Surfaces the implicit dependency the corpus is built on.

  2. Corpus migration — every cross-cascade behaviors test that uses a setup matching a multi-bluebook command must FQN-prefix the setup. Likely 15-30 setups across the 15 files identified in i155's pre-push failure.

  3. resolve() restored — re-enable strict ambiguity error on bare-name dispatch. Once corpus migrated and validator catches future regressions, runtime can be strict.

Acceptance :
  - Validator reports cross-bluebook collisions
  - Pre-push behaviors green with strict resolve()
  - Restructure + integration tests still pass
