# i362 — Behaviors-runner parity bug: Ruby and Rust runners disagree on how setup-chain integer state propagates into downstream

Behaviors-runner parity bug: Ruby and Rust runners disagree on how setup-chain integer state propagates into downstream given clauses evaluated during a cascade. Concretely: given a setup of EnterDaydream + EnterSleep (which sets sleep_cycle=1 sleep_total=8), and a test command WakeUp kind: :cascade, a downstream policy-triggered command with given { sleep_cycle < sleep_total } — (1) the Ruby runner evaluates the given against sleep_cycle=0 sleep_total=0 (integer defaults), so the check is 0 < 0 = false and the refused-path fires; (2) the Rust runner correctly evaluates against 1 < 8 = true and the ok-path fires. Direct command dispatch (not via the behaviors runner) evaluates correctly in both. Rust is right. Discovered 2026-04-20 while wiring the wake mood ladder (ClassifyFullWake vs ClassifyPartialWake). Workaround: drop the cascade emits assertion and use expect ok: 'true' plus direct-dispatch isolated tests. Fix: Ruby runner should thread setup-phase then_set writes through to downstream command contexts the same way Rust does.
