# i369 — singleton-policy identifier propagation — leaked upstream identified_by causes orphan records on every cascade tick

singleton-policy identifier propagation — leaked upstream identified_by causes orphan records on every cascade tick

Symptom : statusline reads mood=refreshed and fatigue_state=alert after 191k+ heartbeats. Body structurally frozen ; mood transitions never fire.

Diagnosis (heki dump of heartbeat.heki) : 14,618 records with distinct numeric ids (1, 10, 100, 1000, 10000, ...) ; pulses_since_sleep distribution {1: 14611, 0: 2, None: 4, 83: 1} ; fatigue_state {alert: 14618}. Virtually every cascade tick was creating a NEW heartbeat record at pulses=1 instead of upserting the singleton.

Root cause : event cascades carry the upstream aggregate's full attrs in event.data. When that data reaches a downstream command (e.g. AccumulateFatigue triggered by FatigueOnPulse on BodyPulse), the upstream's identified_by field (e.g. Tick's name=tick or Pulse's name=pulse) is in the data map. command_dispatch::id_for_command honors attrs[identified_by_key], so the heartbeat record gets created with id="tick" or id="pulse".

inject_refs in runtime/mod.rs DID try to fix this — checking « key present but value doesn't match any record » and overriding with lex-min existing record. But the override only works when the repo already has records ; on fresh repos (and on every empty-singleton boot), pick=None and the leaked id passed through anyway, creating the first orphan. After that, lex-min picks the orphan name and keeps creating siblings.

Fix shipped (commit <SHA>) : in runtime/mod.rs::inject_refs, when needs_inject=true and pick=None (empty repo), REMOVE the leaked identified_by key from data so id_for_command counter-mints a fresh id rather than inheriting the upstream id. Verified by clean experiment :
  - rm heartbeat.heki
  - 5 × Tick.MindstreamTick → ONE record, id="1", pulses_since_sleep=5, fatigue=0.005
  Before fix : 5 records with ids tick / 14619 / 14620 / 14621 / 14622, all pulses=1.

Class of bugs this closes : every singleton aggregate downstream of a named-key emitter (Heartbeat ← Pulse ← Tick ; Mood ← Heartbeat events ; Awareness ← BodyPulse ; Consciousness sleep cascades) was vulnerable to first-dispatch identifier inheritance. The fix is one match arm — minimal blast radius.

Affected aggregates surveyed : Heartbeat (this incident), Mood (mood transitions never reached the threshold-crossing events because Heartbeat was orphaning), Awareness (4 BodyPulse subscribers), Consciousness (4 BodyPulse subscribers in sleep). All operationally suspect with the same shape ; all structurally cured by this fix.

Cleanup followup : 14k orphan numeric-id heartbeat records existed when this was diagnosed. The clean experiment (rm + tick) wiped them by replacing the heki with a fresh single-record store. Other aggregates may carry similar orphans accumulated over the project's history — worth a sweep when convenient, but they're inert (lex-min picks the canonical singleton, orphans never get touched).

Out of scope here : this fix targets the EMPTY-REPO path. The post-orphan path (where leaked-name records exist as orphans) is structurally cured because lex-min picks something, but if multiple cascades create different leaked-name records (e.g. id="tick" and id="pulse" both as Heartbeat orphans), lex-min would oscillate. The clean experiment shows fresh state heals correctly ; the long-term invariant is « bluebook declares natural singleton key explicitly ». Filing as i152 candidate if observed.

Status : closed.
