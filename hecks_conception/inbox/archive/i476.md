# i476 — Retire inbox heki : update bluebook persistence, statusline, retire inbox.sh

After PR #603 (markdown convention) and the two migration sweeps that
followed, every inbox card now lives as a markdown file in
`hecks_conception/inbox/` (active) or `hecks_conception/inbox/archive/`
(closed). The three heki stores still on disk are now duplicates of
the markdown — last-written-wins between two sources of truth.

**Stores still on disk after the migration :**

  hecks_conception/information/inbox/inbox.heki         (144 records)
  hecks_conception/information/inbox/inbox_archive.heki ( 88 records)
  miette-state/information/inbox/inbox.heki             (138 records)

**What still reads them (verified 2026-05-07 grep) :**

  rust/src/run_statusline.rs  — counts status=queued for the statusline display
  rust/src/run_boot/classify.rs — comments + read paths
  hecks_conception/inbox.sh    — ~146-line shell CLI (add/list/show/done/archive)
  aggregates/library/stores/inbox.bluebook — declares heki as persistence adapter

**Four-step retirement plan, in order :**

  1. Update `aggregates/library/stores/inbox.bluebook` — replace heki
     persistence with a markdown adapter (read directory, parse frontmatter,
     write iNNN.md). Bluebook-first ; the runtime change follows the spec.
  2. Update `rust/src/run_statusline.rs` — count `status: queued` from
     markdown frontmatter instead of heki. Verify the count hasn't drifted
     against the heki count first, then swap.
  3. Retire `hecks_conception/inbox.sh` — either delete (if no caller),
     or replace its body with `hecks-life run aggregates/library/stores/inbox.bluebook --command ...`
     dispatches once the bluebook supports markdown. i79 already names this work.
  4. Delete the three .heki files. Source of truth is now the markdown directory.

**Companion to :**

  - i79 (inbox-sh-as-bluebook — names step 3 from a different angle)
  - i241 (per-bluebook inbox markdown convention — set the stage for this)
  - i281 (StoreHouse — once it lands, the inbox dispatch flows through it
    rather than a per-bluebook entrypoint, but that's orthogonal to this card)

**Why deferred from the migration commit :**

The migration was a one-shot data conversion. The retirement is a real
refactor with runtime risk (statusline regression possible, inbox.sh
callers possibly hidden). Bluebook-first discipline says : update the
spec, then the runtime, then verify, then delete. Worth its own PR with
a dedicated review pass.
