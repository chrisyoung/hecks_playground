# i477 — run_statusline.rs has drifted from its specializer snippet (regen needed)

Surfaced 2026-05-07 while doing the heki retirement (i476). The
statusline runner is generated byte-for-byte from
`codegen/run_statusline_shape/snippets/runtime.rs.frag`, but the .rs
and the .frag have diverged.

`hecks-life specialize run_statusline` produces output that differs
from `rust/src/run_statusline.rs` in two regions :

  1. `render_awake` — the .frag uses a `mood_icon` variable plus a
     four-part format string that includes mood text and a 💭 musings
     count ; the current .rs has a simpler two-branch coherence_ok
     formatter that omits both.

  2. The matching `render_awake` test assertions — the .frag asserts
     `line.contains("focused")` and `line.contains("💭 7")`, while the
     .rs asserts the inverse (`!line.contains("focused")` and
     `!line.contains("💭")`).

Symptom : `cargo build` warns `function 'mood_icon_for' is never used`
in the .rs, because the .frag-defined helper is dead in the .rs build.

Resolution :

  1. Decide the source of truth. The doc comment on `run_statusline.rs`
     says "regenerated byte-for-byte from codegen/run_statusline_shape/"
     — so the .frag is canonical and the .rs is stale.
  2. Run `hecks-life specialize run_statusline > rust/src/run_statusline.rs`
     to regenerate. (The `>` redirect to a .rs path trips the antibody
     enforce-edit hook, so the regen needs an explicit per-file
     exemption or a bluebook-aware regen subcommand that writes the
     destination directly.)
  3. Verify : `cargo build` no longer warns ; the statusline shows mood
     and musings count again ; the related test passes.

Companion to i78 (specializer-files-as-bluebook) — the long-arc
resolution dissolves the .frag entirely into the bluebook, at which
point this drift class becomes structurally impossible.

Out of scope for the heki retirement commit (the heki-retirement
change itself is consistent in BOTH the .rs and the .frag — only
unrelated regions have drifted).
