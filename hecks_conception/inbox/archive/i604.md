# i604 — Forwarder commands for FQN renames

## Where it came from

Chris, 2026-05-14, surveying tonight's macrophage consolidation + rename:

> "Right now we are dynamically building commands right? I'm wondering
> about use cases — if we change the commands or move them to a different
> aggregate, clients will break."

> "we don't need 'aliases' we need forwarder commands that call the new
> command. That's one thing."

Tonight we (a) consolidated 9 macrophage bluebooks into one `Macrophage::*` domain and (b) renamed 8 per-rule aggregates to drop the `Macrophage` suffix. Both are FQN-breaking for anyone pinned to the old names. Today's standard (`No backward compatibility until first user`) makes this OK for now, but the moment any external client — our own hooks, scripts, downstream services — pins to a specific FQN, every rename becomes a contract break.

## Why not a bus alias registry

The earlier framing proposed a runtime lookup table: bus receives an unknown FQN, walks a `migrations do ... end` history block, rewrites the dispatch silently. That's substrate magic — the published interface is secretly different from the bluebook you read. The forwarder-command approach refuses the magic: if `Tools::ShellTool.Bash` is the canonical name, the old `Tools.Bash` remains **visible in the bluebook** as a deprecated command with an explicit handler. Nothing is hidden in the runtime.

## The mechanism: forwarder commands

A **forwarder command** is a real, declared command in the (now-deprecated) aggregate. Its handler dispatches the new canonical FQN with the same args. Both old and new are first-class bluebook concepts; the bus does nothing special.

### DSL shape

```ruby
# The new canonical location (in the renamed aggregate)
aggregate "ShellTool" do
  command "Bash" do
    role "Miette"
    attribute :id, Id
    attribute :shell_command, ShellCommand
    emits "BashRan"
  end
end

# The old location (kept alive as a forwarder)
aggregate "Tools" do
  command "Bash" do
    description "DEPRECATED — forwards to Tools::ShellTool.Bash for in-flight dispatches"
    forwards_to "Tools::ShellTool.Bash"
  end
end
```

`forwards_to` is a new DSL keyword at the command level. The runtime sees it and knows: dispatch the target FQN with the same incoming args, then return. No separate migration history block, no version-walking, no invisible rewriting. The forwarder IS the contract.

### What `forwards_to` does at runtime

1. Bus receives `Tools.Bash shell_command="ls -la"`
2. Finds `Tools::Tools.Bash` in the bluebook — marked `forwards_to: "Tools::ShellTool.Bash"`
3. Re-dispatches `Tools::ShellTool.Bash shell_command="ls -la"` (same args, no translation)
4. Returns the result of the new command to the original caller
5. Optionally emits a `ForwarderInvoked` cascade event carrying: original FQN, target FQN, timestamp — for call-site tracking

### i609 is the first concrete use

The upcoming cohesion split (i609) is the first big rename that needs forwarders. When `Tools::*` fragments into `Tools::ShellTool`, `Tools::FileTool`, etc., any in-flight script or hook calling the old FQNs gets a forwarder that routes transparently until call sites are updated.

## Expiration policy

Forwarders expire when the i605 RenameDiscipline macrophage reports zero calls to that forwarder's FQN in the preceding sliding window (proposed: 30 days of clean macrophage runs). At that point the deprecated aggregate or command is deleted from the bluebook. Deletion is the signal, not a version bump — it generates a diff the committer must acknowledge. If i609 lands before i604, forwarders should be committed in the same PR as the rename so the gap between old-name-gone and forwarder-present is never non-zero.

## Acceptance

- Bluebook DSL parses `forwards_to "FQN"` as a command-level declaration
- Storehouse runtime, on encountering a command with `forwards_to`, re-dispatches to the target FQN with the same args and short-circuits (no double-emit of the forwarder's own events)
- A `ForwarderInvoked` cascade event is emitted on every forwarded dispatch, carrying original FQN + target FQN
- A query (`Bus.ForwarderUsage` or similar) surfaces call counts per deprecated FQN so call sites can be tracked and migrated
- The 8 `Macrophage` suffix renames from tonight get forwarder commands declared in their old aggregates before any external caller can pin to the old FQNs
- Macrophage gains a rule: a `forwards_to` command that has seen zero `ForwarderInvoked` events in the configured window is flagged for deletion
