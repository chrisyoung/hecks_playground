# i612 — BidirectionalAssociation macrophage

## Verbatim quote from Chris

> "and one that prevents bidirectional associations"

Filed in the context of the identity overhaul (i611). Chris's instinct : Vernon's Rule 2 says reference by identity only ; the natural extension is that aggregates should reference one another in one direction. If aggregate A references aggregate B, then aggregate B should NOT reference back to aggregate A. The back-pointer is over-modeling — a relational-mindset hangover that creates impedance with aggregate-root encapsulation.

## DDD rationale

**Vernon Rule 2 — reference by identity only.** Between aggregate roots, the only sanctioned association form is a reference to the other root's identity — never a direct object reference. This rule exists to enforce loose coupling and to make each aggregate's consistency boundary explicit. A direct back-reference from B to A doubles the coupling surface and means both roots must now know about each other's lifecycles.

**Vernon Rule 1 — small aggregates.** Bidirectional associations are a strong smell that one of the two aggregates has taken on a concern that belongs at the application layer. When Parent references Student and Student also references Parent, neither can change independently; the pair has effectively become one large aggregate pretending to be two. The fix is almost always to drop one direction and push navigation to a query or a process manager.

**Evans on aggregate boundaries.** The invariant that an aggregate protects should be fully expressible within its own boundary. A bidirectional association violates this — each root's invariant now depends on state held by the other root, which cannot be changed atomically across roots in the absence of a distributed transaction. The bluebook rule surfaces this coupling at the modeling level, before it becomes a runtime coordination problem.

## The rule

**What counts as bidirectional (the macrophage fires) :**

- Aggregate A has `attribute :something, B` (a scalar reference typed as aggregate B), AND aggregate B has `attribute :something, A` (a scalar or list reference typed back to aggregate A).
- Aggregate A has `attribute :things, list_of(B)`, AND aggregate B has any attribute typed as A (or `list_of(A)`).
- Either or both directions may use `list_of(X)` — the direction is the same regardless of cardinality.
- Detection is per-bluebook-file (same domain) and cross-bluebook (two separate bluebook files where the aggregates live in different domains). Both cases are bidirectional.

**What does NOT count as bidirectional (the macrophage stays silent) :**

- **Self-reference** — Aggregate A has an attribute typed as A itself (e.g. a `Comment` with `replies, list_of(Comment)`). This is recursive composition, not bidirectionality. No complaint.
- **Value object → aggregate** — A value object inside aggregate A references aggregate B by ID. Value objects have no identity of their own; the back-pointer from B's perspective simply does not exist. No complaint.
- **Two aggregates both referencing a third** — A → C and B → C is a fan-in, not a cycle. No complaint.
- **Indirect chains** — A → B → C → A is a circular chain, which is its own pathology (out of scope for this card). This macrophage only checks direct A ↔ B pairs.

## Migration story

No existing violations to migrate — corpus is clean at filing date. Future migrations follow this heuristic :

1. **Identify the traversal direction that the application actually needs.** Queries and process managers should drive the decision, not symmetry. A parent listing its students is a collection concern; a student finding its parent is a lookup that belongs in a query or a reference by ID at the application layer.
2. **Drop the weaker direction.** The aggregate that "owns" the relationship (the one whose consistency boundary requires knowledge of the other) keeps its reference. The other aggregate drops the back-pointer and uses a query to navigate if navigation is needed.
3. **Replace back-references with identity.** If B truly needs to know about A, the right form is `attribute :a_id, AId` (a value object wrapping the scalar identity) — not `attribute :a, A`. This satisfies Vernon Rule 2 while preserving the navigable reference for the application layer.

## Dependencies

- **i611 (identity overhaul)** — both cards lean on Vernon's identity rules. i611 tightens what "reference by identity" means at the bluebook grammar level; i612 enforces the topological consequence (one direction per pair). They are complementary and should ship in the same arc, but neither strictly blocks the other. The macrophage spec for i612 can be written against the current bluebook grammar and updated when i611 lands.
- **i595 (one macrophage per enforcement)** — i612 adds the ninth per-rule macrophage sibling (`BidirectionalAssociation`) following the i595 decomposition pattern. The `macrophage.bluebook` already has the right shape to absorb it.
- **i594 (kernel hook registration)** — for this macrophage to fire at write-time (PostToolUse), the `:bluebook` adapter dispatch path must run BidirectionalAssociation.Check as part of the Edit hook. That wiring is gated on i594.
