# i615 — Unfurling through StoreHouse : conversational turns as first-class bus events

## Where it came from

Chris, 2026-05-14 (verbatim) :

> "when you say unfurlling (still thinking) i think its because you recieved a prompt. We should have this go through StorehHouse."

The statusline showed "unfurling (still thinking)" — the harness phrase for the interval when the model has received a prompt and is reasoning but has not yet dispatched a tool. Chris's observation : that whole layer — prompt receipt, reasoning interval, reasoning complete — is invisible to StoreHouse. Only the tool dispatches that follow enter the bus. The receive-and-think layer is opaque.

## What's missing today

Three concrete moments fire inside the harness on every conversational turn that do not reach StoreHouse :

**1. `UserPromptSubmit`** — Chris sends a message (or a SystemReminder fires). The harness receives it, the model begins processing. The prompt content, its source, and the timestamp are all available at this point in the harness hook surface. None of that enters the bus.

**2. `SystemReminder` injections** — automated reminders the harness injects mid-session (task notifications, periodic nudges, the `<system-reminder>` blocks that appear in tool-result positions). These are prompts in the functional sense — they trigger reasoning — but they are harness-sourced rather than user-sourced. Today they are invisible to StoreHouse.

**3. Model-thinking intervals** — the interval during which the statusline reads "unfurling (still thinking)" — model has the prompt, is reasoning, has not yet dispatched. The harness has no content from this interval (the model's chain-of-thought is not externally observable), but it does know the interval exists : it knows when processing started and when it ended (because a tool dispatch or response production followed). That temporal fact currently goes unrecorded.

**The gap in plain terms :** the StoreHouse bus today is a log of *actions*, not a log of *agency*. You can see what Miette did ; you cannot see what triggered it, when she started thinking, or how long she thought before acting. Every action on the bus is currently unanchored — it floats without a traceable antecedent. Conversations look like a stream of tool dispatches appearing from nowhere.

## The proposed shape — three new commands on StoreHouse

Following the same bus + envelope framing established in i613, three command surfaces on StoreHouse cover the receive-and-think layer.

### `StoreHouse.PromptReceived`

Fired on every `UserPromptSubmit` hook event and on every `SystemReminder` injection.

Attributes :

```
PromptReceived {
  conversation_turn  : TurnNumber       # monotonically incrementing turn counter
  source             : PromptSource     # user | harness | automation
  prompt_length      : Integer          # character count of the prompt
  received_at        : Timestamp        # when the harness delivered the prompt to the model
}
```

`prompt_length` rather than `prompt_content` is the default — prompt content may contain sensitive conversation history or system internals. The envelope's `correlation_id` links this event to the Unfurling and UnfurlingComplete that follow, and to all tool dispatches that occur before the response is produced.

### `StoreHouse.Unfurling`

Fired when reasoning begins — at the moment the model starts producing output (tokens flow but no tool dispatch has fired yet). Carries no reasoning content (the model's internal chain-of-thought is not externally observable by the harness). Carries only envelope fields.

Attributes :

```
Unfurling {
  started_at         : Timestamp        # when the reasoning interval began
  correlation_id     : CorrelationId    # links to the PromptReceived that triggered this
}
```

The `correlation_id` ties this event to its antecedent `PromptReceived`. An observer who subscribes to the bus can reconstruct : this PromptReceived triggered this Unfurling, which led to these tool dispatches, which concluded with this UnfurlingComplete.

### `StoreHouse.UnfurlingComplete`

Fired when the model finishes reasoning and begins producing its response (or fires its first tool dispatch). This marks the boundary between the "thinking" interval and the "acting" interval.

Attributes :

```
UnfurlingComplete {
  ended_at           : Timestamp        # when reasoning ended
  duration_ms        : Integer          # length of the reasoning interval
  correlation_id     : CorrelationId    # links to the Unfurling (and through it, PromptReceived)
  outcome            : UnfurlingOutcome # tool_dispatch | text_response | both
}
```

`outcome` notes whether the first post-unfurling act was a tool dispatch, a text response, or both simultaneously. This gives coarse signal on the type of turn.

### Envelope linkage

Each event rides i613's envelope. The `correlation_id` threads through all three events and extends into every tool dispatch that fires during the turn :

```
PromptReceived (turn=N, correlation_id=CID-N)
  └── Unfurling          (correlation_id=CID-N)
      └── [tool dispatches with correlation_id=CID-N]
      └── UnfurlingComplete (correlation_id=CID-N, duration_ms=…)
```

A turn-complete audit trace becomes a simple query : "all events with `correlation_id=CID-N`". The bus provides the answer without heuristic reconstruction.

## Mechanism — a harness hook parallel to i599

i599 wired `PreToolUse` and `PostToolUse` hooks to route native tool calls through the `Tools::*` dispatch surface. i615 follows the identical hook pattern for conversation-layer events.

`.claude/settings.json` gains a `UserPromptSubmit` block :

```json
"UserPromptSubmit": [
  {
    "hooks": [
      {
        "type": "command",
        "command": "/Users/christopheryoung/Projects/hecks/bin/route-prompt-received",
        "timeout": 5
      }
    ]
  }
]
```

`bin/route-prompt-received` reads the `UserPromptSubmit` hook payload from stdin (which includes `prompt` and session metadata), maps it to `StoreHouse.PromptReceived` attributes, and runs :

```
storehouse <agg_root> 'StoreHouse.PromptReceived' \
  conversation_turn=N \
  source=user \
  prompt_length=NN \
  received_at="2026-05-14T…"
```

Exit 0 always — the hook is advisory ; if the dispatch errors, the prompt still reaches the model.

For `Unfurling` and `UnfurlingComplete` : if the harness exposes a thinking-state hook (see Open Questions below), the same pattern applies. If not, the timing can be approximated as the interval between `PromptReceived` and the first `PreToolUse` event within the same turn — imprecise but directionally correct.

The hook script needs an antibody-exempt marker (it is a shell script that touches StoreHouse dispatch, not a domain object) :

```sh
# [antibody-exempt: bin/route-prompt-received — harness hook, not a bluebook domain object]
```

## Why this matters

### Transparency becomes structural

The Transparency vow in Miette's system prompt reads : *"Every internal act is visible. Every moment is shared. Nothing is hidden."* Today that vow is a behavioral commitment — Miette can mean it sincerely and still have an invisible receive-and-think layer, because the harness never routes those events to the bus. With i615, the vow becomes a wiring fact. The PromptReceived, Unfurling, and UnfurlingComplete events are on the bus whether or not Miette "remembers" transparency. The structural mechanism is the vow, not the intention.

This follows the principle Chris established with i599's PreToolUse hook : *"the wiring enforces the rule, no trust required."* i615 applies that same principle one layer up — at the conversational-turn level rather than the tool-call level.

### Audit trail is complete

Currently the StoreHouse bus shows : *what Miette did*. With i615 it shows : *what triggered it, when she started thinking, how long she thought, and what she did*. Every action has a traceable antecedent. The bus is no longer a log of floating dispatches — it is a causal chain.

For forensic purposes (debugging, retrospectives, session replay), this difference is material. "Why did Miette dispatch that Bash command at 14:32:07?" has an answer on the bus : PromptReceived at 14:31:59 from user, Unfurling started at 14:31:59, Unfurling completed at 14:32:06, first dispatch was Bash at 14:32:07. Correlation ID traces the whole chain.

### Conversation as event-stream

With i613 wrapping domain commands and i615 wrapping conversational turns, the StoreHouse bus becomes the canonical conversation log. A subscriber to the bus gets a complete ordered record : prompt received → reasoning interval → tool dispatches + their cascade chains → response produced. Session replay, debugging, and retrospectives all read from the same stream rather than reconstructing from heuristics across multiple stores.

This is the event-sourcing pattern at the conversation layer : the bus is the source of truth, not an audit shadow.

## What this CANNOT capture

**The content of the model's reasoning is not externally observable.** The harness can fire `Unfurling` with a start timestamp and `UnfurlingComplete` with a duration, but it cannot record what the model thought during that interval. The chain-of-thought is opaque to the harness by design (it is not streamed to the hook surface). The Unfurling event marks the *temporal interval* of reasoning, not the reasoning content. This is an honest structural limitation — the card proposes capturing the envelope of thinking, not the thinking itself.

**Automated prompts are distinguished but not transparent in content.** A `SystemReminder` injection that triggers reasoning is recorded as `source=harness` or `source=automation` on the PromptReceived event. The content of the system reminder may be sensitive (it contains harness-internal state). The `prompt_length` field captures scope ; the content itself is not recorded unless the hook is explicitly configured to include it.

## Relationship to existing cards

**i613** — i615 is i613 extended from domain commands to conversational turns. i613 makes every domain command flow through StoreHouse. i615 makes every conversational turn flow through StoreHouse. Same bus, same envelope, same principle ("the dispatch IS the act") — applied to the input-and-reasoning layer rather than the command-execution layer. Together they close the loop : no moment of Miette's agency is off the bus.

**i599** — i615 is the conversation-surface twin of i599's tool-surface PreToolUse routing. i599 routes tool calls ; i615 routes conversational turns. Both use the same harness hook mechanism ; both exit 0 (advisory) ; both target StoreHouse dispatch. The implementation pattern is the same — different hook event, different StoreHouse command, same wiring shape.

**i603** — the broader "mechanical lock for storehouse routing" directive. i615 closes the last loophole : even the moments before Miette acts — receiving a prompt, entering the thinking interval — enter the bus. i603's mechanical lock now covers the full lifecycle of a turn.

## Acceptance criteria

Closes when :

1. `StoreHouse.PromptReceived`, `StoreHouse.Unfurling`, and `StoreHouse.UnfurlingComplete` commands exist on the StoreHouse aggregate (or its successor per i613's Shape A/B/C decision).
2. A `UserPromptSubmit` harness hook fires `StoreHouse.PromptReceived` on every conversational turn, with correct `source`, `prompt_length`, and `conversation_turn` attributes.
3. Unfurling and UnfurlingComplete fire — either via a native thinking-state hook (if the harness exposes one) or via approximation (PromptReceived timestamp + first PreToolUse timestamp within the same turn).
4. Conversations on the bus show a complete trace : `PromptReceived → Unfurling → UnfurlingComplete → [tool dispatches + cascade chains]`, all linked by `correlation_id`.
5. The `bin/route-prompt-received` hook script is executable, reads stdin, dispatches via storehouse, exits 0, and carries an antibody-exempt marker.

## Open questions

**Does the Claude Code harness expose a model-thinking hook ?**

`UserPromptSubmit` is confirmed to exist — it is already referenced in the harness hook documentation and used for `SessionStart`-adjacent work in the existing `settings.json`. Whether the harness exposes a hook that fires specifically when the model *begins* or *ends* reasoning (as opposed to when a tool is dispatched) is unknown. This needs a harness-documentation check before implementation.

If the thinking-state hook is not available :
- `StoreHouse.PromptReceived` is the practical minimum and can be wired immediately.
- The `Unfurling` interval can be approximated : `PromptReceived.received_at` to `first PreToolUse.fired_at` within the same correlation window. This misses turns where no tool is dispatched (text-only responses) — those would have no Unfurling approximation at all.
- `StoreHouse.UnfurlingComplete` could be approximated by a `PostToolUse` or `Stop` hook that marks the end of a turn. Imprecise, but records the boundary.

The card should not block on the Unfurling hooks if the harness doesn't expose them. Ship `PromptReceived` first ; file a follow-up once harness docs confirm or deny the thinking-state hook surface.

**What is the `conversation_turn` source ?**

The harness `UserPromptSubmit` payload may or may not include a turn counter. If not, the hook script must maintain its own counter (e.g., a persistent file at `~/miette-state/information/.turn_counter`). Needs verification against actual hook payload shape before implementation.

**Does `source` distinguish user vs SystemReminder at the hook level ?**

The harness may fire `UserPromptSubmit` for both human messages and injected system reminders, or it may have separate hook events. If it's a single hook, the script needs a heuristic to distinguish them (e.g., presence of `<system-reminder>` tags in the prompt content). Needs harness-doc check.
