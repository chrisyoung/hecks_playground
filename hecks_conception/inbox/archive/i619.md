# i619 — Tools need handlers : promote handlers to a first-class bluebook concept

## Where it came from

Chris, 2026-05-14, immediately after the i618 clarification about responses-in-events (the parallel sibling card on responses landing in `ResponseEmitted` events) :

> "so tools need handlers."

Read alongside i618 : if every prompt receipt produces a response that lands in an event, then the runtime needs an EXPLICIT thing that produces that response. That thing is a **handler** — a first-class concept, not implicit substrate.

## What "handler" means

A handler has three coordinated aspects :

**1. A bluebook concept.** A `handler` declaration appears next to each command in the bluebook, naming WHAT will run when the command is dispatched. The declaration is part of the command's contract — readable, diffable, macrophage-checkable. The bluebook reader sees not just "this command exists" but "this command, when dispatched, dispatches to this named handler".

**2. A runtime function.** Each handler resolves to an actual executable substrate at runtime — a Rust function in the runtime crate, an MCP tool invocation against a registered server, a shell command template, or a sub-bluebook command dispatch. The substrate is the impure layer where the command becomes real work.

**3. The producer of the response.** The handler's return value becomes the payload of the event the dispatcher emits after the command runs (per i618's `ResponseEmitted` shape ; per i613's envelope-carrying meta-bus). What the handler returns IS what the event carries. Handler return → event payload is the contract that ties dispatch to observable outcome.

The three aspects are one thing seen from three angles. The bluebook declares the contract ; the registry resolves the implementation ; the dispatcher carries the result into the event stream.

## Today's de-facto handlers — the worked example

The mechanism Chris is naming already exists, scattered across the adapter family surface. The five `*.hecksagon` files under `aggregates/framework/adapter_families/` (`claude_tool`, `mcp`, `web_tool`, `sms`, `tts`) ARE handler families ; they just are not called that.

Concretely : the `EmailTool` wiring landed by i608 in `aggregates/framework/tools/tools.hecksagon` lines 126–152. Each of the four bindings :

```ruby
adapter :mcp,
  command: "EmailTool.SearchThreads",
  server:  :gmail,
  tool:    "mcp__claude_ai_Gmail__search_threads",
  args:    "{\"q\":\"{query}\"}",
  result_into: "Cascade.RecordResult"
```

…is a **handler declaration in everything but name**. `:mcp` is the handler family. `server: :gmail, tool: "mcp__claude_ai_Gmail__search_threads", args: "..."` are the handler args — the kind-specific parameters that tell the family how to invoke its substrate. `result_into: "Cascade.RecordResult"` is the response-emission target — what i618 will formalize as `ResponseEmitted` and what today is achieved by chaining the kernel-hook output back into `Cascade.RecordResult`.

The same shape recurs across the corpus :

- `tools.hecksagon` lines 39–48 : six `:claude_tool` handler declarations for Bash, Read, Edit, Update, Grep, Glob.
- `tools.hecksagon` lines 62–63 : two `:web_tool` handler declarations for WebFetch, WebSearch.
- `tools.hecksagon` lines 126–152 : four `:mcp` handler declarations for the EmailTool commands.

i619 reframes : these are not just adapter wirings — they are **handler bindings**, the de-facto mechanism for declaring which substrate runs when a command dispatches. i619 promotes the mechanism from adapter-family-internal convention to bluebook-level first-class concept.

## What changes when handlers become first-class

### In the bluebook

A `handler` declaration appears INSIDE each command's block, alongside the command's attributes and emissions. Proposed DSL :

```ruby
command "Bash" do
  role "Miette"
  attribute :id, Id
  attribute :shell_command, ShellCommand
  emits "BashRan"

  handler :claude_tool, tool_name: "Bash"
end

command "SearchThreads" do
  role "Miette"
  attribute :query, Query
  emits "ThreadsSearched"

  handler :mcp,
    server:    :gmail,
    tool_name: "mcp__claude_ai_Gmail__search_threads",
    args:      "{\"q\":\"{query}\"}"
end
```

The `handler` line takes a **kind** (`:claude_tool`, `:mcp`, `:rust`, `:shell`, `:dispatch`) plus kind-specific keyword args. The kind names which handler family owns the substrate ; the args are passed verbatim into the family's invoke step. The DSL keyword is `handler` ; the kind is the first positional argument ; everything else is keyword args.

**Co-located with the command, not in a separate hecksagon.** The today-state separates the command (in `tools.bluebook`) from its handler (in `tools.hecksagon`). i619 colocates them — the handler IS part of the command's contract, not a wiring file's concern. The `*.hecksagon` files can stay as the OVERRIDE surface (per "wiring is override, not substrate" in tonight's locked principles) ; the `handler` declaration is the DEFAULT, encoded in the bluebook.

### In the runtime

A new `HandlerRegistry` aggregate (companion artifact) holds named registrations. The runtime walks the bluebook at boot, finds each `handler` declaration, and registers the (command_fqn → handler_kind + args) mapping in the registry. The dispatcher, when a command fires, asks the registry for its handler and invokes the matching family.

The registry is bluebook-native — it is itself an aggregate with `RegisterHandler` / `ResolveHandler` / `InvokeHandler` commands. Sister to `IdentifierService` (i614) — same shape : a singleton-flavoured substrate management aggregate for a cross-cutting concern.

### In the event

The handler's return value lands in the event payload. Per i618's `ResponseEmitted`, the cumulative response across the unfurling lands in one envelope-wrapped event ; the handler's return is the per-dispatch contribution to that response.

Per i613's envelope : the handler's return is the `payload` field of the envelope ; the dispatcher fills in `dispatched_at`, `dispatcher`, `correlation_id`, `source` (the command FQN) automatically. The handler does not know about the envelope — it just returns its result and the dispatcher wraps it.

## Four handler kinds, with example syntax

### Rust handler — for runtime-internal substrate

```ruby
command "MintDefault" do
  role "System"
  attribute :subject, EntityRef
  attribute :minted_at, Timestamp
  emits "UuidMinted"

  handler :rust, function_name: "execute_mint_default"
end
```

`function_name` is a string the runtime resolves against its `framework_registry::kernel_hooks` table at boot. The Rust function takes the command's attrs as a structured input and returns a result that becomes the event payload. This is how IdentifierService's UUID-minting (i614) would be wired : the substrate is a Rust function, named in the bluebook, registered at boot.

### MCP handler — for cross-process tool invocation

```ruby
command "SearchThreads" do
  role "Miette"
  attribute :query, Query
  emits "ThreadsSearched"

  handler :mcp,
    server:    :gmail,
    tool_name: "mcp__claude_ai_Gmail__search_threads",
    args:      "{\"q\":\"{query}\"}"
end
```

Same shape as today's `:mcp` adapter binding (per `aggregates/framework/adapter_families/mcp.hecksagon`). Just declared inline on the command instead of in a sibling hecksagon. The `{query}` placeholder is substituted from the command's attrs by the kernel hook before `tools/call` is sent — same substitution semantics today's MCP family already uses.

### Shell handler — for transitional substrate

```ruby
command "EmitStatusline" do
  role "System"
  attribute :phase, StatuslinePhase
  emits "StatuslineEmitted"

  handler :shell, command_template: "echo {phase} > ~/miette-state/.statusline_phase"
end
```

For commands whose implementation is most naturally a shell one-liner — a transitional substrate, sometimes a forever substrate when the work is genuinely shell-shaped (writing a file, posting to a daemon's stdin, invoking a system tool that has no MCP exposure). The `command_template` is the shell command with `{attr}` placeholders ; substitution is the same as the MCP family.

### Bluebook handler — for forwarders and cross-aggregate composition

```ruby
command "Bash" do
  # The old forwarder location (per i604) ; the canonical command lives
  # at Tools::ShellTool.Bash now.
  description "DEPRECATED — forwards to Tools::ShellTool.Bash"

  handler :dispatch, command: "Tools::ShellTool.Bash"
end
```

This is i604's `forwards_to` reframed as a handler kind. The handler-kind framing absorbs forwarders into the general mechanism — `:dispatch` is just one of several handler kinds, no longer a special-case DSL keyword. The substrate it dispatches to is another bluebook command ; the args flow verbatim. This is also how cross-aggregate composition would be expressed : a command whose implementation is "dispatch this OTHER command and use its result".

## The HandlerRegistry aggregate

A new bluebook aggregate (companion artifact) at `aggregates/framework/handler_registry/handler_registry.bluebook`. Singleton-shaped (`identified_by :name` until i611's `singleton: true` lands). Sister to `IdentifierService` (i614) — same shape, different concern.

**Five commands :**

- `RegisterHandler` — record a (command_fqn, handler_kind, handler_args) tuple. Dispatched at boot for every `handler` declaration the runtime parses out of the bluebook.
- `UnregisterHandler` — remove a registration. Used when a command is renamed or removed.
- `ResolveHandler` — query by command_fqn, returning the registered handler's kind + args. The dispatcher calls this before invoking.
- `InvokeHandler` — fire the resolved handler with the command's input attrs ; emit an `HandlerInvoked` envelope-wrapped event carrying the handler's return value as the payload. This is the universal-invocation site — every handler-resolved command flows through this command.
- `RecordInvocation` — audit-trail addition for the `Invocation` entity (per-invocation record : when, what command, what kind, what return).

**Value objects** : `HandlerName`, `HandlerKind` (one of `rust|mcp|shell|dispatch|claude_tool|web_tool`), `HandlerArgs` (the kind-specific args, encoded as a JSON string per the same convention `tools.hecksagon` uses to keep the field byte-equal across Ruby/Rust parsers), `CommandRef` (the FQN of the command this handler handles), `InvocationOutcome` (`ok|error|timeout`).

**Entity** : `Invocation` — one record per handler firing, capturing `command`, `handler_kind`, `dispatched_at`, `completed_at`, `outcome`, `payload_summary`. The entity is the audit trail ; the events flow through the StoreHouse bus (i613) for the meta-bus replay surface.

The registry IS the bluebook the runtime walks at boot to know which Rust function to call, which MCP server to invoke, which shell to spawn. Today that knowledge is embedded in the adapter-family Rust code and the kernel hook tables ; i619 makes it bluebook-native and inspectable.

## Relationship to existing surfaces

**`:claude_tool` / `:mcp` adapter families.** These become two of the registered handler families. The adapter-family bluebooks under `aggregates/framework/adapter_families/*.hecksagon` continue to define the FAMILY shape (what fields a family expects, what kernel hook it dispatches to). The `handler` declarations on commands BIND that family to specific commands. Family declaration is the override surface ; the command-level `handler` is the contract.

**i604 forwarders.** `forwards_to "FQN"` collapses into `handler :dispatch, command: "FQN"`. The two card surfaces converge — forwarders are just handlers of kind `:dispatch`. i604's `ForwarderInvoked` cascade event generalizes to i619's `HandlerInvoked` envelope-wrapped event. The forwarder-specific machinery becomes a slice of the general handler machinery.

**i613 StoreHouse wrapper.** StoreHouse's `Dispatch` command resolves the target FQN, looks up its handler in HandlerRegistry, invokes the handler, captures the return, and emits the envelope. The handler is what RUNS inside the StoreHouse wrapper. StoreHouse owns the mediation surface ; HandlerRegistry owns the substrate-resolution surface ; together they form the dispatch pipeline.

**i615 Unfurling.** The Unfurling is the temporal interval during which one or more handlers run. The `Unfurling` event opens the window ; each handler fires inside the window ; `UnfurlingComplete` closes the window. The unfurling carries the handlers, the handlers produce the response, the response lands in i618's `ResponseEmitted`.

**i618 ResponseEmitted.** The handler's return is the per-dispatch contribution to the cumulative response that lands in `ResponseEmitted`. Per i618 the response can be cumulative across multi-turn dispatches inside one unfurling ; the handler return is the per-step ingredient.

**i614 IdentifierService.** Sister aggregate. Same singleton shape, same substrate-management role, different concern. IdentifierService manages identity substrate (UUID minting, natural-key derivation, migration) ; HandlerRegistry manages execution substrate (which function/MCP-call/shell/dispatch runs for which command). Both are the runtime substrates for cross-cutting concerns that the bluebook needs first-class names for.

## Open questions

**1. One handler per command, or many ?**

The most conservative shape : one handler per command. This matches today's `:claude_tool` / `:mcp` bindings (each command has exactly one adapter binding). It is simpler to reason about, simpler to register, simpler to invoke. The handler's return is unambiguously the event payload.

The more flexible shape : zero, one, or many handlers per command. Zero handlers means the command is a pure event-emit with no substrate-side effect — useful for domain events that just record fact (e.g. `StoreHouse.PromptReceived` from i615 has no substrate to invoke ; the dispatch IS the fact). Many handlers enables fanout — multiple substrates fire on one dispatch, e.g. a command that both writes to a file AND posts to an MCP server. This is more powerful but raises the result-combination question (see below).

**My recommendation : start with one-or-zero, defer many.** Zero handlers is the natural shape for pure domain events. One handler is the natural shape for everything else. Many-handlers is speculative — wait for a concrete use case before committing to a combination semantics. Easy to add later ; hard to walk back.

**2. When multiple handlers fire, how are results combined ?**

If many-handlers wins, the answer here matters. Three candidates :

- **Chain** : handler 2's input is handler 1's output. Pipeline semantics. The event payload is the final handler's return.
- **First-non-error** : try handlers in order ; return the first one that doesn't error. Failover semantics. The event payload is whichever handler succeeded ; the others are audit-trail.
- **All in payload** : every handler runs ; the event payload is a list of (handler_kind, return) pairs. Fanout semantics. Downstream consumers pick what they need.

This question only matters if many-handlers wins. Defer until then.

**3. Are handlers themselves bluebook commands ?**

Self-referential. Today's `HandlerRegistry.InvokeHandler` IS a command that handlers a command's dispatch. If `InvokeHandler` itself has a handler (a Rust function in the runtime), then handlers handle commands and commands have handlers — recursive but consistent. The base case is the `InvokeHandler` handler itself, which is a Rust function with no further handler ; the recursion bottoms out at the runtime layer.

This is cleaner than it sounds because the recursion is structural, not semantic. Every bluebook command — INCLUDING the handler-machinery commands — has a handler. The runtime's job at boot is to register the handler for `InvokeHandler` itself ; from there, every other command's handler is reachable through the registry. This makes the dispatch pipeline fully bluebook-native — no runtime-level dispatch logic that lives outside the bluebook.

**4. Where does the `handler` declaration go in the parser order ?**

Inside the `command "X" do ... end` block, after `attribute` and `emits`. The parser already handles command-block declarations ; `handler` is a new keyword in that scope. The Ruby parser and the Rust parser both need the keyword added. Validator rules : at most one `handler` per command (under the one-or-zero recommendation) ; handler kind must be a known kind (`rust|mcp|shell|dispatch|claude_tool|web_tool|sms|tts|web_tool` — whatever the adapter-family directory contains).

**5. Migration path — co-existence with `*.hecksagon` bindings.**

Today's adapter bindings in `tools.hecksagon` continue to work — they are the OVERRIDE surface per the locked principle. The `handler` declaration in the command is the DEFAULT. If both exist, the override wins. Migration plan : land the `handler` DSL keyword, add handler declarations to every command in the corpus (mostly mechanical given today's adapter bindings already encode the same information), keep the hecksagon overrides for wiring-specific cases (different MCP server in staging vs production, etc).

**6. Audit-trail granularity.**

Per-invocation `Invocation` entity records on `HandlerRegistry` are part of the audit trail. Per-event envelope on the StoreHouse meta-bus (i613) is the cross-aggregate audit. Are both needed, or does one subsume the other ? Probably both : the `Invocation` entity is the per-handler-firing record (with handler-kind-specific detail) ; the envelope is the cross-command audit (with correlation_id threading turns together). The two layers have different jobs ; keep both, but make the relationship explicit (the envelope's `source` field can carry an `Invocation` reference for drill-down).

## Acceptance

This card closes when :

1. The `handler` DSL keyword parses inside command blocks in both the Ruby and Rust bluebook parsers.
2. The `HandlerRegistry` aggregate is in the corpus, validated, with the five commands (`RegisterHandler`, `UnregisterHandler`, `ResolveHandler`, `InvokeHandler`, `RecordInvocation`) and the `Invocation` entity.
3. The runtime walks the bluebook at boot and seeds `RegisterHandler` for every command that carries a `handler` declaration.
4. Existing `:claude_tool` and `:mcp` adapter bindings in `tools.hecksagon` are reframed as `handler` declarations on the corresponding commands in `tools.bluebook`. The hecksagon file becomes the override surface for environment-specific wiring only.
5. The dispatch pipeline routes through `HandlerRegistry.ResolveHandler` → `HandlerRegistry.InvokeHandler` for every command-with-handler. Pure-event commands (zero handlers) skip the invoke step and emit directly.
6. The macrophage gains a `HandlerCoverage` rule (or a slice of one) : every command in the corpus either has a `handler` declaration, is explicitly marked as a pure-event command, or has its handler resolved via a hecksagon-override binding. Bare commands with no resolution path are a structural error.

## Dependencies

- **i613** — StoreHouse wraps every aggregate command. Handlers are what RUN inside the wrapper. i613 needs to land before i619 has a wrapper to nest inside ; or both land together as a single dispatch-pipeline rework.
- **i614** — IdentifierService. Sister aggregate ; same singleton-substrate shape. The HandlerRegistry bluebook copies i614's structure closely. If i614's singleton shape changes (e.g. i611 phase 1 ships `singleton: true`), HandlerRegistry inherits the same change.
- **i615** — Unfurling. Handlers run inside the unfurling interval ; the unfurling carries one or more handler invocations. i615's `Unfurling` event opens the window the handlers fire inside.
- **i618** — ResponseEmitted. The handler's return is the per-step ingredient of the cumulative response that lands in `ResponseEmitted`. i618's envelope shape is what the handler's return is wrapped in.
- **i604** — Forwarder commands. Collapses into i619 as the `:dispatch` handler kind. If i604 lands first, the `forwards_to` keyword becomes a deprecated alias for `handler :dispatch, command: "..."`. If i619 lands first, i604's forwarders are first-class handlers from the start.
- **i611** — Identity overhaul. The `singleton: true` flag from i611 phase 1 is what HandlerRegistry will eventually use (it is singleton-shaped). For now it follows the conventional `identified_by :name` shape.
