# i101 — query-as-first-class-ir-not-opaque-ruby-block

query-as-first-class-ir-not-opaque-ruby-block — Today's DSL stores `query "Foo" do ... end` as a name + an opaque Ruby proc. Symptom : zero queries declared across 47 aggregates in the corpus, even though most reads are exactly the shape `query` was meant for. Root cause : the IR is anemic — no declared inputs, no declared output shape, no declarative where/order/limit clauses, no relationship to the storage adapter, no cross-aggregate composition. The Rust runtime cannot execute a Ruby proc, so resolve_query in mod.rs can only special-case hardcoded names (MatchInput). The validator cannot check field references. Generators have nothing to walk. Reads bleed into writes via QueryBuilder.delete_all / update_all. Proposed shape : queries become first-class IR nodes parsed from declarative DSL — `description`, `attribute :input, Type` (declared inputs), `where field: value | :input_ref | operator(:input)`, `order :field, :asc|:desc`, `limit N`, `pluck :field` or `count`, `returns Type | list_of(Type)`. Same first-class status as commands. The where/order/limit clauses become IR fields, not procs. Unlocks : Rust runtime executes queries directly via heki adapter ; validator checks field references at parse ; generators emit Ruby query classes from IR ; UIs render forms from declared inputs ; reads stop bleeding into writes ; awareness fields like unfiled_wishes become queries on DreamWish, not snapshots in singletons (i98 retires). Implementation order : (a) DSL parser change ; (b) Rust runtime resolve_query walks IR ; (c) validator ; (d) generator emits from IR ; (e) cross-aggregate composition (v2). Sibling of i92 (queries-as-aggregate-surface) — same direction, same arc. Filed 2026-04-26 after Chris asked why query feels anemic.
