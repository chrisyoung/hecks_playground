# i104 — runtime-posttooluse-listener-as-bluebook

runtime-posttooluse-listener-as-bluebook — Claude Code's PostToolUse hook contract dispatches a shell command registered in ~/.claude/settings.json. The command receives the tool-input JSON on stdin and (per Claude Code semantics) signals back to the agent via exit 2 + stderr. Today's enforcer (i104) bridges this with /Users/christopheryoung/.claude/hooks/enforce_bluebook.sh — a thin shell adapter that classifies the file extension, dispatches Enforcer.RecordXxx + Enforcer.Complain into aggregates/enforcer.bluebook, and exits 2 on imperative edits so the complaint surfaces as a system reminder. The brain is bluebook (Enforcer aggregate) but the adapter is shell because there's no runtime primitive for a bluebook capability to register as a Claude Code PostToolUse listener. Structural fix : capabilities/enforce_bluebook/enforce_bluebook.bluebook declares the listener (matcher pattern, classification table, dispatch chain) ; a Rust runner registers itself with Claude Code's hook contract and walks the bluebook on each tool call. The shell adapter retires entirely. Sibling of i80 (cli-routing-as-bluebook) — same direction : every external surface a bluebook capability, no shell adapters. Until the runner lands, the shell is the only piece of the enforcer loop that's still imperative ; the loop self-flags every edit to itself, which is fine, the discipline mechanism doesn't break. Filed 2026-04-26 after the enforcer caught its own creation in real time, exit 2 routing the complaint into the agent's context as a live system reminder.
