# i121 — Self-introspecting validators retire the whitelist

Self-introspecting validators retire the whitelist — generalise i114 across all three project whitelists. The same pattern recurs three times: a validator with a manual escape hatch attesting that THIS case is justified. Each escape hatch is a confession that the rule was too strict and the validator can't verify the justification by itself.

The three instances:
1. exempt_registry.heki + [antibody-exempt: ...] markers — the bluebook-first enforcer's whitelist of files that are kernel-surface or transitional. Covered by i114: replace with 'is this script dispatched by a bluebook?' query against the IR.
2. [loc-ratchet-override: <reason>] markers in commit messages — the LoC ratchet's escape hatch when non-bluebook code grows. Real intent: 'growth is OK if it closes a runtime gap a new bluebook now needs.' Replace with 'does this PR's IR diff add a bluebook shape that wasn't expressible before, and does the non-bluebook growth implement that shape?' Concrete example PR #483: antibody.bluebook gains RegisterExemptions (list_of(VO) Many-form), command_dispatch.rs gains 226 lines of bulk-shape detection — the validator can verify the connection structurally.
3. [antibody-exempt: file — reason] markers in source files — same as (1) but inline in the file rather than in the heki registry. Same query retires both.

Underlying gap: the validator can't see the bluebook IR while it's validating. Once it can (via a small query API exposed to CI hooks), all three escape hatches retire together. The rewrite is one substrate (IR introspection) that three validators consume.

Acceptance: each whitelist becomes empty over time as the IR query absorbs its rationale. New PRs no longer need to write override markers; the validator either accepts the change because the IR diff justifies it, or blocks because the diff doesn't. Override markers in commit messages become artifacts of an earlier era.

Sibling to i114 (which addresses only whitelist 1). i121 names the structural pattern across all three; i114 remains the first concrete implementation, paving the path the other two follow. Same inversion as dump_shape (Phase D): instead of patching the validator's output (registering exceptions), ask the grammar to generate the rule.
