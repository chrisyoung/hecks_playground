# i143 — i142 Tier 1 incomplete — load_combined_domain merge dedupe must honor context. PR #515 added Context.Aggregate.Command R

i142 Tier 1 incomplete — load_combined_domain merge dedupe must honor context. PR #515 added Context.Aggregate.Command RESOLUTION to command_dispatch::resolve, but didn't update the merge in load_combined_domain (hecks_life/src/main.rs around line 1660). The merge predicate is still 'existing.name == agg.name' regardless of context — so when two bluebooks declare same-name aggregates in different contexts, only one survives merge and the other is silently dropped. The dispatch resolver can only see surviving aggregates, so Context.Aggregate.Command can't disambiguate aggregates that were dropped. SYMPTOM ON MAIN TODAY : boot_miette.sh dispatches 'Identity.Identify' which fails with UnknownCommand. After PR #514 (path tiebreaker), being.bluebook's Identity (b-e-i) wins over boot.bluebook's Identity (b-o-o) alphabetically. Being.Identity has RecordSession, not Identify, so the boot dispatch fails. Mitigated only by boot_miette.sh's '|| true' that swallows the error — boot is silently broken, not visibly. FIX : merge predicate becomes '(existing.name, existing.context) == (agg.name, agg.context)'. With this, all three Identity aggregates survive merge. Boot.Identity.Identify resolves Boot's copy ; Being.Identity.RecordSession resolves Being's. Same-name same-context still dedupes (organ-wins within a context, the canonical case from i108). Boot-split agent (a2fc0036) found this carefully and stopped before pushing through ; pattern mirrors how i140 was filed and dissolved — both surfaces of the same structural cut. Once this lands, the boot.bluebook split is unblocked AND the live boot ritual is repaired.
