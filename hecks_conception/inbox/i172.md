# i172 — i147 scope clarification

i147 scope clarification — adapters vs kernel. Chris's framing during W3-B review (2026-05-01) : 'things like html will be done with adapters. Remember the only thing we have to project is the bluebook.' The Futamura projection target is the bluebook itself. The kernel files getting retired (parser, dispatch, ir, command_dispatch, interpreter, runtime/mod) DEFINE the language ; they become byte-identically regenerable from the language's own meta-shape. Adapters are the runtime-to-world bridge (HTTP, shell, filesystem, browser, render-target) ; they're concrete bindings, not language definition. W3-B's adapter_llm.rs retirement via driven_adapter_shape is technically clean (byte-identically regenerable, new fixture rows = new backends) but it's specializing an ADAPTER, not the kernel. Different arc. Implication for the i147 NEEDS-META-SHAPE tier : re-read the survey's 7 files with this lens. interpreter.rs / command_dispatch.rs / runtime/mod.rs / behaviors_runner.rs are kernel (project from bluebook ; belong in i147). adapter_llm.rs / driven adapters / future html_renderer.rs are adapters (different arc — adapter_implementation_shape work, NOT i147). Acceptance : NEEDS-META-SHAPE tier files are tagged kernel-or-adapter before any of them are picked up. Adapter work moves to its own arc. Kernel work continues under i147. The survey at /tmp/i147_kernel_survey.md is updated to reflect this taxonomy ; alternatively it's reconceived as two surveys (kernel + adapter) so the projection target stays clean.
