# i239 — i239 hecksagon corpus + filesystem registry + versioning

i239 hecksagon corpus + filesystem registry + versioning — the bluebook RAG/CalVer loop, applied to hecksagons

═══ Why this card exists ═══

Phase 2 of adapter-family activation (i238 :tts) is slow because every
new family forces a 13-touchpoint walk across Ruby + Rust : IR, parser,
builder, canonical dump, tests, antibody registry. Two prior agents lost
to this. The diagnosis is structural : adapter-family declarations are
*data* but we parse them as *syntax to be re-parsed every boot*. Bluebooks
don't have this problem because the corpus is vector-indexed and each
bluebook carries a CalVer version. Hecksagons deserve the same treatment.

═══ The unified frame ═══

Three threads, one thread :

  1. Hecksagon corpus as RAG source. Point V0 RAG at the .hecksagon
     corpus the same way it's pointed at .bluebook. (Adjacent : i233.)

  2. Filesystem as registry. hecks_conception/registry/ holds versioned
     .hecksagon files. Boot reads the filesystem, resolves declarations
     by name+version, makes them queryable to consumer-hecksagon parsing.
     No persistent aggregate ; the directory IS the source of truth.

  3. Versioning on hecksagons. Every hecksagon carries
     `version: "YYYY.MM.DD.N"` (CalVer, like bluebooks). Consumers can
     pin a family version or float to latest.

═══ What changes about adapter-family activation (i238) ═══

Before : design IR, write parsers both halves, write builders both halves,
ship. (The slow path, where two agents already failed.)

Inside this frame :

  (a) Canonical IR designed once — adapter_family / provider /
      behavior_kind as registry records, not as block syntax to re-parse
      every boot.
  (b) One-time ingestion pass reads .hecksagon source → canonical IR.
      Runtime never re-parses source ; it reads the registry.
  (c) Consumer-side adapter resolution via registry lookup. ONE generic
      FamilyAdapterBuilder replaces resolve_llm_adapters /
      resolve_compute_adapters / planned resolve_tts_adapters.

This is the meta-shape move : the meta-shape of an adapter family is
itself in the registry. Adding :fs / :http / :embedding becomes appending
a record, not walking 13 touchpoints.

═══ Versioning sketch ═══

  Hecks.adapter_family "tts", version: "2026.05.04.1" do ... end
  adapter :tts, version: "2026.05.04.1", name: :miette_speech do ... end
  # Or float : adapter :tts, name: :miette_speech do ... end

═══ Step-wise execution ═══

  Step 1  Establish registry/ directory ; move framework/ contents ;
          version-suffix filenames.
  Step 2  Add `version:` field to hecksagon top-level parser, both halves,
          parity passing.
  Step 3  Capture body blocks of Hecks.adapter_family / .provider /
          .behavior_kind into IR (the original Phase 2a, but the IR
          records are now registry residents).
  Step 4  One-time ingestion at boot : parse registry/ into in-memory
          resolution source.
  Step 5  Consumer-side adapter resolution via registry lookup ;
          FamilyAdapterBuilder on both halves ; route
          `adapter :KIND, ... do ... end` through it when :KIND is
          registry-known. Closes Voice PR #38 from MERGEABLE-on-paper
          to actually-parses.
  Step 6  Migrate :llm and :compute hand-coded resolvers to registry
          lookup ; retire the old resolvers.
  Step 7  V0 RAG over the hecksagon corpus.

Steps 1-3 = one PR. Step 4 = one PR. Step 5 = one PR. Step 6 = one PR.
Step 7 = its own card.
