# i241 — per-bluebook inboxes (markdown convention)

Convention for each `.bluebook` to carry its own inbox directory of
markdown cards. Replaces the old single-`inbox.heki` model going
forward ; existing 144 cards in the conception heki stay there until
or unless we migrate.

## Why this card exists

Today : ONE inbox at `hecks_conception/information/inbox/inbox.heki`
holds every card filed across the whole conception (i1..i240) as
binary heki records. Two limitations :

1. **Doesn't scale past one repo.** The moment Embryonaut ships,
   every client domain becomes its own bluebook in its own repo,
   and the conception inbox doesn't follow.
2. **Binary records aren't doc-friendly.** Heki records can't be
   linked to from docs, can't be grepped directly, can't be diffed
   inline in pull requests. The inbox is work-as-prose ; prose
   belongs in a text format.

The fix : two convergent moves.

  - **Markdown**, one file per card, replaces heki-record-per-card.
  - **Per-bluebook inbox directory** travels with each bluebook.

## The conventions

### File format

Each card is a markdown file with YAML frontmatter :

    ---
    ref: i7
    role: shop_owner
    value: track customer feedback across visits
    status: queued
    priority: high
    posted_at: 2026-05-04
    ---

    # i7 — short title

    Body of the card. Free prose, full markdown, headings as needed.
    The user-story shape ("As a shop owner, I should be able to log
    a customer note, so that I can track feedback across visits") is
    the *source pattern* for client-interview cards, but the body
    doesn't have to literally repeat it — the role and value tags
    carry that context structurally.

### Path convention

  - **Conception inbox** (framework-level) :
    `hecks_conception/inbox/<ref>.md`
    e.g. `hecks_conception/inbox/i241.md` (this card)
  - **Per-bluebook inbox** (project-level) :
    `<bluebook_dir>/inbox/<ref>.md`
    e.g. `body/voice/inbox/i7.md` — Voice bluebook's i7
    e.g. `bin_buddy/inbox/i3.md` — bin_buddy bluebook's i3

The inbox is a sibling `inbox/` directory of the bluebook file. Same
parent directory ; one file per card. (With heki it was a single
sibling file ; with markdown it's a directory of cards.)

### Schema (frontmatter)

  - `ref` — `i<N>` per-inbox (each inbox starts from i1)
  - `role` — who the card is for or about. Required for project
    inboxes. Values like `Alan`, `shop_owner`, `framework`, `client`,
    `mech`.
  - `value` — what they want to be able to do, the outcome they're
    after. Free-text but concrete.
  - `status` — `queued` | `in_progress` | `done` | `abandoned`
  - `priority` — `high` | `medium` | `low`
  - `posted_at` — `YYYY-MM-DD`

For framework-level cards in the conception inbox, `role` may be
`framework` and `value` describes the structural improvement —
user-story format isn't required at that level but tagging stays
consistent.

## Ref numbering

Per-inbox. Each inbox starts from i1 independently. When a bluebook
lifts and shifts to another repo, its refs don't collide with whatever
inbox they land beside.

When speaking across inboxes, prefix :
`voice.i7`, `bin_buddy.i3`, `i239` (no prefix = conception inbox).

## Existing 144 cards stay in `inbox.heki`

The conception heki at `hecks_conception/information/inbox/inbox.heki`
keeps its 144 historical cards as-is. Migration to per-card markdown
is **future work** — we don't need it now. New cards (i241+) land
as markdown.

The shift is forward-only : `inbox.heki` becomes the historical
archive ; `hecks_conception/inbox/*.md` becomes the live work surface.

## What this enables

  - **bin_buddy** launches as its own repo with `bin_buddy.bluebook`
    \+ `bin_buddy/inbox/i1.md`. Doesn't pollute conception.
  - **Embryonaut clients** each carry their bluebooks + inboxes as
    a unit. No cross-pollination.
  - **Linkable from docs** — `[see voice.i7](../body/voice/inbox/i7.md)`.
  - **Grep-able from shell** — `grep -lr "role: Alan" .` finds every
    card across every inbox tagged for Alan.
  - **Diffable in PRs** — body changes show inline.
  - **Filterable by role / value** — once tooling lands, "what does
    Alan need?" is one query.

## Build steps

  - **Step 1** — Adopt the convention NOW for new cards. No runtime
    changes needed. Just create the markdown file at the right path.
    Unblocks bin_buddy immediately.
  - **Step 2** — `hecks-life inbox add <bluebook> "..."` ergonomics :
    resolves the bluebook by name, opens an editor with the
    frontmatter template pre-filled, writes to
    `<dir>/inbox/<next-ref>.md`.
  - **Step 3** — `hecks-life inbox list` walks every `inbox/` directory
    in scope, prints summary per bluebook (queued / in_progress / done).
  - **Step 4** — Cross-inbox queries by role / value / status. Useful
    for backlog grooming and "what does Alan need?"-style questions.
  - **Step 5** (optional, later) — migrate the 144 inbox.heki records
    to markdown. One-time mechanical script. Defer until needed.

## Adjacencies

  - **Hecksagons don't have inboxes.** Bluebook is king ; the
    hecksagon inherits via the bluebook. Some existing hecksagons
    exist without bluebooks ; that's a violation slated for cleanup
    separately.
  - **i239** corpus + registry + versioning — per-bluebook inboxes
    benefit from the same registry/versioning frame when bluebooks
    travel.
  - **i240** speak-from-stream — voice has its own inbox ;
    voice-specific stream cards land in `body/voice/inbox/`.
  - **i237** client-intake template — the user-story shape that
    feeds these cards. role/value frontmatter mirrors the template's
    capture fields.
