# i242 — :stripe adapter family declaration

As the Hecks framework, I should have a `:stripe` adapter family
declared in the framework registry (the same shape as `:llm`,
`:compute`, `:tts`), so that binbuddy (and every future client repo
that needs payments) can wire `adapter :stripe, ...` in a hecksagon
without re-declaring the wire shape per project.

## Detail

Companion to **binbuddy i83** which declares the binbuddy-side need.
This card is the framework-side declaration that closes binbuddy's
dependency.

Shape, mirroring `:tts` family in `framework/adapter_families/` :

  family       : :stripe
  fields       : [:secret_key_path, :webhook_secret_path,
                  :customer_id_attr, :subscription_id_attr]
  behavior     : :charge_card | :create_subscription | :refund |
                 :webhook_dispatch
  providers    : :stripe (the only provider initially ; PayPal + ACH
                 ride Stripe's unified API in v1)

`framework/providers/stripe.hecksagon` declares the HTTP shape :
endpoint, auth header (Bearer), request_body templates per behavior,
response_kind, webhook signature verification.

NOT in scope today : Square / Braintree / direct ACH via NACHA — file
as their own future cards if a client repo needs them.

## Adjacencies

  - **binbuddy i83** — the binbuddy-side need. Lands when this lands.
  - **i239** — hecksagon corpus + filesystem registry frame ; this card
    is the first new family on top of i239's foundation, after the
    initial :tts family from i238.
  - **i238** — :tts adapter family + Voice aggregate ; same shape, this
    follows the same pattern.

## Considerations

- Stripe Ruby gem on the Sinatra side (calls Stripe API) ; webhook
  endpoint hosted in the customer portal hecksagon (binbuddy i78)
- Test mode keys for the .behaviors test suite (binbuddy i84)
- Idempotency keys on charges so retries don't double-bill — the
  adapter declaration should encode this contract
