# i245 — bluebook DSL : VO shorthands + value-object rules

As the Hecks framework, the bluebook DSL should support concise
syntax for the most common value-object idioms, plus a first-class
`rule` block on `value_object` declarations, so that "use a
value object for every primitive" stops costing more characters
than it earns.

## Why now

While building bin-buddy on 2026-05-04 we adopted the discipline
"every primitive is a value object" — Email, PhoneNumber, ZipCode,
Money, Weekday, all of it. The parser already accepts
`attribute :email, Email` and dumps `attr email type=Email` ; it
works end-to-end. But the syntax is still verbose enough that
people will reach for `String` instead :

```ruby
attribute :customer_account_email, Email
attribute :address_line_1,         StreetLine
attribute :address_line_2,         StreetLine
# ...
then_set :customer_account_email, to: :customer_account_email
then_set :address_line_1,         to: :address_line_1
then_set :address_line_2,         to: :address_line_2
```

When the attribute name matches `snake_case(VOName)` the symbol-name
is redundant, and when `then_set`'s key matches its value source the
hash-rocket is redundant. Stripping that out lets the domain breathe.

## What V1 of this card lands

### 1. `attribute VOClass` — auto-named-from-class

When the attribute name would equal `snake_case(VOClass)`, accept :

```ruby
attribute Email           # ↔ attribute :email, Email
attribute Money           # ↔ attribute :money, Money
attribute StripeSubscriptionId   # ↔ attribute :stripe_subscription_id, StripeSubscriptionId
```

When the attribute needs a *different* name from the VO class
(e.g. `last_email` typed `Email`, or two `StreetLine` attributes
named `address_line_1` / `address_line_2`), keep the explicit form :

```ruby
attribute :last_email,     Email
attribute :address_line_1, StreetLine
attribute :address_line_2, StreetLine
```

Both forms coexist ; the shorthand is purely an opt-in for the
common case. Bluebook authors choose per-attribute.

### 2. `then_set :foo` — same-name shorthand

When `then_set`'s key matches its source (the input attribute of the
same name), accept the bare form :

```ruby
then_set :email          # ↔ then_set :email, to: :email
then_set :phone          # ↔ then_set :phone, to: :phone
```

Literal-value sets keep the explicit form — `then_set :status, to:
"active"` — because there's no shorthand to remove.

### 3. `then_set :a, :b, :c` — variadic same-name

Most signup-cascade commands set 5–10 attributes from same-name
inputs. Inline list :

```ruby
then_set :customer_account_email, :address_line_1, :address_line_2,
         :city, :state, :zip, :gate_code, :access_notes,
         :trash_day, :recycle_day
```

Each symbol expands to a `then_set :sym, to: :sym`. Mix freely with
other forms in the same command body.

### 3b. `then_append :foo` — same-name `append:` shorthand

Same shape as #2 for the append-to-list case :

```ruby
then_append :images       # ↔ then_set :images, append: :images
then_append :tags
```

Literal-value appends keep the explicit form
(`then_set :tags, append: "system-generated"`).

### 4. `accepts :a, :b, :c` — declare-and-then-set in one line

For the very common pattern where a command takes a set of input
attributes and then-sets them onto the aggregate same-name :

```ruby
command "RegisterCustomer" do
  role "Public"
  description "..."
  accepts :account_email, :first_name, :last_name, :phone
  emits "CustomerRegistered"
  # implicit : declares the four attributes (typed by the
  # aggregate's matching attribute) AND then_sets them all
  # same-name onto the aggregate.
end
```

Each symbol in `accepts` :
1. Declares a command attribute named `:sym` typed by the aggregate's
   `:sym` attribute (so the same VO type carries through).
2. Adds a `then_set :sym` (per #2) to the command body unless the
   bluebook author overrides with an explicit `then_set` for that
   attribute.

`accepts` does NOT cover :
- Command-level `role` (which is "who can dispatch this command",
  orthogonal to "what inputs it takes").
- Literal-value `then_set`s (`then_set :status, to: "active"`).
- Cross-attribute mappings (`then_set :address_line_1, to: :line_1`).

Mix freely : `accepts :foo, :bar` followed by `then_set :status, to:
"active"` is the canonical pattern.

**Naming note on `role`** : `accepts :role` (symbol in a list) and
`role "Owner"` (string-arg call) parse unambiguously. Conceptually
they ARE the same domain word — Account's `:role` attribute holds
which role the account *is* ; the command-level `role "Owner"`
declares which role can *dispatch*. Same concept, different
perspectives. Bluebook authors don't need to rename their domain
attribute on Hecks's behalf — the framework accommodates the
domain, not the other way around. The two reads coexist.

### 5. PM transitions : `from:` / `to:` keywords

The current PM `transition: { from_state: :to_state }` hash form is
hard to read with multiple from-states. Cleaner :

```ruby
on "PaymentFailed", from: :active, to: :past_due do
  # ...
end

on "SubscriptionCanceled", from: [:active, :past_due, :inactive], to: :canceled do
  # ...
end
```

The hash form keeps working for back-compat ; `from:`/`to:` is the
new ergonomic surface.

### 6. Variadic `states`

Replace the per-line :

```ruby
state "active"
state "past_due"
state "inactive"
state "canceled"
```

With :

```ruby
states :active, :past_due, :inactive, :canceled
```

Symbols → string conversion at parse time. Order preserved (matters
for PM "starts in first state" semantics — i220-2).

### 7. `find_by_*` implies `limit 1`

Queries whose name starts with `find_by_` or `find_one_*` get
`limit 1` implicitly :

```ruby
query "find_by_email" do
  description "Look up one account by email."
  where(email: :email)
  # implicit limit 1 — query name says "find one"
end
```

Authors can override with an explicit `limit 5` if they want a
top-N "find" semantics. The default-1 case is the overwhelming
majority.

### 8. Drop redundant `description` when a code-comment precedes

```ruby
# Read the inventory for one address — used at task-generation
# time and on every driver-app route stop.
query "find_by_address" do
  where(address_id: :address_id)
end
```

The code-comment IS the description. Currently authors duplicate
it as a `description "..."` string inside the block — pure
restating. The DSL should hoist the immediately-preceding comment
block into the description field.

If the author DOES write an explicit `description "..."` it wins
(overrides the comment).

### 9. `rule` on `value_object`

Constraints belong with the value object, not at the dispatch
boundary :

```ruby
value_object "Email" do
  attribute :value, String
  rule "must contain @ and a domain" do
    contains "@"
    matches /\A[^\s@]+@[^\s@]+\.[^\s@]+\z/
  end
end

value_object "Money" do
  attribute :amount_cents, Integer
  rule "must be non-negative" do
    at_least 0
  end
end

value_object "Weekday" do
  attribute :value, String
  rule "must be a valid weekday" do
    one_of "mon", "tue", "wed", "thu", "fri", "sat", "sun"
  end
end

value_object "ZipCode" do
  attribute :value, String
  rule "must be 5 or 9 digits" do
    matches /\A\d{5}(-\d{4})?\z/
  end
end
```

Rule matchers (`contains`, `matches`, `at_least`, `at_most`,
`one_of`, `length`, `present`, custom predicate blocks) check at
construction time. Failed construction raises a structured error
with `vo_name`, `rule_message`, and the offending value — the
adapter / portal layer renders it as a 422 with a clean message.

## Implementation surface

— **Parser** : `codegen/parse_blocks_shape/snippets/` updates for
  attribute-class-shorthand + bare-symbol-then_set + variadic-then_set
  + value-object rule block. Regenerate `rust/src/parse_blocks.rs`.

— **Ruby parity** : `ruby/hecks/dsl/` mirror updates so both
  parsers accept the same syntax and `parity_test.rb` stays green.

— **IR** : new field on `Mutation` (or wherever `then_set` lives)
  for the implicit-source case. New `rules: Vec<Rule>`
  on `ValueObject` IR.

— **Runtime** : VO construction validates against rules ;
  raises `RuleViolation` with structured error data. Top-level
  dispatch turns these into `RuntimeError::RuleFailed` so the
  HTTP / behaviors layers can render them.

— **Behaviors test surface** : new matcher `expect_rule_failure`
  for testing the rule-failure path explicitly.

— **Generators** : Sinatra portal generators check VO rules at
  form-input time so the user sees the message before round-tripping
  to the backend.

## Considerations

- These are syntactic sugar (1, 2, 3) plus one new DSL primitive
  (4). Existing bluebooks keep parsing — nothing breaks.

- bin-buddy adopted the discipline "every primitive is a VO" on
  2026-05-04 ; ~14 aggregates have been refactored. After this card
  lands, all of them get a sweep to use the shorter forms — that's
  ~150 attributes and ~80 then_set rewrites that the shorthand
  collapses by half.

- Rules land at the VO boundary, not at the command boundary.
  That's a deliberate choice : VOs are reusable across aggregates,
  so per-VO rules travel with them. A command that takes an
  Email gets validation for free. (We'll never share VOs across
  bluebooks per Chris's "no DRY for VOs" rule, but the pattern of
  the same-shape-VO-redeclared-locally still gains validation
  for free per declaration.)

- Tie to i239 (adapter family meta-shape) : rules on VOs is
  a similar shape — declarative validation that the framework's
  runtime enforces, not bluebook authors writing imperative checks.

## Parity gate

Every framework change in this card has to land in BOTH the Rust
parser/runtime AND the Ruby DSL/runtime ; the dual-runtime parity
contract (`parity/parity_test.rb`) must stay green when the PR
is opened.

  - Rust side : `codegen/<shape>/snippets/`, regenerated `rust/src/`
  - Ruby side : `ruby/hecks/dsl/`, `ruby/hecks/bluebook_model/`,
    `parity/canonical_ir.rb`
  - Verification : `ruby -Iruby parity/parity_test.rb` reports the
    expected pass count + 0 unintended drift
  - Hecksagon parity : `ruby -Iruby parity/hecksagon_parity_test.rb`
    when adapter / hecksagon surface changes

An agent’s PR is not ready for merge until parity is verified
locally and the relevant golden goldens / canonical-IR shapes are
updated together. No Rust-only or Ruby-only changes ship.
