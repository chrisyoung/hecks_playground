# i247 — value objects know how to do things

As the Hecks framework, a value object should be able to declare
the things it *knows how to do* — Money knows how to add, Weekday
knows how to compare, Timestamp knows how to measure a duration —
so the domain can compute things in its own vocabulary instead of
bleeding the math into adapter glue or query helpers.

## Why

Today VOs are passive : they hold a value, validate it (post-i245),
and stop there. The first time someone needs to compute "next
month's billing date" or "is Tuesday before Friday?" or "did this
take more than two hours?", the answer is either :

1. Pull the inner value out, do raw String/Integer math, wrap
   the result back up. *(Loses the type, leaks primitives.)*
2. Put the math on an adapter or a query helper. *(Wrong
   layer ; the math is domain logic, not adapter glue.)*
3. Inline the math in the command body. *(Scattered, untestable.)*

Real domain types — Money, Weekday, Duration — *do things*. The
DSL should let bluebooks declare what each VO knows.

## DSL

```ruby
value_object "Money" do
  attribute :amount_cents, Integer

  rule "non-negative" do
    requires { amount_cents >= 0 }
  end

  knows "add", returns: Money do |other|
    Money.new(amount_cents: amount_cents + other.amount_cents)
  end

  knows "subtract", returns: Money do |other|
    Money.new(amount_cents: amount_cents - other.amount_cents)
  end

  knows "format", returns: String do |locale: :en_US|
    # "$45.00" for en_US, "45,00 €" for de_DE, etc.
  end

  knows "is_zero", returns: Boolean do
    amount_cents == 0
  end
end

value_object "Weekday" do
  attribute :value, String
  rule { one_of "mon", "tue", "wed", "thu", "fri", "sat", "sun" }

  knows "days_until", returns: Integer do |other|
    # 0..6 wraparound
  end

  knows "is_before", returns: Boolean do |other|
    days_until(other) < 4
  end
end

value_object "Timestamp" do
  attribute :iso8601, String
  rule { matches /\A\d{4}-\d{2}-\d{2}T.../ }

  knows "duration_since", returns: Duration do |earlier|
    # ...
  end

  knows "is_within", returns: Boolean do |window_start, window_end|
    # ...
  end
end
```

The body of a `knows` block is a Ruby block that runs against the
VO's own state plus the named arguments. Returns a typed value
(another VO, primitive, or Boolean).

## Wiring with rules and aggregates

Once Money knows how to add, an aggregate-level rule (i246) reads
naturally :

```ruby
aggregate "AddOn" do
  attribute :unit_price,  Money
  attribute :quantity,    Quantity
  attribute :total_price, Money

  rule "total_price equals unit_price × quantity" do
    requires { total_price == unit_price.multiply(quantity) }
  end
end
```

Pure domain logic, in domain language, in the bluebook.

## Implementation surface

— **IR** : `ValueObject.behaviors: Vec<Behavior>` ; each carries
  a name, ordered parameter list, return-type reference, and a
  body (closure or structured-expression IR).

— **Parser** : `knows "name", returns: T do |...args...| ... end`
  block recognizer inside `value_object` declarations.

— **Runtime** : VO instances expose declared behaviors as instance
  methods. Method dispatch validates arg types, runs the body,
  validates the return type matches the declaration.

— **Standard library** : a small set of pre-declared VOs ship with
  Hecks for the universal cases : `Money`, `Duration`, `Period`,
  `DateOnly`, `Timestamp`, `EmailAddress`. Their behaviors are
  built-in. Custom VOs (Weekday, BinCount) live in user bluebooks.

## Considerations

- Behaviors are pure : no side effects, no I/O, no mutation. The
  runtime can enforce by parsing the body for forbidden patterns
  (file ops, network calls, dispatch). Same posture as DDD value
  objects in the literature.

- For the standard-library VOs, the behaviors are framework-side
  Rust + Ruby implementations (canonical). For user VOs they're
  user-bluebook-side blocks the runtime evaluates.

- Tie to i246 (aggregate rules — rules reference what VOs know).
  Tie to i248 (specifications — specs use VO behaviors as predicates).
