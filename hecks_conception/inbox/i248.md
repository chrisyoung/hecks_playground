# i248 — specifications (Evans-style composable predicates)

As the Hecks framework, an aggregate should be able to declare
named *specifications* — composable predicates over its state
that other domain code can ask "does this record match?" — so
common conditional logic gets a name, lives in one place, is
testable in isolation, and can compose.

## Why

Eric Evans named this pattern. Real domains have repeated
predicates :

  - "Is this Subscription dispatchable?" — `operational_status ==
    active AND billing_status == active AND service_address.status
    == active`
  - "Is this ServiceTask overdue?" — `status == pending AND
    Time.now > window_end + grace_period`
  - "Is this DriverApplication awaiting decision?" — `status ==
    background_check_pending`

Each shows up in 3–10 places — query filters, conditional
dispatches, admin dashboards, route generators. Without a name,
the predicate is duplicated and inevitably drifts. With a name,
it's the kind of thing the domain *talks* about.

## DSL

```ruby
aggregate "Subscription" do
  # ... attributes, commands ...

  specification "Dispatchable" do
    requires :operational_status, equals: "active"
    requires :billing_status,     equals: "active"
    requires :service_address,    matches: "Active", on: ServiceAddress
  end

  specification "InGracePeriod" do
    requires :billing_status, equals: "past_due"
    requires :grace_period_ends_at, after: Time.now
  end

  specification "AtRisk" do
    matches "InGracePeriod"
    OR matches "Subscription.PaymentFailedThisMonth"
  end
end
```

Specifications compose with `AND`, `OR`, `NOT`, and reference each
other across aggregates by name (`Subscription.Dispatchable`,
`Customer.HighValue`).

## Use sites

Specifications are queryable, filterable, and dispatchable :

```ruby
# Query side
query "active_addresses_for_routing" do
  description "Address has an active dispatchable subscription."
  matches Subscription.Dispatchable
end

# PM dispatch side
dispatch "ServiceTask.Generate", for_each: {
  from: Subscription.matches("Dispatchable")
}

# Admin filter side
view "AtRiskCustomers" do
  filter Subscription.matches("AtRisk")
end

# Test side
test "AtRisk includes payment-failed subscriptions" do
  given Subscription, payment_failed_at: "..."
  expect_specification :AtRisk, matches: true
end
```

## Implementation surface

— **IR** : `Aggregate.specifications: Vec<Specification>` field.
  Each carries name, predicate tree (composable AND / OR / NOT
  with leaf matchers).

— **Parser** : `specification "Name" do ... end` block recognizer
  at aggregate scope. Composability via `matches "OtherSpec"` and
  `AND` / `OR` / `NOT` operators.

— **Runtime** : specifications evaluate against an aggregate's
  current state. Cached for the duration of a command dispatch.
  Cross-aggregate specs perform repository lookups (which i249
  references make type-safe).

— **Query integration** : a query can declare `matches SpecName`
  to use the spec as a where-clause-equivalent. Generated SQL (if
  the persistence adapter supports it) collapses spec predicates
  to native query operators ; otherwise the runtime walks
  `repo.all` and filters in memory.

## Considerations

- Specifications can call VO operations (i247) — `requires { price.is_zero }`.
- Specifications can reference aggregate invariants (i246) — `requires
  invariant: :foo` checks an invariant as a Boolean.
- Specifications are pure (no mutation, no I/O beyond named
  repository lookups via i249 references).
- Performance : caching one spec evaluation per command dispatch
  per aggregate instance is the floor. Cross-aggregate spec lookups
  should respect query indices when the persistence layer supports
  them.

## Parity gate

Every framework change in this card has to land in BOTH the Rust
parser/runtime AND the Ruby DSL/runtime ; the dual-runtime parity
contract (`parity/parity_test.rb`) must stay green when the PR
is opened.

  - Rust side : `codegen/<shape>/snippets/`, regenerated `rust/src/`
  - Ruby side : `ruby/hecks/dsl/`, `ruby/hecks/bluebook_model/`,
    `parity/canonical_ir.rb`
  - Verification : `ruby -Iruby parity/parity_test.rb` reports the
    expected pass count + 0 unintended drift
  - Hecksagon parity : `ruby -Iruby parity/hecksagon_parity_test.rb`
    when adapter / hecksagon surface changes

An agent’s PR is not ready for merge until parity is verified
locally and the relevant golden goldens / canonical-IR shapes are
updated together. No Rust-only or Ruby-only changes ship.
