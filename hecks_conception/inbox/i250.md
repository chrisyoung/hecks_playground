# i250 — events have identity

As the Hecks framework, an event emitted by a command should be
declarable with an identity — using `identified_by:` on the emits,
the same keyword aggregates use for their primary key — so the
runtime can recognize two reports of the same event as one event
without programmer-jargon like *idempotent*, *dedupe*, or
*witnessed-by* leaking into the domain language.

## Why

Webhook handlers retry. Stripe sends `invoice.payment_failed`
once, the network drops the response, Stripe sends it again. The
runtime must recognize : same event, same effect, recorded once.

Currently every command runs as if it's fresh — receiving two
`Subscription.RecordPaymentFailed` reports for the same Stripe
event ID double-stamps the failure timestamp.

The DDD-correct framing is that *events have identity*. Just like
two `Customer` records with the same email are the same customer,
two `PaymentFailed` events with the same `stripe_event_id` are the
same event. The bluebook never has to say *idempotent* — it just
says *identified by*, which is a word it already uses.

## DSL

Reuse the keyword that's already in the vocabulary :

```ruby
aggregate "Customer" do
  identified_by :email
end

command "RecordPaymentFailed" do
  accepts :stripe_event_id, :stripe_subscription_id,
          :payment_failed_at, :grace_period_ends_at
  emits "PaymentFailed", identified_by: :stripe_event_id
end

command "Upload" do
  accepts :sha256_of_image, :service_task_id, :photo_type, :url,
          :captured_at, :gps_lat, :gps_lng
  emits "PhotoUploaded", identified_by: :sha256_of_image
end

command "MarkSent" do
  accepts :notification_id, :sent_at
  emits "NotificationSent", identified_by: :notification_id
end
```

Reads naturally : *"emits PaymentFailed, identified by
stripe_event_id."*

When the runtime receives a command whose emitted event would have
the same identity as an already-recorded event of that type, the
command is a no-op : the prior event stands, no new event emits,
no state mutates, the prior result returns. *That's* the dedupe
semantics — emerging from identity, not from a programmer
keyword.

## Implementation surface

— **IR** : `Emits.identified_by: Option<AttributeName>` field on
  the command's emits declaration. (When absent, the runtime mints
  an identity from the dispatch ; when present, the named input
  attribute IS the identity.)

— **Parser** : extend the `emits "Name"` recognizer to accept the
  `, identified_by: :attr` keyword argument.

— **Runtime** : per-aggregate event log keyed by (event_type,
  identity). On dispatch, if the would-be event's identity already
  exists in the log, return prior result without re-running the
  command body.

— **Persistence** : the event-identity index persists with the
  aggregate's heki ; survives restarts.

## Considerations

- The Stripe webhook adapter (i83 / bin-buddy.hecksagon) routes
  inbound webhooks to commands ; the inbound event's `stripe_event_id`
  flows into the command's `accepts`, then into the `emits
  identified_by:`, and the runtime dedupes from there.

- Default retention : event-identity index entries persist
  alongside their aggregate. Old entries can be pruned by an
  admin-driven retention policy ; not auto-expired.

- Conflict case : if a second command dispatches with the same
  identity but DIFFERENT non-identity attributes, the runtime
  raises `EventIdentityConflict { event_type, identity,
  prior_state, current_state }` rather than silently picking one.

- Tie to i246 (aggregate invariants) : event identity participates
  in invariants the same way attribute values do. Tie to i248
  (specifications) : specs can ask "has this event already
  occurred?" by querying the event log for a given identity.

- The bluebook never says *idempotent*. It says *identified by*.
  The same word it uses for aggregate primary keys. One concept,
  one word, applied consistently. Domain-true.

## Parity gate

Every framework change in this card has to land in BOTH the Rust
parser/runtime AND the Ruby DSL/runtime ; the dual-runtime parity
contract (`parity/parity_test.rb`) must stay green when the PR
is opened.

  - Rust side : `codegen/<shape>/snippets/`, regenerated `rust/src/`
  - Ruby side : `ruby/hecks/dsl/`, `ruby/hecks/bluebook_model/`,
    `parity/canonical_ir.rb`
  - Verification : `ruby -Iruby parity/parity_test.rb` reports the
    expected pass count + 0 unintended drift
  - Hecksagon parity : `ruby -Iruby parity/hecksagon_parity_test.rb`
    when adapter / hecksagon surface changes

An agent’s PR is not ready for merge until parity is verified
locally and the relevant golden goldens / canonical-IR shapes are
updated together. No Rust-only or Ruby-only changes ship.
