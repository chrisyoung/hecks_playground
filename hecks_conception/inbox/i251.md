# i251 — aggregate cardinality (has_many / has_one)

Cardinality between aggregates should be first-class, declared in
the bluebook, generating helpers and surfacing in dashboards
instead of being inferred from FK fields.

## DSL

One verb (`has`), and English does the cardinality work. Singular
class name → 1:1 ; plural class name → 1:N. The DSL inflects.

### Cardinality from the noun

```ruby
aggregate "Customer" do
  has ServiceAddresses        # plural noun → has-many
  has Subscriptions           # plural noun → has-many
  has BinInventory            # singular noun → has-one
end

aggregate "ServiceAddress" do
  has ServiceTasks            # plural → has-many
  has Photos, through: ServiceTask
  has BinInventory            # singular → has-one
end
```

The parser recognizes the trailing `s` (plus standard English
inflection rules : `Inventories ↔ Inventory`, `People ↔ Person`,
`Series ↔ Series`, etc.) and routes to has-one or has-many
accordingly. The class name itself stays singular per Ruby
convention (`class Photo`, never `class Photos`) ; the DSL's
const-missing hook resolves `Photos` to a plural-reference of
`Photo` at parse time.

`has_many TargetAggregate` keeps working as the explicit form
when an author prefers it ; both forms emit the same IR.

### Bounded arity

Cardinality can be a range, not just "one or many." `has` accepts
a Ruby range as a leading positional arg :

```ruby
has (1..10) Workers      # between 1 and 10 (inclusive both ends)
has (5) Workers          # exactly 5
has (1..) Workers        # at least 1 (open upper bound)
has (..3) Workers        # at most 3 (open lower bound)
has (0..) Workers        # zero or more — same as `has Workers`
has (1..1) Plan          # exactly 1 — same as `has Plan`
```

This collapses what would otherwise be three separate declarations
(the relation + a min-count rule + a max-count rule) into one
domain-natural sentence. The runtime enforces both bounds as
implicit `rule`s on the aggregate.

Concrete bin-buddy uses :

```ruby
aggregate "Route" do
  has (1..) ServiceTasks      # a published route has at least one task
end

aggregate "Subscription" do
  has (1..1) Plan             # exactly one plan per subscription
  has (0..) AddOns            # zero or many royalty add-ons
end

aggregate "ServiceAddress" do
  has (1..2) BinInventories   # at least one inventory ; can split trash/recycle
end
```

The plural form (`Workers`) is required when the range allows >1 ;
a singular form with a range >1 (`has (1..10) Worker`) is a parse
error — the grammar should match.

### Verbose form (for aliased / non-default cases)

When the relation needs a custom name (aliased, multiple-of-same-
class, through-join) or the FK doesn't follow convention, use the
`as:` and `via:` keywords explicitly :

```ruby
has Route,    as: :default_route                   # singular alias
has Routes,   as: :recent_routes                   # plural alias
has Workers,  as: :dispatchers, via: :dispatcher_email
has Workers,  as: :drivers,     via: :driver_email
has Photos,   through: ServiceTask
```

Mirrors i245's attribute-side rule : convention-driven shorthand
when the default applies ; explicit `as:` / `via:` when the
relation diverges from default.

### Generated accessors

- `customer.service_addresses` (returns Array)
- `customer.bin_inventory` (returns single record or nil)
- Admin UI : "Customer profile" page automatically lists
  addresses, subscriptions, with click-through.

## Implementation surface

— **IR** : `Aggregate.relations: Vec<Relation>` ; each : kind
  (`has_many | has_one`), target, via (FK), optional `through` for
  indirect relations.

— **Parser** : `has_many TargetAggregate, via: :fk` recognizer
  at aggregate scope.

— **Runtime** : generated query helpers ; cached per aggregate
  instance.

— **Admin UI** : the dashboard renders "linked records" panels
  derived from these declarations.

## Considerations

- Subset of i249 references — references is single-record, has_many
  is multi-record. The two coexist : a Subscription
  `references Customer` ; a Customer `has_many Subscription`.
- `through` for indirect relations (Customer has_many Photo via
  ServiceAddress + ServiceTask).

Every framework change in this card has to land in BOTH the Rust
parser/runtime AND the Ruby DSL/runtime ; the dual-runtime parity
contract (`parity/parity_test.rb`) must stay green when the PR
is opened.

    expected pass count + 0 unintended drift
  - Hecksagon parity : `ruby -Iruby parity/hecksagon_parity_test.rb`
    when adapter / hecksagon surface changes

An agent’s PR is not ready for merge until parity is verified
locally and the relevant golden goldens / canonical-IR shapes are
updated together. No Rust-only or Ruby-only changes ship.
