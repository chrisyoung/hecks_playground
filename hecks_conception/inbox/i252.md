# i252 — commands expect and guarantee

A command should be able to declare what it *expects* before it
runs and what it *guarantees* after — named blocks of state checks
that read in domain language instead of programmer terms like
"precondition" or "postcondition."

## DSL

```ruby
command "Subscribe" do
  role "Customer"
  description "..."
  accepts :customer_account_email, :service_address_id, :plan_code,
          :stripe_subscription_id, :monthly_price

  expects "address must be active" do
    service_address.status == "active"
  end
  expects "no existing active subscription on this address" do
    Subscription.find_by_address(service_address_id).nil?
  end

  guarantees "subscription is operationally active" do
    operational_status == "active"
  end
  guarantees "billing status mirrors stripe" do
    billing_status == stripe_subscription.status
  end

  emits "Subscribed"
end
```

`expects` checks the world before the command applies its
mutations. `guarantees` checks the aggregate's state after. Both
are Boolean blocks ; if either returns false the runtime raises
a structured error and rolls the dispatch back as if the command
never happened.

## Failure shape

Failed expectations and guarantees raise the same family of
structured errors that aggregate rules (i246) and VO rules
(i245) raise. The portal layer renders them as 422s with the
message and the offending state. *Same* error pattern across
the entire domain — one error story, four declaration sites
(VO rule / aggregate rule / expects / guarantees).

## Considerations

- `given` clauses persist as the inline-conditional form (gate
  whether a command applies its mutations to a particular
  record). `expects` is the structured contract form (the
  command shouldn't even attempt to run if these aren't true).

- Tie to i248 (specifications — `expects` blocks can reference
  specs as predicates : `expects "subscription is dispatchable"
  do matches Subscription.Dispatchable end`).

- Tie to i246 (aggregate rules — rules run automatically on any
  state mutation ; `expects` / `guarantees` run only on the
  named command).

- Tie to i247 (VO behaviors — `expects` blocks can call VO
  behaviors freely : `expects "amount must be positive" do
  amount.is_positive end`).

## Parity gate

Every framework change in this card has to land in BOTH the Rust
parser/runtime AND the Ruby DSL/runtime ; the dual-runtime parity
contract (`parity/parity_test.rb`) must stay green when the PR
is opened.

  - Rust side : `codegen/<shape>/snippets/`, regenerated `rust/src/`
  - Ruby side : `ruby/hecks/dsl/`, `ruby/hecks/bluebook_model/`,
    `parity/canonical_ir.rb`
  - Verification : `ruby -Iruby parity/parity_test.rb` reports the
    expected pass count + 0 unintended drift
  - Hecksagon parity : `ruby -Iruby parity/hecksagon_parity_test.rb`
    when adapter / hecksagon surface changes

An agent’s PR is not ready for merge until parity is verified
locally and the relevant golden goldens / canonical-IR shapes are
updated together. No Rust-only or Ruby-only changes ship.
