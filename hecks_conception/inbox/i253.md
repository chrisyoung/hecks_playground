# i253 — process managers undo their work on failure

As the Hecks framework, a process manager should be able to declare
what to *undo* if one of its later steps fails — so multi-step
domain processes (driver onboarding, customer signup, refund flow)
recover from partial failures without leaving the system in a
half-finished state.

## Why

The DriverOnboarding PM (V1.1) cascades :

  Approve → Account.SignUp(role: driver) → Notification.SendDriverWelcome

If `Account.SignUp` succeeds but `Notification.SendDriverWelcome`
fails (SendGrid down, malformed email, whatever), the application
record sits at `approved` *and* the account exists, but the welcome
email never went out. Half-done.

The same pattern shows up in :
- Subscribe → CreateStripeCustomer → ChargeFirstMonth → ActivateSubscription
- AddOn.Request → Stripe charge → ServiceTask.Generate
- DriverApplication.Reject → Notification.SendApplicationDeclined

DDD's saga pattern : each forward step has an undo. If a later
step fails, the runtime walks the prior steps in reverse order
calling the undo.

## DSL

```ruby
process_manager "DriverOnboarding" do
  # ... states and transitions ...

  on "DriverApproved", from: :background_check_pending, to: :approved do
    dispatch "Account.SignUp", with: { ... }
    undo_with "Account.Deactivate", with: { email: from_pm(:email) }
  end

  on "DriverActivated", from: :approved, to: :active do
    dispatch "Notification.SendDriverWelcome", with: { ... }
    # No undo needed — notification is the last step ; failure means
    # the welcome didn't go out, but the account still exists and
    # the application is active. Manual retry from admin portal.
  end
end
```

`undo_with` declares the command to dispatch if a *later* step in
the cascade fails. The runtime walks the cascade backward,
dispatching each `undo_with` in reverse order.

## Implementation surface

— **IR** : `Transition.undo: Option<DispatchSpec>` field on each
  PM transition.

— **Runtime** : when a cascade step fails, `runtime/pm_engine.rs`
  walks back through the prior transitions in this cascade,
  dispatching each `undo_with` in LIFO order. The undo dispatches
  themselves go through normal command dispatch (subject to rules,
  expectations, etc.) — if an undo fails, the runtime logs the
  failure and surfaces it in the AuditLog (i94) for manual review.

— **Behaviors** : new matcher `expect_compensated do |scenario| ...
  end` that runs a cascade, induces a step failure, and verifies
  the undo cascade ran.

## Considerations

- Not every step needs an undo. Notifications, audit-log entries,
  and other "outbound" effects are typically NOT undone (you can't
  unsend an email). The default is no undo ; opt-in per
  transition.

- Tie to i250 (event identity) : if an undo dispatches a command
  that emits an event with the same identity as one already
  recorded, the event log skips re-emit (deduplication of undo).

- Tie to i246 (aggregate rules) : an undo command must obey the
  same rules as a forward command. Can't undo into an
  invalid state.
