# i254 — views per role

As the Hecks framework, an aggregate should be able to declare
named *views* — different shapes of the same record, scoped by
role — so that a customer's pickup record exposes
"scheduled_date, status, before_photo_url, after_photo_url" while
the admin's view of the same pickup also exposes "worker_account_email,
route_id, failed_reason, internal_notes" without any per-portal
templating chasing this manually.

## Why

Today every portal hand-renders aggregate state with its own
field-list. Customer portal templates a Pickup row with a
specific subset ; admin portal templates the *same* Pickup row
with a different subset. Drift is inevitable :
- Add a new attribute → forget to add it to admin → admin can't
  see it.
- Mark an attribute internal-only → forget to remove it from
  customer → customer sees admin notes.

A first-class view declaration in the bluebook puts the
field-shape decision where the data lives.

## DSL

```ruby
aggregate "ServiceTask" do
  # ... attributes, commands, rules ...

  view "for_customer" do
    show :scheduled_date,
         :status,
         :before_photo,
         :after_photo,
         :completed_at
  end

  view "for_driver" do
    show :scheduled_date,
         :window_start,
         :window_end,
         :access_notes_from_address,
         :status
    show ServiceAddress.address_line_1, as: :address
    show ServiceAddress.gate_code,      as: :gate_code
  end

  view "for_admin" do
    show_all
    plus :route_id,
         :worker_account_email,
         :failed_reason,
         :internal_notes
  end
end
```

Portal renderers consume views by name :

```ruby
# Customer portal route handler
get "/pickups/:id" do
  render ServiceTask.find(params[:id]).view("for_customer")
end
```

The view definition is the single source of truth ; every
template / route / API response that wants the customer's view
of a pickup gets the same shape.

## Implementation surface

— **IR** : `Aggregate.views: Vec<View>` ; each carries a name
  and an ordered list of field projections (own fields,
  cross-aggregate joins via i249 references, computed fields
  via i247 VO behaviors).

— **Parser** : `view "name" do show :a, :b, ... end` block
  recognizer at aggregate scope.

— **Runtime** : `record.view("for_customer")` returns a
  projection (a hash, a struct, JSON, depending on the consumer).

— **Authorization** : view names suggest role gating but don't
  enforce it. Combine with role-gated routes in the portal
  hecksagons (i75 / i92) for the actual gate.

## Considerations

- Tie to i249 (references) : views can pull from referenced
  aggregates without manual joins.
- Tie to i247 (VO behaviors) : views can include computed fields
  (`monthly_price.format(:en_US)`).
- Tie to i248 (specifications) : views can include spec results
  (`is_dispatchable: matches?("Dispatchable")`).
- Generators : Sinatra portal generators consume views to
  scaffold default templates. One bluebook view → three portal
  templates (homeowner / driver / admin) that all pull from the
  same shape.
