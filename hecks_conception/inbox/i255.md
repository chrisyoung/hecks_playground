# i255 — bluebook rule vocabulary

As the Hecks framework, the bluebook DSL should use six distinct
keywords for six distinct kinds of domain rule. Each keyword names
its concept in English, with no programmer jargon ("invariant,"
"precondition," "postcondition," "idempotent") and no umbrella
term swallowing multiple concepts.

This card is foundational : i245 (DSL ergonomics + VO rules), i246
(aggregate rules), i250 (event identity), i252 (commands expects /
guarantees), and i253 (PM undo) all sit on top of this vocabulary.

## The six keywords

| Keyword | Where it lives | What it means |
|---|---|---|
| **`rule`** | inside `aggregate` or `value_object` | something that must always be true. Checked by the runtime on every state mutation ; a violated rule rolls the dispatch back. |
| **`given`** | inside `command` | a guard that gates whether the command applies its mutations to a particular record. The command can fire ; the mutations only land when the `given` is true. |
| **`expects`** | inside `command` | what must already be true *before* the command runs. A failed `expects` is a structured error — the command never started. |
| **`guarantees`** | inside `command` | what the command ensures is true *after* it runs. A failed `guarantees` is a runtime invariant violation — the command's contract was breached. |
| **`policy`** | inside `aggregate` or top-level | when X event happens, dispatch Y command. The bluebook's reactive surface — already a Hecks DSL primitive. |
| **`transition`** | inside `process_manager` | a state-machine move : on this event, from this state to that state. Already a Hecks DSL primitive (the `on … from: … to: …` form lands with i245). |

## Why six and not one

Programmer-side it's tempting to call all of these "invariants"
or "constraints" or "validations." But each one *does a different
thing in the domain* :

  - A **rule** of the aggregate is a fact about the world that
    must always hold. "A subscription's cancel_date is after its
    start_date" is true regardless of what command tried to make
    it otherwise.

  - A **given** is the command's *applicability* gate. "Apply this
    pickup-completion only to pickups whose status is in_progress."
    Not a violation if the gate is closed — just a no-op for that
    record.

  - An **expects** is the command's *precondition*. "Subscribe
    expects the address to be active." Not a violation of the
    aggregate's rules ; a violation of the command's contract.

  - A **guarantees** is the command's *promise*. "Subscribe
    guarantees the new subscription's operational_status is
    active afterward." This is what the caller can rely on.

  - A **policy** is reactive : "on PaymentFailed, fire
    SendPaymentFailedNotification." It connects events to
    cascades.

  - A **transition** is the state machine's grammar : "from
    submitted on BackgroundCheckRequested move to
    background_check_pending."

Six concepts, six words. Anyone reading the bluebook knows what
a `rule` does versus what an `expects` does — same way they know
what a *recipe* does versus what a *receipt* does. The words
disambiguate themselves.

## What this displaces

In the wild, programmer-shaped specs reach for :

  - "invariant" — too abstract ; covers VO + aggregate + command
    contract simultaneously, hides which is which
  - "precondition" / "postcondition" — Eiffel-shaped, doesn't
    travel beyond programmers
  - "idempotent" — pure jargon ; the underlying domain concept is
    *event identity* (i250 — events have identity, declared via
    `identified_by:` on emits, the same word aggregates use for
    their own primary key)
  - "validator" / "constraint" — DB / form-validation terms ;
    pull domain logic toward the persistence layer
  - "saga" — DDD term but still mechanical-sounding ; the
    behavior is "process manager undoes its work on failure"
    (i253), and the keyword is simply `undo_with`

## Already-existing alignments

- `policy` is already a Hecks DSL primitive — keep as is.
- `transition` is already inside `process_manager` — keep,
  with the i245 ergonomic shift `transition: { a: :b }` →
  `from: :a, to: :b`.
- `given` is already a Hecks DSL primitive (command guards) — keep.

## What changes

- VO `value_object "Email" do invariant ... end` → `rule ...`
  (i245 was using `invariant` ; switch.)
- Aggregate-level rules : new card i246 lands them as `rule`
  (already correctly named there).
- Command pre/post : new card i252 lands them as `expects` /
  `guarantees` (already correctly named there).
- Event identity : new card i250 lands `identified_by:` on
  `emits` — no idempotent jargon (already correctly framed).
- PM undo : new card i253 lands `undo_with` (named for what
  it does — undo the last step).

## Considerations

- This card is the canonical reference. i245 / i246 / i250 /
  i252 / i253 each cite it. If anyone proposes a 7th rule
  keyword, the bar is "name a domain concept the existing six
  don't already cover." Most proposed additions collapse into
  one of the six on inspection.

- `rule` deliberately has the broadest plain-English meaning of
  the six. That's correct : a rule of the aggregate is the
  most common kind of domain rule. The narrower kinds (gates,
  contracts, identities, reactions) get the more specific
  keywords.

- Bluebook authors can grep for any of the six and find every
  instance of that kind of rule across the corpus.
  Discoverability is part of the design.
