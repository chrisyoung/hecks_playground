# i258 — runtime drops multi-attribute command values to `[0 items]`

When a command has many attributes and `then_set`s several of them
from same-name inputs, the runtime persists at least one attribute
as `[0 items]` (the list-empty render) instead of the input value.
The behavior is reproducible and consistent across four V1 commands.

## Failing tests (all on bluebook-foundation post-enrichment)

| Aggregate | Command | Test failure |
|---|---|---|
| ServiceAddress | AddAddress | `expected address_line_1: "1234 N Hayden Rd", got "[0 items]"` |
| BinInventory | SetInventory | `expected trash_bin_count: 1, got "[0 items]"` |
| Plan | RegisterPlan | `expected monthly_price: 4500, got "[0 items]"` |
| Subscription | Subscribe | `expected plan_code: "full_in_out", got "[0 items]"` |

Each agent independently verified by stashing their enrichment
changes and re-running against the unmodified bluebook — failure
reproduces identically on the un-enriched form. **Pre-existing,
not enrichment-introduced.**

## Pattern

What the failing commands share :

- Many attributes (5+) defined on the aggregate
- The command takes most or all of them as inputs
- Several attributes share a VO type (StreetLine × 2 in
  ServiceAddress ; BinCount × 2 in BinInventory ; etc.)
- The command body has many `then_set :foo, to: :foo` lines

What the passing commands share :

- Few attributes (≤3) on the command
- Each attribute is a unique VO type
- One or two `then_set` lines

Hypothesis : the runtime's `apply_mutations` (or the dispatch path
that resolves input attribute values) loses track when several
attributes resolve to the same VO type, possibly conflating
them or rendering one as a sentinel-empty value. The `[0 items]`
marker matches the runtime's list-empty render, suggesting the
attribute is being treated as a list type when the input was a
single value.

## Reproduction

```bash
cd ~/Projects/bin-buddy
~/Projects/hecks/rust/target/release/hecks-life behaviors \
  aggregates/subscription/subscription.behaviors
```

The `Subscribe` test reproduces in isolation. A minimal-case
reproduction would help :

- Two-VO aggregate where both VOs are `Email` (or any shared type)
- A command that takes both as inputs and `then_set`s both
- Test that both attributes hold the input value

If the minimal case reproduces the `[0 items]` symptom, the bug is
the multi-attribute → shared-VO-type code path in dispatch. If it
doesn't reproduce, something else is interacting (count, ordering,
cascade resolution).

## Implementation surface

— `rust/src/runtime/command_dispatch.rs` — `dispatch_inner` walks
  the command's attributes ; the `apply_mutations` step writes them
  to the aggregate state. Trace where `[0 items]` first appears.

— `rust/src/runtime/aggregate_state.rs` — Value enum's `List(Vec<Value>)`
  is what `[0 items]` renders as. If a String input is being wrapped
  to `List` somewhere, that's the bug.

— `rust/src/parse_blocks.rs` — `then_set` parsing should preserve
  the to-source as a same-name reference, not a list. Verify.

## Considerations

- This is the runtime gap that's blocking 4 of bin-buddy's
  behaviors from passing today. Fixing it gates V1 readiness.

- Tie to i245 (DSL ergonomics) : the `accepts :a, :b, :c` shorthand
  expands to per-attribute then_sets. If this bug is in the
  expansion path, the shorthand will inherit it.

- Tie to i250 (event identity) : event-identity dedup might also
  rely on attribute-resolution paths that hit this bug.

- Surface the fix as a behaviors test in the framework's test
  corpus so regression is caught.
