# i259 — `requires { ... }` silently strips command on multi-statement body

When a `rule` block's `requires { ... }` body contains multiple
Ruby statements (an if/else expression, a multi-line conditional,
etc.) instead of a single boolean expression, the parser silently
drops the surrounding command from the IR. Subsequent dispatches
fail with `unknown command: AggregateName.CommandName` even though
the bluebook clearly declares the command.

## Reproduction

The Plan agent (during the i255 enrichment pass) hit this :

```ruby
rule "included_movements aligns with direction" do
  requires {
    if direction == "in_out"
      included_movements % 2 == 0
    else
      included_movements > 0
    end
  }
end
```

Tests fail with `unknown command: Plan.RegisterPlan`, etc. — every
command on the aggregate is gone, not just the one tied to this
rule.

Rewriting the body as a single boolean expression restores
dispatch :

```ruby
rule "included_movements aligns with direction" do
  requires {
    (direction == "in_out" && included_movements % 2 == 0) ||
    (direction != "in_out" && included_movements > 0)
  }
end
```

## What's wrong

Two issues compound :

1. The parser tolerates the multi-statement body without erroring.
   Domain authors expect "if it parses, it's accepted." When the
   parser silently rejects, debugging is invisible.

2. The cascade : an unparseable `requires` block causes its rule
   to be silently dropped, which causes the surrounding `aggregate`
   to be silently truncated, which causes dispatches to its
   commands to fail with `unknown command`. The error surface lies
   far from the cause.

## What should happen

When a `requires { ... }` body can't be evaluated as a single
boolean expression, the parser should raise a structured error :

```
RuleBodyError
  aggregate     : Plan
  rule          : "included_movements aligns with direction"
  block_lines   : 23..30
  body_excerpt  : |
                  if direction == "in_out"
                    included_movements % 2 == 0
                  else
                    included_movements > 0
                  end
  message       : `requires { ... }` body must be a single boolean
                  expression. Multi-statement bodies aren't yet
                  supported. Combine with `&&` / `||` or split into
                  multiple `requires` blocks.
  hint          : Try : (direction == "in_out" && included_movements
                  % 2 == 0) || (direction != "in_out" &&
                  included_movements > 0)
```

The error should fire at parse time, surface to the bluebook
author with file + line, and never silently strip a command from
dispatch.

## Implementation surface

— `rust/src/parse_blocks.rs` — the `requires { ... }` block
  recognizer should validate the body is a single expression.
  Multi-statement bodies → structured error.

— `rust/src/parser.rs` — the top-level parser should propagate
  block-level errors with file + line context, not absorb them
  into a silently-empty IR.

— Optional V2 : multi-statement `requires` bodies could be supported
  (each statement is an AND-clause). For now, single-expression-only
  + clear error is the right floor.

## Considerations

- Tie to i246 (aggregate rules) : the framework agent implementing
  i246 should fold this fix in — it's the same code path.

- Tie to i247 (VO behaviors) : `knows "..." do ... end` blocks
  may have the same problem if their body is multi-statement.
  Audit at the same time.

- Tie to i252 (expects/guarantees) : `expects "..." do ... end`
  blocks must avoid the same pitfall — block bodies in any rule-
  family keyword should error consistently when multi-statement.

- The Plan agent's flag noted this should be a "louder error" —
  agreed. Silent stripping costs hours to debug ; an error message
  with file + line costs seconds.
