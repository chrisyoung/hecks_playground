# i260 — hecks-life as a Cloudflare Worker (WASM + D1 + wrangler)

Tonight's bin-buddy walking-skeleton works locally — `hecks-life serve .`
on port 3110 — but the production target is Cloudflare. Wrangler
deploys to Workers (WASM at the edge), not arbitrary Rust binaries
with `std::net` listeners and local filesystems. To make the skeleton
actually walk *where production lives*, three things change in the
runtime :

## 1. Cross-compile to WASM

  - Add `cdylib` crate-type and `wasm32-unknown-unknown` target.
  - Use the `workers-rs` crate's `#[event(fetch)]` macro for the
    Worker entry point.
  - Cargo feature flags split the binary build (`bin = "hecks-life"`
    against `std::net`) from the WASM build (`cdylib` against
    `worker::Request`/`Response`). One source tree, two targets.

## 2. Rewrite the HTTP layer

  - `read_request` (which today owns a `BufReader<TcpStream>`) becomes
    a thin wrapper around `worker::Request` — read method, path, body,
    cookies via `req.headers().get("cookie")`.
  - `write_response` (which today writes raw HTTP/1.1 bytes to a
    `TcpStream`) becomes `worker::Response::ok(body)` with header
    builders for Set-Cookie / Location.
  - The `route_multi` match table stays — it's the abstraction that
    survives the port. Only the I/O edges change.

## 3. Persistence : memory for dev, D1 for prod, R2 for blobs

  - **Memory** is the LOCAL DEV default. `.heki` is Miette-specific
    (her organs persist between sessions) — not the generic framework
    backend. Ordinary bluebook dev runs in-memory ; state evaporates
    between restarts. Cleaner ; matches "the runtime is a function
    of the bluebook" mental model.
  - **D1** (Cloudflare SQLite) for production aggregate state. SQL
    gives us rows, indices, `where` / `order_by` / `limit` semantics
    that already speak the IR's language. Schema generated from the
    bluebook IR — one `CREATE TABLE` per aggregate, columns per
    attribute. For walking-skeleton v1, regenerate from scratch on
    every deploy.
  - **R2** (Cloudflare's S3-compatible object store) for binary blobs
    declared by `adapter :object_store` in the hecksagon. bin-buddy's
    photo evidence (`Photo.Upload` → before/after JPEGs) lands here.
    The IR doesn't change — `backend :r2` is just a different binding
    in `wrangler.toml`. The Worker uses `env.PHOTOS.put(key, body)`
    and emits signed URLs for retrieval.
  - **KV** *maybe* for session tokens later — survives isolate
    restarts cleanly without a D1 round-trip per request.

## 4. Hecksagon mirrors the bluebook ; world is configuration only

Two separation rules that this card formalizes for every future repo :

  - **Adapters live in the hecksagon**, not the world file. Adapters
    say WHICH backend wires which command/event (`adapter :stripe`,
    `adapter :r2`, `adapter :persist`). The hecksagon mirrors the
    bluebook structurally — one hecksagon per bluebook, the same
    aggregate boundaries, with adapter declarations attached to the
    relevant aggregate. bin-buddy already does this for `Photo`,
    `Subscription`, `Notification`.
  - **The `.world` file is configuration only** — env vars, paths,
    secrets, feature flags. It doesn't declare adapters ; it provides
    the values adapters consume. Local-dev `.world` says
    `heki dir "information"` (Miette case) or nothing (memory case) ;
    prod `.world` says `D1_BINDING_NAME "DB"`. Same hecksagon, two
    different world configs.

This means the local-vs-prod story is one hecksagon edit (memory →
D1 / S3 → R2) and one world swap (env vars), not a structural rewrite.

## Why D1 specifically

  - Workers are stateless across requests ; persistence MUST be
    external. D1 is Cloudflare-native, has SQL, and is bound to the
    Worker via `env.DB` — no external network calls.
  - KV is great for caches, terrible for relational data with `where`
    clauses. R2 is for blobs. D1 is the right shape.
  - Queries already speak SQL semantics conceptually (`where(field:
    :param)`) — translating to actual SQL is mechanical.

## Scope

This is framework-level engineering, not bin-buddy-specific. Once it
lands, EVERY hecks bluebook can be `wrangler deploy`'d. Estimated 2-3
days of focused work :

  - Day 1 : split build, get a hello-world Worker compiling + deploying
  - Day 2 : port HTTP layer + auth path through workers-rs
  - Day 3 : repository abstraction + D1 schema generation + persistence
    smoke test on bin-buddy

## Until this lands

bin-buddy runs locally on port 3110 ; deployment is via Cloudflare
Quick Tunnel (`cloudflared tunnel --url http://localhost:3110`)
which gives a public `<random>.trycloudflare.com` URL. Acceptable
for the kickoff demo with Alan ; not acceptable for production.
