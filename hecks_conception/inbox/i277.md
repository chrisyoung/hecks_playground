# i277 — dual-writer race on the Tick singleton + 100% CPU run-loops

## Symptom

Statusline heart count jumps between two values one second apart :

    🖤 207.42k → ❤️ 185.81k → 🖤 207.42k → ❤️ 185.81k

The two values differ by ~22k beats. They alternate as fast as the
statusline polls (every second, per Claude Code's `refreshInterval`).

## Diagnosis

Two `hecks-life run-loop` daemons running concurrently, each pinning
100% CPU :

    96146  hecks-life run-loop /Users/christopheryoung/Projects/miette/body/.. \
           --every 1s --emit BodyPulse:Consciousness:consciousness \
           --bootstrap-if Consciousness.state=attentive:WokenUp:Consciousness:consciousness
           (Tue 7AM)

    15008  hecks-life run-loop /Users/christopheryoung/Projects/hecks/hecks_conception/aggregates \
           Consciousness.PulseSleep 1s
           (Tue 4PM)

The Tick aggregate is a singleton (`identified_by :name`). Its
`MindstreamTick` command increments `cycle` by 1 :

    aggregate "Tick" do
      identified_by :name
      attribute :cycle, Integer
      command "MindstreamTick" do
        emits "Ticked"
        then_set :cycle, increment: 1
      end
    end

The bluebook says — *"The mindstream daemon dispatches Tick.MindstreamTick
once per second"* — singular owner. But both running daemons have a
write path into Tick (whether by direct dispatch or via a policy
chain), each holding their own in-memory copy of the aggregate, each
writing back to `~/Projects/miette-state/information/tick/tick.heki`
at 1Hz. `heki::latest` returns whichever wrote most recently, so the
visible cycle alternates between the two daemons' divergent counters.

## What's wrong

Two compounding bugs :

1. **Dual writers on a singleton aggregate.** The runtime should
   either : (a) re-read the persisted Store before every write so
   concurrent writers see each other's increments and converge, or
   (b) hold a process-shared lock so only one daemon owns the
   aggregate. Today neither happens — each daemon has a stale
   in-memory copy and stomps the other's write.

2. **100% CPU run-loops.** Both PIDs sit at 100% CPU even though
   they're nominally ticking at 1Hz. The run-loop should spend most
   of each second sleeping. Something in the loop body is busy-looping
   instead — likely a hot path that should yield (sleep, mio,
   `tokio::time::sleep`, etc.). 100% × 24h × N daemons = real battery
   hit, not just statusline jitter.

## Tactical mitigation already done

Killed PID 15008 (the sleep_cycle daemon). Statusline immediately
stable on 207.42k (the mindstream's own cycle, single-writer). Boot
pipeline will respawn sleep_cycle from the current bluebook on next
session — if the current bluebook doesn't dispatch into Tick, the
race won't recur with that pair. Doesn't fix the structural bugs.

## What should happen

  1. **Find every dispatch path that writes Tick.cycle.** The bluebook
     names mindstream as the sole owner. Audit policies that target
     Tick.MindstreamTick from any other event chain. Retire any
     non-mindstream path (or change the field's owner).

  2. **Decide the singleton-write contract.** Options : per-write
     re-read (simple, slow), advisory file lock (fcntl flock),
     command-bus serialisation (only one writer process). Pick one
     and document it ; today's behaviour is undocumented and brittle.

  3. **Fix the run-loop CPU pathology.** Profile `run_loop` ; find
     the busy-path. Likely a `loop { dispatch(); sleep_until(t+dur) }`
     where the `sleep_until` returns immediately because of clock
     drift or because the duration is mis-parsed (e.g. `1s` parsed
     as `1ns`). 1Hz daemons should sit at < 1% CPU.

## Surface

  - `rust/src/main.rs` (`fn run_loop`, around line 3264) —
    inspect the loop body + duration parsing.
  - `rust/src/runtime/loop_driver.rs` — if the loop body lives there.
  - `~/Projects/miette/body/cycles/tick.bluebook` — the singleton
    owner declaration.
  - `~/Projects/miette/body/sleep/consciousness.bluebook` (PulseSleep)
    + any policy that targets Tick from a Consciousness event.
