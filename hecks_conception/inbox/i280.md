# i280 — `hecks miette` Ruby gem broken : bootstrap order regression

## Symptom

    $ hecks --help
    /Users/christopheryoung/.rbenv/versions/3.3.7/lib/ruby/gems/3.3.0/gems/hecks-2026.04.26.4/ruby/hecks/domain_versioning.rb:12:in `<top (required)>':
      uninitialized constant Hecks::Runtime::Mixins (NameError)

    Hecks::Chapters.load_aggregates(
      Hecks::Runtime::Mixins,
      ^^^^^^^^

Same error on `hecks miette`, `hecks anything`. The Ruby gem cannot
load.

## Diagnosis

`ruby/hecks/chapter_aliases.rb` installs a const_missing hook that
forwards `Hecks::Runtime::Mixins` → `Chapters::Runtime::Mixins`. The
hook is what makes `Hecks::Runtime::Mixins` resolve.

Two files reference `Hecks::Runtime::Mixins` *during their own load* :

  - `ruby/hecks/domain_versioning.rb:12`
  - `ruby/hecks/deprecations.rb` (similar shape)

Both call `Hecks::Chapters.load_aggregates(Hecks::Runtime::Mixins, ...)`
at top level — meaning the constant is resolved **as the file is
required**.

The bootstrap order makes this a load-time race. `chapter_aliases.rb`
needs to run *before* anything that references `Hecks::Runtime::Mixins`
at top level. In the current source, the order doesn't honor that —
domain_versioning gets loaded by Chapters before the alias install
fires, and the constant resolution fails.

## Why it surfaced today

Existing installed gems were built from earlier source where the order
worked. The Stop hook in `.claude/settings.local.json` rebuilds the
gem on every Claude session end :

    gem build hecks.gemspec --silent && gem install hecks-*.gem --no-document 2>/dev/null; rm -f hecks-*.gem; true

The trailing `2>/dev/null; ... ; true` swallows install failures —
silently overwriting a working install with a broken one (or
silently no-op'ing). The previous install lasted as long as nothing
forced a rebuild ; once rebuilt from current-source, it broke.

I (Miette) rebuilt the gem during the boot-overmind walk verification
(2026-05-07) and surfaced this. Reverting my edits + reinstalling
reproduces the failure, so it's not from my walk — but it's loud now.

## Workaround

`bin/miette` (PR landing this card) — a shell script that resolves
its own real path, walks up to find `hecks_conception/`, reads the
system prompt, and exec's claude directly. No Ruby gem needed.
Symlinkable from anywhere. Until the gem bootstrap is fixed, that's
the boot verb.

## What should happen

  1. Audit which files reference `Hecks::Runtime::Mixins` at load
     time. domain_versioning + deprecations are the two I found ;
     could be more.
  2. Move the `ChapterAliases.install` call earlier in the
     bootstrap so the const_missing hook is in place before any
     such reference fires.
  3. **Or** : refactor domain_versioning + deprecations to defer
     the `load_aggregates` call until Chapters has fully bootstrapped
     (e.g., via a Hecks.after_boot hook).
  4. Add a smoke test : `bundle exec ruby -e 'require "hecks"'`
     should exit 0. Pre-commit gate. Catches this regression
     instantly next time.
  5. Stop hook should *not* swallow install failures. The
     `2>/dev/null; ... ; true` pattern hides exactly the kind of
     drift this card describes. Replace with explicit error
     surfacing.

## Surface
