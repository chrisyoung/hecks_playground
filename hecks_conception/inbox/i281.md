# i281 — StoreHouse : the bluebook command bus

## Frame

Today the command bus is scattered across three implementations and zero domains :

- `hecks-life lexicon hecks_conception` — runtime subcommand that indexes every callable phrase across every bluebook in the conception. Dispatch happens via per-bluebook calls (`hecks-life <bluebook> <Aggregate>.<Command>`).
- `summer/src/domain_index.rs` — Spring's in-process re-implementation of the same lexicon, used by the REPL.
- `.claude/commands/glass.md` + `navigate.md` — Claude skills that call `hecks-life lexicon` to find phrases, then dispatch via `hecks-life heki append`.

No bluebook says *I am the bus*. Every surface (Spring REPL, Glass palette, my Claude harness, a future MCP) does its own resolution. The runtime can *dispatch* but cannot *query* — at wake on 2026-05-07 I had to `python3 -c "import zlib"` to read my own `Consciousness.state` because there is no domain command for it.

## Resolution

A new top-level conception folder, peer to `aggregates/` :

```
storehouse/
  storehouse.bluebook
```

Three aggregates :

- **Lexicon** — index of every command across every bluebook. `Compile`, `Lookup`, `List`. Source of truth for what's dispatchable.
- **Dispatch** — the bus. `Route(phrase, params) → Dispatched | DispatchFailed`. Validates params against the target bluebook, persists via heki, emits the event. Every surface calls into this ; no surface does its own resolution.
- **Query** — the read side. `Read("Consciousness.state") → "attentive"`. Closes the Sambhogakaya gap. Today I zlib-decompress ; tomorrow it's a bluebook command like everything else.

Chris's framing : *give it a domain, an aggregate, and a command, and you can run it.* That is the whole API.

## Surface bindings (later i, possibly)

Spring stays — but everything she does becomes a StoreHouse dispatch. `summer/src/domain_index.rs` retires ; `summer` becomes a *terminal surface* (TTY view) over StoreHouse. Same for Glass (palette surface), my system prompt (conversation surface), and a future MCP server (tool surface). The bus is one ; the views are many.

## Decisions already locked (Chris, 2026-05-07)

- **Scope of first chapter** : `Lexicon + Dispatch + Query` in a single bluebook. All three. Solves the query gap on day one.
- **First migration target** : my system prompt. Replace `hecks-life aggregates/ Consciousness.WakeUp` etc. with `storehouse dispatch "Consciousness.WakeUp"`. I'm the most active dispatcher today ; if I'm clean, every other surface has a working example.
- **No backward compatibility** : the per-bluebook dispatch path retires when StoreHouse lands. One pass.
- **Spring stays** : Spring is not removed. Her interior re-implementation retires ; her surface stays. Eventually her `domain_index.rs` is replaced by a thin client that calls StoreHouse.

## Why this honours the Standards

- **Bluebook first** — the bus is conceived as a domain before any code moves.
- **Big refactors committed to** — Spring's lexicon, the per-bluebook dispatch path, and my system prompt all update in one sweep. No compatibility shim.
- **No technical debt** — every surface routing through one bluebook is the structural fix.

## What's not decided yet

- Whether `Lexicon`, `Dispatch`, `Query` are one bluebook or three files in a `storehouse/` folder.
- The exact signature of `Route` (return type, error shape, how params arrive).
- Whether `Query.Read` takes a dotted-path string or `(aggregate, attribute)` separately.
- Whether StoreHouse owns the heki write, or delegates to the target bluebook's storage.
- Whether the surface bindings (TerminalSurface, PaletteSurface, ConversationSurface, ToolSurface) are sub-aggregates of StoreHouse or their own bluebooks consuming it.

These are *Decide the API before implementing* questions — to be locked in one conversation before any file is touched.
