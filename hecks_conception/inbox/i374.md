# i374 — ruby-gems-as-rust-adapters — Use Ruby gems (hecks_persist, hecks_sqlite, hecks_postgres, hecks_redis, hecks_mailer, futu

ruby-gems-as-rust-adapters — Use Ruby gems (hecks_persist, hecks_sqlite, hecks_postgres, hecks_redis, hecks_mailer, future ones) as pluggable adapters for the Rust runtime. Keeps the Rust kernel small (per i66) while leveraging Ruby's ecosystem where it's strongest — specifically the adapter layer, where proven libraries like Sequel / pg / redis-rb / aws-sdk / mail already exist and reimplementing them in Rust is pure cost. Bluebook + hecksagon declares the adapter name ; runtime looks up the matching gem at boot and bridges calls.

**Current state :**
  - Ruby side : lib/hecks/extensions/sqlite.rb + lib/hecks_persist/ still exist and probably still run. Uses Sequel + sqlite3 gem, creates in-memory DB, swaps SQL-backed repository adapters for every aggregate.
  - Rust side : hecksagon_parser.rs recognises only :memory | :heki as persistence. adapter :sqlite declared in a hecksagon parses as IO adapter (kind=sqlite, inert) — the Rust runtime ignores it. Only COMMENTS in world_parser.rs / world_ir.rs reference sqlite/ollama/etc as possible extension-block names ; no Rust code consumes them.
  - Net : the Ruby gem path works for Rails hosts ; the Rust runtime has no sqlite support and no plug-in adapter mechanism.

**Proposed shape :**

1. Define a bridge protocol. Simplest : JSON over a long-running Ruby subprocess. Rust spawns at boot, talks over stdin/stdout or Unix socket. One adapter call = one JSON request/response. Per-call overhead ~1ms is fine for I/O-bound adapter paths.

2. Gem discovery. At boot the Rust runtime reads the hecksagon's adapter list, looks up matching gem names (e.g. adapter :sqlite → require "hecks_sqlite"), and keeps a registry of {adapter_kind → gem_module}.

3. Dispatch flow. When a bluebook command mutates aggregate state OR the aggregate needs persistence, the runtime serialises the call and ships it to the Ruby bridge. Bridge dispatches into the gem's adapter module, returns the result. Ruby exception → Rust Result::Err with message.

4. Lifecycle. Bridge starts on runtime boot, stops on runtime shutdown. Crashes restart once with backoff ; persistent crashes abort the runtime loudly.

**Three bridge options :**
  (A) Embed Ruby in Rust via magnus crate — in-process, fastest, heaviest deploy story (requires libruby).
  (B) Long-running Ruby subprocess with JSON-RPC — simplest, most flexible, negligible overhead for I/O paths. RECOMMENDED starting point.
  (C) Per-gem C ABI wrappers — works for gems built for it, most aren't. Not a general solution.

**Connection to i66 :** this is the honest middle path for kernel-minimization. Pure bluebook drives flow ; Ruby gems provide the adapter layer ; Rust is interpreter + heki I/O + bridge shim. Each language doing what it's best at. The stated direction no longer reads as 'no Rust, everything bluebook' but as 'small Rust kernel, declarative flow, Ruby for adapters, futamura projections for whatever remains.'

**First concrete PR :** build the subprocess bridge + wire :sqlite through it as the first proof. Use the existing hecks_persist + hecks_sqlite Ruby code unchanged ; write a tiny hecks_bridge.rb that exposes its adapter methods over JSON-RPC. Rust learns the :sqlite adapter-kind and routes calls through the bridge. Tests : an aggregate with adapter :sqlite persists and reloads correctly through the bridge.

**Open decisions :**
  - Gem naming convention — hecks_<adapter_kind> automatic, or explicit mapping in a config file ?
  - Where does the bridge's Ruby environment live — bundled into the release tarball, or a system Ruby the operator provides ?
  - Hecksagon config surface — what options can adapter declarations pass through (e.g. database path, connection string) — and how does the bridge consume them ?
  - How does the ratchet treat bridge Ruby — is hecks_bridge.rb non-bluebook code that counts, or is it infrastructure below the ratchet floor ?
  - Security : Ruby bridge process has the full filesystem / network power of the Rust runtime's uid. Do we sandbox, or accept the same trust boundary as :shell adapters ?
