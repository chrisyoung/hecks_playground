# i390 — runtime-daemon-spawn-primitive — boot_miette.sh keeps daemons in shell because the runtime cannot yet spawn long-running

runtime-daemon-spawn-primitive — boot_miette.sh keeps daemons in shell because the runtime cannot yet spawn long-running processes from a bluebook surface. Six daemons launch via `( cd "$DIR" && nohup ./script.sh > /dev/null 2>&1 & )` — a wrapping subshell pattern that on macOS leaks the wrapper as a PPID=1 orphan. Tonight five such orphans accumulated over a 12-hour session before being noticed. The transitional fix landing tonight (boot_miette.sh phase 0 — reap orphan boot_miette.sh shells with PPID=1 at boot start) is defense in depth ; the structural fix is i90 : boot_miette becomes a bluebook + a Rust runner that walks it. For the runner to retire the shell, the runtime needs a primitive that bluebook can dispatch to spawn a daemon : `adapter :daemon, command: "./mindstream.sh", pidfile: "information/.mindstream.pid", restart: :if_dead` (or similar). Capability declares the daemon ; runner spawns + writes pidfile + checks liveness. heart already uses the cadence-loop primitive (i76) which is one shape of this — the new primitive is the more general "keep this script alive" form. With it, all six daemons (mindstream, breath, circadian, ultradian, sleep_cycle, plus heart) declare via bluebook and the runner manages their lifecycle ; no wrapping subshells, no orphaning, daemon health derives from the bluebook declaration not from PID files written by shell. Once this lands, the launcher-pattern rewrite I almost shipped tonight (replacing `(cd ... && nohup ... &)` with cleaner shell) becomes irrelevant — the shell goes away. Sibling of i90 (boot-miette-as-bluebook) and i94 (daemon-health-checks-as-bluebook). Filed 2026-04-26 after Chris caught me reaching for shell to fix a shell bug instead of naming the runtime gap.
