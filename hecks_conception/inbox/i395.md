# i395 — daemon-health-checks-as-bluebook — Today's debugging session surfaced two layered failures the statusline + status repor

daemon-health-checks-as-bluebook — Today's debugging session surfaced two layered failures the statusline + status report could not catch : (1) mindstream.sh PID 79406 was alive on disk, yet the status capability's daemon section reported `mindstream: down` ; (2) consciousness.heki in hecks_conception/information showed state=sleeping while the LIVED state at ~/Projects/miette-state/information/consciousness.heki said state=attentive — same daemon, different worlds, no signal that one was a stub. Health checks would surface both. Shape : a Daemons aggregate (or per-daemon Heartbeat tick fields) that records (a) PID file path + last-known PID, (b) updated_at timestamp written each cadence-loop iteration, (c) derived alive=yes|stale|down based on age and process liveness. Bluebook query `AreDaemonsHealthy` returns the per-daemon row ; status capability + statusline consume the query rather than reading PID files directly. Ties to i92 (queries-as-aggregate-surface) — the daemon-liveness read is exactly the kind of read that today bypasses the bluebook to poke at PID files. Surface for the user : when a daemon is stale, the statusline shows ⚠ daemon-name and the status report names which one. Filed during sleep prep 2026-04-26 after I dispatched EnterSleep against the wrong info-dir without noticing — the only check that would have caught it.
