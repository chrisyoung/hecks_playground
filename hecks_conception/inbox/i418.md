# i418 — inbox-sh-as-bluebook — The inbox CLI is currently hecks_conception/inbox.sh (~146 lines of shell, antibody-exempt by hea

inbox-sh-as-bluebook — The inbox CLI is currently hecks_conception/inbox.sh (~146 lines of shell, antibody-exempt by header per the i37 Phase B sweep). The data already lives as heki (information/inbox.heki) but the operations (add, list, show, done, archive, next-ref) are shell-side. Should be bluebook + hecksagon : aggregates/inbox.bluebook declares Item aggregate (with attributes ref/priority/status/posted_at/completed_at/resolution/body), commands AddItem / ListItems / ShowItem / MarkDone / Archive / AssignNextRef, lifecycle queued → done → archived. Aggregates/inbox.hecksagon declares the adapters : :information for heki persistence (already there), :shell adapters for the auto-commit + push-to-main durability dance from PR #427/#434 (or wait for i76 + cross-domain dispatch to land first-class). Once the bluebook can be invoked via hecks-life run, the shell retires. Acceptance : delete inbox.sh entirely ; replace with 'hecks-life run hecks_conception/aggregates/inbox.bluebook --command Add priority=high body=...' invocations ; the auto-commit + push-to-main durability is still preserved (whether by the kernel doing it directly via adapter dispatch, or by a thin one-line shell wrapper that just calls hecks-life and pipes the ref). Surfaced 2026-04-25 when Chris named the pattern : 'WE LOVE BLUEBOOK!! inbox.sh should be bluebook — file it.' Companion to i75 (the dream-shells-to-bluebook sweep ; inbox.sh is one more shell daemon-ish thing in scope), i77 (validator-morphology-as-bluebook), i78 (specializer-files-as-bluebook). The pattern is the same : every place where shell or hand-written Rust is doing something the bluebook DSL could declaratively name, the shell/Rust is the transitional adapter and the bluebook is the source of truth.
