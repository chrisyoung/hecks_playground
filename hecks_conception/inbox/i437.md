# i437 — queries-as-aggregate-surface — The bluebook DSL already has `query` as a first-class concept. Aggregates can declare que

queries-as-aggregate-surface — The bluebook DSL already has `query` as a first-class concept. Aggregates can declare queries today, alongside `command`, `attribute`, `lifecycle`, etc. The keyword exists, the parser knows it, the runtime resolves it — you can see this in `dispatch_hecksagon` in main.rs (the is_query branch that calls `rt.resolve_query`). What this names : use that existing surface to express the read-shapes that today live as `hecks-life heki <verb>` CLI calls. The DSL doesn't grow ; the USAGE of the DSL grows to cover reads that currently bypass it. Same grammar, same keyword, same runtime path. Just stop reaching past the aggregate to talk to the storage layer directly, and start declaring the reads as `query` blocks on the aggregates that own the data. The heki CLI verbs stay where they are — still useful for kernel-level work, debugging, and the bluebook-internal implementation of those queries. They just stop being the interface domain code reaches for ; that gets routed through aggregate queries instead. Sibling of i80 (cli-routing-as-bluebook) and i70 (bluebook-as-executable-endpoint) — same direction : every read and write through the aggregate, no bypass.
