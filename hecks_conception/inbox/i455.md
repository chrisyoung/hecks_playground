# i455 — runtime-cadence-loop-primitive — Heart.sh and the other body daemons (mindstream, breath, circadian, ultradian, sleep_cy

runtime-cadence-loop-primitive — Heart.sh and the other body daemons (mindstream, breath, circadian, ultradian, sleep_cycle) all have the same shape : a shell while-true-sleep-N-dispatch-command loop. The bluebooks for the cadence-driven aggregates exist (heart.bluebook, etc.), and the shell exists only because hecks-life has no primitive for 'loop this command at this cadence.' Surfaced sharply 2026-04-25 when wiring interoception : adding 5 lines of shell to heart.sh to dispatch DaemonRhythm.RecordTick was the wrong move — bluebook is the runtime, shell is transitional, and the ONLY reason the transition hasn't happened is this missing runtime feature. Two candidate shapes : (a) a CLI subcommand 'hecks-life loop <bluebook> --command <Cmd> --every <duration>' that runs the dispatch loop in the Rust runtime instead of shell ; (b) a hecksagon adapter directive 'adapter :timer, name: <id>, every: "1s", dispatch: "Aggregate.Command"' that the runtime interprets at boot to spawn the cadence thread. Option (b) is more declarative ; option (a) is simpler to ship. Most likely : ship (a) first as a minimum-viable runtime feature, then later refactor to (b) when timer-as-adapter feels right. Acceptance : delete heart.sh entirely, replace with 'hecks-life loop hecks_conception/aggregates/heart.bluebook --command Beat --every 1s &' in boot_miette.sh ; verify Heart.beat_count advances at the same cadence as before ; verify no new shell line was added anywhere. Companion : once this lands, the i75 dream-shells-to-bluebook sweep accelerates — every daemon's loop driver becomes a hecks-life loop invocation, and the actual logic moves into bluebook policies. Cross-references : i75 (the parent sweep), PR #442 (interoception, the first concrete consumer waiting on this), heart.hecksagon (the declarative target for option b).
