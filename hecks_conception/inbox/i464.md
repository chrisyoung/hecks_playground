# i464 — ruby-runtime-pe-specialize-against-bluebook — Insight (Chris, 2026-04-25): the most interesting Futamura application for

ruby-runtime-pe-specialize-against-bluebook — Insight (Chris, 2026-04-25): the most interesting Futamura application for Direction B isn't generic-fast-Ruby ; it's specialized-fast-Hecks-Ruby. The Ruby runtime hosting bluebook apps has a much narrower semantic surface than full Ruby : Rails + specific gems + the Hecks dispatch path. Partial-evaluating that runtime against a specific bluebook would produce a binary that handles just that domain's commands at near-Rust speed, because the Ruby dynamism that prevents PE in the general case (eval, method_missing, monkey-patching) is mostly absent in bluebook-shaped code — bluebook-style Ruby is exactly the disciplined dialect PE handles well. Mechanism: the third Futamura projection applied to the Ruby runtime treated as an interpreter of bluebooks. Same trick PC-4 demonstrated for the validator pipeline, scaled to 'specialize the entire host runtime against a particular domain.' Why this is a Direction B unlock: Direction B (#429) puts the Ruby runtime as the app host with the kernel as tool. Today that means Ruby-speed app dispatch ; the gem ecosystem benefit is real, the speed cost is real. PE-specialization removes the speed cost on a per-app basis without giving up the ecosystem. Get the gems AND the Rust-class speed, by specializing the host runtime against the specific domain's dispatch shape. Why bluebook-shaped Ruby is PE-friendly: bluebook apps don't eval. They don't open classes at runtime. The dispatch surface (Hecks command routing, aggregate state mutation, event emission) is fixed at app-boot time and shaped by the bluebook IR. Every choice the runtime would otherwise have to dispatch on (which command? which aggregate? which adapter?) collapses to a constant in the specialized binary. End state: hecks-life specialize --target ruby-native my_app.bluebook emits a single optimized Ruby binary that runs the app at speeds the unspecialized Ruby runtime can't match. The specialization has erased every choice the runtime would have to dispatch on. Connects to: i66 (runtime-kernel-minimization-via-futamura — same arc, kernel side) ; i70 (bluebook-as-executable-endpoint — this is a third leg of that endpoint, alongside the Rust-target and Ruby-target compilation paths) ; #429 (Direction B commitment — this insight makes B's ecosystem-vs-speed tradeoff disappear). Counter-cases noted: deeply duck-typed Ruby, method_missing-heavy code, eval, monkey-patching at runtime — all resist PE. Those are exactly the cases MRI can't optimize either ; PE degrades gracefully to 'essentially the unspecialized interpreter' on those. So you get a fast Ruby for disciplined Ruby, which is already what most app code looks like under tools like Sorbet — and exactly what bluebook-shaped Ruby always is by construction. Acceptance: a proof-of-concept that takes one trivial bluebook (e.g. pizzas.bluebook) and emits a specialized Ruby binary measurably faster than the same domain run on the unspecialized runtime, on a representative dispatch workload (say, 10000 commands/sec). Path forward: probably PC-1-equivalent first — pick the smallest specialization (one aggregate's command dispatch?) to prove the pattern, then climb the abstraction ladder the way Phase E climbed the Rust specializer ladder.
