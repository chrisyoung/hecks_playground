# i467 — dashboard-section-composition-as-bluebook — Today I learned (the hard way) that every dashboard tweak — adding a section

dashboard-section-composition-as-bluebook — Today I learned (the hard way) that every dashboard tweak — adding a section, removing a row, surfacing a new aggregate's data — requires editing hecks_life/src/run_status/render.rs and assemble.rs. That's imperative Rust at the dashboard surface : the bluebook (capabilities/status/status.bluebook) declares ATTRIBUTES on the StatusReport aggregate, but the SECTIONING + ROW COMPOSITION + ORDERING all live in Rust. Result : Chris asks 'remove pronouns', I edit render.rs, the enforcer complains (correctly — it's Rust), I either exempt or revert. Both feel wrong. The structural fix : status.bluebook declares its sections AS DATA (a list of sections, each with title + a list of (label, field) rows). The runner walks the declaration, looks up each field on the StatusReport state, and renders. Adding/removing rows becomes a bluebook edit. Same direction as i91 (dashboard-as-bluebook) but more specific : the section/row composition table itself is bluebook. Sibling of i101 (query-as-first-class-IR) — both are about replacing Rust composition surfaces with declared-IR composition. Filed 2026-04-26 after the enforcer caught me in a loop : Chris asked for 'add enforcer to daemons', I started writing run_enforce_watch in Rust, the enforcer complained, I reverted. The deeper gap is that the ONLY path to add a daemon row today IS Rust ; until this lands, the enforcer cost is a real friction every dashboard change pays.
