# i479 — Lifecycle validator doesn't recognise i255 bare-VO attribute form for then_set references

Surfaced 2026-05-07 while landing storehouse/lexicon.bluebook
(commit 4e5f9a99). The lifecycle validator inside `hecks-life
check-lifecycle` (which the conception's pre-commit invokes)
treats the i255 bin-buddy bare-VO form as an unrecognised
attribute when it appears in `then_set` :

```
attribute Role, as: :role
...
then_set :role, to: :role
```

Validator says : *"then_set :role references :role but the command
has neither an attribute nor a reference named 'role' — the field
will stay null at runtime."* Same failure on
`bin-buddy/aggregates/account/account.bluebook` (3 errors there
when checked) — bin-buddy's pre-commit doesn't run this gate, so
its bluebooks ship despite the validator.

Worked around in storehouse/lexicon.bluebook by making the Lexicon
singleton stateless — the singleton carries no mutable state ;
LexiconCompiled events carry the timestamp + count instead. Clean
result, but the workaround is forced, not principled.

## Resolution

The validator should recognise `attribute VO, as: :alias` declarations
as creating the `:alias` name in the command's attribute scope. The
existing primitive form `attribute :alias, Type` already works ; the
bare-VO form needs the same treatment in the validator's attribute-
scope lookup.

Touch points :

  - `rust/src/check_lifecycle.rs` (or wherever the lifecycle validator
    lives) — when scanning a command's attributes for `then_set` target
    resolution, accept both primitive and bare-VO forms.
  - Verify `bin-buddy/aggregates/account/account.bluebook` and
    `bin-buddy/aggregates/notifications/notifications.bluebook` pass
    `hecks-life check-lifecycle` once the validator is updated.
  - Re-examine storehouse/lexicon.bluebook — could optionally restore
    state attributes (compiled_at, phrase_count) if it reads better
    with state on the singleton, once the validator catches up.

## Why this matters

The i255 rule vocabulary is the canonical bin-buddy style and the
direction of travel for the framework. As bluebooks under
hecks_conception/ adopt this style (StoreHouse just did), every one
of them will hit this validator wall. Fixing the validator unblocks
the migration ; leaving it forces every author to either bypass the
hook (which is forbidden) or shape the bluebook around the gap
(losing expressiveness).

Companion to i478 (StoreHouse first chapter, where this surfaced)
and the broader i255 wiring caveats already noted there.
