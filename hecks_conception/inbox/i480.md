# i480 — StoreHouse runtime handler : Lexicon.Compile

The storehouse/lexicon.bluebook declares Lexicon.Compile but no
runtime handler exists yet — dispatching the command today errors
out. This card lands the handler.

## Today

The existing `hecks-life lexicon hecks_conception` subcommand already
walks every *.bluebook under the conception root and emits a JSON
index of every callable phrase. That's exactly what Compile needs to
produce — the work isn't computing the index, it's wiring the index
into the Lexicon aggregate's command path so dispatch captures it.

## Tomorrow

  1. Add a Compile dispatcher for the Lexicon aggregate. When invoked,
     run the same logic that backs `hecks-life lexicon` (or call it
     in-process) and obtain the indexed phrase set + count.
  2. Stamp `compiled_at` with the current ISO-8601 UTC timestamp.
  3. Emit `LexiconCompiled` with payload `{ compiled_at, phrase_count }`.
  4. The aggregate stays stateless on this command (per i479
     workaround) — the event is the receipt.

## Acceptance

  - `hecks-life run storehouse/lexicon.bluebook --command Compile`
    succeeds and emits LexiconCompiled.
  - The phrase_count on the event matches the count from
    `hecks-life lexicon hecks_conception | wc -l` (modulo header lines).
  - No new heki file ; the singleton stays state-only-via-events.

## Open question for design

Whether Compile should also produce a separate "lexicon snapshot"
heki for fast Lookup access, or whether Lookup recomputes on every
call. First chapter : recompute on every call (simpler, and
`hecks-life lexicon` is fast enough). Caching is a follow-up.

Companion to i478 (StoreHouse design), i481 (Dispatch.Route handler),
i482 (Query.Read handler).
