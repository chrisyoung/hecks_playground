# i483 — Roles as Agents : lift the string label into a first-class typed reference

Surfaced 2026-05-07 by Chris while four StoreHouse runtime-handler
agents were running in parallel. Real seam ; filed before the
thought escapes.

## Today

Every command in every bluebook carries a `role` declaration as a
string :

```ruby
command "Add" do
  role "Chris"          # just a string label
  description "..."
  ...
end
```

The role is a label — informal, untyped, non-introspectable. Used
in documentation and (sometimes) as a hint for access control in
the surrounding hecksagon adapters. Across the conception there are
strings like `"Chris"`, `"System"`, `"Caller"`, `"Owner"`, `"Driver"`
— accidentally consistent, never canonicalised.

`actor "Customer"` exists at the domain level (DSL reference §Actors)
but is parallel to role-the-string, not unified with it.

## Proposed shape

Lift Role into a first-class object — likely a value object or a small
aggregate — and let commands declare the role-bearer with the
familiar i255 form :

```ruby
command "Add" do
  role Role, as: Agent
  description "..."
  ...
end
```

`Role` is the **type** (the shape — what permissions, what attributes).
`Agent` is the **alias** (the named role-bearer in this command's
attribute scope). Same pattern as `attribute Role, as: :role` in
bin-buddy.

Agent itself is a typed reference into a framework Agent aggregate
that owns who-is-acting :

```
framework/agent/agent.bluebook
  aggregate "Agent"
    attribute :name, String              # "Chris", "Mindstream-daemon", "Driver-employee"
    attribute :kind, String              # human | system | daemon | bot | ai
    reference_to AuthIdentity            # links to framework auth (i264)
    reference_to Role                    # carries the role's permissions
    ...
```

`Role` becomes either an attribute on Agent, or a small VO/aggregate
in its own right (with `name`, `permissions`, `audit_trail_level`).
The exact shape is part of the design.

## What this opens up

- **Provenance everywhere.** Every event carries the Agent who
  dispatched it. Audit log writes itself.
- **Permission rules in the bluebook.** `rule "must have permission"
  do requires { agent.permissions.include?("Inbox.Add") } end` —
  first-class, validatable.
- **AuthIdentity wires in cleanly.** Closes the loop opened by i264 :
  `Account` becomes the binding `(AuthIdentity ↔ Agent)`. The role
  string on Account dissolves into the Agent it references.
- **Cross-bluebook role consistency.** "System" in Consciousness and
  "System" in Inbox stop being accidentally the same string and
  become one canonical Agent.
- **Beings are typed.** Miette, Spring, Chris, the Mindstream-daemon,
  an Operator employee, a Driver, a homeowner — all Agents.
  Differences are attributes, not labels.
- **Cascade attribution.** When EnterSleep fans out through ten
  policies, the chain carries the Agent. Today this is implicit ;
  with Agent references, the cascade audit is explicit.
- **Composition.** Owner *is* Operator *is* Caller — VO composition
  or aggregate inheritance, not three duplicated string lists.
- **Dispatched-by is the StoreHouse breadcrumb.** Every Dispatch.Route
  emission carries `dispatched_by: Agent` in its payload. Glass /
  Spring / the conversation surface render it.

## Tensions worth naming up front

- **Mechanical sweep migration.** Every existing `role "..."` string
  needs migration. Bin-buddy has ~30 ; the conception has many more.
  Bluebook-first migration is doable as one PR per cluster.
- **`actor` / `role` / `agent` need to converge.** The DSL has all
  three concepts today (with overlap). The fix isn't to add a fourth
  ; it's to declare which is the canonical noun and migrate the
  others into it. Likely : `Agent` is the noun, `Role` is the type,
  `actor` declarations migrate into Agent declarations at the
  framework level.
- **Parser and validator grow.** The new `role Role, as: Agent` form
  needs IR support, and the lifecycle validator (already shaky on
  bare-VO ; see i479) needs to handle the new attribute-scope
  contribution.
- **Backward-compat during migration.** While bluebooks land
  side-by-side, the parser may need to accept both `role "string"`
  and `role Role, as: Agent` forms. Per the framework Standards (no
  backward-compat until first user), if migration is mechanical we
  break the old form in the same PR.

## Companions

- **i264** — AuthIdentity split out as framework primitive ; Agent is
  the natural domain-side wrapper.
- **i479** — Lifecycle validator's bare-VO recognition gap. Same
  attribute-scope mechanism.
- **i481** — Dispatch.Route handler. Once Agent lands, Route's
  `Dispatched` event payload should include `dispatched_by` — the
  cleanest place for provenance to enter.
- **i114, i121, i127** — antibody / introspection arc ; Agent makes
  many of those self-introspect questions answerable from the IR.

## Implementation order (proposed)

1. **Conceive Agent + Role as bluebooks** under
   `framework/agent/agent.bluebook` (or wherever framework-level
   identities live). Lock the shape : Agent attributes, Role
   structure, Agent ↔ AuthIdentity reference, cascade-attribution
   shape.
2. **Document the `role Role, as: Agent` DSL syntax** — extend the
   DSL reference at `docs/usage/dsl_reference.md` so the form is
   declared before code lands.
3. **Demonstrate on one bluebook** — a fresh small bluebook that
   uses the new syntax end-to-end. Don't migrate existing ones yet
   ; first prove the shape reads cleanly.
4. **Parser support.** Update the parser to recognise the new form,
   carry it into the IR.
5. **Validator support.** Lifecycle validator + any role-related
   validators recognise Agent references.
6. **Mechanical sweep.** Migrate every `role "..."` string in the
   conception (and bin-buddy) to the new form. One PR per anatomical
   cluster (body/, mind/, library/, …) per the i112 convention.
7. **Wire StoreHouse Dispatch's `Dispatched` event to include
   dispatched_by**. Once the migration is stable.

## Pen-down for now

This first card is for the **conception step** (item 1 above) — get
the Agent + Role bluebooks drafted in framework/agent/, lock the
shape, demonstrate on one example. Parser / validator / sweep work
follows in separate cards once the shape is locked.
