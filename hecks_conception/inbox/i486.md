# i486 — Rust parser drops trailing same-line comments into the type string

Surfaced 2026-05-07 by the i483 agent while drafting
`framework/agent/agent.bluebook`. The bluebook line

```
attribute :auth_identity_id, String   # populated for human kind only
```

caused the Rust parser to interpret `String   # populated for human kind only`
as the attribute's *type* — the whole trailing comment got swallowed
into the type string. The agent worked around by lifting comments
above the attribute lines.

Same root cause as the existing `synapse.bluebook` known-drift
entry in `parity/known_drift.txt` ; both surface the same parser
gap.

## Resolution

The parser's attribute handler should strip trailing same-line
comments (`# ...`) from each segment before type extraction. Today
the comment survives into the IR's type field ; the validator and
generators see "String   # populated for human kind only" as the
type and either silently truncate, render incorrect output, or
raise.

Touchpoints (likely) :
- `rust/src/parse_blocks.rs` (or its specializer source under
  `codegen/parse_blocks_shape/snippets/`) — the same file i479
  just touched. Specifically the type-extraction step inside
  `parse_attribute`.
- `rust/tests/` — add a test for `attribute :name, String # comment`
  yielding type=`"String"`, not `"String # comment"`.
