# i494 — Meta-bluebook DSL gaps : Rule, ProcessManager, command guards, query body, aggregate-level invariants

Surfaced by the bin-buddy keyword audit (session 2026-05-08, parent task : "make sure we support all the keywords in bin-buddy"). The DSL is structurally richer than its self-describing meta — `aggregates/language/grammar/bluebook.bluebook` declares 12 entities, but bin-buddy alone uses ~23 keyword surfaces. Coverage today is ~57%.

## The drift

The meta-bluebook DECLARES what every parser must produce as IR. When the DSL grows a feature without its meta entry, both parsers (Ruby in `lib/hecks/dsl/`, Rust in `rust/src/parser.rs`) end up handling syntax that has no IR shape — the runtime walks past the block, drops the structure, and the bluebook's promise of "self-describing" silently fails.

The Rust parser at `rust/src/parser.rs:351–360` admits this for `rule` :

> *"i259 — `rule "..." do ... end` blocks delegate to consume_rule_block ... **Rules aren't first-class IR yet — i246 lifts them** — so the consumer just walks past the block."*

i246 is the existing card for the Rule lift. This card folds the rest of the surveyed gaps under a single canonical-DSL goal. **i493** lands `pre` + `effects` as new DSL clauses ; both i493 and i494 are evolution-of-the-DSL siblings. Anything i493 adds also needs its meta entry.

## Gaps to close in `aggregates/language/grammar/bluebook.bluebook`

### 1. Rule + rule body (i246 — existing card, restated for completeness)

```ruby
rule "name" do
  requires "..."     # precondition expression(s)
  expects  "..."     # invariant assertions
  guarantees "..."   # postconditions
end
```

Used at aggregate level AND inside command bodies in bin-buddy. Most-used missing piece. New entities :
- `Rule { name, level (:aggregate|:command), description }`
- `Requires { rule_ref, expression, message }`
- `Expects   { rule_ref, expression, message }`
- `Guarantees{ rule_ref, expression, message }`

### 2. ProcessManager + body

```ruby
process_manager "ServiceTaskCompletion" do
  state :status
  correlates_by :service_task_id
  starts_on  "ServiceTask.Start"
  ends_on    "ServiceTask.Complete"
end
```

Used at top-level in bin-buddy. NO entity at all in meta. Likely a runtime gap entirely (does the current parser even produce IR for `process_manager` blocks?). New entities :
- `ProcessManager { name, description, state_field }`
- `Correlation   { pm_ref, by_field }`
- Lifecycle hooks on PM : `starts_on` / `ends_on` (events, not commands)

### 3. Command guards : when / when_any / when_present / dispatch

```ruby
command "Foo" do
  when      :elapsed > 30
  when_any  [:weather_hazard, :already_serviced]
  when_present :note
  dispatch  "Bar.Trigger"
end
```

Used in bin-buddy command bodies as guard / cascade clauses. No entity in meta ; `Given` is the closest cousin but doesn't cover the conjunction forms (`when_any`) or the dispatch verb. Probable shape :
- Extend `Given` with a `kind: :when | :when_any | :when_present` field
- Add `Dispatch { command_ref, target_command }` as a structured cascade alongside `emits`

(Note : i493's `effects` clause covers some of this surface — Dispatch.Route as effect. Coordinate.)

### 4. Query body : where / order_by / limit

```ruby
query "ByCustomer" do
  attribute :customer_id, String
  where     :customer_id => :customer_id
  order_by  :created_at, :desc
  limit     50
end
```

i258 fixed the parser's continuation-line handling for `where` / `order_by` / `limit` clauses, but the `Query` entity in meta still has only `name + description`. The structured body has no IR. New entities :
- `Where     { query_ref, field, op, value }`
- `OrderBy   { query_ref, field, direction }`
- `Limit     { query_ref, count }`

### 5. Aggregate-level invariants / specifications / validations / scopes / ports

From `docs/usage/dsl_reference.md` examples (not in bin-buddy, but in active DSL elsewhere) :

```ruby
invariant "amount must be positive" do
  amount > 0
end

specification "Premium" do |pizza|
  pizza.price > 20
end

validation :name, presence: true
scope :affordable, price: 15.0

port :admin do
  allow :find, :all, :create_pizza
end
```

None have meta entries. Probable shapes :
- `Invariant     { aggregate_ref, name, expression, message }`
- `Specification { aggregate_ref, name, predicate_expression }`
- `Validation    { aggregate_ref, attribute_ref, kind, options }`
- `Scope         { aggregate_ref, name, predicate }`
- `Port          { aggregate_ref, name, allowed_commands }`

## Suggested execution order

1. **Lift Rule (i246)** — most-referenced gap, blocks several other inbox cards (i247, i248, i249, i252, i253, i259).
2. **ProcessManager** — bin-buddy's biggest unique need ; verify whether the parser even produces IR for it today, then close.
3. **Query body** — small, mechanical, builds on i258's parser work.
4. **Command guards (`when` family + `dispatch`)** — extends `Given` ; touches both parsers ; coordinate with i493's `pre`/`effects` semantics.
5. **Aggregate-level invariant / specification / validation / scope / port** — the largest cluster ; dsl_reference uses them but bin-buddy doesn't, so could be deferred.

## Why this matters now

Embryonaut's first commercial domains (bin-buddy) are being modelled in the DSL. New dev adoption means the DSL surface gets read by people who don't know which keywords are first-class and which are parsed-and-discarded. Closing this drift makes the meta-bluebook a usable spec ; it also lets the system_prompt's grammar appendix (the bluebook-DSL-in-system-prompt work happening alongside this card) carry the *full* DSL when devs read it.
