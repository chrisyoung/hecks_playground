# i501 — Parity suite retirement to bluebook (i499 Phase C)

## Position up front

**Most of the parity suite should NOT retire to behaviors-as-DSL.** The parity contract is structurally hostile to behaviors :

- It is meta-tooling that exercises the parser kernel, not domain behavior.
- Forcing it through `.behaviors` would either reduce to a thin shim that calls back into Ruby/Rust runners (cargo-cult retirement), or require teaching the behaviors runner to invoke a sibling parser and diff JSON — a feature with exactly one consumer that creates a circular dependency (the runner that proves parity uses the parser whose parity it proves).

**What should happen instead** : retire the **Ruby driver shells** (`*_test.rb`) and migrate the **contract declaration** (what fixtures, what known drift) into a parity bluebook that a dedicated `hecks-life parity` subcommand reads. The diff-and-execute logic stays in Rust. This lets the contract surface in bluebook (so it participates in the rest of the kernel surface) without pretending dual-target dispatch is domain behavior.

## The parity contract as a bluebook

A single `parity/parity_suite.bluebook` :

```ruby
Hecks.aggregate "ParitySuite" do
  command "RunSuite" do                 # surface only ; runner dispatches
    given :flavor                       # :domain | :hecksagon | :world | :fixtures | :behaviors
    given :scope                        # path globs
    then_emit :ParitySectionRan
  end

  value_object "Section" do
    attribute :name           # "Synthetic fixtures", "Real bluebooks", ...
    attribute :globs, [String]
    attribute :max_diff_lines, Integer, default: 40
    attribute :soft, Boolean, default: false   # nursery
  end

  value_object "KnownDrift" do
    attribute :path, String
    attribute :reason, String
    attribute :flavor, Symbol
    attribute :since, Date
  end

  value_object "ParityVerdict" do
    attribute :path, String
    attribute :status, Symbol     # :match | :unexpected_drift | :expected_drift | :unexpected_pass | :error
    attribute :diff_excerpt, String, default: ""
  end
end
```

The five parity tests collapse into **five `Section`s** parameterized by `flavor`. The seven hardcoded path bucket sets in `parity_test.rb` (SYNTHETIC, REAL, CAPS, CATALOG, MIETTE, MISC, NURSERY) become `Section` value objects with `globs`.

This is **not** a `Parity` aggregate per fixture — that would mean ~250 ParityVerdict aggregates, which is ceremony for a directory walk. Parity is a **property the kernel runs OVER fixtures**, not a domain in fixtures.

`fuzz/fuzz_test.rb` is excluded — it's a property-based generator, not a contract ; out of i501 scope.

## Where dual-target dispatch lives

**The runner owns it. Not the bluebook.** The bluebook declares *what to compare* (sections, drift) ; the runner declares *how to compare* (invoke ruby parser, invoke rust parser, normalize, diff).

`then_set :ruby_ir / then_set :rust_ir / then_emit :ParityChecked` would be a lie — there is no aggregate state being mutated, no event truly emitted, no consumer for `ParityChecked`. It would be a behaviors-shaped wrapper around a subprocess pair. The architectural truth : the parity runner is a build-time integrity check, semantically closer to `cargo test` than to a domain command.

Concretely the runner :

1. Loads `parity/parity_suite.bluebook` via `hecks-life dump`.
2. For each `Section` : enumerates globs, invokes Ruby parser via `ruby -Ilib bin/hecks-dump <path>`, invokes `hecks-life dump <path>` for Rust, deep-sorts, diffs.
3. Applies known-drift list (also from bluebook).
4. Prints legend (`✓ ✗ ⚠ ⚑`), exit 1 on unexpected drift.

The Ruby side becomes **`bin/hecks-dump`** — a 30-line CLI replacing the inline `ruby_dump` methods. It's the minimum Ruby surface required because the contract requires invoking the Ruby parser ; this is unavoidable until the Ruby parser itself retires.

## Fixtures-as-input shape

The bluebook describes `Section` (a value object set with globs) ; the runner enumerates the directory. **Per-fixture aggregates would multiply the bluebook by 250+ entries with zero information density** — every entry would have identical shape (`path: "foo.bluebook", flavor: :domain`).

The synthetic fixtures in `parity/bluebooks/*.bluebook` already ARE bluebook files ; they don't need wrapping. The 245-fixture corpus is **the input set**, not the contract. The contract is "every file matched by these globs must round-trip identically" — one sentence, one `Section` per flavor.

## The `known_drift.txt` problem

Lift to **`parity/known_drift.bluebook`** — fixtures-style, structured :

```ruby
Hecks.fixtures "ParityKnownDrift" do
  fixture "cli_dispatch_shape" do
    path "codegen/cli_dispatch_shape/cli_dispatch_shape.bluebook"
    flavor :domain
    reason "parser escape-handling drift"
    since 2026-05-02
  end
  ...
end
```

Unifies the four siblings (`known_drift.txt`, `hecksagon_known_drift.txt`, `world_known_drift.txt`, `fixtures_known_drift.txt`, `behaviors_known_drift.txt`) into one structured source. The `flavor` attribute disambiguates. Reason becomes queryable, `since` enables drift-aging reports. The runner reads via `hecks-life dump-fixtures` (already exists).

The `⚑ unexpected pass` mechanism survives unchanged ; the runner just consults the structured set instead of parsing comments.

## What runner this needs

**Separate subcommand : `hecks-life parity [--flavor=domain|...] [--scope=<glob>]`. Not `hecks-life test`.**

`hecks-life test` (i500, Phase A) executes `.behaviors` files : setup + dispatch + assert. Single-target operation against the Rust runtime. Parity is a **dual-target diff** — different verb, different I/O shape, different failure mode (exit codes for CI gating, not assertion verdicts), different output (drift line-diff, not pass/fail counts). Conflating them would force `test` to grow a `--compare-with-ruby` mode used by exactly one consumer.

Contract :

- Reads `parity/parity_suite.bluebook` + `parity/known_drift.bluebook`.
- Output : same legend (`✓ ✗ ⚠ ⚑`) as today, identical to current Ruby output (so pre-commit hook expectations don't change).
- Exit 1 on unexpected drift ; 0 on known drift ; warns on unexpected passes.
- `--flavor` filter for incremental retirement.
- Calls `bin/hecks-dump` for the Ruby side (subprocess) ; keeps `hecks-life dump/dump-hecksagon/dump-world/dump-fixtures` for the Rust side.

## Phasing

Incremental, one flavor at a time, by simplicity :

1. **`world_parity_test.rb`** (4 fixtures) — smallest surface, 1 known drift entry, prove the pattern.
2. **`behaviors_parity_test.rb`** (1 fixture) — smallest by count ; validates the runner-of-runners shape.
3. **`fixtures_parity_test.rb`** (29 fixtures) — `.fixtures` flavor, separate dump command exists.
4. **`hecksagon_parity_test.rb`** (60 fixtures) — analogous to domain.
5. **`parity_test.rb`** (245 fixtures, 7 path buckets, nursery soft-mode) — last, biggest, most baked-in.

Each step :
- Add its `Section` + drift entries to the two bluebook files.
- Verify `hecks-life parity --flavor=<x>` matches the Ruby driver's output byte-for-byte (meta-parity).
- Replace the Ruby driver's invocation in `tooling/git-hooks/pre-commit` and `.github/workflows/parity.yml` with the new subcommand.
- Delete the `.rb` driver.

`fuzz/fuzz_test.rb` and `fixtures_auto_load_parity_test.rb` are out of scope — separate inboxes.

**Critical unblocker** : `bin/hecks-dump` must exist before step 1. Irreducible Ruby surface. If/when the Ruby parser retires entirely (CLAUDE.md "Always use Rust runtime"), the parity suite retires with it ; that's the natural endpoint.

## What stays Ruby (and why that's fine)

- `parity/canonical_ir.rb` — defines the canonical JSON shape. Retires with the Ruby parser, not before.
- `bin/hecks-dump` (new) — minimal Ruby CLI exposing canonical_ir over a path argument.
- `parity/fuzz/fuzz_test.rb` — property-based generation ; orthogonal.

Total Ruby surface after retirement : ~50 lines (one CLI bin + `canonical_ir.rb` which already exists). Down from ~700 lines across five drivers. That's the right shape : parity becomes a Rust-driven, bluebook-described kernel check with a thin Ruby adapter, until the Ruby parser itself goes.
