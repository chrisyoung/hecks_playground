# i506 — Retire the `hecks` Ruby gem

## TL;DR

The published `hecks-2026.04.26.4` gem blows up on `hecks --help` with
`uninitialized constant Hecks::Runtime::Mixins` (i499 audit ; same
shape as i505, different file). Root cause is a chapter load-order
issue : `domain_versioning/breaking_bumper.rb` references
`Hecks::Runtime::Mixins` while chapters are still loading, before the
`ChapterAliases.install` const_missing hook is wired onto
`Hecks::Runtime`.

## Why retire (not fix)

Per CLAUDE.md : "Always use Rust runtime — `hecks-life` for all
bluebook parsing, .heki storage, daemons. No Ruby." The Ruby `hecks`
CLI is on the deprecation path. Patching the load order buys nothing.

## Action taken this session

Deprecation short-circuit added to `bin/hecks` : prints a migration
notice pointing at `hecks-life` and exits 1, unless `HECKS_RUBY_OK=1`
is set (escape hatch for local dev). Local `./bin/hecks --help` still
broken in the published gem, but users now get a clear message
instead of a NameError stack trace.

## Loose ends (out of scope, eventual sweep)

1. Cut one final `hecks-2026.05.08.1` carrying the deprecation shim,
   or yank `>= 2026.04.26.4` from rubygems.
2. Update `README.md` / `FEATURES.md` to point at `hecks-life`.
3. Decide cutover : delete `ruby/hecks/` source tree once `hecks-life`
   covers the remaining commands users depend on.
4. Remove `bin/hecks`, `bin/hecks_claude`, `bin/appeal` from the
   gemspec ; possibly publish an empty terminal version.
