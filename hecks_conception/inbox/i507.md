# i507 — Retire `ruby/hecks/capabilities/acceptance_test*` (Ruby capability subsystem)

## TL;DR

The i499 audit flagged `ruby/hecks/capabilities/acceptance_test.rb` as a
"broken orphan" failing on `undefined method register_capability`.
Triage revealed two corrections worth recording :

1. **Misnamed file, not a test.** Despite the `_test.rb` suffix, this is
   a capability *declaration* (`Hecks.capability :acceptance_test do …`)
   that registers a visual acceptance-test runner. It generates JS for
   a floating overlay served via the Ruby `static_assets` adapter.
2. **Not orphaned.** It IS wired — `ruby/hecks/concerns/dev_tools.rb:5`
   includes `:acceptance_test` in the `:dev_tools` concern alongside
   `:tailwind`, `:web_client_state`, `:web_debug`. The
   `register_capability` error fires only when run as a standalone
   script (loader missing) ; inside the framework it loads fine because
   `ruby/hecks/registries/capability_registry.rb` is loaded first.

## Decision : retire, but as part of the broader Ruby capabilities tree

Per `CLAUDE.md` "Always use Rust runtime — no Ruby" and the recent
hecks/miette boundary work (commits 6ea40adc, 34cb6c5e), the entire
`ruby/hecks/capabilities/` tree is framework code on the retiring Ruby
runtime. This file's 400 lines (50 + three subdir files of 117 + 78 + 155)
plus its consumer in `dev_tools.rb` retire together with the rest of the
capability subsystem — not solo. Same shape as i504 (studio specs) and
i505 (smoke test) — all Ruby framework, retiring with the runtime.

## Why not "convert to behaviors"

The capability is not a domain contract. It generates JavaScript that
dispatches HTTP commands against a running Ruby web server and renders
a floating DOM overlay. There's no aggregate state, no event log, no
domain invariant — it's framework wiring for a UI affordance.
`.behaviors` is the wrong shape.

## Why not "fix-and-wire"

`register_capability` already exists at
`ruby/hecks/registries/capability_registry.rb:27`. The DSL works in
context. The "fix" would be running the file inside the framework
loader — which is what `dev_tools` already does. Nothing to fix ; the
audit mistook a standalone-script failure for a structural break.
