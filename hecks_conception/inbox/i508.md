# i508 — Rename mis-named `*_spec.rb` modules under `generators/infrastructure/spec_generator/`

## TL;DR

The 14 files in
`/Users/christopheryoung/Projects/hecks/ruby/hecks/generators/infrastructure/spec_generator/`
named `*_spec.rb` are domain modules (mixins for `SpecGenerator`),
not RSpec specs. RSpec auto-discovers them and crashes (i499 audit).
A direct rename appeared trivial but the audit found the names
propagate through three `.bluebook` IR files plus the paragraph + the
container — 126 line-occurrences across 5 external files, plus the 14
source files themselves. That exceeds the agent's 50-ref bail
threshold for unsupervised renames.

## Why this can't be a pure file rename

The aggregate names declared in the bluebook ARE `AggregateSpec`,
`CommandSpec`, ..., `WorkflowSpec`. `Hecks::Chapters.load_aggregates`
underscores those names to `aggregate_spec`, `command_spec`, ... and
`require`s the matching files. So the file basename is structurally
tied to the bluebook aggregate name — renaming files alone breaks
loading.

Two coupled rename surfaces are required, not one :

1. **File basenames** — `aggregate_spec.rb` → e.g.
   `aggregate_spec_generator.rb` (avoids rspec auto-pickup ; matches
   sibling `chapter_spec_generator.rb` convention).
2. **Bluebook aggregate names** — `AggregateSpec` →
   `AggregateSpecGenerator` (so `load_aggregates` snake-resolves to
   the new file).

## Three approach options for whoever picks this up

**Option A — file rename only, decouple file ↔ aggregate names** :
Add a custom mapping in `load_aggregates` (or the paragraph) so
`AggregateSpec` → `aggregate_spec_generator.rb`. Smallest blast
radius but introduces an asymmetry between bluebook name and file
name that future readers will trip on.

**Option B — rename both file AND bluebook aggregate names** (cleaner,
mechanical) : `AggregateSpec` → `AggregateSpecGenerator` everywhere.
Touches 5 external files mechanically + 14 source files (file rename
+ internal `module AggregateSpec` → `module AggregateSpecGenerator`
+ doc-header constant references). Then update the `include` lines
in `spec_generator.rb`. The three `.bluebook` IR mirrors must stay
in sync — verify with parity gate.

**Option C — extract files OUT of the bluebook-driven load tree** :
These mixins don't need to be loaded by `Hecks::Chapters` ;
`spec_generator.rb` already explicitly `include`s each by constant.
A plain `Hecks::Chapters.require_paragraphs` (or even direct
`require_relative` glob) would load them. Then drop the
`SpecGeneratorsParagraph` paragraph entirely — the bluebook
`AggregateSpec`/`CommandSpec` IR aggregates can stay as IR-level
declarations of *what the generators produce*, but stop driving file
discovery. Most architecturally clean ; biggest design-think
required (does anyone else consume those IR aggregates?).

## Why P:medium not P:high

Workaround : `bundle exec rspec spec/` (the configured spec dir) does
not pick up these files — the bug only triggers when someone aims
rspec at this directory directly. So the framework still tests fine.
But the file naming is structurally misleading and i499 explicitly
flagged this as a separate fix.

## Suggested next steps

1. Decide between Options A / B / C above (architecture call).
2. If B : verify the three `.bluebook` mirrors are kept in sync by an
   existing parity gate ; if not, that's a prerequisite.
3. If C : confirm whether downstream consumers (Rust side, generated
   files, MCP tools) actually use the `AggregateSpec` aggregate IR or
   only the Ruby mixin classes.
