# i511 — Catalog bluebook gaps surfaced while wiring catalog/ into pre-push

## TL;DR

Wiring `hecks_conception/catalog/` into the pre-push `.behaviors`
gate (i499 follow-up) surfaced three small bluebook bugs that were
masked by the runner-level `:pending` kind. Each is a one-liner :
adding a `reference_to`, a `then_set`, or a self-id field. None of
them block the gate today (the offending tests are pending), but
every one represents a real lifecycle/update path that won't work in
the live runtime either.

## Findings

1. **`appeal/Feature` lacks `reference_to(Feature)` on lifecycle
   commands** — `PlanFeature`, `BuildFeature`, `VerifyAdditions`,
   `CompleteFeature` are all transition-only commands but have no
   self-ref. The behaviors runner falls into singleton dispatch
   (id="1" via `id_for_command`) so single-command tests pass, but
   chained setups (`PlanFeature` → `BuildFeature`) each *create a new
   Feature in `draft`* instead of operating on the prior one — chained
   lifecycle flows therefore can never advance state. Per
   `feedback_transition_commands_need_self_id.md`, this is the canonical
   shape : every transition command needs a self-ref.
   - File : `hecks_conception/catalog/appeal.bluebook` lines 278-305
   - Pending tests : `appeal.behaviors` `VerifyAdditions runs`,
     `BuildFeature runs`, `CompleteFeature runs`

2. **`rvdc/App.RegisterDomains` lacks `then_set :domains, to: :domains`**
   — RegisterDomains has `attribute :domains, list_of(String)` and
   `emits "DomainsRegistered"` but no mutation clause. The fixture
   pre-loads an App at id=1 with a 4-element `domains` list ; when
   the test dispatches RegisterDomains with `domains: ["sample"]`, the
   update path runs but no mutation copies the new value onto the
   record (the create-attrs copy block at command_dispatch.rs:206-217
   is gated by `is_new`).
   - File : `hecks_conception/catalog/applications/rvdc/rvdc.bluebook` lines 19-25
   - Pending test : `rvdc.behaviors` `RegisterDomains sets domains`

3. **`pre_seed_singletons` doesn't apply lifecycle defaults** — the
   behaviors runner's pre-seed path
   (`rust/src/behaviors_runner.rs:467-486`) creates an empty
   `AggregateState` at id="1" for every aggregate whose commands all
   require self-ref, but skips `apply_lifecycle_default`. Any command
   with a `given` clause that reads the lifecycle field will fail
   against this virgin record. Surfaced by
   `mind.behaviors`'s `AccumulateFatigue cascades through policy chain`
   — `EnterDaydream` requires `state == "attentive"` but
   pre-seeded `Consciousness.state` is null.
   - File : `rust/src/behaviors_runner.rs` `pre_seed_singletons`
   - Pending test : `mind.behaviors` `AccumulateFatigue cascades through policy chain`

## Why it matters

(1) and (2) are silent live-runtime bugs : the affected commands look
correct in the bluebook but won't update state when re-dispatched. (3)
is a behaviors-runner gap that any aggregate with a `lifecycle` and a
`given` will trip over the moment cross-aggregate setups land in its
test ; the comment at line 464-466 acknowledges the tradeoff but the
"test will surface the gap" promise hits as `errored`, not `failed`.

## Suggested resolution

- **(1)** : add `reference_to(Feature)` to `PlanFeature`,
  `BuildFeature`, `VerifyAdditions`, `CompleteFeature`. Drop
  `kind: :pending` from the three appeal.behaviors tests.
- **(2)** : add `then_set :domains, to: :domains` to
  `App.RegisterDomains`. Drop `kind: :pending` from rvdc.behaviors.
- **(3)** : extend `pre_seed_singletons` to call
  `apply_lifecycle_default` after `repo.save`. Drop `kind: :pending`
  from `AccumulateFatigue cascades`.
