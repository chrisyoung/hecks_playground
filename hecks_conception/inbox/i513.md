# i513 — Behaviors DSL extension : `kind: :validation` for validator-rule outcomes

Filed during Tier 2 spec triage of
`spec/hecks/validation_rules/structure/duplicate_policies_spec.rb`.
The spec couldn't be converted to `.behaviors` because the DSL has no
way to express "given this domain shape, the validator emits these
errors."

## The problem

`Hecks::ValidationRules::Structure::DuplicatePolicies` is a framework-
level rule, not a command on a domain aggregate. Its surface :

```ruby
described_class.new(domain).errors  # => [ValidationMessage, ...]
```

Each `ValidationMessage` carries a `.message` string. A rule fires
when two `(event_name, trigger_command)`-equal policies coexist ; it
stays silent on legitimate fan-out (same event, different triggers)
and on shared-trigger / different-event wiring.

Behaviors DSL today knows three test kinds, all of which dispatch
*against a real boot of the bluebook under test* :

| kind        | shape                                        |
|-------------|----------------------------------------------|
| `:command`  | dispatch a command, assert state             |
| `:query`    | run a query, assert `count:` / `<attr>:`     |
| `:cascade`  | dispatch, assert exact ordered emit list     |

None of those carry the "synthesize a domain in-test, run a validator
against its IR, assert error-count + message substrings" shape.

## Proposed DSL extension

A new test kind, `kind: :validation`, that takes a bluebook block as
input and asserts on the validator's error output :

```ruby
test "DuplicatePolicies flags two policies sharing event and trigger" do
  tests "DuplicatePolicies",
        on:   "Structure",            # rule namespace (Structure / Naming / References / WorldConcerns)
        kind: :validation
  bluebook "Dup" do
    aggregate "Heart" do
      attribute :beats, Integer
      command "Beat" do; emits "HeartBeat"; end
      command "Tick" do; reference_to(Heart); emits "Ticked"; end
    end
    policy "TickOnBeat"      do; on "HeartBeat"; trigger "Tick"; end
    policy "TickOnBeatAgain" do; on "HeartBeat"; trigger "Tick"; end
  end
  expect violations: 1,
         message_includes: %w[HeartBeat Tick TickOnBeat TickOnBeatAgain]
end

test "DuplicatePolicies passes on legitimate fan-out" do
  tests "DuplicatePolicies", on: "Structure", kind: :validation
  bluebook "FanOut" do
    # ...same domain shape with distinct triggers...
  end
  expect violations: 0
end
```

Two new keywords inside the test block :

| Keyword        | Purpose                                                                  |
|----------------|--------------------------------------------------------------------------|
| `bluebook`     | Inline domain definition that the validator will be run against          |
| `expect`       | Adds `violations: <Int>` and `message_includes: [<substr>, ...]` shapes  |

## Pieces of work

1. **DSL surface** — register `:validation` as a behavior kind ; add
   `bluebook` block parser (likely already lives in `Hecks.bluebook`,
   reuse) ; extend `expect` with `violations:` + `message_includes:`.
2. **Runner wiring** — `hecks-life behaviors` learns to instantiate
   `Hecks::ValidationRules::<Namespace>::<Rule>.new(domain).errors`
   when it sees `kind: :validation`. Cross-runtime detail : the rule
   itself is Ruby today ; runner needs to shell to Ruby OR the rules
   need a bluebook port (downstream work).
3. **Conceiver coverage** — auto-generate a `:validation` test pair
   (one violating fixture, one passing fixture) for each registered
   validation rule.
4. **Tier-2 spec sweep** — once the DSL ships, convert
   `spec/hecks/validation_rules/**` (every Structure / Naming /
   References / WorldConcerns rule) to `.behaviors` and retire the
   rspec specs.

## Coordination

- Coordinates with **i494** (meta-bluebook DSL gaps : `validation`
  is one of the aggregate-level clauses listed there). i513 is the
  *test-side* sibling — i494 grows the source DSL ; i513 grows the
  behaviors DSL that exercises validators.
- The Ruby-vs-Rust split for the actual rule code is its own
  question ; the DSL extension can ship before the rules port.

## Until then

`spec/hecks/validation_rules/structure/duplicate_policies_spec.rb`
(and its peers) stay as rspec. Triage labels them Tier 2 — convert
once this DSL extension lands.
