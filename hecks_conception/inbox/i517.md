# i517 — Runtime + smoke followups for the i516 sleep redesign

The i516 sleep redesign landed across two repos (miette `<musings retire>`,
hecks `bb6b02eb` + earlier `a675d22` / `4bf17537`). The schema, prompt, bridge,
wake review composer, cycles 1-3 housekeeping design, and Musings retirement
are all in. **Sleep still doesn't run end-to-end** because of one runtime bug
plus a handful of smaller followups. This inbox tracks them.

## P0 — The load-bearing runtime bug

### Policy dispatcher doesn't propagate aggregate_id

When a policy fires a command-trigger (`policy "Foo" do ; on "EvtX" ; trigger
"CmdY" ; end`), and the target command (`CmdY`) has no required identifier
attribute, the runtime mints a **fresh UUID** for the target aggregate
instead of threading the originating event's `aggregate_id` through.

Effect : `EnterSleep` lands on `id: consciousness` (the canonical name id —
fixed in this session by passing `name: "consciousness"` in the CLI dispatch).
But during the sleep cycle, BodyPulse fires `ElapsePhaseOnPulse` ;
ElapsePhase has `given { state == "sleeping" }` and increments phase_ticks ;
that part should work. But somewhere else in the fan-out, `BecomeAttentive`
gets dispatched (probably via the `AttentiveOnWake` policy on a synthesized
WokenUp, OR via some other policy-chain) — `BecomeAttentive` has no
`identified_by` value, no `given` clauses, no required attrs, so the runtime
mints a fresh UUID, applies its `then_set`s, persists. **A parallel
"attentive" aggregate appears next to the "sleeping" one.** The streamer's
`latest()` then returns whichever was written last (often the UUID one),
making the cycle appear to wake. Phase_ticks never increments on the
canonical aggregate.

Repro from this session :
1. Pre-seed `consciousness.heki` with `id=consciousness, name=consciousness, state=attentive`.
2. Run `hecks-life run-loop --emit BodyPulse:Consciousness:consciousness` in bg.
3. Run `hecks-life sleep` in fg.
4. After ~25s : the heki has TWO records — one `id=consciousness` with
   `state=sleeping, phase_ticks=0`, and one with a UUID id and
   `state=attentive`.

Fix scope : substantial Rust work in `rust/src/runtime/` policy dispatcher.
When dispatching a policy-triggered command, the runtime should propagate
the originating event's `aggregate_id` (or look up the aggregate by
`identified_by` value when the policy's `across` declares a different
aggregate type). ~50–100 LoC in `command_dispatch.rs` / similar.

This is THE blocker for sleep running end-to-end. Until this lands :
- `phase_ticks` won't advance.
- Cycles stall in light/cycle-1.
- The new precise-reading prompt never gets a chance to fire.

Hypothesis worth investigating before code : is `AttentiveOnWake` actually
firing even when we're entering sleep? Maybe one of the policies emits
`WokenUp` as a side effect. Trace the BodyPulse fan-out and identify
which policy first dispatches `BecomeAttentive`.

## P2 — Codegen snippet retirements

The Musings retirement found one consumer it couldn't directly retire :
codegen specializer snippets that name `musings_count` in generated
Rust code (`run_statusline_shape`, `assemble_shape`, `cli_dispatch_shape`,
etc.). These are byte-identical templates the kernel regenerates from ;
direct edits would fail parity. Full retirement here is shape-
regeneration work (i78 territory).

For now : `musings_count` field stays in `run_statusline.rs` reads but
isn't rendered (verified by the `assert!(!line.contains("💭"))` test).
Inert.

## P3 — `with: { ... from_event(...) }` on policies

The `DreamPulseFromImage` bridge policy in `dream.bluebook` was supposed
to pass `impression: from_event(:reading)` so the cascade output reaches
`Consciousness.sleep_summary` for the statusline. The DSL parser doesn't
yet support policy-level data passing (only PM-level `dispatch` honors
the `with:` clause). The bridge fires DreamPulse without the impression
attribute today ; the statusline flips on DreamPulse but the reading
flows through `dream_state.heki` and WakeReview composes from there.

Acceptable for now ; full surface-fix is DSL extension work.
