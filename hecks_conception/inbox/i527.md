# i527 — LivingDiagram : the bluebook as a clickable, observable surface

**Filed:** 2026-05-09
**Source:** Dan's idea, surfaced via Chris while pivoting back to dream-work after the banking review (PR #624 / #625).

## The vision

The bluebook is already a graph :

  - **nodes** — aggregates, commands, events, policies
  - **edges** — `emits` (command → event), `on/trigger` (event → policy → command), `then_dispatch` (command cascade), `reference_to` (aggregate → aggregate)

Today that graph is implicit, expressed only in source form. Dan's
proposal : render it as a *living diagram* in the browser. Click a
node, fill out the form (auto-generated from the command's
attributes), execute the command, watch events ripple through the
edges in real time as cascades fire downstream.

The walking-skeleton today shows "a list of commands per aggregate."
The living diagram replaces that with the graph itself — same
information, but the structure now teaches as it operates.

The end state : this *is* the production dashboard. What you build
your domain in is the same surface you operate it through. Allure
+ HecksAppeal already point this direction ; LivingDiagram makes
the cascade visible, not just the structure.

## What this would conceive

`runtime/living_diagram/living_diagram.bluebook` — or as a chapter
of the existing HecksAppeal domain. Rough shape :

  - **Diagram** (aggregate, lifecycle: idle | rendering | live)
    - domain_name : String
    - rendered_at : Time
    - layout_strategy : LayoutStrategy
  - **DiagramNode** (value object)
    - kind : NodeKind (Aggregate | Command | Event | Policy)
    - name : String
    - position : Position (x, y — for layout persistence)
    - state : NodeState (idle | active | firing | resolved)
  - **DiagramEdge** (value object)
    - kind : EdgeKind (Emits | TriggersOn | Cascades | References)
    - from_node : NodeRef
    - to_node : NodeRef
    - last_traversal_at : Time (when did a real event flow through?)
  - **CascadeTrace** (aggregate, lifecycle: pending | flowing | settled)
    - origin_command : String
    - dispatched_at : Time
    - hops : list_of CascadeHop
  - **CascadeHop** (value object)
    - edge : EdgeRef
    - event_payload : Map
    - resolved_at : Time
  - **CommandForm** (value object — auto-generated from IR)
    - command_name : String
    - fields : list_of FormField
    - submit_url : String

Commands :
  - **Diagram.Render**(domain) — derive nodes + edges from IR
  - **Diagram.OpenForm**(node_id) — show the command form
  - **Diagram.Dispatch**(command, payload) — proxy to the real runtime
  - **CascadeTrace.Begin**(origin_command, dispatched_at)
  - **CascadeTrace.RecordHop**(edge, payload)
  - **CascadeTrace.Settle**

Policies :
  - **TraceCascadesIntoDiagram** : on every runtime EventEmitted, find
    the matching DiagramEdge, mark it traversed, append a hop to the
    open CascadeTrace.

## Surface (web)

  - Stack with the existing HecksAppeal / Allure work — same dev
    server (`rust/src/server`), same SSE stream the existing
    explorer pages already use, just a new view.
  - Layout : force-directed with sticky positions (D3-Force or
    Cytoscape).
  - Form generation : the IR already carries every command attribute
    + type ; rendering is mechanical.
  - Cascade animation : SVG path animation along edges as
    EventEmitted streams in.

## Why this fits dream-work

Dreams are abstract imagery for me. The diagram is *literal*
imagery for the runtime — its own dream made visible. When a cascade
fires, the system narrates itself through the edges, and the
operator sees what would otherwise be inferred from logs. That is
exactly the kind of legibility the framework is supposed to produce.

## Acceptance

  - `runtime/living_diagram/living_diagram.bluebook` (or HecksAppeal
    chapter) parses Ruby↔Rust byte-equal (parity passes).
  - The diagram bluebook is enough that, when implemented, a live
    dispatch on any command shows the cascade flowing through the
    edges in the browser.
  - Walking-skeleton example demonstrates : open a domain, click a
    command node, fill the form, dispatch, watch the cascade.

## Out of scope (named follow-ons)

  - Cross-domain cascade visualisation (Bounded-Context-aware
    cascade traces). Defer.
  - Persisted layout per user. Defer.
  - Time-travel through past CascadeTraces. Defer to a TimeTravel
    inbox stub if desired.

## Relationship to in-flight bluebook conceptions

  - i521 (heki) — orthogonal.
  - i522 (discovery) — the diagram needs discovery to know which
    bluebooks to render ; reuses, doesn't re-invent.
  - i523 (status_assembly) — the diagram could surface assembly
    output as a side-panel ; shared idiom, no overlap.
  - i524 (behaviors_conceiver) — orthogonal.

LivingDiagram could be conceived in parallel with the four originals
or sequentially after them ; the gap is independent.
