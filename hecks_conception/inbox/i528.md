# i528 — One StoreHouse, app-scoped command buses (WASM, host-agnostic)

## Decisions locked (2026-05-10)

  1. `app = project folder name`. For `bin-buddy/aggregates/notifications/notifications.bluebook` ⇒ `app = bin-buddy`. The web-apps-within-a-project case (customer-portal vs admin-portal vs driver-portal) is a separate concern about *who consumes the bus* ; the command bus itself is one per project.
  2. **`::` separator** — `app::domain::Aggregate::Command`. Disambiguates phrases (calling) from paths (querying within a record).
  3. **One CommandBus per app**, identified by `App`.
  4. **WASM model B (host-agnostic) is the destination.** Transitional shape A (host wrapper compiled into the same WASM, workers-rs style) is the first iteration ; the ABI tightens over iterations.
  5. **Api folds into `CommandBus`** — no separate `Api` aggregate. CommandBus carries the bus-domain *and* the HTTP route declarations. If Portal later needs to consume Api as a named contract, we promote it then.
  6. **`Portal` aggregate is out of this iteration.** Ship the bus first ; conceive Portal once a portal is in production.
  7. **Queries are first-class, same four-segment shape, disambiguated by case.** `app::domain::Aggregate::Command` is a command (PascalCase fourth segment) ; `app::domain::Aggregate::query_name` is a query (lowercase fourth segment). Lexicon entries do *not* carry an explicit `kind` field — the convention does the work, the way every other Hecks convention does (CalVer, value-object capitalization, hecksagon adapter naming). Aggregates declare named queries with `query "Name" do … end` blocks (PascalCase in source — the existing DSL with `where` clauses and block params already supports this). At Lexicon Compile time, query names are converted PascalCase → snake_case for the phrase form : `query "ListAll"` in the source becomes `app::domain::Aggregate::list_all` on the wire. Commands stay PascalCase end-to-end. Same dual-form pattern as Ruby's `MyClass` ↔ `my_class.rb`.
  8. **Commands invoke via the Command pattern.** The bluebook IR generates a class per command and per query ; callers in Ruby write `Bin::Buddy::Notifications::SendEmail.new(to_email:, subject:, body:).call` ; in Rust they write the target's idiom. Both converge on the same dispatch pipeline as the indirect `Dispatch.Route(phrase:, params:)` form. The choice of target language idiom is a `:codegen` adapter binding, not a bluebook concern.

## The picture — three layers, two transformations

```
StoreHouse   (the universal bus over the whole conception — every callable phrase)
   ↓ filter(app: <app>)
CommandBus   (a scoped slice — only phrases starting with `<app>::`.
              Artifact : WASM. Carries the HTTP route declarations.)
   ↓ consume
Portal       (future — web app that calls into the CommandBus.
              Out of this iteration.)
```

Two pure-domain layers active (StoreHouse, CommandBus) ; everything about *how they're realized* — WASM, R2, CF Worker, Bearer tokens — lives in **hecksagon adapter bindings**, not in the bluebooks.

The bin-buddy realization : `StoreHouse → CommandBus(app: "bin-buddy")`, with adapter bindings `:wasm`, `:storage → :r2`, `:host → :cf_worker`, `:http → :cf_worker_fetch`, `:auth → :bearer`.

## Layer separation — bluebook ≠ hecksagon

The whole arc obeys the same cut applied everywhere else in Hecks :

- **bluebook** files describe *domain* : aggregates, value-objects, commands, events, rules. No infrastructure leaks in.
- **hecksagon** files describe *adapters* : which adapter family handles which command, which provider is bound, what the wire shape is. All infrastructure lives here.

So `command_bus.bluebook` says "CommandBus is a scoped, callable bus with these commands and these HTTP routes". It does not say *WASM*, *R2*, *Cloudflare*, *Bearer*. `command_bus.hecksagon` says "this CommandBus is realized as a `:wasm` artifact, with storage adapter `:r2`, hosted on `:cf_worker`, exposed via `:cf_worker_fetch`, authenticated with `:bearer`".

## Artifact shape — WASM, host-agnostic (Model B)

CommandBus compiles to a **host-agnostic** `.wasm` artifact with a clean exported ABI (one `dispatch(phrase, params) → event` function, no host knowledge baked in). The CF Worker, AWS Lambda, local CLI, future browser embed all *import* that same WASM and forward calls into it. The WASM is the portable bus ; hosts are skins.

Transitional shape : during the first iteration the host wrapper compiles into the same WASM as the bus (workers-rs style — Model A). The ABI tightens over time and the artifact splits when the bus stabilizes. The bluebook describes the destination ABI ; the hecksagon binding records which shape this deployment ships today.

## Calling convention

Every callable phrase is **four segments**, `::` separator :

```
<app>::<domain>::<Aggregate>::<Command>
```

- **app**       — the project folder name. Inferred at Compile time from the bluebook's location ; not declared in the bluebook source.
- **domain**    — the sub-folder under the app that groups related bluebooks (`storehouse`, `notifications`, `consciousness`).
- **Aggregate** — the aggregate name declared in the bluebook.
- **Command**   — the command name on that aggregate.

Examples :

```
bin-buddy::notifications::Notifications::SendEmail
bin-buddy::subscription::Subscription::Cancel
hecks-conception::storehouse::Dispatch::Route
hecks-conception::storehouse::Lexicon::Compile
miette::consciousness::Consciousness::EnterSleep
```

`Query.Read` paths follow the same convention with one trailing attribute segment :

```
bin-buddy::system_test::SystemTest::last_sms_status
hecks-conception::storehouse::Lexicon::compiled_at
```

## Bluebook layer — what changes + what's new

### Edits to existing bluebooks

| File | Change |
|---|---|
| `storehouse/dispatch.bluebook` | `Phrase` value-object rule : four segments, `::` separator (was : "2..3 dotted segments"). Prose drops hecks-life references — Dispatch dispatches through "the configured storage adapter", with the adapter named in the hecksagon (not the bluebook). |
| `storehouse/lexicon.bluebook` | `Phrase` matches Dispatch. `Compile` takes a **SourceSet** (filesystem path *or* embedded blob *or* fixture set) instead of "the conception root". The index is keyed on the full four-segment phrase, and every entry carries `app` as a first-class field for filtering. |
| `storehouse/query.bluebook` | `Path` value-object : four segments + trailing attribute, `::` separator. Same `app` field on entries. |

### New bluebooks (pure domain — no infrastructure)

| File | Aggregate | Domain (only) |
|---|---|---|
| `storehouse/command_bus.bluebook` | `CommandBus` | A scoped view of StoreHouse, plus its HTTP route declarations. Identified by `App` (singleton per app). Commands : `Scope` (materializes the filtered phrase set), `ListPhrases` (reads it), `Route` (a `Dispatch.Route` constrained to `app == self.app`), `Expose` (declares the HTTP routes : POST /route, GET /lexicon, GET /query, GET /health), `HealthCheck`. **No mention of WASM, storage, hosts, or auth schemes.** |

`api.bluebook` and `worker.bluebook` from earlier drafts both **dissolve** : Api folds into CommandBus per decision #5 ; Worker was deployment specifics, all hecksagon territory.

## Hecksagon layer — adapter families

All bound on a single `storehouse/command_bus.hecksagon` :

| Family | Members | What it adapts |
|---|---|---|
| `:wasm` | `:wasm32_cdylib` | The artifact shape. Declares the export ABI : `dispatch(phrase, params) → event`. |
| `:storage` | `:fs`, `:r2`, `:in_memory` | The heki backend. World file picks one per deployment. |
| `:host` | `:cf_worker`, `:aws_lambda`, `:cli`, future `:browser_embed` | Where the WASM runs. The host adapter provides the WASM with its fetch / invoke entrypoint and binds storage. |
| `:http` | `:cf_worker_fetch`, `:lambda_apigw`, `:axum_local` | The HTTP transport for `Expose`d routes. |
| `:auth` | `:bearer` (service-to-service), `:oauth`, `:jwt` (tenant / user) | Authentication scheme. |
| `:codegen` | `:ruby_command_class`, `:rust_struct`, `:typescript_function`, future `:python_dataclass` | Per-target-language class / type / function generation from the bluebook IR. Ruby gets the Command pattern (`SomeCommand.new(**params).call`) ; Rust gets struct + impl ; TypeScript gets typed functions. All idioms converge on the same dispatch pipeline. |

Each family follows the pattern already used by `:sms` (Twilio) and `:email` (Resend) — the world file picks one provider per deployment, the framework's provider hecksagon declares the wire shape per member.

## What the bin-buddy Worker does on the wire

Same as before, but now CommandBus declares the route shape and adapter bindings carry the realization details :

```
POST /route         { phrase: "bin-buddy::notifications::Notifications::SendEmail", params: {…} }
                    → 200 with the Dispatched event payload
GET  /lexicon       → list of the phrases this Worker serves (filtered : starts_with "bin-buddy::")
GET  /query?path=…  → 200 with the ValueRead event payload
GET  /health        → ok + embedded_count + storage_binding + auth_bound
```

Auth — two-tier via `:auth` adapter bindings :

- **Service-to-service** : `:bearer`, Worker secret. The Pages Function proxy uses this when a Portal calls the Worker on a user's behalf.
- **Tenant / user** : `:jwt` or `:oauth`, scope claim validated against the phrase's required-role. Production-shape for Portal → CommandBus calls.

Storage : `:storage => :r2`, bucket `bin-buddy-heki`, bound at deploy time via wrangler config.

## Renames that fall out

- The Rust crate `hecks-life` → `storehouse`. Binary `hecks-life` → `storehouse`. My system-prompt invocations collapse from `hecks-life storehouse route …` to `storehouse route …`. Big rename, single sweep.
- The `bin-buddy/worker/` scaffold relocates : Workers are produced by `storehouse compile-worker --app bin-buddy --out <dest>` from inside the storehouse crate. The customer repo (bin-buddy) holds bluebooks + the deployed-Worker secrets + the `wrangler.toml` + the Pages Function proxy ; it doesn't hold the Worker *source*.
