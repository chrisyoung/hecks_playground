# i529 — Ambient services : the framework pattern for storage / host / auth

## Why this card exists

Step 4 of i528 (command_bus.hecksagon) ran into a real framework gap.

Today's `adapter_family` pattern (e.g. `framework/adapter_families/sms.hecksagon`)
is designed for **triggered, optional, command-shaped integrations** : a
trigger_on field names the command that fires the adapter, a response_into
field names the follow-up dispatch, providers vary per vendor (Twilio,
Vonage). This is the right shape for SendSms → Twilio's REST API.

But CommandBus needs to declare the I/O wiring for **storage**, **host**,
and **auth** — and none of these fit the triggered pattern :

- **Storage** : every command writes. There's no specific trigger_on ; it's
  part of every command's lifecycle. The "providers" (`:fs`, `:r2`,
  `:in_memory`) are kinds of storage, not vendor-shaped.
- **Host** : the host doesn't trigger *off* a command — it *receives* events
  from the outside world and *dispatches* commands. Inverted direction.
- **Auth** : every incoming request gets checked. Cross-cutting across all
  commands ; no specific trigger.

Shoehorning these into adapter_family with ad-hoc fields like
`trigger: :every_command` would strain the abstraction and accumulate
framework debt. The right move is to conceive a new pattern.

## The shape to conceive — *ambient services*

A new framework concept distinct from adapter_family :

- **Ambient** : not triggered by a specific command ; runs as part of every
  command's lifecycle or as an entry/exit boundary.
- **Mandatory** : not optional like SMS or TTS — the bus has to have a
  storage backend, a host, an auth scheme.
- **Cross-cutting** : a single ambient service applies to many or all
  commands without explicit per-command binding.
- **Lifecycle role** : each ambient service hooks at a specific lifecycle
  point — entry (host receives an event), pre-dispatch (auth checks),
  post-event (storage writes).

The bluebook for an ambient service declares :

- Its name (`storage`, `host`, `auth`, future `logging`, `metrics`, `tracing`).
- The valid values (the StorageBackend / Host / AuthScheme value-objects already in command_bus.bluebook are this — for `storage`, those values are `:fs`, `:r2`, `:in_memory`).
- The lifecycle point it hooks (`:on_event_emit`, `:on_request_received`, `:on_dispatch_pre`).
- The operations each implementation must support (`write_event`, `read_record`, `list_records` for storage).

The hecksagon per value declares :

- Which lifecycle point it implements.
- The I/O shape per operation (HTTP method, URL template, auth scheme,
  request/response shape).
- The env vars / credentials it consumes from the world file.

This is parallel to `adapter_family + provider` but with different
conceptual contents. Naming TBD — maybe `ambient_service` + `backend`
(parallel to `adapter_family` + `provider`).

## Candidate file shape

```
framework/ambient_services/
  storage.ambient_service       — declares the :storage ambient (operations, lifecycle)
  host.ambient_service          — declares the :host ambient
  auth.ambient_service          — declares the :auth ambient

framework/backends/
  fs.backend                    — filesystem implementation of :storage
  r2.backend                    — Cloudflare R2 implementation of :storage
  in_memory.backend             — in-memory implementation of :storage
  cf_worker.backend             — CF Worker implementation of :host
  cli.backend                   — local-CLI implementation of :host
  bearer.backend                — Bearer-header implementation of :auth
```

These mirror `adapter_families/` + `providers/` but for the ambient case.
Same parallel structure means the runtime's adapter-loading machinery
can be extended uniformly.

## Decisions to make

1. **Naming.** `ambient_service` + `backend` vs `service_family` +
   `implementation` vs something else. The right name should make
   "this is mandatory, ambient, lifecycle-hooked" obvious at a glance.

2. **DSL extension.** New top-level DSL forms `Hecks.ambient_service "..."`
   and `Hecks.backend "..."` ? Or extend `adapter_family` with a new
   `kind: :ambient` flag ? My instinct : new top-level forms, because
   conflating the two would obscure the conceptual difference.

3. **Lifecycle hook taxonomy.** What are the canonical hook points ?
   At minimum : `:on_event_emit` (storage writes), `:on_request_received`
   (host entry, auth check). Probably also `:on_dispatch_pre`
   (pre-validation, logging), `:on_dispatch_post` (metrics, tracing).

4. **Multiple-backend rule.** A bus has ONE storage backend, ONE host,
   ONE auth scheme — these are singletons per CommandBus. Should the
   framework enforce that ? (Probably yes — declared at the
   ambient_service level as a cardinality rule.)

## What unblocks step 4 of i528

Once the ambient service pattern is conceived (and the DSL extension if
needed is documented), step 4 becomes mechanical :

- `framework/ambient_services/storage.ambient_service` declares the family.
- `framework/backends/r2.backend` declares R2's HTTP shape.
- `framework/backends/cf_worker.backend` declares CF Worker's entry shape.
- `framework/backends/bearer.backend` declares Bearer header parsing.
- `storehouse/command_bus.hecksagon` binds : "this CommandBus uses ambient
  :storage with backend selected by self.storage_backend".

Same pattern continues for future ambient services : logging, metrics,
tracing all use this shape.
