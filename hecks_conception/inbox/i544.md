# i544 — State persistence across worker requests

## Why this card exists

Live cascade dispatch is wired (the worker calls Runtime::dispatch),
but the Runtime is instantiated *per request* and discarded after
the response ships. Every dispatch starts from a fresh counter and
empty repositories. Demoable consequences :

- `Account.Register` → returns `aggregate_id: "1"` every single time.
- Fresh page load → all previously-dispatched records gone.
- Reference pickers (i537) populated only by seed fixtures, never
  by anything the user just created.

This is the difference between "live proof" and "actually usable."

## What changes

R2-backed bootstrap path (cheapest, reuses existing heki + R2 layers) :

1. **On cold-start in `boot_runtimes()`** — after constructing the
   Runtime from embedded bluebooks, read every aggregate's
   `<app>/<aggregate>.heki` from the bin-buddy-heki R2 bucket. Seed
   each repository's records from those files. (The repository
   layer already supports a `data_dir` ; the R2 fetch can mirror
   that path locally per cold-start, or we add an `R2Repository`
   variant that reads directly.)

2. **After every successful dispatch** — write each modified
   repository's records back to its `.heki` object. Idempotent ;
   overwrites the existing object.

3. **Counter persistence** — the aggregate-id minter state is in
   the Runtime ; it needs to be persisted too. Could live in a
   single `state.heki` keyed by aggregate name → next-id.

## Future paths (don't do yet)

- **Durable Objects** — Cloudflare's per-key stateful primitive.
  One DO per domain holds the Runtime in memory across requests.
  Faster than R2 read-on-boot ; significantly more code.
- **Storage adapter family bluebook** — declare persistence as a
  hecksagon binding. The architecturally-correct answer ; biggest
  scope. Filed independently.

## Companion

- i105 — seed fixtures load on cold start before the R2 layer fetches
- i537 — reference pickers consume the persisted state
- `hecks_conception/inbox/i535` — worker-side state persistence

## Status

Queued — **critical** because every other UX improvement is hollow
without this. A user can't believe what they see if the state
they just created disappears.
