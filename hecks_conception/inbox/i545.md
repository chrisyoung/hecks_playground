# i545 — Surface cascade events in dispatch response

## Why this card exists

Bin-buddy's bluebook has real policies — WelcomeOnRegister fires
Notifications.SendWelcomeEmail on AccountRegistered ;
RouteAssigningOnSubscribe fires
Notifications.SendRouteAssignmentPending on Subscribed. The runtime
ACTUALLY fires these cascades through Runtime::dispatch — the worker
just throws the cascade information away.

Today's response shape :

```json
{"ok": true, "event": "AccountRegistered",
 "aggregate_type": "Account", "aggregate_id": "1"}
```

The user sees one event. The diagram doesn't animate. The downstream
Notification (if it had a separate Pages-Function-realized adapter,
which it does) doesn't appear in the result.

## What changes

After `rt.dispatch(...)` returns successfully, read
`rt.event_bus.history()` (or whatever the API is — there's already
an event store accessible via the bus) and return every event
emitted DURING this dispatch — top-level + every cascade step :

```json
{
  "ok": true,
  "event": "AccountRegistered",
  "aggregate_type": "Account",
  "aggregate_id": "1",
  "cascade": [
    {"event": "WelcomeEmailRequested", "aggregate_type": "Notifications",
     "aggregate_id": "n1", "fired_by": "WelcomeOnRegister"},
    {"event": "WelcomeEmailSent", "aggregate_type": "Notifications",
     "aggregate_id": "n1", "fired_by": ":email adapter"}
  ]
}
```

Renderer (per `i538` / `i535`) consumes the `cascade` array and
either renders each event as a row in the dispatch-result panel,
or animates the diagram edges between aggregates.
