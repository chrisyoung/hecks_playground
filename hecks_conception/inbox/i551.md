# i551 — `:claude_tool` adapter family (bluebook-first, auto-discovered)

## The principle

> "the domain will compose the tool call and the adapter runs them"
> — Chris, 2026-05-12
>
> "adapters should be auto registered in the runtimes by reading the
>  files in their folders" — Chris, 2026-05-12

Two principles, one design :

- **Domain composes ; adapter runs.** The Tools bluebook (and the
  Tools.X commands declared on it) compose what the tool call is.
  The :claude_tool adapter binding executes it.
- **Auto-discovery, not manual registration.** Adding a new adapter
  family is dropping a new file into `framework/adapter_families/`
  + a matching `framework/behavior_kinds/<behavior>.hecksagon`. The
  runtime walks those folders at boot. No Ruby builder edits, no
  Rust parser edits, no canonical IR dumper edits.

## What landed today

Two bluebook-first declarations :

1. **`framework/adapter_families/claude_tool.hecksagon`** — declares
   the `:claude_tool` adapter family. Fields : `command`, `tool`,
   `result_into`. Trigger : `command`. Behavior : `invoke_claude_tool`.

2. **`framework/behavior_kinds/invoke_claude_tool.hecksagon`** — what
   the kernel does when a `:claude_tool` adapter fires. Branches on
   `tool:` and invokes the matching native primitive (shell exec for
   :bash, file substring-substitute for :edit, read for :read, write
   for :write, ripgrep for :grep, glob for :glob). Routes the result
   into the adapter's `result_into` target.

Plus the consumer hecksagon already landed earlier :

3. **`framework/tools/tools.hecksagon`** — six `adapter :claude_tool`
   bindings, one per Tools.X command. Today they fall through to
   IoAdapter because the framework discovery isn't yet active for
   the :claude_tool family ; when the runtime activates the
   discovery (i556), they get picked up as typed instances.

## What still requires code (substrate)

The kernel hook for the `invoke_claude_tool` behavior_kind. Six
small native primitives in Rust :

  - `:bash`   → `Command::new("sh").arg("-c").arg(shell_command).output()`
  - `:edit`   → read file → substring substitute → write back
  - `:read`   → read file, truncate at configured limit
  - `:write`  → write content to file
  - `:grep`   → ripgrep with pattern + search_path
  - `:glob`   → walk filesystem with glob pattern

That substrate is filed as **i556** (kernel hook for the
invoke_claude_tool behavior). The bluebook contract is done ; the
substrate is the only piece left to ship.

## Pairs with

- **i552** — Claude calls StoreHouse (the dispatch direction).
  Together with i551 + i556 : Claude dispatches Tools.X via
  storehouse → matching :claude_tool adapter fires → kernel runs
  the actual tool → result chains back via result_into.
- **i556** — the kernel hook for `invoke_claude_tool` (the only
  remaining substrate).

## Why no Ruby / Rust parser changes

The earlier attempt (2026-05-12) went down the manual-registration
path : ClaudeToolAdapter struct in Ruby + Rust, builder, autoload,
parser arm, etc. Five files touched, with more in the canonical IR
dumper + runtime resolver to come. Chris's correction inverted it :
"that was way too much registration. Adapters should be auto
registered in the runtimes by reading the files in their folders."

The framework already supports `Hecks.adapter_family` and
`Hecks.behavior_kind` as framework_kind declarations (i239 / Phase
1 surface). The auto-discovery walks `framework/adapter_families/*`
and `framework/behavior_kinds/*` at boot. So a new adapter family
IS a bluebook ; the manual-registration path was the legacy way of
adding :llm and :shell, not how new families ship now.

All five Ruby + Rust edits from the manual-registration attempt
were reverted ; only the bluebook-first artifacts kept.
