# i551 — Optional :shell adapter override for Tools.Bash

## Why this card exists

The Tools bluebook (`hecks_conception/aggregates/framework/tools/tools.bluebook`)
declares Bash and the other tool commands. The runtime defaults
to memory ; dispatching `Tools.Bash` records the invocation,
emits BashRan, updates state. The domain just works.

If a deployment wants the dispatch to ALSO produce real-shell
side-effects — actually running `ls -la` when Miette dispatches
Tools.Bash — that's an adapter wire-in via a Tools hecksagon.
The adapter doesn't fix anything broken ; the domain already
runs. The adapter ADDS a side-effect.

## What an override would look like

The existing `:shell` adapter (see `examples/shell_adapter/`)
is template-based. For arbitrary `shell_command` strings at
dispatch time, a new flavor :

```
adapter :shell, command: "Bash" do
  execute_arbitrary true
  output_into "Tools.RecordOutput", attr: :stdout
  exit_into    "Tools.RecordOutput", attr: :exit_code
end
```

When `Tools.Bash` dispatches with shell_command="ls -la", the
adapter runs `/bin/sh -c "ls -la"`, captures stdout + exit, and
fires a follow-on `Tools.RecordOutput` command that backfills
the result fields. Same pattern as the :llm adapter's
`response_into` shape.

## Why this is optional

The domain doesn't need it. From the bluebook's perspective,
the only thing that has to happen on Tools.Bash dispatch is
the state update + event emit. That's already happening.

A deployment WITHOUT this adapter still has a working domain :
every Bash invocation is recorded, every event fires, policies
react. The deployment just doesn't get real shell execution as
a side-effect of the dispatch.

## When to ship it

When a real use-case wants shell side-effects from a Tools.Bash
dispatch. Until then, the Claude harness already runs Bash
directly ; this adapter is the path to bridge runtime-dispatch
to actual execution if/when that bridge becomes useful.
