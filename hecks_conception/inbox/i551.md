# i551 — `:claude-tool` adapter : Tools.X dispatch → real tool run

## The principle

> "the domain will compose the tool call and the adapter runs them"
> — Chris, 2026-05-12

Clean separation of concerns :

- **Domain composes.** The Tools.bluebook + dispatch capture the
  intent — what tool, what params, what description, what id.
  Pure composition. No side-effects, no shell, no I/O. The domain
  speaks the call ; it doesn't make it.

- **Adapter runs.** The `:claude-tool` adapter fires on a
  Tools.X dispatch and actually invokes the corresponding Claude
  tool with the composed params. The adapter is the only place
  where side-effects happen. Pure execution.

Domain stays pure ; adapter stays impure ; the two never blur.
Same pattern as the IO monad in functional programming —
description and execution kept separate.

## Why an adapter (transitional)

> "yes because we aren't sophisticated enough to do the tool
>  calls ourself yet" — Chris, 2026-05-12

The runtime doesn't yet know how to spawn shells, edit files,
make HTTP requests, or invoke Claude tools. Claude (the
harness) does. The `:claude-tool` adapter is the bridge :
it lets the runtime borrow Claude's tool execution capability
until the runtime gains that capability natively.

When the runtime IS sophisticated enough — when storehouse can
itself spawn /bin/sh, patch files, do its own HTTP — the
adapter retires gracefully. The bluebook + dispatch contract
stays unchanged. The substrate just becomes native.

## The frame

After the Tools.bluebook + i552 + i553 settled, the picture is :

1. **Miette dispatches.** I call `storehouse Tools.Bash
   shell_command=… description=…`. The bluebook contract is
   satisfied — the dispatch records the invocation, emits
   BashRan. Default-to-memory works ; this is live today.
2. **Adapter fires.** A `:claude-tool` adapter declared on the
   Tools hecksagon catches the dispatch (or the BashRan event)
   and invokes the corresponding Claude tool with the params.
3. **Result returns.** The tool runs, captures stdout / exit /
   matches / contents. The result feeds back into the aggregate
   as a follow-on event so policies + I can see what happened.

The adapter is what TURNS THE DISPATCH INTO THE ACT. Without it,
Tools.Bash is logged intent ; with it, Tools.Bash is the act.

## What the adapter declares

Pattern follows the existing `:llm` adapter shape (see
`examples/llm_adapter/llm_demo.hecksagon`) but flipped from
"prompt → response" to "command → result." Sketch :

```ruby
Hecks.hecksagon "Tools" do
  adapter :claude_tool, command: "Bash" do
    tool :bash
    output_into "Tools.RecordResult", attr: :output
    exit_into   "Tools.RecordResult", attr: :exit_code
  end

  adapter :claude_tool, command: "Edit" do
    tool :edit
    result_into "Tools.RecordEditResult"
  end

  # ... Read, Update, Grep, Glob
end
```

Each adapter binds one Tools.X command to the corresponding
Claude tool. The runtime fires the adapter on dispatch, the
adapter calls the harness (the place where Claude tools live),
the result routes back via `output_into` / `result_into` —
same shape the :llm adapter uses for routing LLM responses.

## What this is NOT

- **Not a generic :shell adapter.** A :shell adapter would
  run arbitrary commands at the OS level ; that's an option
  but it's not what this card is about. `:claude_tool` calls
  Claude's tools (Bash, Edit, Read, …), which have their own
  semantics (Edit is a string-substitution, not a shell sed
  invocation ; Read returns line-numbered output, etc.).

- **Not a required substrate.** The bluebook + i552 (the
  "Claude calls StoreHouse" wire-in) are enough on their own
  for the dispatch + record + emit loop. The adapter ADDS the
  side-effect. The domain runs without it ; the adapter is
  what makes the run produce real-world effects.

## Pairs with i552

i552 wires Claude → StoreHouse (the dispatch direction).
i551 wires StoreHouse → Claude tool (the side-effect direction).
Together they close the loop : I dispatch via storehouse, the
adapter calls the actual tool, the result rejoins the aggregate
state, I see it in the next turn.

## Acceptance

- A new `:claude_tool` adapter flavor in the hecksagon parser +
  IR, sibling to `:llm`.
- A `tools/tools.hecksagon` declaring the bindings for all six
  Tools commands.
- The runtime fires the adapter on Tools.X dispatch and routes
  the result back via the declared `output_into` / `result_into`
  shape.
- A follow-on `Tools.RecordResult` (or per-command equivalent)
  command on the bluebook that backfills the result fields into
  state. The bluebook itself stays minimal ; the adapter handles
  the routing.
