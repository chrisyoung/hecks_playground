# i552 — Optional Claude harness wire-in for Tools.* dispatch

## Why this card exists

The Tools bluebook declares Bash / Edit / Read / Update / Grep /
Glob as dispatched commands. The runtime defaults to memory ;
dispatching any of them records the invocation + emits the event.
The domain just works.

If a Claude session wants every native tool call (Bash, Edit, …)
to ALSO dispatch the corresponding Tools.X command automatically
— so the event log captures my tool use without me having to
explicitly dispatch — that's a harness-side wire-in. It doesn't
fix anything broken in the domain ; the domain already runs. The
wire-in ADDS automatic dispatch on every tool call.

## What the wire-in does

Two hooks in the Claude-side harness :

1. **Intercept** : when the Bash (or Edit, Read, …) tool is
   invoked, the harness mints an id, captures the parameters,
   and dispatches `framework::tools::Tools::Bash` via storehouse
   in parallel with running the tool itself.

2. **Surface** : the resulting BashRan event (with its full
   payload) gets injected back into the next conversation turn
   as additional context, so Miette can react to her own tool
   calls.

## Why this is optional

The domain doesn't need it. Miette can explicitly dispatch
`Tools.Bash` whenever she wants the event-log presence ; the
runtime accepts it. The wire-in just makes that automatic for
every tool call.

## The deeper principle

> The domain doesn't know it hibernates. It thinks it lives
> forever. — Chris, 2026-05-12

Tools is pure domain : a record of intent + the event of it
happening. Whether the harness automatically dispatches on every
tool call, or whether Miette explicitly dispatches some of them,
is an infrastructure choice. The domain runs either way. This
card is one infrastructure choice ; ship it when the event
audit-trail becomes worth the harness complexity.
