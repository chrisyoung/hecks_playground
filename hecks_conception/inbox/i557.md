# i557 — Phase-2 framework runtime : auto-discovery + kernel-hook registry

## The gap

The framework already supports two declarative forms :

  - `Hecks.adapter_family "X" do … end` — declares an adapter family with
    fields, behavior, providers. Lives at
    `framework/adapter_families/<X>.hecksagon`.
  - `Hecks.behavior_kind "Y" do … end` — declares what the kernel does
    when an adapter of family X (which picks behavior Y) fires. Lives at
    `framework/behavior_kinds/<Y>.hecksagon`.

The parser recognizes both — sets `framework_kind = "adapter_family"` /
`"behavior_kind"` on the parsed Hecksagon IR. But the **runtime layer
has zero code that reads framework_kind**. Grep `rust/src/runtime/` for
`framework_kind` or `adapter_family` : nothing. The declarations are
inert ; the parser knows about them but the dispatcher doesn't.

Today's existing families (`sms`, `tts`) and the new `:claude_tool`
(i551) all live as aspirational declarations. i551 / i556 ship a
**hardcoded** integration just for `:claude_tool` — the runtime
specifically knows to walk `io_adapters` with `kind: "claude_tool"`
and fire `claude_tool_dispatcher`. That works but doesn't generalize.

## What Phase-2 ships

The runtime's missing layer. At boot :

1. Walk `framework/adapter_families/*.hecksagon`. For each, parse the
   declared `fields`, `trigger_field`, `response_field`, `behavior`,
   `providers`. Build `AdapterFamily { name, fields, behavior, … }`
   records keyed by family name.
2. Walk `framework/behavior_kinds/*.hecksagon`. For each, parse
   `requires_field`, `trigger_attribute`, etc. Build `BehaviorKind`
   records keyed by behavior name.
3. Hold both in a runtime-level `FrameworkRegistry`.

In `Runtime::dispatch`, after the existing dispatch logic :

4. Walk loaded hecksagons for any `io_adapter` whose `kind` matches a
   registered adapter family.
5. Look up the family's `behavior` field → resolve to the matching
   behavior_kind.
6. Resolve the behavior_kind → its registered kernel hook (a function
   pointer in a `HashMap<String, KernelHook>` registry).
7. Build the adapter's field values + dispatched command's attrs, call
   the kernel hook, capture the result.
8. Route the result via the adapter's `response_field` target if set.

Kernel hooks themselves are still Rust code (kernel-floor) — they're
the substrate. The registry maps behavior_kind names to their hook
implementations :

```rust
hooks.insert("invoke_claude_tool", &claude_tool_dispatcher::dispatch);
hooks.insert("call_sms_api",       &sms_dispatcher::dispatch);
hooks.insert("render_text_to_audio", &tts_dispatcher::dispatch);
// etc.
```

## What this unlocks

- **sms** : `framework/adapter_families/sms.hecksagon` becomes live. Any
  hecksagon with `adapter :sms, ...` fires the `call_sms_api` behavior →
  kernel hook → Twilio HTTP call → response chains back. No code per
  consumer.
- **tts** : same for `render_text_to_audio`. ElevenLabs / OpenAI / Piper
  providers each get one provider hecksagon ; consumers just bind.
- **claude_tool** : the i551 hardcoded integration retires. The runtime
  finds `:claude_tool` adapters through the general registry path.
- **Future families** : add a new family by writing
  `framework/adapter_families/<name>.hecksagon` +
  `framework/behavior_kinds/<behavior>.hecksagon` + a kernel hook in
  Rust. No runtime edits beyond the new hook itself.

## What stays code-side

The kernel hooks. Each is a small native Rust function that takes
`(adapter_fields, command_attrs)` and returns a result. The framework
registry calls them ; the hooks themselves can't be bluebooked
(they're the substrate). Same retirement contract as the existing
kernel-floor markers : retire when the framework grows the ability
to express side-effects declaratively (some far future).

## What gets parsed today vs needs parser work

Today the parser captures `framework_kind` + `name` on the
Hecksagon IR but NOT the inner declarations (`fields`, `behavior`,
`requires_field`, etc.). Phase-2 needs the parser to either :

- Extend the Hecksagon IR with `adapter_family_payload` / `behavior_kind_payload`
  fields that capture the inner declarations
- OR : have the runtime registry re-parse the framework files
  at boot via a small dedicated reader

The first is more structurally honest (one parser does everything).
The second is faster to implement and could be the v1.

## Sequencing with i551 / i556

- **i551 + i556 + i1b9e02c8** : hardcoded `:claude_tool` integration
  (kernel hook + Runtime::dispatch shortcut for that one family).
  Lands this week.
- **i557 (this card)** : retires the hardcoded path, generalizes to
  the framework registry. Same kernel hook is reused via the
  registry indirection.
- **sms / tts** : pick up parity once i557 ships. New kernel hooks
  for `call_sms_api` and `render_text_to_audio` slot into the same
  registry.

## Acceptance

1. `rust/src/runtime/framework_registry.rs` (new) — types +
   builder + lookup helpers.
2. `Runtime::boot_with_hecksagons` calls the framework discovery
   to populate the registry.
3. `Runtime::dispatch` consults the registry for adapter matches +
   fires the appropriate kernel hook.
4. The hardcoded `:claude_tool` path from i551 is retired (the
   kernel hook stays ; only the dispatcher-side shortcut goes).
5. A test bluebook + hecksagon that declares a new family +
   behavior + kernel hook can end-to-end dispatch without any
   edit to the runtime's hardcoded tables. The framework adds
   itself.
