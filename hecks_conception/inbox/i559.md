# i559 — Pre-commit hook : resolve `$REPO` against the worktree

## What this card carries

The pre-commit hook at `.git/hooks/pre-commit` resolves `$REPO`
from the hook script's own location, not from the worktree that
is actually staging the commit. In a Git worktree, the hook
script lives at `.git/hooks/pre-commit` under the MAIN repo's
git dir (worktrees share hooks via the main repo's `.git/hooks/`
by default). So `dirname "$0"/../..` always lands in the main
working tree, never the worktree-agent's tree.

Every validate call then reads stale (main-tree) bytes instead
of the staged (worktree) bytes. False positives and false
negatives both possible : a staged fix in the worktree can fail
because validate sees the broken main-tree version ; a staged
break in the worktree can pass because validate sees an
unrelated clean main-tree version.

## Symptoms (this evening's parallel run)

Four agents hit variations of the same isolation leak :

- **dispatch_audit primitive wrap** (commit `acda262349713b728`) —
  "the pre-commit hook resolves REPO from its own script
  location, which points to the main repo's working tree, not
  the worktree's." Diagnosed but not fixed at root.

- **mindstream primitive wrap** (commit `a0b62362d036c21a8`) —
  same diagnosis. Worked around with `VALIDATE_SKIP=1`.

- **update i527** (commit `a223e760d463e0547`) — the Edit
  tool's path resolution lands outside the worktree even when
  given worktree-rooted paths. Related symptom : tools assume
  one canonical repo.

- **Tools.RecordResult** (commit `acbc49ac20e752bc2`) — agent
  had to manually copy the modified file from main into the
  worktree before the hook would see it. The hook was reading
  main and ignoring the worktree's staged change.

The shared shape : *agent does the right thing in its worktree,
hook validates against the wrong tree, commit blocked or
silently miscertified.*

## Root cause

`.git/hooks/pre-commit`, line 32 :

```bash
REPO="$(cd "$(dirname "$0")/../.." && pwd)"
```

In a worktree, `$0` resolves to `<main>/.git/hooks/pre-commit`
(or, depending on Git version, to the worktree's `.git` text
file path, but in either case `dirname "$0"/../..` does not
reliably point to the worktree's working tree). The hook then
uses `$REPO` as the root for every subsequent file read :

```bash
STOREHOUSE="$REPO/rust/target/release/storehouse"
CONCEPTION_DIR="$REPO/hecks_conception"
...
[ -f "$REPO/$bb" ] || continue
out=$("$STOREHOUSE" validate "$REPO/$bb" 2>&1)
...
[ ! -f "$REPO/$companion" ] && continue
```

Every one of these reads from the main tree when the staged
files live in a worktree.

## The fix

One line. Replace :

```bash
REPO="$(cd "$(dirname "$0")/../.." && pwd)"
```

with :

```bash
REPO="$(git rev-parse --show-toplevel)"
```

`git rev-parse --show-toplevel` returns the working tree of the
checkout that invoked the hook — main tree for a main commit,
worktree for a worktree commit. That is exactly the semantic
the hook wants.

## Acceptance

- Pre-commit hook uses `git rev-parse --show-toplevel` for
  `$REPO`.
- A worktree agent staging a bluebook change has its STAGED
  bytes validated, not the main tree's bytes.
- A worktree agent staging a fix to a file that is broken on
  main passes validation (was failing before).
- A worktree agent staging a break to a file that is clean on
  main fails validation (was passing before).
- `VALIDATE_SKIP=1` is no longer needed for routine worktree
  commits.
- Existing main-tree commit path is unchanged (the new
  resolution returns the same value there).
