# i563 — Rename-drift validator : bluebook-driven dispatch (no kernel Rust)

## What landed

A previous agent (`ad32f874b74a0be03`) attempted the rename-drift
validator as kernel-surface Rust (`rust/src/rename_drift.rs` +
`rust/tests/rename_drift_test.rs`) ; the antibody hook correctly
blocked the commit. Per Chris's call, the validator was redesigned
to live in the bluebook, not in `.rs`.

The redesigned shape :

- `hecks_conception/aggregates/discipline/immunity/rename_drift.bluebook`
  — `RenameDriftCheck` aggregate with `Finding` entity (one record per
  stale reference), lifecycle `idle → scanning → checking → done |
  violations_found`, and per-aggregate value-objects (CheckRef,
  RepoRoot, Status, ViolationCount, FilePath, LineNo, ReferenceKind,
  ReferenceTarget). Three policies wire the Tools.* cascade :
  `CatalogBluebooks` (ScanStarted → Tools.Glob),
  `ExtractDeclarations` (GlobMatched → Tools.Grep),
  `AlertOnFinding` (FindingRecorded → Immunity.DetectThreat).

- `hecks_conception/aggregates/discipline/immunity/rename_drift.behaviors`
  — 12 behavior tests covering Scan / RecordFinding / Pass / Fail
  state transitions, event emission, and Finding accretion.

## What's NOT in this card

The Tools.* cascade is bluebook-described : policies name the
trigger + `across "Tools"` boundary. The runtime today doesn't
auto-fire cross-domain triggers ; that's a separate runtime
concern (the cascade is correct shape, the wiring is pending). The
validator-as-bluebook contract is now the source of truth ; when
the runtime grows cross-domain policy dispatch, this bluebook will
"just work" without changes.

The previous agent's `rust/src/rename_drift.rs` +
`rust/tests/rename_drift_test.rs` were NOT brought into this
worktree — they're discarded by design.

## Runtime gap discovered (follow-up)

While wiring the lifecycle status as a value-object (per the
no-primitive-envy rule), the runtime initialized `status` as an
empty list `[0 items]` because of `apply_defaults` in
`rust/src/runtime/command_dispatch.rs:521` :

```rust
} else if attr.list || vo_names.contains(&attr.attr_type.as_str()) {
    state.set(&attr.name, Value::List(vec![]));
}
```

This auto-lists EVERY VO-typed attribute, but per CLAUDE.md
2026-05-12 locked conventions :

> **List shape is explicit** — `attribute :foos, Foo` is SCALAR.
> Lists require `list_of(X)`. The auto-list heuristic is retired
> in both the Ruby and Rust parsers.

The PARSER drops the heuristic, but the RUNTIME retains it. The
workaround applied here : every scalar VO attribute carries
`default: "<initial>"` so the if-branch (`attr.default.is_some()`)
takes precedence and bypasses the auto-list. Works, but it's a
band-aid — the runtime should match the locked convention.

The fix is one branch removal in `apply_defaults`. Scope is small,
but it's a runtime concern with corpus-wide effects (every existing
bluebook using a VO attribute relies on the current behavior, so
removing the heuristic requires sweeping each one to make sure
list_of intent is explicit).
