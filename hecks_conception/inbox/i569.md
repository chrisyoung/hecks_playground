# i569 — Behaviors framework gap : five capabilities that retire the rust/tests cluster

## What's blocked

The following five `rust/tests/*.rs` integration tests all carry
`[antibody-exempt: ...]` markers whose retirement trigger is the same
shape : "the `.behaviors` framework can drive X directly."

| File | Trigger phrase |
|---|---|
| `rust/tests/antibody_hecksagon_test.rs` | "behaviors framework can drive hecksagon smoke tests directly" |
| `rust/tests/terminal_capability_test.rs` | "behaviors framework can drive capability shape assertions directly" |
| `rust/tests/run_boot_test.rs` | "behaviors framework gains capability-detection coverage end-to-end" |
| `rust/tests/restructure_integration_test.rs` | "behaviors framework gains a `:fs` tempdir fixture covering Layout.Plan/Apply/RevertTo end-to-end" |
| `rust/tests/validator_test.rs` (+ `validator_rules_test.rs`, `validator_warnings_test.rs`) | "behaviors framework can drive validator-output assertions directly" |

The i558 audit (Tier-3 retired-trigger walk, 2026-05-12) named this
as a single cluster (recommended action #6) and noted that one
bluebook covers all five.

## Why they're stuck as `.rs` today

The `.behaviors` runner today exercises ONE shape (read any of
`tools/behaviors/behaviors.behaviors`, `tools/dump/dump.behaviors`,
`tools/actions/actions.behaviors` for examples) :

```
test "Command accepts an attribute" do
  tests "CommandName", on: "AggregateName"
  input  attr: "value"
  expect attr: "value"
end
```

That is : dispatch a single command, assert state propagation via
`then_set`. It does NOT model :

1. **Hecksagon-shape assertion** — that a `.hecksagon` parses to
   the expected adapter / gate / persistence set
   (`antibody_hecksagon_test.rs` shape).
2. **Capability-shape assertion** — that a paired
   `.bluebook` + `.hecksagon` declares the expected aggregate +
   command + io-adapter set (`terminal_capability_test.rs` shape).
3. **Capability-detection** — that a runtime + adapter registry
   correctly identifies "this domain has the boot capability" /
   "this domain has the restructure capability"
   (`run_boot_test.rs` shape).
4. **`:fs` tempdir fixtures** — sandbox tree setup + filesystem
   assertions after dispatch (`restructure_integration_test.rs`
   shape ; also `heki_path_coherence_test.rs`).
5. **Validator-output assertions** — that a Domain literal
   (or `.bluebook` source) produces the expected validator
   error / warning set (`validator_test.rs`, `validator_rules_test.rs`,
   `validator_warnings_test.rs` shapes).

Each of those is a small bluebook capability ; the cluster wants
all five.

## Proposed shape

A `Behaviors` extension bluebook (or five sibling bluebooks) that
declares command vocabulary for each pattern. Sketch :

```
test "Boot capability is detected on real bluebook + hecksagon" do
  load_bluebook  "runtime/boot/boot.bluebook"
  load_hecksagon "runtime/boot/boot.hecksagon"
  expect_capability "boot"
end

test "Validator flags duplicate aggregate names" do
  given_bluebook <<~BB
    Hecks.bluebook "T" do
      aggregate "A" do … end
      aggregate "A" do … end
    end
  BB
  expect_validator_error "duplicate aggregate name: A"
end

test "Restructure plan moves files in a sandbox tree" do
  fs_tempdir do |root|
    write_file root, "a/old.bluebook", "…"
    dispatch "Layout.Plan", placements: [{from: "a/old.bluebook", to: "b/new.bluebook"}]
    dispatch "Layout.Apply"
    expect_file_exists root, "b/new.bluebook"
    expect_file_absent root, "a/old.bluebook"
  end
end
```

Each new vocabulary term (`load_bluebook`, `expect_capability`,
`given_bluebook`, `expect_validator_error`, `fs_tempdir`,
`expect_file_exists`, `expect_file_absent`) is a small extension
to the behaviors-runner grammar. The runner already speaks `tests`,
`on`, `input`, `expect` — these are siblings.

## Lowest-friction first step

The simplest of the five is **validator-output assertions** :

- Validator already takes a `Domain` and returns `Vec<String>` errors.
- The `.behaviors` runner already parses `.bluebook` sources for the
  `tests` / `on` directives.
- A new directive `given_bluebook <heredoc>` would parse the heredoc
  as a `Domain` ; `expect_validator_error "msg"` would run
  `validate(&domain)` and assert the message appears.

That single capability retires `validator_rules_test.rs` (39 tests
build `Domain` literals to exercise individual rules) and most of
`validator_test.rs`, and gets the validator-shape clean enough to
attempt the others.

## Acceptance

- One bluebook extension lands that covers at least one of the
  five capabilities above.
- One `rust/tests/*.rs` file retires (its tests port to a
  `.behaviors` companion of the relevant bluebook).
- The antibody-exempt marker on the retired test file goes away.

## Pairs with

- **i78** (specializer-of-specializers / meta-shape pipeline) —
  parallel arc retiring the kernel-floor `.rs` substrate. i78
  retires the production `.rs` ; i569 retires the test `.rs`.
- **i558** (Tier-3 audit) — surfaced this cluster as action #6.

  can live in a `.behaviors` file, so the ratchet's enforced
  coverage gets deeper.
