# i569 — :web_tool adapter family + kernel hooks (WebFetch + WebSearch)

## What this card carries

The bluebook-first substrate for `Tools.WebFetch` and `Tools.WebSearch`
— mirrors `:claude_tool` (i551/i556) but as its own adapter family
with swappable providers. Per Chris's spec :

> WebFetch/WebSearch belong to their own adapter family with swappable
> providers (DuckDuckGo, SERPAPI, plain HTTP, etc.) — same shape as
> `:llm` has Anthropic/OpenAI/Ollama providers.

## Files added

### Bluebook declarations
- `framework/adapter_families/web_tool.hecksagon` — the family. Two
  behaviors (`perform_web_fetch`, `perform_web_search`), two
  providers (`http_get`, `duckduckgo`), four fields
  (`name`, `command`, `tool`, `result_into`).
- `framework/behavior_kinds/perform_web_fetch.hecksagon` — kernel
  hook contract for fetch. Requires `:result_into` ; trigger attr
  `:description`.
- `framework/behavior_kinds/perform_web_search.hecksagon` — kernel
  hook contract for search. Requires `:result_into` ; trigger attr
  `:description`.
- `framework/providers/http_get.hecksagon` — plain HTTP GET via curl.
  No auth ; URL safety enforced at the kernel hook (no file://, no
  localhost, no RFC1918).
- `framework/providers/duckduckgo.hecksagon` — DuckDuckGo HTML-lite
  search (no API key required). Documents the response-parsing
  contract.

### Tools.hecksagon bindings
Two new `adapter :web_tool` rows :
```
adapter :web_tool, command: "Tools.WebFetch",  tool: :web_fetch,  result_into: "Tools.RecordResult"
adapter :web_tool, command: "Tools.WebSearch", tool: :web_search, result_into: "Tools.RecordResult"
```

### Kernel hook
- `rust/src/runtime/web_tool_dispatcher.rs` — two native primitives :
  - `run_web_fetch(attrs)` — `curl -sL <url>` ; HTTP status captured
    as `exit_code` ; body capped at 100 KB ; URL safety rejects
    `file://`, `localhost`, loopback, RFC1918, link-local before
    network call.
  - `run_web_search(attrs)` — `curl` against DuckDuckGo HTML-lite ;
    parse top-N result blocks (title, url, snippet) ; format as
    plain text ; cap at 100 KB.
  - Exposes `lookup_hook(behavior_name)` returning a `WebToolHook`
    function pointer + `WEB_TOOL_BEHAVIOR_NAMES` const slice — the
    integration shape for i557's `FrameworkRegistry` to consume at
    boot without this module having to depend on i557's not-yet-
    merged types.
- `rust/src/runtime/mod.rs` — registers `pub mod web_tool_dispatcher;`.
  **No edits to `Runtime::dispatch` body.** No hardcoded
  `resolve_web_tool_adapters` call. The dispatcher sits behind the
  registry boundary that i557 is building.

## Dependency on i557 (in flight)

i557 is building `rust/src/runtime/framework_registry.rs` — the
typed runtime registry that walks `adapter_families/*` and
`behavior_kinds/*` at boot, wires kernel hooks by behavior name, and
consults the registry in `Runtime::dispatch` (retiring the hardcoded
`:claude_tool` shortcut).

At the time of this push, i557's branch
(`worktree-agent-ab64b35ac491abb17`) ships the orphan-module
scaffolding for `framework_registry.rs` but has **not yet wired the
registry into the dispatch path**. The current i557 surface is the
type-only scaffold ; the live registration step is still pending on
that branch.

i569's response : ship the dispatcher behind the registry boundary,
do not modify `Runtime::dispatch`, expose `lookup_hook` +
`WEB_TOOL_BEHAVIOR_NAMES` for i557 to consume. When both land,
`Tools.WebFetch` / `Tools.WebSearch` auto-dispatch through the
registry to `web_tool_dispatcher`.

If i557 lands first : a small follow-up on this card calls
`registry.register_hook("perform_web_fetch", ...)` +
`registry.register_hook("perform_web_search", ...)` from the
registry's seed function. The closures already exist
(`perform_web_fetch_hook` + `perform_web_search_hook` in
`web_tool_dispatcher.rs`).

If i569 lands first (this card) : kernel hook sits unused until
i557 merges. The bluebooks are validated structurally NOW ; live
dispatch waits.
