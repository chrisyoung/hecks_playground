# i594 — Bluebook-driven kernel hook registration

## The gap that surfaced

While landing i593 (`:mcp` adapter family), I conceived two bluebooks :

- `aggregates/framework/adapter_families/mcp.hecksagon` — declares the family with `behavior :invoke_mcp_tool`.
- `aggregates/framework/behavior_kinds/invoke_mcp_tool.hecksagon` — declares the contract.

And one Rust file :

- `rust/src/runtime/mcp_dispatcher/mod.rs` — implements the impure transport (stdio MCP protocol dance).

The bluebooks parse cleanly, the kernel hook compiles, daemons still alive. **But the adapter doesn't actually fire** because `framework_registry::seed_kernel_hooks` hardcodes the name → function mapping :

```rust
fn seed_kernel_hooks(registry: &mut FrameworkRegistry) {
    registry.register_hook(
        "invoke_claude_tool",
        claude_tool_dispatcher::dispatch_via_registry,
    );
    // To make :mcp work, the line below would need to land here.
    // But that trips the macrophage on framework_registry.rs.
    // registry.register_hook(
    //     "invoke_mcp_tool",
    //     mcp_dispatcher::dispatch_via_registry,
    // );
}
```

The macrophage blocked the edit (the file has no `[antibody-exempt: …]` marker yet). Chris chose to revert the registration line and find a non-Rust path — i.e. close the loop so adding a family is pure-bluebook.

## What the bluebook-driven shape might look like

Several candidate paths, each with its own trade-offs :

### 1. Static registration via build-time generation

The `framework_registry` walks `aggregates/framework/adapter_families/*.hecksagon` at runtime boot, reads each family's `behavior :name`, and looks up an implementation via a sibling registry. Implementations register themselves through `inventory` (or similar linkage-time discovery crate) — so adding a family is :

```rust
// rust/src/runtime/mcp_dispatcher/mod.rs
inventory::submit!(KernelHookEntry {
    behavior_name: "invoke_mcp_tool",
    handler: dispatch_via_registry,
});
```

`framework_registry` reads `inventory::iter::<KernelHookEntry>()` and seeds the registry. No edits to `framework_registry.rs` per new family. Trades : adds a dependency, requires re-thinking how `seed_kernel_hooks` selects which implementations to load.

### 2. Convention-based module discovery

Each adapter family lives in a fixed module location (`runtime/<family>_dispatcher/mod.rs`). At build time, a build.rs script walks `framework/adapter_families/*.hecksagon`, reads the names, and generates a `seed_kernel_hooks_generated.rs` that the registry includes. The build artefact becomes part of the bluebook contract.

### 3. Generic registry table in a .behaviors file

`framework/adapter_families/mcp.behaviors` declares the implementation pointer as a behavior parameter the runtime knows how to read :

```
behavior :invoke_mcp_tool, rust_module: "mcp_dispatcher"
```

A loader Rust file reads the table, looks up `<module>::dispatch_via_registry` via a fixed convention. Implementation modules just need to exist ; no edits to a central registry file.

### 4. Antibody-exempt the registry once, accept that the file IS the registry

Add the `[antibody-exempt: …]` marker to `framework_registry.rs` with a rationale ("kernel-floor framework hook registry ; new entries are part of the kernel surface, retires when adapter-family loading is fully data-driven"). Future families add their line ; the marker accepts that this file's churn is structural. Cheapest path, but accepts that the bluebook-first principle has a small kernel-floor exception.

## What landed despite the gap

Even without the registration, the work parks usefully :

- `mcp.hecksagon` + `invoke_mcp_tool.hecksagon` are valid declarative data. When the registration question is answered, they don't change.
- `mcp_dispatcher/mod.rs` is ~300 LoC of working MCP stdio client (initialize → tools/call → close, JSON-RPC parsing, `{attr}` placeholder substitution). It compiles, has no warnings, and is callable from anywhere in the runtime.
- `runtime/mod.rs` declares the module (`pub mod mcp_dispatcher;`).

So the day registration lands, :mcp works end-to-end with no further Rust additions.

## Acceptance

- Adding a new adapter family is a pure-bluebook operation : write `<family>.hecksagon` + `<behavior_kind>.hecksagon` + a Rust implementation module. **No edits to `framework_registry.rs`**.
- The macrophage stays silent on family additions.
- Existing `invoke_claude_tool` registration migrates to the new mechanism with no behavior change.
- :mcp adapter actually fires end-to-end (the test : a SessionStart hook dispatches Session.Begin through the MCP universal door and the wake review composes).
