# i595 — One macrophage per enforcement (not a singleton)

## Where it came from

Chris, mid-i590-Item-#3 cleanup :

> "It would be nice if we didn't have just one macrophage — we should have a macrophage named after each enforcement."

The trigger : surveying the macrophage stderr label drama (hecks-life staleness → enforcer→macrophage rename → [macrophage] vs [enforcer]). The single `Macrophage` aggregate currently does everything :

- Counts bluebook_edits / imperative_edits / exempted_edits / fixtures_runtime_violations
- Holds last_complaint + last_complaint_at (one slot for any rule)
- Branches internally on edit type to decide which rule applies

That's a confessional shape — the aggregate IS the discipline, but its name is generic. *"The macrophage flagged something"* doesn't tell you which rule fired ; you have to read the complaint text to know whether bluebook-first, antibody-exempt, fixtures-runtime, or something-else was triggered.

## What "one per enforcement" looks like

Each rule becomes its own aggregate, named after what it enforces. The macrophage *family* is then the set of aggregates carrying the discipline.

| Today (single Macrophage)                | Decomposed (per-rule macrophages)         |
|-------------------------------------------|--------------------------------------------|
| `Macrophage.bluebook_edits`               | `BluebookFirstMacrophage.bluebook_edits`   |
| `Macrophage.imperative_edits`             | `BluebookFirstMacrophage.imperative_edits` |
| `Macrophage.exempted_edits`               | `BluebookFirstMacrophage.exempted_edits`   |
| `Macrophage.fixtures_runtime_violations`  | `FixturesRuntimeMacrophage.violations`     |
| `Macrophage.last_complaint`               | `<Rule>Macrophage.last_complaint`          |

Candidate per-rule macrophages (the ones I can name today) :

1. **`BluebookFirstMacrophage`** — the original. Flags imperative edits without an antibody-exempt marker.
2. **`FixturesRuntimeMacrophage`** — the fixtures-runtime check (already a separate counter on today's singleton — the decomposition makes it visible at aggregate level).
3. **`AntibodyExemptionMacrophage`** — checks that exemption markers are well-formed + name a real concern, not pre-emptive blanket markers.
4. **`WarningsMacrophage`** — enforces "warnings are errors waiting to happen". Currently informal ; would become structural.
5. **`LinearReferenceMacrophage`** — flags references to retired tools (Linear is the canonical example). Currently a CLAUDE.md note ; would become an enforced rule.
6. **`LineCountMacrophage`** — the 200-line file limit. Currently a pre-commit hook ; would become a macrophage with audit trail.
7. **`TestSpeedMacrophage`** — the "tests must run under 1 second" rule. Currently a hook ; same migration.

Each holds its own counts + last_complaint + last_complaint_at. Adding a new rule = new aggregate, not a branch inside an existing one.

## Surface implications

- **Hook side** : `bin/macrophage-hook` currently shells `storehouse macrophage` (one verb). Decomposed shape : the hook either calls a router (`storehouse macrophages run-all`) or calls each macrophage explicitly and aggregates the complaints. Probably the router is cleaner.
- **State side** : each macrophage's state lives in its own `.heki` instead of all rules sharing `macrophage.heki`. Audit trail is per-rule.
- **Statusline side** : per-rule counters can surface to the statusline ("3 bluebook violations this session, 1 line-count violation"). Today's singleton loses that resolution.
- **CLAUDE.md / Standards** : each rule is a Standard ; each Standard maps to a macrophage. The discipline graph becomes legible.

## What does NOT change

- The hook surface (PostToolUse + stdin payload) stays the same.
- The "let the hook block ; report ; the human decides" standard stays.
- Antibody-exempt markers continue to work as today.
- The complaint text shape stays — "Edit wrote .rs (path). The <Macrophage> expected ...".

## Migration path

1. Keep the current `Macrophage` aggregate alive as a thin router / facade.
2. Conceive the first per-rule macrophage (`BluebookFirstMacrophage`) ; move the bluebook_edits / imperative_edits / exempted_edits / last_complaint fields to it ; the singleton macrophage forwards to it.
3. Conceive the second (`FixturesRuntimeMacrophage`) — same shape, fixtures_runtime_violations moves.
4. Retire the singleton once both per-rule aggregates are live and the hook calls a router.
5. Add 3-7 above one at a time as each rule's enforcement turns mechanical.

## Acceptance

- Every active rule has a dedicated `<Rule>Macrophage` aggregate.
- The complaint text says "The <Rule>Macrophage expected ..." with the rule's name woven in (not the generic word "macrophage").
- Adding a new enforcement = writing a new bluebook + behaviors, no edit to a router-branch.
- Statusline can show per-rule counters when relevant.
