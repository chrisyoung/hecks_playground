# i600 — Cross-aggregate query DSL (where / order_by / joins)

## Where it came from

Tonight's pigeoncoop audit surfaced that every `query` block in every
bluebook uses prose `description "..."` — including queries that
describe joins, filters, and orderings across aggregates :

  - Shoutout.AboutMyStudentThisYear : describes joins of Shoutout +
    Parent.students + AcademicCalendar.school_year
  - Notification.UnifiedInbox : describes pulling from Announcement /
    Shoutout / Message / Event / Newsletter and resolving snippets
  - Payments::Ledger.MyAnnualPayments : describes a CQRS read-model
    query over Donation + MerchPurchase + TuitionPayment

These are SPECS for queries, not working queries. The runtime can't
execute them. They describe what should happen ; nothing makes them
happen.

## What the DSL would look like

A real `where` / `order_by` / `joins` form inside `query` blocks :

    query "AboutMyStudentThisYear" do
      where  recipient: in(Parent.students.for(self))
      where  status: "approved"
      where  created_at: in(SchoolYear.current.range)
      order  created_at: :desc
    end

The runtime would compile this to a heki query plan (or whatever
substrate the query layer eventually has). Today the runtime has no
query plan ; it just has aggregate-state reads via storehouse.

## Why it matters

The Party-Role pattern only works structurally — to actually serve
the parent-dashboard / unified-inbox / annual-payments queries the
inbox stories demand, the DSL has to evolve past prose.

## Scope

This is framework-level work, not pigeoncoop-specific. Touches the
bluebook parser, the validator, the runtime's query layer, and every
existing prose query in every bluebook.
