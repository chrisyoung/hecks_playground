# i601 — Cascade failure / retry / ordering story

## Where it came from

Tonight's pigeoncoop audit surfaced that cascade policies are silent
about failure :

    policy "NotifyOnAnnouncementSent" do
      on      "AnnouncementSent"
      trigger "SendNotification"
      map     recipient: :recipient, source_kind: "announcement", ...
    end

What happens if `SendNotification` fails? What if the announcement
fan-outs to 200 recipients and 8 silently drop? What if two cascades
fire in racing order and the second depends on the first having
completed?

The bluebook captures the WHAT but not the HOW-IT-RECOVERS. In a real
school setting, a parent missing a critical absence notification
because the chain quietly broke is a real, costly failure mode.

## What's needed

1. **Per-policy retry contract** : exponential backoff, max attempts,
   dead-letter destination.
2. **Per-policy ordering guarantees** : strict ordering vs. eventual,
   single dispatch vs. parallel fan-out.
3. **Per-policy audit trail** : which cascades fired, which succeeded,
   which entered dead-letter, when.
4. **Per-policy idempotency contract** : safe to retry vs. side-
   effecting (don't double-charge a parent for the same tuition).

## What this is not

This isn't about replacing the cascade pattern — it's about giving it
a failure-handling surface. The existing declarative shape stays.

## Scope

Framework-level (runtime + bluebook DSL). Affects every cascade policy
in every bluebook : pigeoncoop, calendars, payments, the discipline
macrophages, the framework cascades.
