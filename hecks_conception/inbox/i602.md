# i602 — Card as the lock for client-approved features

## Where it came from

Chris, after tonight's pigeoncoop audit + reverted ClientSignOffMacrophage :

> "We have a couple of things now that the cards will need — we will
> have to mark cards as being modeled properly and then they have to
> be designed properly and then they will need client sign off. Also !
> Yesterday we were trying to figure out how to have a macrophage
> protect from deleting. We did it by assigning some sort of id to
> the card to lock it. Now that we will have client sign off on the
> cards — that's how we can mark a feature locked in the software too !
> It can reference the client sign off and the commit. We'd have to
> open a new card to make changes after that."

The earlier `ClientSignOffMacrophage` (conceived + reverted tonight)
tracked files and tags as the locking mechanism. **The card-as-lock
approach is more honest** : the card itself moves through states ;
each transition stamps a commit ; the signed-off state is the lock.

## Card lifecycle

```
queued → modeled → designed → signed_off → locked → (superseded)
```

- **queued** (today's default) : the story is captured.
- **modeled** : the bluebook captures the aggregate / commands / queries
  the story requires. Stamped with `modeled_at` + `modeled_commit`.
- **designed** : behaviors + fixtures specify the testable shape.
  Stamped with `designed_at` + `designed_commit`.
- **signed_off** : the client has confirmed the feature does what they
  expected. Stamped with `signoff_at`, `signoff_by`, `signoff_commit`,
  `signoff_scope` (list of path patterns the signoff covers).
- **locked** (auto after signoff) : the feature's canonical state.
  Code touching its scope without a new card → macrophage complains.
- **superseded** : when a new card opens to change a locked feature,
  the old card moves here with `superseded_by: <new ref>`.

## Frontmatter additions (Inbox aggregate)

```yaml
status: locked
modeled_at: 2026-05-13
modeled_commit: abc123
designed_at: 2026-05-13
designed_commit: def456
signoff_at: 2026-05-13
signoff_by: 'Joey Bellus'
signoff_commit: ghi789
signoff_scope: ['site/index.html', 'site/recovery.html']
locked_at: 2026-05-13
superseded_by: ~
```

## The macrophage : CardLockMacrophage

8th per-rule macrophage in the i595 family. Reads cards in `locked`
status. On every edit, asks : "does this touch any path in any locked
card's signoff_scope ?" If yes, complains : "this change touches scope
locked by <card-ref> (signed off by <client> at <signoff_commit>).
Open a new card, OR add an antibody-style exemption marker."

This IS the ClientSignOffMacrophage we conceived + reverted tonight,
reframed correctly. State lives ON THE CARD (where the discipline
naturally lives), not in a separate macrophage aggregate. The
macrophage just reads cards. Single source of truth.

## What this unifies

- The Inbox aggregate gets a real lifecycle (state machine).
- Sign-off becomes a domain event, not a git ceremony.
- The reverted ClientSignOffMacrophage returns in a smaller form.
- The change-via-new-card pattern enforces honesty : changes to
  signed-off features REQUIRE a new card with a new signoff. The
  audit trail is the inbox itself.
- Tonight's regression-class (we stripped Joey's recovery nav link)
  becomes structurally impossible — the macrophage would refuse
  the edit, OR demand an exemption marker, OR ask for a new card.
