# i603 — Mechanically lock every tool call to storehouse

## Where it came from

Chris, 2026-05-14 :

> "We need a way to mechanically lock you to using the storehouse for
> all calls."

The trigger : tonight I called the Gmail MCP tools directly (`mcp__claude_ai_Gmail__search_threads`, `get_thread`, `create_draft`) without routing through storehouse. The bypass happened because (a) there's no `EmailTool` aggregate in `Tools.bluebook` to dispatch into, and (b) no harness-level enforcement that catches the bypass. Trust-the-AI-to-remember is not a substrate.

## What the mechanical lock looks like

Three coupled pieces. None of them alone is sufficient.

### 1. PreToolUse hook in `.claude/settings.json` (the auto-router)

Matched against every native tool name. Reads the tool-call JSON from stdin, maps `tool_name` → `Tools::<Cat>.<Method>`, dispatches via storehouse BEFORE the native handler fires. This piece is already filed as **i599** ; that card is the cornerstone of this lock.

### 2. Complete `Tools.bluebook` coverage of every native tool category

The PreToolUse hook can only auto-route to an aggregate that exists. Today `Tools.bluebook` has 18 aggregates covering shell, file, search, web, task, sidequest, wakeup, cron, monitor, notify, plan, worktree, ask, skill, lsp, meta, remote-trigger, and cascade. **Missing** :

- `EmailTool` (Gmail family : Search / GetThread / CreateDraft / ListDrafts / ListLabels / etc.) — the gap that surfaced tonight.
- Possibly others as Claude Code's tool surface grows. The audit needs to be ongoing : whenever Claude Code's deferred-tool catalog adds a new family, `Tools.bluebook` should add a matching aggregate.

Each new aggregate gets the standard shape : state carries identifier + summary attributes ; large payloads ride in the event ; the `:claude_tool` adapter family wires the native invocation.

### 3. The lock's failure mode — what happens when there's no matching aggregate ?

Three options ranked from soft to hard :

- **Soft** : the hook surfaces a complaint to additionalContext ("tool call X has no Tools.bluebook aggregate ; routing as raw") but the native call proceeds. Audit trail exists ; discipline is advisory.
- **Medium** : the hook records the bypass to `.last_dispatch` with a flag, so the statusline visibly shows "unrouted: X" until Tools.bluebook catches up. Visible drift pressure without blocking work.
- **Hard** : the hook BLOCKS the native call until a Tools.bluebook aggregate exists OR an antibody-style exemption marker is set. Maximum discipline ; risk of paralyzing legitimate work in the gap window when Claude Code adds new tools.

Chris's call which level lands first. The PreToolUse infrastructure supports all three ; the choice is per-tool-family policy.

## Why behavioral lock isn't enough

Tonight I made 6+ Gmail tool calls without routing. Each one was a small lapse. The pattern shows that even with the discipline named in the system prompt + tonight's earlier diagnostic, behavioral memory doesn't scale. Mechanical enforcement is the only durable answer — every drift, even one this small, compounds.

## Acceptance

- i599's PreToolUse hook is live.
- `Tools.bluebook` has an `EmailTool` aggregate covering Gmail's MCP surface.
- A native Gmail tool call (e.g., `mcp__claude_ai_Gmail__search_threads`) routes through storehouse, lands in `.last_dispatch`, surfaces on the statusline, and either succeeds via the dispatch or surfaces the appropriate failure mode for level chosen.
- Audit of Claude Code's full deferred-tool catalog vs `Tools.bluebook` coverage — every native family has a counterpart aggregate (or is explicitly excluded with a documented reason).
