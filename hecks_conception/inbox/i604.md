# i604 — Command-bus version-aliases : rename-safe API surface

## Where it came from

Chris, 2026-05-14, surveying tonight's macrophage consolidation + rename :

> "Right now we are dynamically building commands right? I'm wondering
> about use cases — if we change the commands or move them to a different
> aggregate, clients will break."

> "The command bus could look up commands if you pass a command — we
> could keep aliases on the command bus. We could use versioning to
> store the aliases."

Tonight we (a) consolidated 9 macrophage bluebooks into one `Macrophage::*` domain and (b) renamed 8 per-rule aggregates to drop the `Macrophage` suffix. Both are FQN-breaking for anyone pinned to the old names. Today's standard (`No backward compatibility until first user`) makes this OK for now, but the moment any external client — our own hooks, scripts, downstream services — pins to a specific FQN, every rename becomes a contract break.

## The mechanism

**Bus walks version history to resolve dispatches.**

Each `Hecks.bluebook "X", version: "YYYY.MM.DD.N"` declaration already carries a version. Each version-bump that includes a rename or move records the migration : `BluebookFirstMacrophage → BluebookFirst` (rename), `Tools::EmailTool moved from Communications::EmailTool` (move), etc.

Dispatch flow when a command comes in :

  1. Bus receives FQN, e.g., `Macrophage::BluebookFirstMacrophage.RecordImperativeEdit`
  2. Bus tries direct resolution in the current bluebook version : not found
  3. Bus walks version history of the `Macrophage` bluebook : finds `BluebookFirstMacrophage → BluebookFirst` rename at version 2026.05.14.1
  4. Bus rewrites the dispatch to the current FQN `Macrophage::BluebookFirst.RecordImperativeEdit`
  5. Bus emits a deprecation event (cascade) carrying : original FQN, resolved FQN, version-where-renamed
  6. Bus dispatches the resolved FQN normally

The deprecation events can be aggregated for analytics : *"in the last week, 47 calls hit `BluebookFirstMacrophage` (deprecated)"*. When the count drops to zero in a configured window, the migration entry can be retired.

## Where the migration history lives

Proposed : `migrations:` section in the bluebook header, declarative.

```ruby
Hecks.bluebook "Macrophage", version: "2026.05.14.2" do
  migrations do
    rename "BluebookFirstMacrophage" => "BluebookFirst", at: "2026.05.14.2"
    rename "FixturesRuntimeMacrophage" => "FixturesRuntime", at: "2026.05.14.2"
    rename "AntibodyExemptionMacrophage" => "AntibodyExemption", at: "2026.05.14.2"
    rename "WarningsMacrophage" => "Warnings", at: "2026.05.14.2"
    rename "LinearReferenceMacrophage" => "LinearReference", at: "2026.05.14.2"
    rename "LineCountMacrophage" => "LineCount", at: "2026.05.14.2"
    rename "TestSpeedMacrophage" => "TestSpeed", at: "2026.05.14.2"
    rename "CardLockMacrophage" => "CardLock", at: "2026.05.14.2"
  end
  aggregate "Macrophage" do ... end
  aggregate "BluebookFirst" do ... end
  # ...
end
```

Future migrations can also record :

  - `move "Person" => "Identity::Person", at: "..."` — cross-domain move
  - `command_rename "OldCmd" => "NewCmd", on: "Aggregate", at: "..."`
  - `command_arg_rename "old_attr" => "new_attr", on: "Aggregate.Cmd", at: "..."`
  - `deprecate "OldCmd", at: "...", removal: "..."` — announces retirement plan

## Why version-stored vs. per-aggregate aliases

- Bluebook stays clean — no `aliases: [...]` clutter on each aggregate
- Single mechanism at the bus layer (one query path resolves both current and historical names)
- Bluebook DIFF between versions is the source of truth for what migrated
- Pattern matches protobuf field-number history, kafka schema registries, GraphQL's `@deprecated` directive

## DDD framing

Evans' Open Host Service / Published Language pattern (Blue Book Ch. 14) :
the FQN dispatch surface IS the Published Language. Internal model can
evolve freely as long as the Published Language stays stable. Bus-alias
mechanism is the implementation of that stability for our specific
dispatch model.

Additional support :
- Vernon's event upcasters (Implementing DDD) — same idea for events
- Greg Young's CQRS command versioning — same idea for commands
- Meyer's Design-by-Contract substitutability rules — formalize what
  the alias mechanism must preserve (preconditions can't strengthen,
  postconditions can't weaken when an old FQN is resolved to a new one)

## Acceptance

- Bluebook DSL parses a `migrations do ... end` block at the bluebook header level (after `Hecks.bluebook "X", version: "..."`)
- Storehouse command bus, on dispatch failure (FQN not found in current state), walks the migration history for that bluebook and attempts resolution
- Successful resolution dispatches the rewritten FQN AND emits a deprecation cascade event carrying original FQN + resolved FQN + migration entry
- A query (`Bus.DeprecationCounts` or similar) surfaces how often each deprecated FQN is being hit
- Tonight's renames (the 8 in `Macrophage::*`) get retroactive `migrations do ... end` entries so old `BluebookFirstMacrophage` FQNs still resolve
