# i605 — RenameDiscipline macrophage

## Where it came from

Chris, 2026-05-14, after reading i604 (command-bus version-aliases) :

> "Would the renames happen automatically? Do we need a macrophage?"

The i604 mechanism keeps old FQNs working by having the command bus walk a `migrations do ... end` block in the bluebook header. But i604 alone is behavioral — the developer has to remember to add the rename entry. Forget the entry, clients silently break. Exactly the discipline-gap pattern the i595 macrophage family exists to close. RenameDiscipline is the structural counterpart.

## The rule it enforces

For every commit that touches a bluebook file, diff the new version against the previous version. For each **disappeared** aggregate, command, or attribute, the new version's `migrations do ... end` block must carry a covering entry :

  - Aggregate disappeared → `rename "OldAggregate" => "NewAggregate", at: "..."`
  - Command disappeared from an aggregate → `command_rename "OldCmd" => "NewCmd", on: "Aggregate", at: "..."`
  - Attribute disappeared from a command or aggregate → `attr_rename "old" => "new", on: "Aggregate.Cmd", at: "..."`
  - Aggregate moved across bluebooks → `move "Aggregate" => "NewDomain::Aggregate", at: "..."`
  - Aggregate genuinely retired (no successor) → `retire "Aggregate", at: "...", reason: "..."`

If no migration entry exists for a disappearance, the macrophage complains. Standard pattern : "The RenameDiscipline macrophage expected ...". The developer either adds the migration entry, OR adds the antibody-exempt marker explaining why a hard break is acceptable.

## Bonus : heuristic candidate detection

When the macrophage detects a disappearance, it can ALSO scan the new version for likely successors :

  - Levenshtein distance below threshold against any new aggregate name
  - Same command-list signature (an aggregate with the same set of command names as the disappeared one is probably the renamed version)
  - Shared identified_by + same VO declarations

The complaint becomes :

  > "The RenameDiscipline macrophage expected a migration entry for the
  > disappeared aggregate `BluebookFirstMacrophage`. A likely successor
  > is `BluebookFirst` (Levenshtein 11 ; same command list). If this is
  > a rename, add :
  >
  >   rename \"BluebookFirstMacrophage\" => \"BluebookFirst\", at: \"2026.05.14.2\"
  >
  > If it's a genuine retirement, add :
  >
  >   retire \"BluebookFirstMacrophage\", at: \"...\", reason: \"...\"\"

Friendly rather than just punitive. The macrophage does the boring diff work ; the developer confirms the intent.

## Where it lives in the Macrophage family

9th per-rule sibling under `Macrophage::*` (after tonight's suffix-drop rename lands, the FQN reads `Macrophage::RenameDiscipline.RecordCheck` etc.). Matches the existing pattern : `Macrophage::BluebookFirst`, `Macrophage::FixturesRuntime`, `Macrophage::AntibodyExemption`, `Macrophage::Warnings`, `Macrophage::LinearReference`, `Macrophage::LineCount`, `Macrophage::TestSpeed`, `Macrophage::CardLock`, **`Macrophage::RenameDiscipline`**.

## Hook integration

Unlike the other per-rule macrophages (which fire on every Edit / Write / Bash via PostToolUse), RenameDiscipline fires specifically on **pre-commit** — it needs the git pre-image to diff against. Could live as a pre-commit gate sibling to the existing parity / lifecycle / behaviors gates (Gates 1–9), OR fire from the macrophage-hook with a special-case pre-image lookup.

Likely shape : new pre-commit gate `Gate 10 : rename discipline` that runs `storehouse macrophage rename-check` against staged bluebook diffs.

## Acceptance

- New aggregate `Macrophage::RenameDiscipline` lives in `macrophage.bluebook`
- Standard macrophage shape : counters, complaint history entity, StartSession / RecordCheck / Complain commands
- Pre-commit gate runs the check on staged bluebook diffs ; complains when migration entries are missing
- Heuristic candidate-detection surfaces the likely rename in the complaint text
- Antibody-exempt markers work for legitimate hard-break cases (the "no backward compat until first user" window)
