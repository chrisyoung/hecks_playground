# i608 — EmailTool : `:claude_tool` adapter wiring for Gmail

## Where it came from

Tonight Chris said : *"ALL of your tool calls should go through the StoreHouse."* The concrete bypass was Gmail — I'd been calling `mcp__claude_ai_Gmail__search_threads` and `mcp__claude_ai_Gmail__get_thread` directly, never touching the bus. The bluebook side just landed (`EmailTool` aggregate, four commands : SearchThreads, GetThread, CreateDraft, ListDrafts). The runtime side does not yet route the dispatches.

## What's missing

`framework/adapter_families/claude_tool.hecksagon` (and / or the Rust dispatcher in `rust/src/adapters/claude_tool/`) needs four new bindings :

| Command | Native MCP tool | Args mapping |
|---|---|---|
| `EmailTool.SearchThreads` | `mcp__claude_ai_Gmail__search_threads` | `query` → `q`, plus paging |
| `EmailTool.GetThread` | `mcp__claude_ai_Gmail__get_thread` | `thread_id` → `thread_id` |
| `EmailTool.CreateDraft` | `mcp__claude_ai_Gmail__create_draft` | `to` → `to`, `subject` → `subject`, `body` → `body_markdown` |
| `EmailTool.ListDrafts` | `mcp__claude_ai_Gmail__list_drafts` | (no args) |

The adapter chains the captured output through `result_into: Cascade.RecordResult` so the outcome becomes a first-class event (same shape as ShellTool / FileTool / SearchTool / WebTool).

## Acceptance

- `storehouse storehouse route 'Tools::EmailTool.SearchThreads' --args '{"id":"…","query":"from:joey is:unread","description":"…"}'` returns the same thread list the native MCP tool would.
- Same for GetThread / CreateDraft / ListDrafts.
- `.last_dispatch` reflects each call and the statusline picks it up.
- `Cascade.RecordResult` fires with the captured Gmail-API response in the event payload.
