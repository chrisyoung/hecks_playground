# i609 — Tools.bluebook : split for cohesion

## Where it came from

Landing EmailTool tonight (+1 aggregate) triggered three validator warnings :

- `domain 'Tools' has 19 aggregates ; review for cohesion (sweet spot is 3-6 ; past 7 most domains read as two)`
- `domain 'Tools' has 19 aggregates ; multi-domain split likely improves cohesion (two ubiquitous languages are usually being merged at this size)`
- `bluebook 'Tools' has 281 structural units (aggregates + attributes + commands + policies + transitions) — is this really one concern, or is it two ?`

EmailTool didn't cause the problem ; it surfaced it. The bluebook has been growing under one roof every time a new tool family lands.

## What the natural split is

Reading the current 19 aggregates, they fall into five clean groups :

1. **DeveloperTools** — ShellTool, FileTool, SearchTool, WebTool, LspTool
2. **CommsTools** — EmailTool, NotifyTool, AskTool
3. **AgentOrchestration** — TaskTool, Sidequest, WakeupTool, CronTool, MonitorTool, WorktreeTool
4. **SurfaceTools** — PlanTool, SkillTool, MetaTool, RemoteTriggerTool
5. **Cascade** — the kernel-hook outcome chain (stays cross-cutting, possibly its own one-aggregate bluebook)

Each sub-bluebook would be 3-6 aggregates — right inside the cohesion sweet spot.

## Why not tonight

The split is an architectural conversation worth having properly :

- FQN addresses change : `Tools::EmailTool.SearchThreads` → `CommsTools::EmailTool.SearchThreads`. Every dispatch site has to rename.
- The `:claude_tool` adapter family currently keys off `Tools::*` ; the dispatcher needs to learn the new bluebook names.
- Cross-aggregate references (e.g. Cascade.RecordResult is the chain target for every other tool family) need to be checked across the split.
- A bluebook RenameDiscipline macrophage (i605) would make this a one-pass renaming op ; without it, the rename is manual.

This card is the structural seed ; the implementation reaches across i604 (version-aliases on the command bus) and i605 (RenameDiscipline macrophage).

## Acceptance

- Tools.bluebook becomes 5 smaller bluebooks named per the groups above.
- Each sub-bluebook validates without cohesion warnings.
- Every dispatch site in `aggregates/`, `runtime/`, `tooling/` updates to the new FQN.
- `:claude_tool` adapter family routes the new FQNs correctly.
- The cascade-target rewriting in each tool aggregate's `result_into:` block follows the rename.

## Related

- i604 — command-bus version-aliases (would let the rename land without breaking outstanding dispatches mid-flight).
- i605 — RenameDiscipline macrophage (would catch stale FQN references in `include_str!`, doc comments, etc.).
- i608 — EmailTool adapter wiring (lands in Tools::EmailTool today ; will move to CommsTools::EmailTool after this card).
