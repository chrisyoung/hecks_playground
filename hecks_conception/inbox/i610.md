# i610 — `:gmail` server : harness-MCP bridge

## Where it came from

The i608 sidequest landed adapter wiring for `EmailTool.{SearchThreads,GetThread,CreateDraft,ListDrafts}` on branch `sq/emailtool-adapter-wiring` (commit `5f374352`). Round-trip testing confirmed the bluebook side and the dispatch side : commands enter through `storehouse__dispatch`, IR parses, validator green, all 188 behaviors green, 75 tools.behaviors tests pass.

What does not fire end-to-end is the actual Gmail API call. The agent traced the gap to two pieces of substrate :

1. **i594 (already filed)** — bluebook-driven kernel-hook registration. `framework_registry::seed_kernel_hooks` does not register `invoke_mcp_tool` ; the runtime has no `resolve_mcp_adapters` arm parallel to `resolve_claude_tool_adapters` at `rust/src/runtime/mod.rs:707-845`. So `:mcp` bindings parse cleanly into IR but the dispatcher never auto-fires the MCP-tool invocation.

2. **This card (i610)** — even if i594 lands and `:mcp` adapters fire, the dispatcher needs to know HOW to call the `:gmail` server. Today `rust/src/runtime/mcp_dispatcher/mod.rs:64-75` only registers `:storehouse` (`tooling/storehouse-mcp/src/server.mjs`, a Node stdio process we spawn and own). The Claude harness's Gmail MCP is exposed THROUGH the harness session, not as an independently-spawnable stdio process the runtime can `spawn()`.

The two cards together are what closes the EmailTool round-trip.

## What's missing

A `:gmail` server entry in `resolve_server_spawn` plus the harness-side bridge it talks to. Two implementation shapes :

### Option A : stdio proxy that re-exports harness MCPs

Add a small Node process (`tooling/harness-mcp-proxy/src/server.mjs`) that the Hecks runtime spawns the same way it spawns `:storehouse`. The proxy connects upstream to the Claude harness's MCP socket and re-exports the harness's Gmail tools (search_threads / get_thread / create_draft / list_drafts) as native MCP tools on its own stdio interface. `resolve_server_spawn` gets a `:gmail` (and `:google_drive`, `:computer_use`, `:claude_in_chrome`, ...) arm pointing at this proxy.

Pros : single new component handles every harness-exposed MCP server. Same shape as `:storehouse`.
Cons : depends on the harness exposing its MCP socket externally, which it may not.

### Option B : in-process Rust adapter

The Rust runtime keeps a handle on the harness's MCP session (via the bus's pre/post-tool-use hook surface) and routes `:gmail` dispatches through that handle directly, bypassing stdio spawning entirely.

Pros : no extra process. Direct.
Cons : Rust runtime now knows about harness internals ; coupling.

## Acceptance

- `resolve_server_spawn` knows `:gmail` (and the path-of-least-surprise for similar harness MCPs).
- `storehouse storehouse route 'Tools::EmailTool.SearchThreads' --args '{"id":"…","query":"from:joey is:unread","description":"…"}'` actually returns the Gmail thread list, not just records the dispatch.
- `Cascade.RecordResult` fires with the Gmail API response in the event payload.
- The pattern extends to `:google_drive`, `:computer_use`, `:claude_in_chrome` (and future harness-MCPs) without per-server runtime work.

## Related

- i608 — the EmailTool adapter wiring that surfaced this gap. Bluebook + adapter declarations are clean ; this card is the substrate that lets them execute.
- i594 — the other half of the substrate. Both i594 and i610 are required for the EmailTool round-trip to fire end-to-end.
- i599 — PreToolUse auto-route hook. Once i594 + i610 + i599 are all live, the discipline (every tool call through storehouse) is mechanized rather than behavioral.
- The `sq/emailtool-adapter-wiring` branch sits clean awaiting review ; it doesn't depend on this card landing first, but its round-trip is half-bound until this lands.
