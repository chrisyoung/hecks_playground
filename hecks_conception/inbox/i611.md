# i611 — Identity overhaul : natural keys, no synthetic ids

## Where it came from

Chris, 2026-05-14, after the macrophage consolidation + the Tools split conversation :

> "identity works like this: identified_by: should be a field or list of fields that doesn't change for the entity. Singletons should just be a different type of adapter. so we don't have to overload identified_by. All entities should have identified_by. It should never be a uuid. Entities, by definition have fields that do not change. This solves the parent child identity stuff and completely removes the concept of an id. Id after this will be derived through identified_by which will concatenate its fields. For global ids - aggregate heads - we can append a uuid. otherwise entities inside of aggregates should concatenate their parent's ids. Value object ids are the full value, field, concatenated."

> "well need a new macrophage to enforce this"

Followed, same session, by a softening clarification on the "must have" reading :

> "hmmm. I think you can use uuids as the default then. If we don't supply identified_by"

This shifts the strict position slightly. See the dedicated section below — **"UUID as default when identified_by is absent"** — for the refined interpretation.

## Why this is right

Eric Evans, *Domain-Driven Design* Chapter 5 : "An entity has a thread of continuity. Its defining characteristic is identity rather than the attributes of the moment." Identity is therefore something the domain knows — a name, a slug, a date-coded reference — not something the database mints. The synthetic `:id` column is a persistence concern that has leaked upward into the domain language ; in an event-sourced system the leak gets worse, because the synthetic id ends up serialized into every event payload and every query parameter.

Vaughn Vernon, *Implementing Domain-Driven Design* Rule 2 : "Reference Other Aggregates by Identity." When the identity IS the natural key, every cross-aggregate reference carries its own context — `Person(identity: "alice")` is self-describing in a way `Person(id: "01ARZ3NDEKTSV4RRFFQ69G5FAV")` never is. Replaying an event log a year later, the natural key still resolves ; the ULID does not.

Surrogate ids in event-sourced systems specifically cost :

- Every event carries an opaque token. Logs become unreadable without a join.
- Test fixtures must invent / freeze ids that have no domain meaning, polluting both setup and assertions.
- Re-importing an aggregate from one store to another either preserves the surrogate (defeating fresh-start guarantees) or rewrites every reference (defeating event-log immutability).
- The bluebook's `identified_by :id` lies — `:id` is not a field of the domain, it is a slot the persistence layer fills. The bluebook should not be lying.

Chris's correction is a return to the contract : the bluebook names the actual identity, the runtime derives an addressable form, and persistence is the runtime's problem (locked principle 3, 2026-05-12 : "domain doesn't know it hibernates").

## The six rules

### 1. `identified_by:` lists natural-key fields only

Never `:id`. Never a synthetic UUID/ULID attribute declared in the bluebook. The fields named are real domain attributes whose values do not change over the entity's lifetime. The list can be one field or many — `identified_by :identity`, `identified_by [:school_year, :student_identity]`, `identified_by :iso_code`.

Good aggregates should declare `identified_by` ; it is not strictly required (the runtime defaults to a UUID when absent). See **"UUID as default when identified_by is absent"** below.

Test : if a human can rename / re-mint the attribute without changing what the entity *is*, that attribute is not part of the identity.

### 2. No `attribute :id, Id` declarations

The concept of "id" disappears as a bluebook field. Every aggregate / entity gets its addressable form by concatenating its `identified_by` field values at runtime. The runtime is responsible for the encoding (e.g. `Person:alice` for a single-field identity, `Ticket:event-2026-spring|alice` for a multi-field one) — that string IS the id ; the bluebook does not name it.

Consequence : the `value_object "Id"` block also disappears. There is no Id type ; identities are typed by their constituent VOs (Identity, ThreadId, ToolName, etc.) which already carry the domain's meaning.

### 3. Aggregate roots that need global addressability append a ULID suffix

For roots whose natural-key fields don't disambiguate sufficiently (e.g. `ShellTool` invocations — two `Bash` runs at the same second with the same command shouldn't collide), a synthetic ULID is appended *after* the natural-key concatenation. This is the ONE place a synthetic disambiguator lives — and it is explicitly a *suffix*, not the identity itself.

Proposed DSL :

```ruby
aggregate "ShellTool" do
  identified_by :shell_command, suffix: :ulid
  attribute :shell_command, ShellCommand
  attribute :description, Description
end
```

The suffix is declarative, named (`:ulid` means "append a ULID minted at dispatch"), and visible at the identity site so a reader knows the addressing scheme without spelunking through the runtime. Alternative suffix kinds the runtime could later support : `:timestamp`, `:dispatch_seq`, `:content_hash`. Today only `:ulid` lands.

### 4. Entities inside an aggregate concatenate the parent's id

An entity declared inside an aggregate inherits the parent's addressing form. The bluebook declares only the LOCAL part of the entity's identity ; the framework prepends the parent.

```ruby
aggregate "Event" do
  identified_by :title

  entity "Ticket" do
    identified_by :code
    attribute :code, TicketCode
    # ...
  end
end
```

Ticket's runtime address becomes `Event:gala-2026/Ticket:T-001`. Self-ref dispatch (the universal id fallback added in the 2026-05-12 sidequest) accepts both the full form AND the relative form when context is unambiguous.

### 5. Value objects' identity is the full concatenation of their fields

Two VOs with the same field values ARE the same VO (value equality). Conceptually already true ; under this overhaul it becomes the addressing form too. A `PersonName(given: "Ada", family: "Lovelace")` resolves to `PersonName:Ada|Lovelace`. The bluebook declares no `identified_by` on a value_object block ; the framework treats all attributes as the identity.

Consequence : `value_object "Id" do attribute :value, String end` is doubly dead. (a) There is no Id concept anymore, and (b) a single-field VO whose only attribute is `value` would resolve to its own value as identity — which is just the string itself, no wrapper needed.

### 6. Singletons get a dedicated adapter, not an overloaded `identified_by`

Today, singleton aggregates (`Consciousness`, `Macrophage::BluebookFirst`, `Inbox`, etc.) overload `identified_by :name` with a name constant — the name field is structurally an attribute but semantically a placeholder for "there is exactly one of these". That overload buys nothing and obscures the singleton contract.

Proposed : a `:singleton` flag at the aggregate level, OR a `:singleton` adapter family the runtime resolves :

```ruby
aggregate "Consciousness", singleton: true do
  # no identified_by — there is exactly one Consciousness
  attribute :state, State
  attribute :idle_seconds, IdleSeconds
end
```

`identified_by` is freed to always mean "natural-key fields of an instance-bearing entity". Singletons addressable as `Consciousness` (no key — there is only the one). The runtime's persistence adapter for singletons stores at a known path ; no key-resolution table needed.

## UUID as default when identified_by is absent

Chris, 2026-05-14 (same session, follow-up clarification) :

> "hmmm. I think you can use uuids as the default then. If we don't supply identified_by"

This softens the original "all entities should have identified_by" position. The revised reading :

**If `identified_by` is declared** : the strict i611 rules apply in full. Those fields are the natural key ; no surrogate UUID should be mixed in unless `suffix: :ulid` is explicitly requested for disambiguation. The IdentityDiscipline macrophage checks for `attribute :id, Id`, `identified_by :id`, and `value_object "Id"` as violations — these remain hard violations regardless of whether `identified_by` is present.

**If `identified_by` is NOT declared** : the runtime defaults to a UUID. This is the pragmatic fallback for aggregates and entities where no natural key has been thought through. The bluebook does not declare the UUID as an attribute ; it simply has no `identified_by` line. The runtime mints a UUID at first-persist time and uses it transparently.

The "no UUIDs" position is therefore narrower than the original framing suggested : UUIDs as a **bluebook-declared concept** are gone (`attribute :id, Id` + `value_object "Id"` are dead). UUIDs as the **runtime's default-when-absent** are fine and expected.

### When the UUID default is appropriate

- **Ephemeral records** — event payloads, audit log entries, trace spans. Nothing outside the record needs to address this thing by name ; a UUID is the right non-identity.
- **Mint-and-forget records** — a command invocation that produces a result immediately and is never queried by a caller who holds a natural key. The runtime needs SOME address ; UUID is least surprise.
- **Early-draft aggregates** — a bluebook under active design that hasn't settled on its natural key yet. The UUID default lets dispatch work without blocking the design conversation. A macrophage advisory (not a hard violation) can remind the team to come back.
- **Singletons (before i611 phase 1 lands)** — until `singleton: true` is in the parser, existing `identified_by :name` singletons are fine as-is ; after phase 1, they move to the singleton flag rather than to UUID-default (which would be wrong — singletons have no instance-bearing identity at all).

### When the UUID default is NOT appropriate

If a human operator ever needs to locate a specific record by a property they know — "find me the Ticket for Alice at the spring gala" — and the only address is a UUID, then the system has failed to model identity properly. Natural-key `identified_by` exists for those cases. The UUID default is a "you didn't bother to think about it" fallback, not a recommended path.

Good design still names a natural key. The UUID default is the escape hatch, not the destination.

### Macrophage posture

The IdentityDiscipline macrophage checks four hard violations :

- `id_attribute` — `attribute :id, Id` in any bluebook block.
- `identified_by_id` — `identified_by :id` (surrogate, not a natural key).
- `id_value_object` — `value_object "Id"` declarations.
- `dangling_identity` — `identified_by` fields that are not declared as attributes.

It does **not** treat a missing `identified_by` as a violation. The original i611 checks `missing_identity` (aggregate without `identified_by` or `singleton: true`) and `missing_entity_id` (entity without `identified_by`) have been removed — they conflict with the UUID-default fallback Chris confirmed. An aggregate without `identified_by` is not broken ; it has opted into the UUID default. Whether that is wise design is a review concern, not a macrophage concern.

## Concrete examples

### Tools::ShellTool (`aggregates/framework/tools/tools.bluebook:71-114`)

**Before** (today) :

```ruby
aggregate "ShellTool" do
  identified_by :id
  attribute :id, Id
  attribute :shell_command, ShellCommand
  attribute :description, Description

  value_object "Id" do
    attribute :value, String
  end

  value_object "ShellCommand" do
    attribute :value, String
  end

  command "Bash" do
    attribute :id, Id
    attribute :shell_command, ShellCommand
    attribute :description, Description
    emits "BashRan"
  end
end
```

**After** (post-i611) :

```ruby
aggregate "ShellTool" do
  identified_by :shell_command, suffix: :ulid
  attribute :shell_command, ShellCommand
  attribute :description, Description

  value_object "ShellCommand" do
    attribute :value, String
  end

  command "Bash" do
    attribute :shell_command, ShellCommand
    attribute :description, Description
    emits "BashRan"
  end
end
```

Runtime address : `ShellTool:echo ok|01HXY9...`. The `shell_command` IS the entity's natural surface ; the ULID is the disambiguator for concurrent invocations of the same command. Notice the command no longer takes `:id` — the harness no longer mints one as a separate concern ; the runtime mints the ULID when persisting.

### Tools::FileTool (`aggregates/framework/tools/tools.bluebook:117-282`)

**Before** :

```ruby
aggregate "FileTool" do
  identified_by :id
  attribute :id, Id
  attribute :file_path, FilePath
  attribute :description, Description

  value_object "Id" do
    attribute :value, String
  end

  command "Read" do
    attribute :id, Id
    attribute :file_path, FilePath
    # ...
  end
end
```

**After** :

```ruby
aggregate "FileTool" do
  identified_by :file_path, suffix: :ulid
  attribute :file_path, FilePath
  attribute :description, Description

  command "Read" do
    attribute :file_path, FilePath
    # ...
  end
end
```

Runtime address : `FileTool:/etc/hosts|01HXY...`. Each file path + ULID identifies one invocation.

### Tools::EmailTool (`aggregates/framework/tools/tools.bluebook:438-544`)

**Before** :

```ruby
aggregate "EmailTool" do
  identified_by :id
  attribute :id, Id
  attribute :thread_id, ThreadId
  # ...

  value_object "Id" do
    attribute :value, String
  end
end
```

**After** :

```ruby
aggregate "EmailTool" do
  identified_by :thread_id, suffix: :ulid
  attribute :thread_id, ThreadId
  attribute :to, EmailAddress
  attribute :subject, Subject
  attribute :description, Description

  # No more value_object "Id" — ThreadId already carries identity meaning.
end
```

Note : SearchThreads and ListDrafts don't have a thread_id ; they would identify by description + ULID, OR (cleaner) move those two commands to a different addressing aggregate where `description + suffix: :ulid` is sufficient.

### PigeonCoop::Event with embedded Ticket entity (`sandbox/pigeoncoop/pigeoncoop.bluebook:659-837`)

**Before** : Event has no explicit identified_by ; Ticket entity defines `attribute :code, TicketCode` but has no `identified_by`. Addressing rules are implicit.

**After** :

```ruby
aggregate "Event" do
  identified_by :title          # natural key — the title doesn't change once published
  attribute :title,       EventTitle
  attribute :description, EventDescription
  attribute :starts_at,   Timestamp
  # ...

  entity "Ticket" do
    identified_by :code         # local part — parent prepends Event:<title>
    reference_to Parent, as: :holder
    attribute :code,    TicketCode
    attribute :status,  TicketStatus
    attribute :payment, Payment
  end

  entity "Registration" do
    identified_by :registrant   # local part — addressed by holder identity
    reference_to Parent, as: :registrant
    attribute :registered_at, Timestamp
  end
end
```

Runtime addresses :
- `Event:gala-2026`
- `Event:gala-2026/Ticket:T-001`
- `Event:gala-2026/Registration:parent-alice`

Ticket's full identity carries the parent context for free ; cross-aggregate references from a Payment record to "the ticket that was bought" resolve unambiguously.

### PigeonCoop::Person (`sandbox/pigeoncoop/pigeoncoop.bluebook:17-105`)

Already follows the new pattern : `identified_by :identity`, `attribute :identity, Identity`. No change required. **This is the worked example of what every other aggregate should look like.**

### PigeonCoop::Parent (`sandbox/pigeoncoop/pigeoncoop.bluebook:132-138`)

**Before** : `aggregate "Parent" do attribute :students, list_of(Student) ... end` — no identified_by.

**After** : Parent shares the Person identity (Fowler Party-Role), so :

```ruby
aggregate "Parent" do
  identified_by :identity   # same identity space as Person
  attribute :identity, Identity
  attribute :students, list_of(Student)
  # ...
end
```

### Macrophage::BluebookFirst (`aggregates/discipline/macrophage/macrophage.bluebook:301-406`)

**Before** : `identified_by :name`, `attribute :name, Name`, `value_object "Name" do attribute :value, String end` — pure singleton-via-overload.

**After** :

```ruby
aggregate "BluebookFirst", singleton: true do
  # no identified_by — there is exactly one BluebookFirst macrophage
  attribute :session_started_at, Timestamp
  attribute :bluebook_edits,     EditCount
  attribute :imperative_edits,   EditCount
  # ...
end
```

The `Name` VO disappears entirely along with the `:name` attribute. All eight per-rule macrophages (BluebookFirst, FixturesRuntime, AntibodyExemption, Warnings, LinearReference, LineCount, TestSpeed, CardLock) — plus the umbrella Macrophage aggregate itself — become singletons. The Consciousness aggregate (`catalog/mind.bluebook`) gets the same flag, made explicit instead of implicit.

## Migration / blast radius

Grep counts (across the whole `hecks/` repo, not just `hecks_conception/`) :

- **29** `identified_by :id` declarations across **6** bluebooks :
  - `hecks_conception/aggregates/framework/tools/tools.bluebook` — 20 occurrences (all 18 Tools aggregates + Cascade + one comment line)
  - `hecks_conception/aggregates/framework/audit/dispatch_audit.bluebook` — 2 aggregates
  - `hecks_conception/aggregates/framework/session/session.bluebook` — 1
  - `adapters/auth/auth.bluebook` — N
  - `sandbox/pigeoncoop/pigeoncoop.bluebook` — 1 (the `:identity` already-good case ; grep counted the substring)
  - `examples/banking/hecks/banking.bluebook` — N
- **67** `attribute :id, Id` declarations (commands + aggregates) — every Tools command + EmailTool/TaskTool/Sidequest/etc.
- **28** `value_object "Id"` declarations — one per aggregate that overloaded `:id`.
- **42** `identified_by :name` singletons — every one needs review : real singleton, or genuinely name-keyed entity ?

API surface that moves :

- `storehouse__state(aggregate, id:)` MCP signature — `id` becomes `identity` (or `address`). Today's id field carries either a ULID OR the universal id fallback ; under i611 it always carries the identity-string the framework derived.
- `storehouse query Domain::Aggregate.snake_case id=<value>` — same rename. The universal-id fallback from the 2026-05-12 sidequest already accepts both forms, so the new addressing slots cleanly into the existing dispatcher.
- `.heki` keyed records — each store currently keys by `id` ; needs translation pass to re-key by derived identity. The framework knows the derivation function ; a one-shot migration walks every store, recomputes the key, and rewrites the file.
- `Cascade.RecordResult` — currently shares the `id` of the originating invocation (the contract that makes the join work). Under i611, Cascade should `identified_by` the same natural-key + suffix combination as its origin. The runtime substrate that mints the id once and reuses it for the cascade-target stays unchanged ; only the bluebook declarations move.
- Test fixtures (`.fixtures` files) — every fixture currently provides an `id:` field. Either the loader infers it from the natural-key fields (preferred — fewer lies in fixtures), or fixtures explicitly opt into the suffix via `_ulid: <value>` for deterministic replay.

Subagent / external callers : Linear is retired ; no external client pins to FQNs yet ; the i604 forwarder mechanism (when it lands) will paper over any rename that this overhaul forces. i611 should land WITH i604, not before.

## The DSL syntax decisions (propose, not decide alone)

These are the three shape decisions Chris needs to weigh in on. None are unilateral.

### A. ULID suffix on aggregate roots

**Proposed** :

```ruby
identified_by :natural_field, suffix: :ulid
```

Alternative considered :
- `identified_by :natural_field, disambiguator: :ulid` — more accurate ("suffix" suggests a string append ; "disambiguator" names the role).
- `identified_by [:natural_field, :ulid_suffix]` and the framework recognises `:ulid_suffix` as a synthetic — too magic, no different from today's `:id` lie.
- `identified_by :natural_field` AND `disambiguates_with :ulid` on a separate line — splits identity declaration awkwardly.

The `suffix:` keyword keeps the declaration to one line and names the role honestly.

### B. Singleton adapter form

**Proposed** :

```ruby
aggregate "Consciousness", singleton: true do
  # no identified_by
  attribute :state, State
end
```

Alternatives :
- `aggregate "Consciousness", :singleton do ... end` — Ruby-symbol-flag form. Same content, slightly more terse.
- A dedicated DSL keyword : `singleton "Consciousness" do ... end` (no `aggregate`). Cleaner but introduces a parallel top-level surface that the IR builder has to learn. Probably overkill ; the flag is enough.
- A registry of singleton names in a separate `singletons do ... end` block. Centralizes the truth but separates the singleton declaration from its body. Probably worse.

The aggregate-level flag is the smallest change that captures the semantic shift.

### C. Entity parent-id concatenation

**Proposed** : entities declare ONLY their local `identified_by`. The framework prepends the parent's address automatically. No DSL addition required ; the runtime knows entities are nested.

```ruby
aggregate "Event" do
  identified_by :title
  entity "Ticket" do
    identified_by :code     # framework derives Event:<title>/Ticket:<code>
    attribute :code, TicketCode
  end
end
```

Alternative considered :
- `identified_by :code, scoped_to: :event` — explicit parent reference. Redundant : the entity's lexical position inside the aggregate already names the parent.
- Allow entities to opt OUT of parent-scoping (a globally-unique entity addressed without the parent prefix). The Event/Ticket case suggests no — Tickets ALWAYS need their event for context. If a use case appears, add the opt-out then ; default is parent-scoped.

## Phased rollout

This is a deep change. Five phases :

### Phase 1 — DSL surface (the builder + parser)

Land the three syntactic forms in the bluebook parser :
- `identified_by ..., suffix: :ulid`
- `aggregate "...", singleton: true do`
- Entity-level `identified_by` with framework-derived parent-scoping

Both the Ruby builder (for retired-runtime references) and the Rust parser (the live runtime) get the new shapes. No semantic changes yet — the new forms are accepted but the runtime still uses today's `:id` mechanism. Tests assert the IR contains the new fields.

### Phase 2 — IdentityDiscipline macrophage live

Land the macrophage (artifact 2 of this card) and wire it into PostToolUse. It complains about every `attribute :id, Id`, every `identified_by :id`, every `value_object "Id"`, and every `identified_by` that names a non-existent attribute (dangling). Aggregates without `identified_by` are NOT complained about — they have opted into the UUID default. The macrophage does NOT block — it complains. The complaints accrete as a forcing function.

This gives the team a complaint backlog to work down before the runtime contract changes.

### Phase 3 — Tools bluebook conversion (the cleanest test bed)

Convert `aggregates/framework/tools/tools.bluebook` first (or whichever sub-bluebooks i609 has split it into by then). All 18 Tools aggregates use the same `:id` + ULID pattern ; converting them is a uniform pass with one shape. Cascade follows the same conversion. After this lands, the i611 macrophage's complaint count drops by ~half. Update the `:claude_tool` adapter family to mint the ULID at the suffix-derivation site instead of expecting it as an argument.

### Phase 4 — All other aggregates + entities

Sweep the remaining bluebooks : `dispatch_audit`, `session`, the 42 `identified_by :name` singletons (review each ; convert to `singleton: true` or to a real natural key), every entity that lacks `identified_by`. Sandbox bluebooks (pigeoncoop, banking) and adapters (auth) land in their own commits.

### Phase 5 — `.heki` store migration + id-field retirement

One-shot migration script walks every `.heki` store, recomputes the natural-key-derived address for each record, rewrites the file. The MCP signature renames from `id:` to `identity:` (or stays `id:` carrying the derived value — the more compatible choice). The fixture loader stops requiring an explicit `id:` field. The Ruby/Rust runtime's universal-id fallback narrows from "ulid OR snake_case(Agg)=X" to just the natural-key form.

Phases can overlap : Phase 2 (the macrophage) and Phase 3 (Tools conversion) can run concurrently once Phase 1 lands. Phase 5 should wait until Phases 3 and 4 are complete — otherwise the migration script has nothing stable to migrate to.

## Dependencies

- **i604** (forwarder commands) — every bluebook that renames `attribute :id, Id` to a natural-key attribute is a contract break for any pinned caller. i604's `forwards_to` mechanism is the only way to land i611 incrementally without a hard cutover. **Land i604 before i611 Phase 3.**
- **i605** (RenameDiscipline macrophage) — the IdentityDiscipline macrophage proposed here is a sibling in the same family. The two macrophages would discover each other's blind spots (RenameDiscipline catches dropped commands ; IdentityDiscipline catches the same when an `:id` attribute is renamed away). Land in either order — they don't block each other.
- **i612** (BidirectionalAssociation macrophage) — 9th per-rule sibling, already in flight. IdentityDiscipline lands as the 10th. Both observe bluebook structure and complain about violations of a domain-modelling rule ; same shape, different concern.
- **i609** (Tools.bluebook cohesion split) — happens concurrently. The split creates 4-5 smaller bluebooks ; i611's conversion to natural-key identity touches every one of them. Order : either i609 first then i611 converts each split bluebook, OR i611 converts the monolithic Tools.bluebook first and i609 splits the converted version. Slightly cleaner the second way (smaller diffs per phase) but either works.
- **i555** (VO-inside-aggregate locked convention) — already locked. i611's deletion of `value_object "Id"` blocks is consistent with i555 ; each aggregate's identity is already typed by a local VO (Identity, ThreadId, etc.).

## Related

- The 2026-05-12 self-ref dispatch sidequest (`snake_case(AggName)=<id>` + universal `id=<value>` fallback) — under i611, the universal fallback continues to work ; the value it carries IS the derived natural-key address.
- The list-shape decision (`attribute :foos, Foo` is SCALAR ; lists require `list_of(X)`) — orthogonal but the same flavour : making the bluebook honest about what it declares rather than relying on heuristics.
