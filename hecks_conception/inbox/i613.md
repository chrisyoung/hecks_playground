# i613 — StoreHouse wraps every aggregate command (the universal door at the bluebook level)

## Where it came from

Chris, 2026-05-14 (verbatim) :

> "I think all aggregate command should be wrapped by StoreHouse commands"

The directive landed alongside two related ones from the same evening :

- "ALL of your tool calls should go through the StoreHouse" — already being mechanized at the tool layer (Tools.bluebook now has 19 aggregates ; i608 wired `EmailTool` through `:mcp`). i613 generalizes from "tool calls" to "every domain command".
- "we don't need 'aliases' we need forwarder commands that call the new command" (i604, reframed on `sq/i604-forwarder-commands` at commit `8b2e136f`). The forwarder-command pattern is the mechanic ; i613 is its universal application.

## The operational claim : one logging surface

Chris, 2026-05-14 (verbatim) :

> "by wrapping all commands in StoreHouse commands we now have one logging surface"

This is the sharpest statement of why the wrapper pattern matters. The rationale is not aesthetics or structural symmetry — it is **observability concentration**.

Today every aggregate has its own dispatch site. Logging the dispatch means instrumenting every aggregate — either at the adapter level (each `:claude_tool` binding writes its own trace) or recovered after the fact from event-log heuristics scattered across N stores. The "audit trail" is a sprawling concern with no single home.

With the wrapper pattern, every domain command flows through StoreHouse before it reaches its aggregate. That makes the log **one event stream instrumented in one place**. You add logging to `StoreHouse.Dispatch` (and its policy siblings) and every command — present and future — is covered. You remove it from StoreHouse and coverage drops to zero. The aggregate implementations stay silent on observability entirely ; that concern never leaks down.

**Contrast without the wrapper :** without this, capturing a complete dispatch audit means either (a) instrumenting every individual aggregate command in every bluebook — a maintenance surface that grows with the corpus — or (b) reconstructing it from event logs after the fact with heuristics that break on rename or structural change. Both are worse than a single aggregate whose event stream IS the audit.

**Precedent already in the corpus :** `Cascade.RecordResult` in `framework/tools/tools.bluebook` is the proof-of-concept for this pattern at the tool layer. Every tool call — Bash, Read, Edit, Grep, WebFetch — emits a `RecordResult` through one cascade surface. i613 generalizes that pattern from "tool calls have one outcome surface" to "all domain commands have one dispatch surface." The mechanism already works ; i613 is the corpus-wide application.

This framing makes the secondary benefits (transaction-boundary scoping, policy enforcement, cascade choreography) follow naturally — they are additional concerns that, once you have one logging surface, you get nearly for free by adding policy variants to the same StoreHouse aggregate. The logging surface is why the wrapper exists ; the rest ride along.

## The structural follow-on : bus + envelope

Chris, 2026-05-14 (verbatim) :

> "and so storehouse needs its own event bus as well that is just the event from bluebooks. We can add an envelope that way too"

### The event bus

The logging surface (above) is a point in the dispatch flow — one place through which every command passes. Chris's structural follow-on converts that point into a **stream** : StoreHouse's own event bus, carrying every event emitted by every wrapped command invocation. The bus is the data structure that makes the logging surface meaningful.

Without the bus, "one logging surface" is a place you *can* instrument. With the bus, that surface *emits* an ordered, queryable, replayable event stream — the chronicle of all domain action that flowed through the wrapper. An observer who subscribes to StoreHouse's bus gets the complete history of every wrapped command's outcome. No polling, no heuristic reconstruction from scattered event stores.

This is different from the individual aggregate event buses (each aggregate already emits to its own store). StoreHouse's bus is the **meta-bus** : not "what did `Person.Register` emit" but "what did every command that flowed through StoreHouse emit, and in what order." The ordering is cross-aggregate ; the chronicle is corpus-wide.

`Cascade.RecordResult` in `framework/tools/tools.bluebook` already does something in this direction — it streams the outcomes of every tool call through a single surface. i613's event bus is the generalization : every domain command's outcome, not just tool outcomes, enters the stream. `Cascade.RecordResult` is the embryo of the StoreHouse bus.

### The envelope

Each event on the bus rides inside an **envelope** — a wrapper around the underlying domain event that adds cross-cutting metadata without touching the domain event itself. The domain event stays focused on the business fact ; the envelope carries the operational context.

Minimal envelope shape :

```
Envelope {
  dispatched_at    : Timestamp           # when the dispatch entered the bus
  dispatcher       : DispatcherId        # who/what called StoreHouse.Dispatch
  correlation_id   : CorrelationId       # tie together a logical operation across commands
  source           : CommandFQN          # the underlying domain command being wrapped
  payload          : DomainEvent         # the domain event itself, unchanged
}
```

Natural additions as the corpus matures :

```
  trace_context    : W3CTraceContext     # W3C trace headers for distributed tracing
  causation_id     : EventId             # event-sourcing causal chain (what caused this)
  tenant_id        : TenantId            # if the corpus goes multi-tenant
```

The envelope is uniform regardless of shape choice (A, B, or C). Every command that flows through StoreHouse — whether via a named wrapper (`Shape A`), a generic `Dispatch`, or a policy variant (`AuditedDispatch`) — emits its domain event wrapped in the same envelope. The cross-cutting metadata fields are always the same ; only `source` and `payload` change per event.

### Why the envelope matters for cross-cutting concerns

Before the envelope, cross-cutting metadata had nowhere clean to live. Audit trails that need "who dispatched this" are forced into the domain event payload (polluting the business fact) or reconstructed from adapter-layer logs (fragile). Distributed tracing that needs W3C trace headers has to instrument every aggregate independently.

With the envelope, these concerns have a dedicated carrier :

- **Audit** : `dispatched_at` + `dispatcher` + `correlation_id` on every envelope gives you the audit trail without touching any domain event.
- **Observability** : `trace_context` on the envelope propagates W3C trace headers through every domain command, automatically, via the bus.
- **Causal chains** : `causation_id` on the envelope lets you reconstruct "command B was caused by command A" without embedding that relationship in domain state.
- **Transaction boundaries** : `correlation_id` groups commands that belong to the same logical operation, enabling rollback coordination without a two-phase commit protocol.

The domain events stay clean. `PersonRegistered` carries name + email + id — nothing about who dispatched it or why. The envelope carries the rest.

`Cascade.RecordResult` already does this for tool calls : it captures `tool`, `output`, `exit_code`, `ok` as the operational wrapper around the tool's raw output. The domain "event" (the tool ran) is kept separate from the operational context (did it succeed, what did it return). i613's envelope generalizes that pattern — `Cascade.RecordResult` is envelope-shaped for tool calls ; StoreHouse's envelope generalizes it to all domain events.

### How the envelope reframes the shape choice

The envelope is neutral between shapes — it is added by the bus layer regardless of which wrapper shape StoreHouse uses. But it sharpens the analysis :

**Shape B (generic `Dispatch`) becomes more compelling.** If the envelope carries all cross-cutting metadata — `dispatcher`, `correlation_id`, `trace_context`, `causation_id` — then the named policy commands in Shape C (`AuditedDispatch`, `TransactionalDispatch`) are no longer the *only* way to express those concerns. They become *convenience commands* that set specific envelope fields or enforce specific field constraints. That is a weaker argument for Shape C : the envelope makes audit and tracing available on every envelope regardless of which command name was used.

**Shape C still holds, but for a different reason.** The named policy commands are not just "configure the envelope differently." `AuditedDispatch` requires an `audit_reason` — a substantive attribute that the caller must supply, not a metadata field the bus fills in automatically. `TransactionalDispatch` enforces rollback semantics — a policy that the bus cannot express through metadata alone. The policy commands carry *commitments the caller makes*, not just *metadata the bus attaches*. That is what earns their place in the bluebook ; the envelope does not replace them.

## The principle being stated

**The bus is bluebook-native, not adapter-native.** The logging-surface claim (above) is the operational reason why. This section names the structural consequence.

Today the dispatch rule "everything goes through StoreHouse" is enforced at the MCP boundary — `storehouse__dispatch` is the universal door, and the convention is *I dispatch through it instead of calling aggregate commands directly*. That rule lives in the MCP server's surface, in the system prompt, in tonight's macrophage rules — but **not in the bluebook**. A bluebook-reader looking at `Person.Register` or `Shoutout.Approve` sees a domain command, not a command-that-must-be-mediated.

Chris's instinct : encode the mediation in the bluebook itself. Make `StoreHouse` an actual bluebook-level concept whose commands are the canonical entry points. The dispatch rule stops being adapter-level discipline that the runtime hopes you remember and becomes bluebook-level structure that the runtime can read, diff, and macrophage-check.

This is the same shape as **Rule A** in the 2026-05-12 principles ("Claude calls StoreHouse — not StoreHouse intercepts Claude") taken one step further. Rule A says *the dispatch direction* is Claude → bus. i613 says *the dispatch surface* — the things Claude is allowed to call — is itself a bluebook-encoded concept, not a runtime-level convention layered on top of arbitrary aggregate commands.

It also extends Principle 1 ("the dispatch IS the act"). If the dispatch IS the act, then the dispatch shape — the universal-door wrapper — IS part of the contract. Hiding it in the MCP surface makes the contract invisible.

## Three shapes (and which I think is right)

### Shape A — one StoreHouse aggregate, one wrapper command per domain command

```ruby
aggregate "StoreHouse" do
  command "DispatchPersonRegister" do
    forwards_to "Person.Register"
  end
  command "DispatchShoutoutApprove" do
    forwards_to "Shoutout.Approve"
  end
  command "DispatchToolsShellToolBash" do
    forwards_to "Tools::ShellTool.Bash"
  end
  # ... one wrapper command for every domain command in the corpus
end
```

**Pros.** Maximum explicitness — every wrapper is a named, diff-able, macrophage-checkable bluebook concept. Catalog listings show every callable command on StoreHouse as a first-class entity. The mediation surface is visible at a glance. Plays well with i604 forwarders : the same `forwards_to` DSL keyword carries both intentions.

**Cons.** N wrappers for N commands ; the corpus has hundreds. Every new domain command needs a paired wrapper (or a macrophage screams), inflating the cognitive load of adding commands. The `StoreHouse` aggregate becomes a giant flat list of forwarders that obscures structure. Renames cascade — rename `Person.Register` and you also rename `StoreHouse.DispatchPersonRegister` (i604's rename-safety mechanism mitigates this but doesn't eliminate the cognitive duplication).

### Shape B — a single StoreHouse.Dispatch command that resolves at runtime

```ruby
aggregate "StoreHouse" do
  command "Dispatch" do
    description "The universal door. Resolves command_fqn to the target aggregate command at dispatch time and forwards args verbatim."
    attribute :command_fqn, CommandFQN
    attribute :args, Args
    forwards_to :resolved_at_runtime
  end
end
```

**Pros.** One command for the entire corpus. Matches the current MCP surface (`storehouse__dispatch` takes a `command` parameter ; the bluebook now mirrors that shape one-to-one). No N-wrapper explosion. New domain commands light up immediately with no per-command bluebook work. **Importantly, under the logging-surface framing, Shape B delivers Chris's operational goal immediately and completely — every command flows through `StoreHouse.Dispatch`, so you instrument one command and you have one log. The generic fallback IS the one logging surface.**

**Cons.** Treats command names as runtime data, not bluebook structure. `command_fqn` is a String VO carrying a name that the macrophage cannot statically verify against the bluebook catalog — it's the same kind of late-binding hole that motivated forwarder-commands-instead-of-bus-alias-registry in i604. The bluebook says "you can call StoreHouse.Dispatch with some FQN" but tells you nothing about which FQNs are valid ; the validity question is pushed back to runtime resolution. Domain command renames do not surface in the StoreHouse bluebook at all — the static visibility argument for i613 is weakened. Shape B gives you the logging surface but not the bluebook-level encoding of which commands are mediated.

### Shape C — hybrid : curated StoreHouse commands for cross-cutting concerns + a Dispatch fallback

```ruby
aggregate "StoreHouse" do
  # Cross-cutting commands that genuinely add behaviour
  command "AuditedDispatch" do
    description "Dispatch with audit-trail emission. Use for any command whose invocation must hit the audit log."
    attribute :command_fqn, CommandFQN
    attribute :args, Args
    attribute :audit_reason, AuditReason
    emits "AuditedDispatchRequested"
  end

  command "TransactionalDispatch" do
    description "Dispatch inside a transaction boundary. Rolls back the underlying command's emitted events on failure."
    attribute :command_fqn, CommandFQN
    attribute :args, Args
    emits "TransactionalDispatchOpened"
  end

  # The fallback for everything else
  command "Dispatch" do
    description "Plain pass-through dispatch. No cross-cutting policy applied ; the bus resolves command_fqn and forwards args."
    attribute :command_fqn, CommandFQN
    attribute :args, Args
    forwards_to :resolved_at_runtime
  end
end
```

**Pros.** The cross-cutting commands earn their place in the bluebook because they add real behaviour (audit emission, transaction scoping, cascade choreography). Authors can express "dispatch this with audit" instead of layering an adapter convention. The fallback `Dispatch` keeps the corpus-wide coverage of Shape B without the per-command wrapper explosion of Shape A. Matches Evans' Open Host Service pattern (Blue Book Ch. 14) more cleanly than either pure shape : the StoreHouse aggregate IS the Published Language for the dispatch surface, and its commands genuinely model the protocol Chris wants downstream consumers to use.

**Cons.** Asks an open question the corpus hasn't answered yet : *which cross-cutting concerns actually need bluebook-level expression ?* If we name them prematurely we get a flat list nobody uses ; if we name them late we leak the discipline into adapters first and then have to repatriate. The choice of which concerns to elevate is itself a design problem. The logging surface itself is delivered equally well by Shape B's plain `Dispatch` ; Shape C adds value only if the named policy commands (AuditedDispatch, TransactionalDispatch) are actually needed — otherwise it's Shape B with extra naming ceremony.

### My recommendation : Shape C (held, but the bus+envelope framing sharpens *why*)

**How the bus+envelope framing shifts the analysis.** The original recommendation for Shape C rested on cross-cutting concerns needing bluebook-level expression. The logging-surface sharpening narrowed the argument : Shape B delivers the core logging value immediately. The envelope follows-on sharpens it further still : once you have an envelope on the bus, metadata concerns like audit timestamps and trace headers are available on *every* event automatically — you don't need a named `AuditedDispatch` command just to record *when* something happened.

This is the strongest version of the Shape B case. Under this framing, Shape B + envelope delivers : one logging surface, corpus-wide event stream, cross-cutting metadata on every event, W3C trace propagation, causal chain reconstruction — all without any named policy commands.

**Why Shape C still holds.** The envelope carries metadata the *bus* fills in. The named policy commands carry commitments the *caller* makes. `AuditedDispatch` requires an `audit_reason` attribute — a substantive claim about why this dispatch needed auditing. That is not a metadata field ; it is a contract between the caller and the audit system. The envelope cannot express it. `TransactionalDispatch` commits to rollback semantics the bus must enforce — again not a metadata field, a behavioral guarantee. These are the things that justify bluebook-level names.

So Shape C holds, but its justification is now cleaner : the named policy commands express *caller commitments and behavioral guarantees*, not metadata. Metadata is the envelope's job. If a cross-cutting concern is purely metadata (trace headers, correlation ids, timestamps), it goes on the envelope and Shape B is sufficient for it. If it requires a substantive caller attribute or an enforced behavioral guarantee, it gets a named command and Shape C is the right answer.

**Shape A** is still out : N wrappers for N commands buys static visibility at the cost of corpus bloat, and the bus+envelope delivers corpus-wide coverage without it. **Shape B** is the honest baseline and the right answer if the corpus never develops concerns that require caller commitments beyond what the envelope supplies. **Shape C** holds as the growth path : start with Shape B's `Dispatch` (plus the envelope), and add named policy commands only when a concern genuinely requires a caller contract.

If Chris reviews this and says "the envelope handles everything I need for audit and tracing — no named policy variants," the recommendation should flip to Shape B. That decision should be explicit.

This is also the Evans Open Host Service framing reread with the envelope in view : the Published Language exposes the *behavioral* protocol (the named policy commands) ; the bus handles the *operational* protocol (envelope metadata). The two layers have different jobs and neither should do the other's.

**Open questions sharpened by the envelope :**

1. **Does `AuditedDispatch` survive the envelope ?** The envelope carries `dispatched_at` and `dispatcher` automatically. If the audit requirement is *who + when*, the envelope satisfies it without a named command. `AuditedDispatch` survives only if it carries something the envelope cannot : a caller-supplied `audit_reason` (a narrative claim) or an `audit_required: true` enforcement gate that rejects envelopes without that field. If neither is needed, `AuditedDispatch` collapses back into Shape B's plain `Dispatch`.

2. **Where does the envelope live in the bluebook ?** The envelope is a value object — probably declared inside the `StoreHouse` aggregate alongside the commands that produce it. Does every emitted event from a StoreHouse command automatically ride an envelope, or is the envelope an explicit `emits` in the command declaration ? The first is a runtime guarantee ; the second is a bluebook-visible contract. Both are defensible.

3. **Shape C's named policy commands — speculative or near-term ?** This question was open before the envelope. The envelope sharpens it : if audit and tracing are satisfied by the envelope, `AuditedDispatch` and `TransactionalDispatch` are both further away than they looked. `TransactionalDispatch` may be the nearer candidate (rollback semantics are genuinely behavioral, not metadata). Surface this tension when Chris reviews.

## How `forwards_to` makes this work (and why i604 lands first)

The i604-reframe on `sq/i604-forwarder-commands` introduces a new DSL keyword :

```ruby
command "Foo" do
  forwards_to "OtherAggregate.OtherCommand"
end
```

This same keyword is what Shape A and Shape C use to express "this StoreHouse command actually dispatches the target command with the same args, then short-circuits". In Shape A it's literal (one explicit target per wrapper) ; in Shape C the cross-cutting variants use it after their policy emits ; the fallback `Dispatch` uses a runtime-resolved variant (`forwards_to :resolved_at_runtime` is sketch syntax — could be `forwards_to lookup_from(:command_fqn)` or similar).

**Without i604 landing first, i613 has no mechanism.** The `forwards_to` keyword + its runtime semantics + its `ForwarderInvoked` cascade event are prerequisites. i604 needs to ship before i613 can be implemented in any of the three shapes.

## Relationship to i604

i604 introduces `forwards_to` for the **rename-transition** use case — keep `Tools::Tools.Bash` alive after rename to `Tools::ShellTool.Bash` ; the old name is a forwarder. i613 is the **universal-application** of that same mechanic — `StoreHouse.<...>` is a forwarder onto the underlying domain command, not as a transition tool but as a permanent universal door. Both share the keyword ; both share the `ForwarderInvoked` cascade ; both share the macrophage that detects unused forwarders.

What's distinct : i604's forwarders are *expected to expire* (the RenameDiscipline macrophage from i605 detects stale forwarders and demands their deletion). i613's StoreHouse wrappers are *expected to live forever* — they are the dispatch surface, not a transition aid. The macrophage needs to know the difference (probably via a `permanent: true` flag on the command or a `kind:` on `forwards_to`).

## Relationship to i599

i599 mechanizes the routing of **native Claude Code tool calls** (Bash, Read, Edit, Write, Grep, Glob, WebFetch, WebSearch) through `Tools::<Cat>.<Method>` via a PreToolUse hook. i613 mechanizes the routing of **all domain commands** through `StoreHouse.<...>` via bluebook-level wrappers.

Together they close the loop : i599 ensures every tool-side dispatch enters the bus ; i613 ensures every domain-side dispatch is mediated by a bluebook-level StoreHouse command. **Every dispatch — tool or domain — enters the bus.** No invisible side channels.

The two layers also nest cleanly. A `Tools::ShellTool.Bash` dispatch from i599 lands in Tools — but Tools commands are domain commands, so they too get wrapped by `StoreHouse.<...>` under i613. The hook-to-bus path becomes : native Bash → PreToolUse hook → `StoreHouse.DispatchBash` (Shape A) or `StoreHouse.Dispatch command_fqn="Tools::ShellTool.Bash"` (Shape B/C) → `Tools::ShellTool.Bash`. Three layers ; each layer's contract is in the bluebook ; the macrophage can audit the whole chain.

## Why this matters / what it changes

**One logging surface.** This is the primary operational gain. Every domain command flows through `StoreHouse.Dispatch` (or a policy variant). Instrumentation — logs, traces, audit events — is added once, in one aggregate, and covers the entire corpus. Today that concern is either absent or scattered ; under i613 it has one address.

**Cross-cutting concerns become bluebook-level.** Audit trails, transaction boundaries, cascade choreography — today these live in adapter wiring (the `:claude_tool` family writes to `.last_dispatch`, emits `Cascade.RecordResult`, etc.) and the bluebook is silent on them. With Shape C, the audit / transaction policies are first-class commands ; you can read the StoreHouse aggregate and see what mediation exists. These are secondary benefits that ride the logging surface once it exists.

**Bluebook-level encoding of the dispatch rule.** Today the rule "every call enters the bus" is named in the system prompt, enforced by tonight's macrophage hook on PostToolUse, advised by i599's PreToolUse hook. None of those are visible in the bluebook itself. Under i613, the rule becomes *the StoreHouse aggregate exists and has the wrapper / fallback commands required to mediate every domain command in the corpus* — a structural fact the macrophage can check by IR inspection.

**FQN form impact.** Under Shape A, `storehouse__dispatch` would now expect `StoreHouse.DispatchPersonRegister` instead of `Person.Register` — or both, with `Person.Register` keeping its bluebook home and the StoreHouse wrapper being one valid alias for it. Under Shape C, the FQN remains `Person.Register` for direct dispatches (still allowed — the wrapper is a *door*, not a *gate*) and `StoreHouse.Dispatch command_fqn=Person.Register args={...}` for mediated dispatches. The MCP surface (`storehouse__dispatch`) doesn't change ; the bluebook-level expression of what it does becomes richer.

**Adapter wiring stays unchanged at the substrate level.** Wiring is override ; this card touches only the contract. The `:claude_tool` family still binds to `Tools::ShellTool.Bash` — that aggregate command exists and works exactly as today. The StoreHouse wrapper is bluebook-additive : a new layer of structure, not a substrate change.

## A macrophage to enforce — `StoreHouseWrapperCoverage`

Once the shape is chosen, the macrophage gets a new rule. For Shape C :

- Every aggregate command in the corpus (excluding `StoreHouse` itself and any explicit allow-list) must be reachable through `StoreHouse.Dispatch` — verifiable by reflecting on the corpus and confirming the command resolution at runtime would succeed. The fallback covers this universally, so the check is essentially "no aggregate is privately registered".
- Every aggregate command marked `cross_cutting:` (a new attribute on the command declaration, listing which named StoreHouse policies apply — e.g. `cross_cutting: [:audit]`) must have a matching wrapper command on StoreHouse. A command marked `cross_cutting: [:audit]` that has no `StoreHouse.AuditedDispatch` route is a structural error.

For Shape A : every aggregate command must have a paired `StoreHouse.Dispatch<Aggregate><Command>` wrapper. The macrophage walks both lists and complains about mismatches.

For Shape B : nothing to enforce structurally ; the single `StoreHouse.Dispatch` command handles everything by name.

The macrophage rule is part of the i595 family (mechanize-the-discipline) and should be filed alongside i605's RenameDiscipline once the shape is chosen.

## Migration / phasing

This is corpus-wide. Three phases :

**Phase 0 — i604 lands first.** `forwards_to "FQN"` parses and runs. `ForwarderInvoked` cascade fires. The mechanic exists.

**Phase 1 — StoreHouse aggregate exists.** Land Shape C's minimal surface : `StoreHouse.Dispatch` (the fallback), plus 1-2 obvious cross-cutting commands if any are already needed (audit feels like the first candidate — i608's EmailTool wiring already does ad-hoc audit ; consolidating it into `StoreHouse.AuditedDispatch` may be its first user). The dispatch CLI / MCP surface can route to either StoreHouse or the direct command ; both work.

**Phase 2 — macrophage enforces coverage.** Once Shape C is settled and a few cross-cutting policies are in use, the macrophage adds `StoreHouseWrapperCoverage` and the corpus catches up. Any new `cross_cutting:`-tagged command must have its StoreHouse wrapper.

**Phase 3 (deferred) — direct dispatches deprecated ?** The strongest version says "you must route through StoreHouse" — every direct `Person.Register` call gets a forwarder onto `StoreHouse.Dispatch`. Probably not the first goal ; we'd need first-user evidence that the discipline is worth the friction. File as a follow-up.

- **i603** (mechanical lock for storehouse routing) — the broader directive Chris was articulating tonight ; i613 is the bluebook-level slice of i603.

## What this card is NOT

- Not a rename. The existing `Tools::ShellTool.Bash`, `Person.Register`, etc. keep their bluebook homes. StoreHouse wraps ; it does not replace.
- Not an MCP-surface change. `storehouse__dispatch` still works as today ; i613 makes the bluebook-level shape match what `storehouse__dispatch` is already doing.
- Not a runtime-perf concern. A forwarder is one extra hop ; the cost is negligible compared to the discipline gain.
