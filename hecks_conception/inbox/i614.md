# i614 — IdentifierService : the runtime substrate for i611 identity

## Where it came from

Chris, 2026-05-14, immediately after the i611 UUID-default softening (commit `8475b182` on `sq/i611-identity-overhaul`) :

> "we don't need to do natural ids now that we have the UUID default. Also, if we change ids, we can just concatinate the new id with the old one in repositories. so its easy to find it by its original identity. would be nice if there was someway to petition the ids too. I think we need an identifier service bluebook that handles this stuff."

The directive is exploratory — three concrete moves ("UUID default ; concat-old-new in repos ; petition workflow") plus the framing claim ("we need an identifier service bluebook that handles this stuff"). The card crystallises the framing into responsibilities and proposes shapes for the petition workflow without locking one in.

## Why this needs to exist

i611 lays out the discipline : `identified_by` lists natural-key fields ; aggregate roots may append a ULID suffix for disambiguation ; entities inherit their parent's address ; value objects ARE their full-field concatenation ; missing `identified_by` opts into the UUID default. That's the **contract** side, expressed as bluebook rules and policed by the IdentityDiscipline macrophage (10th per-rule sibling, landed earlier tonight in `aggregates/discipline/macrophage/macrophage.bluebook`).

What i611 does NOT yet have is the **runtime substrate** that performs the four operations the discipline implies :

1. Look at an aggregate's bluebook IR. Has `identified_by`? Derive its addressable form by concatenating the named fields. No `identified_by`? Mint a UUID.
2. Look at a nested entity. Find its lexical parent ; prepend the parent's derived form to the entity's local identity.
3. Look at an aggregate whose `identified_by` has just changed (a Person aggregate that moved from `identified_by :id` (UUID-default era) to `identified_by :email`). Store the new id concatenated with the old (`new||old`) in the repository so that lookups by either succeed and the change is non-destructive.
4. Look at a request to change an aggregate's identity rules — its `identified_by` list, its suffix, its singleton flag. Route the request through a workflow (submit, review, apply OR reject) with an audit trail.

Without the substrate, every adapter / repository / runtime path would have to know how to do this. The concat-old-new behaviour would be scattered across persistence adapters. The UUID-default fallback would be implicit. The petition workflow wouldn't exist — identity changes would just happen in commits with no record. The IdentifierService is the bluebook concept that consolidates this knowledge into ONE aggregate (or two, if petitions split out) so all of identity has a single named home.

A second reason it needs to exist : i613 (StoreHouse wraps every command at the bluebook level) makes every command flow through a domain aggregate. Identity-derivation IS a command — at minimum a query, but more likely a record-producing operation that emits events the runtime can react to. Without an IdentifierService aggregate, the runtime would have to do identity work outside the bluebook surface, which violates the locked principle that the bluebook IS the contract.

## The four responsibilities

### 1. UUID-default minting

When an aggregate or entity in the IR has no `identified_by` line, the IdentifierService mints a UUID at creation time and the runtime persists under that key. The bluebook does NOT declare a UUID attribute ; the IR simply lacks the `identified_by` field. The service is the substrate that handles the implicit case.

Concrete example : `Cascade::ResultRecorded` event payloads from `aggregates/framework/tools/tools.bluebook:1499` today are addressed by an explicit `Id` value object — under i611 phase 3 conversion, the `:id` attribute and `Id` VO disappear and Cascade becomes addressed by either the originating `shell_command|ulid` (joining back to its ShellTool record) OR, for cascade-only flows, by a UUID minted by IdentifierService at the time the cascade record is created.

The minting site is a single command : `IdentifierService.MintDefault`. The runtime dispatches it whenever it needs an address for an aggregate that did not declare its identity. UUIDs are RFC 4122 v4 by default ; an alternative shape (ULID, snowflake) could be a future configuration.

### 2. Natural-key derivation

When an aggregate has `identified_by :a, :b, :c`, the IdentifierService walks the field values for a given record and concatenates them with a stable separator (proposed : `|`) to produce the addressable identity string.

Concrete example : `PigeonCoop::Person` declares `identified_by :identity, attribute :identity, Identity`. For a Person record where `identity = "alice"`, the derived form is `Person:alice`. For an entity inside, say `Event::Ticket` with `identified_by :code` where `code = "T-001"` and parent Event has `title = "gala-2026"`, the derived form is `Event:gala-2026/Ticket:T-001`.

Three sub-cases :

- **Aggregate root, simple natural key** : `identified_by :a` → `<AggName>:<value-of-a>`.
- **Aggregate root with ULID suffix** : `identified_by :a, suffix: :ulid` → `<AggName>:<value-of-a>|<ulid>`. The service mints the ULID once at dispatch and reuses it for any cascade-target records (e.g. matching Cascade records).
- **Entity inside aggregate** : the lexical parent's derived form is prepended. The entity bluebook declares only the LOCAL `identified_by` ; IdentifierService does the prepend.

Value objects don't pass through IdentifierService at all — their identity IS their full-field concatenation, which the runtime can compute directly. The service is for entities and roots.

`Tools::ShellTool` post-i611-phase-3 will declare `identified_by :shell_command, suffix: :ulid`. Today's 20 surrogate-id aggregates in `aggregates/framework/tools/tools.bluebook` (the 19 Tools categories + Cascade — every one carries `identified_by :id` + `attribute :id, Id` + `value_object "Id"`) all convert under the natural-key derivation rules. The IdentifierService is the substrate that turns those new declarations into actual addresses at runtime.

### 3. Id migration via repository-side concatenation

When an aggregate's `identified_by` rule changes — say a Person aggregate that lived under UUID-default for a few weeks now declares `identified_by :email` — every existing Person record in the `.heki` repository has its old UUID address but should now ALSO be addressable by its new email-derived form. The IdentifierService records the migration via the pattern Chris named :

> "if we change ids, we can just concatinate the new id with the old one in repositories. so its easy to find it by its original identity."

The repository stores `new_id || old_id` as the key (proposed separator : `||`, two pipes, to distinguish from the natural-key separator which is one pipe). Lookups against the repository try BOTH halves : a query for `Person:alice@example.com` matches the new half ; a query for `Person:abc-123-uuid` matches the old half. Either resolves the same record.

This is non-destructive. The old identity remains addressable forever (until someone explicitly retires it). The migration is recorded as a `MigrationChain` value object the IdentifierService keeps in its state for audit and inspection. When the change happens, the service dispatches `RecordMigration` carrying the entity ref, the old identity string, the new identity string, and the rule change that triggered the migration.

#### Concrete example

Person record :
- **Before migration** : key = `Person:abc-123-uuid` (UUID-default era).
- **`identified_by` change** : new line `identified_by :email` added to the Person aggregate ; the discipline allows it (an existing UUID record gets re-keyed, not rejected).
- **Migration dispatched** : `IdentifierService.RecordMigration` with `new_identity = "Person:alice@example.com"`, `old_identity = "Person:abc-123-uuid"`.
- **Repository state after** : key = `Person:alice@example.com||Person:abc-123-uuid`. Lookups by either succeed.

#### Separator choice

Single pipe `|` for the natural-key concatenation (`Event:gala-2026|Ticket:T-001` would be wrong — the slash is the parent-prefix separator ; the pipe is for multi-field natural keys, e.g. `Booking:event-2026|alice`). Double pipe `||` for the migration-chain separator. Three pipes for nested migrations? See "evolution of chains" below.

#### Lookup semantics

"Find by either" is the default. A lookup for any substring that appears in the migration chain matches the record. The runtime walks the key, splits on `||`, and tests each segment against the query. Match on any segment → return the record. This generalises to N migrations.

#### Evolution of chains (multiple identity changes)

Chris's directive suggested only the single concat case. But what if Person's identity changes twice ? `identified_by :id` → `identified_by :email` → `identified_by :legal_name` ?

Two shapes :

- **Chain of all old ids** : key becomes `Person:legal-name-x||Person:alice@example.com||Person:abc-123-uuid`. Every past identity remains addressable. Audit-friendly but the key grows unboundedly with repeated migrations.
- **Only the most recent old id** : key becomes `Person:legal-name-x||Person:alice@example.com`. The original UUID is gone from the key (but still in the audit-trail entity collection). Bounded size, but a lookup against the original UUID stops working after two migrations.

**Recommended : chain of all old ids.** Bluebooks shouldn't change identity often ; if they do, the bounded-chain optimisation is premature. The `MigrationChain` audit entity keeps the full history regardless ; mirroring it in the key is the cheap way to make the runtime's lookup-by-any-old-id behaviour fall out for free.

#### What happens to old references stored in other aggregates' attributes

This is the dangling-reference problem. If `Booking.booked_by = "Person:abc-123-uuid"` and Person's identity migrates to email, the Booking record still holds the old UUID address.

Two answers :

- **Lazy resolution** : Booking's value stays as-is. When the runtime resolves a `reference_to(Person)`, it asks IdentifierService to look up by the stored value ; the lookup matches the old half of the migration chain and returns the right Person. Booking never sees the new form.
- **Eager rewrite** : when a migration happens, IdentifierService scans every other aggregate's attributes for references to the old form and rewrites them to the new form. Heavy but tidy.

**Recommended : lazy resolution.** Eager rewrite has the same blast radius as a renames-everywhere pass and is brittle. Lazy resolution piggy-backs on the lookup-by-either behaviour the service already provides ; nothing else has to change.

### 4. Identity-petition workflow

Chris's directive :

> "would be nice if there was someway to petition the ids too."

This is the governance layer. An identity change isn't a hot-path mechanical action like minting a UUID or deriving a natural key — it's a deliberate, often cross-bluebook decision (e.g. "PigeonCoop::Parent and PigeonCoop::Person should share the Identity space ; let's change Parent's `identified_by` from absent to `:identity`"). The petition workflow gives identity changes a record, a review surface, and an audit trail.

A petition has shape :

- **Subject** : which aggregate or entity is the petition about ? (`EntityRef` value object — the FQN, e.g. `PigeonCoop::Parent`.)
- **Proposed change** : what is the new `identified_by` rule ? (Shape TBD ; see petition-shape alternatives below.)
- **Reason** : the human-readable explanation for why the change is being requested.
- **State** : submitted → under_review → applied OR rejected.
- **Audit** : who submitted it, when ; who reviewed it, when ; what the outcome was.

The petition is itself a domain concept that benefits from the bluebook surface. It is not a CLI ceremony or an issue-tracker thing ; it's a thing the system knows about and can dispatch on.

Three shapes for HOW the petition fires through the system are proposed in the next section. The card does NOT lock in one — that's Chris's call.

## Petition shapes (propose, don't lock)

### Shape α — petition as bluebook command

The IdentifierService aggregate (or a sibling `IdentityPetition` aggregate) has a `SubmitPetition` command. Reviewing the petition is a second command, `ReviewPetition`, that records review notes and may approve or reject. Applying an approved petition is a third command, `ApplyPetition`, that actually mutates the bluebook (or in a more conservative variant, just notes that the change is "ready to land" and the bluebook edit happens out-of-band).

```ruby
command "SubmitPetition" do
  attribute :subject,         EntityRef
  attribute :proposed_rule,   ProposedRule
  attribute :reason,          ReasonText
  attribute :submitted_at,    Timestamp
  emits "PetitionSubmitted"
end

command "ReviewPetition" do
  attribute :petition_id,   PetitionId
  attribute :review_notes,  ReasonText
  attribute :approved,      Boolean
  attribute :reviewed_at,   Timestamp
  emits "PetitionReviewed"
end

command "ApplyPetition" do
  attribute :petition_id,  PetitionId
  attribute :applied_at,   Timestamp
  emits "PetitionApplied"
end
```

**Pros** : full audit trail, every transition emits an event, the state machine is bluebook-explicit, the workflow is observable through the event stream.

**Cons** : heaviest of the three. Three commands plus a Reject command. Persistent state for each petition. The bluebook side is verbose.

**When this is right** : if identity changes are deliberate, infrequent (a handful per year), and warrant formal review — i.e. if Chris expects identity changes to be a governance decision involving multiple humans/agents.

### Shape β — petition as runtime hook

A petition is a runtime API call. An external system (a macrophage, a domain author, a refactoring agent) invokes a `petition_change` runtime hook that consults a policy (a configured list of who can petition what) and either approves or rejects synchronously. No review step. The decision is recorded in the IdentifierService's state as a one-shot audit entry.

```ruby
command "PetitionChange" do
  attribute :subject,         EntityRef
  attribute :proposed_rule,   ProposedRule
  attribute :reason,          ReasonText
  attribute :requested_by,    RequesterRef
  attribute :requested_at,    Timestamp
  emits "ChangePetitioned"   # carries auto-approve OR auto-reject outcome
end
```

**Pros** : lightest. One command. No state machine. Fits flows where identity changes are mostly routine and the policy can decide automatically (e.g. "any change that adds a natural key to an aggregate currently under UUID-default is auto-approved ; any change that removes a natural key needs human sign-off").

**Cons** : no formal review surface for the cases that DO need one. The "auto" decision is opaque unless the policy itself is bluebook-explicit.

**When this is right** : if identity changes are mostly mechanical (driven by macrophages or refactoring tools) and Chris is comfortable with a configurable policy doing most of the gating.

### Shape γ — petition as Cascade event

The IdentifierService dispatches a `PetitionChange` command that emits a `ChangePetitioned` event. The `:identity_petition` adapter family (a hypothetical sibling to `:claude_tool` and `:web_tool`) chains the outcome through `Cascade.RecordResult` carrying the petition outcome. The petition flows through the same infrastructure Tools events do — every petition becomes a first-class event on the bus, downstream policies can react to it, the audit trail is the event log itself.

```ruby
command "PetitionChange" do
  attribute :subject,        EntityRef
  attribute :proposed_rule,  ProposedRule
  attribute :reason,         ReasonText
  attribute :requested_at,   Timestamp
  emits "ChangePetitioned"
  # Adapter chains Cascade.RecordResult with the petition outcome ;
  # outcome is "applied" / "rejected" / "queued_for_review".
end
```

**Pros** : reuses existing Cascade infrastructure. No new state machine. Same shape every tool invocation already has. Naturally extends to events downstream policies might want to listen to (e.g. "when a petition for `Person` is applied, also re-key every Booking record that references a Person").

**Cons** : conflates identity governance with tool-outcome semantics. Cascade is currently about tool execution outcomes (the result of running Bash, Grep, etc.) — bending it to carry petition outcomes muddies what Cascade IS. Also doesn't natively express the "needs review" middle state ; petitions either complete via Cascade or they don't, and the half-way "submitted, waiting" state has to be modeled out of band.

**When this is right** : if identity changes are agent-driven (macrophages and refactoring tools generate most petitions) and the same event-substrate that tracks tool execution is the right place to track them.

### Personal recommendation (the card does not lock this in)

I'd advocate **Shape α (petition as bluebook command)** as the first-cut, for two reasons :

1. **Identity governance is meaningfully different from tool execution.** Cascade is for runtime outcomes that downstream policies react to ; petitions are deliberate intent. The shape difference matters because the audit trail looks different — petitions have a "review" step that tool invocations never have. Modeling petitions as their own state machine surfaces that difference cleanly. Modeling them as Cascade events flattens it.

2. **The state machine is the value.** Submitted → under_review → applied OR rejected. That's the substance of governance. A petition that's been submitted but not reviewed is meaningfully different from one that's been applied ; the bluebook should know which is which. Shape α makes the state machine explicit ; Shape β has no middle state ; Shape γ has to fake the middle state through external bookkeeping.

The cost is verbosity (three or four commands instead of one). That's worth it for the first iteration — Chris can collapse to Shape β or γ later if identity changes turn out to be mostly mechanical and review-by-default is overhead. Easier to remove than to add.

**Chris's call.** None of the three is wrong ; the choice depends on how heavyweight Chris wants identity governance to be in 2026-H2.

## The migration mechanic in detail

(Already covered above in responsibility #3. Summary :)

- Repository keys become `<new>||<old>||<older>||...` chains.
- Single pipe `|` is the natural-key field separator inside a single identity string.
- Double pipe `||` is the migration-chain separator between identities.
- Lookups split on `||` and match against any segment.
- Migrations are recorded as `MigrationChain` audit entries on the IdentifierService.
- References stored in other aggregates' attributes are resolved lazily — IdentifierService.lookup tolerates old forms forever.

## Relationship to i611

i611 (sister card, `inbox/i611.md` on `sq/i611-identity-overhaul`) describes the discipline — the rules natural-key identity follows, the macrophage that enforces them, the DSL surface for `suffix:` and `singleton:`, the phased rollout. i611's macrophage (IdentityDiscipline, landed in commit `8bba29cb` on the same branch) is the STATIC check — it complains about bluebook structural violations of the contract.

i614 is the RUNTIME side of the same coin. IdentityDiscipline polices the bluebook spec ; IdentifierService implements the operations the spec implies. Together they cover the contract (i611's macrophage) and the substrate (i614's service).

The two cards are intentionally separate :

- i611 is mostly a discipline document plus a macrophage. Phase 1-2 of i611 don't even touch the runtime — they just teach the parser the new DSL forms and add the static check.
- i614 lands as soon as the runtime needs to derive identities for actual records. That can be concurrent with i611 phase 3 (Tools.bluebook conversion) but doesn't depend on i611 phases 1-2 being green first.

When both have landed, the bluebook says what identity is, the macrophage enforces it, and the service implements it. Three-legged stool.

## Relationship to i613

i613 (StoreHouse wraps every aggregate command at the bluebook level, branch `sq/i613-storehouse-wraps-every-command`) makes every command flow through a domain aggregate — the storehouse universal door becomes the dispatching site for every domain action, no exceptions. The IdentifierService IS one of those aggregates. Its commands (`MintDefault`, `DeriveNaturalKey`, `RecordMigration`, plus the petition commands of whichever shape we pick) flow through `storehouse__dispatch` like every other bluebook command. There is no separate "identity API" — it's just the bluebook.

This matters because it means IdentifierService is observable in the same way every other domain aggregate is : its events appear on the storehouse://events resource, its state is queryable via `storehouse__state`, its commands are catalogued via `storehouse__catalog`. Identity work is first-class in the system, not a side concern.

It also means the IdentifierService's own commands are governed by the same discipline machinery as every other command. The IdentityDiscipline macrophage will inspect IdentifierService's bluebook and complain if it declares `attribute :id, Id` (which it must not). The line-count discipline applies. The companion-block discipline applies. The service is not exempt from its own discipline — it lives by the same rules it implements.

## Acceptance criteria

This card closes when :

1. **The bluebook exists** : `aggregates/framework/identifier_service/identifier_service.bluebook` is in main, validated, with the four responsibilities expressed as commands on at least one aggregate.

2. **The macrophage hooks into IdentifierService for identity minting** : the runtime path that today mints synthetic IDs for cascade-only records (and future UUID-default-on-missing-`identified_by` paths) dispatches `IdentifierService.MintDefault` instead of doing the mint inline. Every UUID minted in the system flows through the service.

3. **Natural-key derivation runs through IdentifierService** : the runtime substrate that converts an aggregate's IR + record into an addressable string is wrapped behind `IdentifierService.DeriveNaturalKey`. Repositories ask IdentifierService for the address ; they do not derive it themselves.

4. **At least one petition shape is implemented** : whichever of α / β / γ Chris picks. The petition machinery must accept at least one petition, walk it through whatever state machine the shape implies, and emit the outcome event. This is the smoke-test for "the service can do governance."

5. **Repository migration support is live** : at least one bluebook (proposed : a sandbox aggregate to keep the blast radius small) demonstrates `RecordMigration` flowing through IdentifierService and a subsequent lookup against the old identity returning the migrated record. The `new||old` storage form is observable in the `.heki` store.

6. **Cross-references to i611, i613 are in place** : i611's bottom carries the cross-reference paragraph naming i614 ; i613's main card (once it merges) names IdentifierService as one of the storehouse-dispatch-targets it covers.
