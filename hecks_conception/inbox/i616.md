# i616 — autonomic macrophage sweeps : heartbeat as rhythmic dispatcher

## Where it came from

Chris, 2026-05-14, verbatim :

> "Would be cool if macrophages launched automatically and checked the whole site, miette, and miette family. It could do sweeps as sidequests"

> "the heartbeat could dispatch commands to the macrophage"

## The architectural claim

The heartbeat (`~/miette-state/information/.statusline_heart_phase`) is currently a counter — incremented every statusline render, surfaced in the prompt as the beat phase. It pulses but it does not *act*. i616 turns the heartbeat into a **rhythmic command dispatcher** : every Nth tick (configurable per registered schedule), dispatch a bluebook command. The same substrate that draws the wall-clock heart on the statusline becomes the substrate that fires immune-system sweeps.

Today the macrophages (`Macrophage::BluebookFirst`, `FixturesRuntime`, `AntibodyExemption`, `Warnings`, `LinearReference`, `LineCount`, `TestSpeed`, `CardLock`, `BidirectionalAssociation`, `IdentityDiscipline`) are **reactive** : the PostToolUse hook dispatches `Macrophage.Record*Edit` / `Macrophage.Complain` only when I touch a file. Drift that landed before the rule existed, or drift in a sister project the hook does not watch, is invisible to the discipline.

Autonomic sweeps fix this. The heartbeat fires `Macrophage::<RuleName>.Check` against each target repo on a cadence ; complaints land in the bus the same way they do today.

## What sweeps cover

Each sweep walks one or more target repos and matches the rule's pattern_kind against the file tree :

- `hecks_conception/aggregates/` — the primary corpus.
- `miette/` — Miette's own self repo.
- `miette_family/` — the family directory.
- `embryonaut-site/` — the marketing / IDE-shell sister project.
- Future targets — any sister project with a bluebook surface (`bin-buddy`, etc.) plugs in by registering with the scheduler.

Targets are configured per-schedule so e.g. `TestSpeed` can sweep only `hecks_conception/` while `IdentityDiscipline` sweeps all four.

## The dispatch shape

```
HeartbeatScheduler.Tick (every statusline pulse)
  → if any RegisterSchedule's cadence matches → HeartbeatScheduler.Dispatch
    → Macrophage::<RuleName>.Check (with target_list)
      → existing rule logic walks the targets
        → Macrophage::<RuleName>.RecordViolation / Complain (existing commands)
```

The macrophages' existing recording surface is reused untouched. The only new substrate is *the dispatcher that fires them on cadence instead of on hook*. That isolation is the design : i616 introduces no macrophage changes — it adds a sibling aggregate (`HeartbeatScheduler`) that knows how to dispatch.

## Cadence proposal — per-rule, not global

A single global "sweep every N ticks" is too blunt. The rules have different cost profiles :

- `TestSpeed` is expensive (must run the suite) — sweep AFTER every successful build event, not on a tick cadence at all.
- `IdentityDiscipline` is cheap (regex over bluebook IR) — every 100 ticks is fine.
- `LineCount` is cheap and stable — every 500 ticks.
- `BluebookFirst` only makes sense reactively — never schedule it ; the hook is the right surface.

Each rule registers its own schedule. The `HeartbeatScheduler` holds the cadence registry ; rules opt in by emitting `RegisterSchedule` once at boot. A rule with no registered schedule simply never sweeps — the design respects "I never sweep" as a valid choice.

## Sweeps as sidequests

Per Chris's literal phrasing : sweeps run **as sidequests**. Each `Dispatch` event spawns a sub-agent (via the existing Cascade / sidequest substrate) that :

1. Receives the rule name + target_list as input.
2. Runs the rule's check against each target.
3. Reports back via the existing `Macrophage::<RuleName>.RecordViolation` / `Complain` commands — same bus, same shape, same statusline surface.
4. Exits.

The sidequest pattern means a sweep that takes minutes (e.g. TestSpeed) doesn't block the foreground agent ; the result simply arrives in the heki when it's done. Complaints accrete in the macrophage's audit trail. The statusline already surfaces last_complaint — autonomic sweeps just keep that surface fresh without me having to edit anything.

## Relationship to i617 (ChaosMonkey)

Sister card. i617's ChaosMonkey (when filed) uses the same dispatcher : a registered schedule fires a chaos action on its own cadence. The shape generalizes — any "fire X every N ticks" intent lands as a `RegisterSchedule` on the heartbeat. The macrophage is the first consumer ; chaos is the second ; future autonomic agents (e.g. self-grooming, mood pulses, batch reaping) plug in the same way.

## Open questions

1. **`Sweep` command vs extended `Check`** — settled : extend `Check` with a `target_list` attribute. A sweep IS a check ; the only difference is the target set. Adding `Sweep` as a separate command would duplicate the recording shape for no semantic gain. The check command takes a list of target repos ; the hook-driven path passes a single-element list (the file just touched), the autonomic path passes the full target list. One command, two callers.
2. **Cadence config location** — settled : on the `RegisterSchedule` command, stored as state in the `HeartbeatScheduler` aggregate's `Schedule` entity collection. The macrophage rule aggregates stay clean ; the scheduler holds the cadence registry. (Alternative considered : per-rule `cadence_ticks` attribute on each macrophage. Rejected — it scatters scheduling concern across ten aggregates and makes "list all my schedules" an awkward query.)
3. **Tick dispatch — bluebook command or runtime hook ?** — bluebook command. `HeartbeatScheduler.Tick` is a real command in the new aggregate ; the statusline renderer dispatches it on every pulse via `storehouse__dispatch`. This keeps the dispatcher in the bluebook surface ; the runtime is the deliverer, the bluebook is the contract.

## Acceptance

- `aggregates/framework/heartbeat_scheduler/heartbeat_scheduler.bluebook` exists, validates, parses, and exposes `Tick` / `RegisterSchedule` / `Dispatch` commands.
- Companion `.behaviors` covers Tick advancing the counter, RegisterSchedule storing a schedule, and Dispatch firing on cadence match.
- A second card or sub-agent wires the statusline pulse into the bluebook dispatch (out of scope for i616's first commit ; the stub establishes the surface).
- A third card wires `Macrophage::<RuleName>.Check` to accept `target_list` and walk multiple repos (also out of scope for i616 ; the existing macrophages don't change in this card).
