# i617 — ChaosMonkey : resilience-by-disturbance on a circadian rhythm

## Chris (verbatim, in order, 2026-05-14)

> "we should also have a ChaosMonkey that modifies runstate to be invalid and checks to see if the tests run."

> "it can be dispatched by the heartbeat as well"

> "or actually, it can be the first thing dispatched by circadian"

> "its okay that it breaks things live - it will push us to be more resilliant. It can report on weaknesses"

## The shape

A `ChaosMonkey` aggregate that **actively corrupts runtime state** and then verifies whether the discipline layer (tests + macrophages) catches the corruption. Borrowed in spirit from Netflix's ChaosMonkey — but bluebook-native, weakness-reporting, and dispatched by a circadian rhythm rather than wired into infrastructure.

The verification cycle is the load-bearing part. A chaos perturbation is only valuable if the system reacts to it. So every corruption is paired with an explicit verification — did the discipline layer notice ? If yes, the system is resilient to that class of failure. If no, the system has a blind spot, and ChaosMonkey makes that blind spot visible.

## What makes this different from Netflix's ChaosMonkey

1. **Bluebook-native.** The corruption isn't an external script poking at infrastructure ; it's a bluebook command (`CorruptAttribute`, `BreakReference`, `CorruptHeki`) dispatched on a bluebook aggregate. The act of corruption goes through the bus — it's an event with a chronicled cause.

2. **Production-acceptable.** Chris's commitment, verbatim : *"its okay that it breaks things live - it will push us to be more resilliant."* This isn't a staging-only tool. The disturbance IS the discipline. (See "Production safety boundaries" below — some surfaces stay exempt.)

3. **Weakness-reporting.** Every corruption is followed by verification. When verification finds nothing, the gap gets a name and a record. The audit trail becomes the backlog for growing macrophage / test coverage.

4. **Daily, not tactical.** Heartbeat (i616) fires on every invocation — fast, per-turn, sweep-shaped. Circadian is slower : once per day, or once per session boot, or configurable. Chaos lives at the strategic rhythm, not the tactical one.

## Three corruption modes (first draft)

The bluebook stub ships with three corruption commands. Each mutates state in a way the discipline layer SHOULD catch ; whether it does is the experiment.

### 1. `CorruptAttribute`

Mutate an aggregate's attribute to a value the value-object should reject.

Example : a `Money` VO with negative cents ; a `Timestamp` VO with non-ISO text ; an `EditCount` VO with a string instead of an integer. A well-disciplined system catches this at the boundary (the VO refuses construction) or downstream (a behavior fails ; a query renders wrong).

### 2. `BreakReference`

Change an aggregate's `reference_to(X)` to point at a non-existent id.

Example : `Order.customer_id = "ghost"`. A well-disciplined system catches this in any query that resolves the reference, or via a macrophage that checks ref integrity. A blind spot here means dangling refs can persist undetected.

### 3. `CorruptHeki`

Mutate the on-disk `.heki` file directly — bypass the bus, write malformed JSON / wrong schema / outright garbage.

This tests the **load path**, not the runtime path. Does the runtime fail loudly on next boot ? Does it silently swallow the bad row ? Does it crash mid-load ? This is the deepest layer of disturbance — the system has to defend itself from its own persistence.

## The verification cycle

```
1. ChaosMonkey.PerturbCircadian fires  (dispatched by circadian)
2. ChaosMonkey picks an aggregate + corruption kind  (random or weighted)
3. Records the original value (for revert)
4. Dispatches CorruptAttribute / BreakReference / CorruptHeki
5. Dispatches RunVerification  →  runs tests + macrophage sweep
6a. If discipline flags the corruption  →  RecordWeakness(found_by: …)
6b. If discipline stays silent          →  RecordWeakness(blind_spot: true)  ⚠ loud surface
7. Dispatches RevertCorruption  →  restores the original value from step 3
```

A `Corruption` entity persists for each act : timestamp, target, kind, before/after, outcome. A `Weakness` entity persists only for uncaught corruptions — that's the backlog of blind spots.

## The circadian dispatcher — open question

Chris's directive : *"or actually, it can be the first thing dispatched by circadian."* So circadian is the dispatcher. The question is whether circadian is its own aggregate or a cadence-mode of `HeartbeatScheduler` (the i616 proposal).

**Recommendation : separate aggregate, lightly coupled.**

Reasons :
- Heartbeat is per-invocation. Circadian is per-day (or per-session, or per-N-invocations). The cadence is materially different — heartbeat ticks dozens of times per session, circadian ticks once.
- Heartbeat's payload is "run all sweeps" — the discipline layer scanning for known violations. Circadian's payload is "introduce a disturbance" — the discipline layer being tested.
- Sweep-vs-test is a meaningful conceptual seam. Folding both into one scheduler would conflate the audit (heartbeat) with the experiment (circadian).
- Circadian can subscribe to heartbeat events if it needs a clock signal — but its own cadence is computed from `last_fired_at`, not from "every heartbeat".

A future `Circadian` aggregate (or `CircadianScheduler`) would own : `last_fired_at`, `cadence` (daily / per-session / per-N-invocations), and a single command `Tick` that fans out to ChaosMonkey + any other slow-rhythm subscribers. This card does NOT lock that down ; i617 + i616 surface the need, the dispatcher aggregate gets its own card.

## Production safety boundaries

Chris's go-ahead to break things in production is real. Still, some surfaces are off-limits — corruption there would hurt rather than harden :

- **Financial transactions** (Stripe / Plaid / anything money-moving)
- **User-facing customer commitments** (bin-buddy pickup commitments, scheduled routes)
- **External-API side effects** (anything that calls out and can't be reverted)
- **Migrations in flight** (corrupting an aggregate mid-migration is destructive, not informative)

The bluebook stub includes an `ExemptedTarget` entity. ChaosMonkey reads exemptions before picking a target ; the exemption list lives in the aggregate state itself (bluebook-native, dispatchable, queryable). Exemptions can be added by `ExemptTarget` with a required `reason` — same shape as `[antibody-exempt: file — reason]` markers Chris already trusts.

## Corruption-revert policy

**Proposed : auto-revert on, opt-out per-corruption.**

The default cycle ends with `RevertCorruption` restoring the original value. The corruption is intentional + recorded, not a persistent break. This keeps live systems usable while still giving the discipline layer a real test.

A `Corruption` may carry `revert_policy: "auto" | "manual" | "leave"` :
- `auto` (default) — revert immediately after `RunVerification`
- `manual` — wait for an operator `RevertCorruption` dispatch (useful when a weakness is discovered and Chris wants to inspect the broken state before restoring)
- `leave` — never revert (only for corruptions explicitly meant to persist, e.g. when ChaosMonkey is being used to seed a deliberately-broken fixture for a debugging session)

The default safety floor : if `RevertCorruption` fails (target deleted, heki write fails, etc.), ChaosMonkey emits a loud event so the system can surface the failed-revert as a real problem.

## Relationship to i616

i616 (heartbeat / macrophage sweep) and i617 (circadian / ChaosMonkey) are sister cards — together they form the **autonomic discipline layer** :

| Rhythm    | Dispatched by | Purpose                       | Posture                  |
|-----------|---------------|-------------------------------|--------------------------|
| Heartbeat | every invocation | macrophage sweep            | audit — what already exists |
| Circadian | once per day  | chaos perturbation            | test — what would break    |

Heartbeat finds the violations the system already has. Circadian finds the violations the system would tolerate. The pair gives the discipline layer both eyes — passive and active.

## Acceptance (first-draft contract)

- `ChaosMonkey` aggregate parses + validates clean.
- Commands : `CorruptAttribute`, `BreakReference`, `CorruptHeki`, `RunVerification`, `RecordWeakness`, `RevertCorruption`, `ExemptTarget`, `PerturbCircadian`.
- `Corruption` + `Weakness` + `ExemptedTarget` entities persist via the bus.
- Behaviors stub : at least one test per command. Implementation (the actual corruption + verification mechanism) is later substrate work — i617 ships the contract, not the engine.
- Verification runner : a placeholder command for now (`RunVerification` records an outcome ; the wiring into the actual test runner + macrophage sweep is a follow-up).

## Open questions (carry-forward for future cards)

- Is `Circadian` its own aggregate, or a cadence-mode of `HeartbeatScheduler` ? *(recommendation : own aggregate ; needs its own card)*
- Auto-revert : always-on, or per-corruption ? *(recommendation : auto default, opt-out via revert_policy)*
- When ChaosMonkey breaks a live system, what's the operator-notification shape ? *(loud stderr complaint via macrophage hook ? a dedicated `WeaknessAlarmed` event ? both ?)*
- Should `ChaosMonkey` weight which aggregates it picks based on past Weaknesses (favouring blind-spot adjacent aggregates) ? *(probably yes ; meta-learning over the audit trail.)*
- Does the `RunVerification` runner shell out to `hecks verify` + a macrophage sweep, or does it dispatch named verification commands ? *(the latter is bluebook-native ; recommend dispatching `Macrophage::Macrophage.RunSweep` (i616) + a `Verification.RunSuite` command yet to be specified.)*
