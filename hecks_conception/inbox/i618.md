# i618 — ResponseEmitted : response payload on the event, cumulative chain per turn

## Verbatim from Chris (2026-05-14)

> "when we spawn a prompt, your result should be in the event - your response. If there are several responses each should be attached to a new event that has all of your responses"

## What i615 left unspecified

i615 (merged to main, commit `e8287f8e`) introduced three events that route the receive-and-think layer through StoreHouse :

- `StoreHouse.PromptReceived` — fires when a prompt arrives.
- `StoreHouse.Unfurling` — fires when reasoning begins.
- `StoreHouse.UnfurlingComplete` — fires when reasoning ends, with duration.

What i615 did **not** specify : where the model's actual response text goes. The three events cover the input-and-reasoning layer. The output layer — the text the model produces after unfurling — is still absent from the bus. i618 closes that gap.

## The proposed event — `StoreHouse.ResponseEmitted`

Chris's directive contains two interlocking constraints :

1. **The response lives in the event** — not in a separate log, not in state only. The event payload carries the response text.
2. **When there are multiple responses, each gets its own event, and each event carries all prior responses** — cumulative, not differential.

Together these define a single new event command : `StoreHouse.ResponseEmitted`.

### Shape

```
ResponseEmitted {
  response_text      : String           # the current response (this turn-fragment)
  prior_responses    : List(String)     # ALL prior responses in the same conversational turn, in order
  response_index     : Integer          # 1-based position of this response within the turn
  correlation_id     : CorrelationId    # links to the originating PromptReceived
  turn_complete      : Boolean          # true if this is the final response in the turn
}
```

Plus the standard i613 envelope (timestamp, source, session_id, etc.).

### The cumulative pattern

Event N carries responses 1 through N — not just response N. This is the load-bearing constraint from Chris's directive : "all of your responses" on each event.

Concretely : if a turn produces three response fragments (initial text → tool result absorbed → more text → another tool result → closing text), the events read :

| Event | `response_text` | `prior_responses` |
|-------|----------------|-------------------|
| ResponseEmitted #1 | "first fragment" | [] |
| ResponseEmitted #2 | "second fragment" | ["first fragment"] |
| ResponseEmitted #3 | "third fragment" | ["first fragment", "second fragment"] |

A reader who pulls only event #3 sees the complete response chain for the turn without replaying earlier events.

### Tradeoff : quadratic payload growth

The cumulative pattern means event N is at least as large as event N-1 plus the new response. In a turn with K responses of average length L, total payload stored is O(K² × L). For a short turn (2–3 responses) this is benign. For a long agentic turn with many tool calls and intermediate responses, it can grow materially.

Three mitigation options, in order of implementation complexity :

**Option A — payload-as-is (ship first)** : store the full cumulative chain in every event. Simple to implement, honest representation of Chris's intent, fine for typical turn lengths. Revisit if specific turns produce objectionably large events.

**Option B — reference compression** : each ResponseEmitted stores `response_text` (current) plus `prior_response_ids` (a list of correlation IDs pointing to prior events) rather than the full prior text. A reader wanting the full chain follows the references. Reduces storage to O(K × L) at the cost of multi-event reads for full reconstruction.

**Option C — state-vs-payload split** : aggregate state holds the latest response only; the event payload carries the cumulative chain. This is already the natural CES (command-event-state) shape — state is a projection of events, not a separate store. No change to the event shape, but makes clear that state readers get a "latest response" view and event readers get the full chain. This is the recommended framing even with Option A — it clarifies what state vs events are for.

**Recommendation** : start with Option A (full cumulative payload), framed as Option C (state holds latest, events hold chain). Revisit compression if turn lengths regularly exceed, say, 10 responses.

## Multi-turn flow walkthrough

A concrete sequence for a turn that includes two tool calls :

```
[1] StoreHouse.PromptReceived
      turn=7, correlation_id=CID-7, source=user, prompt_length=142

[2] StoreHouse.Unfurling
      correlation_id=CID-7, started_at=T+0ms

[3] StoreHouse.UnfurlingComplete
      correlation_id=CID-7, duration_ms=1200, outcome=both

[4] StoreHouse.ResponseEmitted
      correlation_id=CID-7
      response_index=1
      response_text="I'll check the file first."
      prior_responses=[]
      turn_complete=false

[5] Tools::FileTool.Read (correlation_id=CID-7)
      ... Cascade.RecordResult fires ...

[6] StoreHouse.ResponseEmitted
      correlation_id=CID-7
      response_index=2
      response_text="The file looks fine. Running the spec now."
      prior_responses=["I'll check the file first."]
      turn_complete=false

[7] Tools::ShellTool.Bash (correlation_id=CID-7)
      ... Cascade.RecordResult fires ...

[8] StoreHouse.ResponseEmitted
      correlation_id=CID-7
      response_index=3
      response_text="Specs pass. Done."
      prior_responses=["I'll check the file first.", "The file looks fine. Running the spec now."]
      turn_complete=true
```

The full conversation state of turn 7 is recoverable from any single event with `correlation_id=CID-7`. A reader who arrives late and sees only event [8] reconstructs the complete response chain from `prior_responses` alone.

## Why cumulative rather than diff-style

The alternative — each event carries only the new response, and a reader replays to reconstruct — requires ordering guarantees and sequential access. A reader who misses an event cannot reconstruct the chain. A reader who wants to audit a specific moment must replay from the beginning of the turn.

The cumulative approach trades storage size for read simplicity. Each `ResponseEmitted` is **independently meaningful** : it is a complete snapshot of the response chain up to that moment. This property matters for :

- **Audit / forensic reads** — drop into any point in the event stream and see the full conversation state.
- **Replay without ordering deps** — if events are delivered out of order (unlikely but possible in a distributed future), any event is self-sufficient.
- **Debugging** — paste a single event into a log query and the full context is there.

The cost is acknowledged (quadratic growth). The payoff is a structurally simpler read path.

## Open questions

### State-vs-payload boundary

Does aggregate state hold only `latest_response` (simple, LRU-style), or the full `response_chain` list ?

The event-sourcing convention is : state is a projection for live queries ; events are the source of truth for history. So state holding `latest_response` is clean — if you want the chain, query the event log. If you want the current response, query state.

This means state size is O(L) (one response) and event payload size is O(K × L) per event. That is the cleanest split.

### Compression strategy for long turns

At what point does a turn become "long enough" to warrant reference compression (Option B) ? This should probably be driven by observed data rather than a pre-set threshold. A reasonable flag : if any single `ResponseEmitted` payload exceeds a configurable byte limit (e.g., 32KB), emit a `ResponseChainOverflow` notice and switch to reference mode for that turn's subsequent events.

This is speculative — file as a follow-on rather than blocking i618.

### Relationship to `Cascade.RecordResult`

i608 / Tools.bluebook wires tool results through `Cascade.RecordResult`. A `ResponseEmitted` event conceptually wraps everything between two `RecordResult`s. The question is whether `Cascade.RecordResult` fires *inside* the ResponseEmitted payload (the response text already incorporates the tool result) or whether the tool result is a peer event on the bus.

The cleaner model : `RecordResult` is a peer. The model receives the tool result, reasons about it, and the *new response text* that follows goes into the next `ResponseEmitted`. The tool result is not embedded in `ResponseEmitted` — it is captured by Cascade's own event chain. The `correlation_id` ties everything together.

This matches how the flow walkthrough above is drawn (step [5] Cascade, step [6] next ResponseEmitted).

### Harness hook surface for response capture

i615's hook wires `UserPromptSubmit` to capture `PromptReceived`. What hook captures the *response* ? The harness likely exposes a `Stop` hook (fires at turn end) and possibly a streaming-output hook for intermediate response fragments.

If only `Stop` is available : a single `ResponseEmitted` per turn, no intermediate events. This is a degenerate but valid implementation — `prior_responses=[]`, `turn_complete=true`, one event per turn. Still useful ; adds the response payload to the bus.

If streaming hooks are available : full multi-fragment ResponseEmitted chain as described above.

Implementation should ship the Stop-hook version first and extend to streaming fragments if/when the harness exposes them.

## Relationship to parent and sibling cards

**i615 (parent)** — i618 is a direct extension. i615 specifies PromptReceived / Unfurling / UnfurlingComplete. i618 specifies the fourth event in the same turn sequence : ResponseEmitted. Together the four events close the full turn loop : *received → thinking → done thinking → responded*.

**i613 (envelope)** — ResponseEmitted rides the same envelope structure as all StoreHouse events. `correlation_id`, `timestamp`, `session_id`, `source` are standard envelope fields. i618 adds no new envelope machinery.

**i614 (migration-on-string)** — not directly related to ResponseEmitted's shape. Indirectly relevant if response text ever becomes an identity-bearing field (unlikely). Noted for completeness.

**i619 (sister, concurrent)** — i619 introduces *handlers* as the structural mechanism that PRODUCES the response text that goes into ResponseEmitted. i618 specifies the event shape (what the payload looks like and when it fires). i619 specifies the mechanism that fills it (handlers receive the prompt and produce the response). The two cards are complementary : i618 is the receptor, i619 is the organ that produces what goes into it. i619 should reference i618's `ResponseEmitted` shape as the emit target.

## Acceptance criteria

Closes when :

1. `StoreHouse.ResponseEmitted` command exists on the StoreHouse aggregate (or its successor per i613's Shape decision).
2. The command accepts `response_text`, `prior_responses`, `response_index`, `correlation_id`, and `turn_complete` attributes.
3. A harness hook captures model responses and dispatches `StoreHouse.ResponseEmitted` on every turn — minimum via the `Stop` hook (single event per turn), extended via streaming hooks if available.
4. The `correlation_id` on `ResponseEmitted` matches the `correlation_id` on the originating `PromptReceived` for the same turn.
5. In a multi-response turn, each `ResponseEmitted` event carries the full cumulative `prior_responses` chain from earlier events in the same turn.
6. The `turn_complete=true` flag fires on the final `ResponseEmitted` of a turn.
