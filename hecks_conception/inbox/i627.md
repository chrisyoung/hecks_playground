# i627 — Autophage : DeployParity

## The incident that surfaced it

Joey ("hasn't seen his recent asks") was reviewing `opt-website.pages.dev`
which last deployed `fa805ac`, 4 days stale. PR #2 (his entire 13-update
batch) merged to main but the deploy step was never run. The project is
wrangler-CLI deployed, not git-connected, so a push to main does nothing
on its own. Every prior session merged and moved on. The client looked at
old work for days and reasonably concluded nothing happened.

I compounded it : truncated `wrangler pages project list` with `tail`,
didn't see the existing `opt-website` project, wrongly concluded "no
project exists," created a redundant `opt-beyond-fitness`, then had to
tear it down. The diagnostic thrash itself is a symptom of having no
deploy-state contract to read.

## What

An autophage that watches the contract : **for each site repo, the
production deployment's source commit should equal the repo's main
HEAD**. When main advances past the deployed commit, that is drift, and
it surfaces as additional-context.

```
aggregate "DeployParity" do
  attribute :repo, Path
  attribute :pages_project, String
  attribute :main_head, CommitSha
  attribute :deployed_commit, CommitSha
  attribute :deployed_at, Time
  attribute :drift_age, Duration       # how long main has been ahead
  attribute :git_connected, Boolean    # auto-deploy on push, or CLI-only

  command "Check"
  command "Clear"

  query "stale_deploys" do
    description "Every DeployParity where main_head != deployed_commit"
  end
end
```

`git_connected: false` is itself a finding worth surfacing : a CLI-only
Pages project is one forgotten command away from this incident every time.

## Connects to

  - **i625 NavSitemapParity** : same shape (a two-state contract nothing
    watches). DeployParity is the deploy-time sibling of the nav-time one.
  - **i626 Fibroblast** : the natural repair path. When DeployParity
    finds main ahead of the deployed commit and the repo is a known
    static-site project, Fibroblast's closing move is to run the deploy
    and re-check. This is one of the *unambiguous* fixes Fibroblast is
    explicitly scoped for : the diagnostic data (repo + project name +
    HEAD) uniquely determines the action.

## Closes when

  - Bluebook at `aggregates/discipline/autophage/deploy_parity/`
  - Registered for the four live site repos : embryonaut-site, emaho,
    opt-website, bin-buddy (+ any future client site)
  - Drift surfaces on first turn when any site's main is ahead of deploy
  - Fibroblast (i626) wired as the closing path for static-site repos
  - Separately : evaluate git-connecting opt-website's Pages project so
    push-to-main auto-deploys, removing the manual step entirely. The
    autophage stays valuable even then (catches failed builds), but
    git-connection removes the most common cause.
