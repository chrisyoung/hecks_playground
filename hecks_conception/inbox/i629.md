# i629 — :shell adapter family : fold the inbox poll into Inbox.Check dispatch

## Done 2026-05-15 (declarative contract — bluebook-first half)

- `framework/adapter_families/shell.hecksagon` — the :shell family.
  Fields name / command / exec / result_into ; trigger_field :command ;
  one behavior :perform_shell_exec ; no providers (the exec is the
  provider ; empty providers is the fence against a god-adapter).
- `framework/behavior_kinds/perform_shell_exec.hecksagon` — the
  behavior : run :exec to completion, cwd = aggregates-root-parent,
  capture stdout/stderr/exit, cap stdout 100 KB, cascade into
  :result_into. Non-zero exit recorded not raised.
- `framework/inbox/inbox.hecksagon` — binds `command: "Inbox.Check"`
  to `exec: "node bin/inbox_poll.mjs"`, result_into Cascade.RecordResult.

The contract is complete and committed. The poller (bin/inbox_poll.mjs)
already runs correctly one-shot (its default mode), which is exactly
what the adapter invokes — no poller change needed.

## Parser-parity finding (2026-05-15) — part of the kernel pass

The consumer binding (`framework/inbox/inbox.hecksagon`) is the FIRST
hecksagon anywhere to use `name:` on an `adapter` row (tools.hecksagon's
claude_tool/web_tool rows omit it). It immediately exposed a Ruby/Rust
hecksagon-parser disagreement :

```
L14  Ruby: "name": "inbox_poll"
     Rust: "name": "\"inbox_poll\""
```

The Rust hecksagon parser does not strip the surrounding quotes from a
string `name:` value on a non-builtin family's adapter row ; Ruby does.
The hecksagon-parity pre-commit gate correctly blocked the binding. Not
skipped, not exemption-pre-empted — it is a real parser bug.

The exact binding to land WITH the parser fix :

```
Hecks.hecksagon "Inbox" do
  adapter :memory
  adapter :shell,
          name:        "inbox_poll",
          command:     "Inbox.Check",
          exec:        "node bin/inbox_poll.mjs",
          result_into: "Cascade.RecordResult"
end
```

Added as **step 0** of the kernel pass : in the Rust hecksagon parser
(`rust/src/hecksagon_parser.rs`), make an adapter row's `name:` string
value strip its quotes identically to the Ruby parser
(`ruby/.../hecksagon` reader). One round-trip rule, both parsers, then
the binding above is parity-clean and lands with the dispatcher. The
family + behavior contracts (shell.hecksagon, perform_shell_exec.hecksagon)
are parity-clean and land now.

## Remaining : the Rust kernel arm (focused, parity-sensitive pass)

Mirror the closest analog, `web_tool_dispatcher.rs` (it already
shells out for WebFetch). Precise plan :

1. **`rust/src/runtime/shell_dispatcher.rs`** (new, ~100-140 lines).
   Mirror web_tool_dispatcher.rs structure : a `ShellResult`
   struct (output / exit_code / ok), a `dispatch(exec: &str,
   cwd: &Path) -> ShellResult` that splits exec into program+args,
   `std::process::Command` with cwd + inherited env, captures
   stdout/stderr, caps stdout 100 KB. Expose
   `register_shell_hooks(&mut registry)` for framework_registry,
   same as `register_web_tool_hooks`. Antibody-exempt header,
   same wording pattern as web_tool_dispatcher.rs.
2. **`rust/src/runtime/mod.rs`** : `pub mod shell_dispatcher;`
   near the web_tool_dispatcher decl (~line 66) ; add
   `resolve_shell_adapters(&result, command_name, &ctx.attrs)`
   in `dispatch` next to `resolve_claude_tool_adapters` (~line
   386) ; implement `fn resolve_shell_adapters` mirroring
   `resolve_claude_tool_adapters` (~line 755) — find the :shell
   adapter whose `command` matches, read its `exec`, call
   `shell_dispatcher::dispatch`, `dispatch_cascade` into
   `result_into`.
3. **`rust/src/runtime/framework_registry.rs`** : register the
   `shell` family + `perform_shell_exec` behavior alongside the
   web_tool / claude_tool entries (the file already walks
   adapter_families/ + behavior_kinds/ ; confirm the new
   hecksagons are picked up, add the hook slot).
4. **`cargo build --release`** the storehouse binary (multi-min).
5. **Specializer byte-identity golden** : adding
   `pub mod shell_dispatcher;` to runtime/mod.rs WILL drift the
   `rust_specializer_produces_byte_identical_runtime_rs` golden
   exactly as i622's `storehouse_log` did. The codegen fragment
   that emits the runtime mod list must be updated in lockstep
   (the HEADER/module-list fragment under codegen/) or the
   parity gate goes red. THIS is the trap that turns a 1-hour
   job into a tangle ; budget for it explicitly.
6. **Retire the transitional members** : delete the `inboxpoll`
   line from Procfile + the `inboxpoll` fixture from
   mindstream.fixtures. Remove the [antibody-exempt] markers from
   bin/inbox_poll.mjs's header that reference the transitional
   status (keep the file ; it is now the adapter's invoked
   program). The existing `inbox: storehouse loop aggregates
   Inbox::Inbox.Check --every 900s` member now performs the poll
   via the :shell binding — one member, one cadence, "no new
   process" literally true.
7. Verify : `storehouse__dispatch Inbox::Inbox.Check` (manual)
   writes a card + draft for a planted test thread ; `overmind`
   restart picks up the slimmed Procfile ; the bus shows the
   Cascade.RecordResult from the shell adapter.

## Why this was not rushed in-session

Kernel-floor + specializer-parity change at the tail of a long
session is how the storehouse binary (which the whole bus, including
the tool routing that wrote this card, runs on) gets broken. The
declarative contract — zero substrate risk — is done and committed.
The Rust arm is scoped to the file + function + line so the next
focused pass is mechanical, not exploratory. Step 5 is the only
non-obvious part and it is called out.
