# i629 — :shell/:exec adapter family (fold the inbox poller into Inbox.Check dispatch)

## The gap

The Inbox bluebook (`framework/inbox/inbox.bluebook`) locks Check to :
refresh the OAuth token, call Gmail `users.history.list` since the
historyId watermark, filter to registered correspondents, and per new
thread write a card + compose a draft. That is a multi-step local
executor. No existing adapter family can run it from a dispatch :

  - `:web_tool` — bridges ONE HTTP fetch (WebFetch/WebSearch shape).
  - `:mcp` / `:claude_tool` — bridge a single tool call.
  - `:sms` / `:tts` — provider-specific outbound.

None run "execute this local program and cascade its outcome."

## Transitional state (shipped 2026-05-15)

`bin/inbox_poll.mjs` (antibody-exempt, doc-headed) IS the Check
executor. It is wired as its own supervised member :

  - Procfile : `inboxpoll: node bin/inbox_poll.mjs --loop 900`
  - mindstream.fixtures : `inboxpoll` fixture, persistent, restart-on-failure

The existing `inbox` member (`storehouse loop ... Inbox::Inbox.Check
--every 900s`) stays as the bus tick / logging surface. Two members,
same 900s cadence : the bus records the Check, the script does the fetch.

## What closes this

A `:shell` (or `:exec`) adapter family : a hecksagon row binding
`command: "Inbox.Check"` to `exec: "node bin/inbox_poll.mjs"`, the
kernel runs it on dispatch and cascades the outcome through
Cascade.RecordResult like the other adapter families. Then :

  - delete the `inboxpoll` Procfile + mindstream members
  - the existing `inbox` loop's dispatch IS the poll
  - bin/inbox_poll.mjs becomes the adapter's invoked program (or is
    reimplemented inside the adapter), antibody-exempt marker removed
  - "no new process" (Chris's locked decision) is then literally true
