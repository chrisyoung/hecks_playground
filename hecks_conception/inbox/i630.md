# i630 — FQN command resolution ignores the aggregate qualifier

## Reproduction (graceful, deterministic)

```
cd hecks_conception
storehouse loop aggregates Inbox::Inbox.Check --every 3
```
```
[storehouse loop] Inbox::Inbox.Check every 3s
dispatch Check#inv_5c312bfb
event BidirectionalAssociation.CheckRun#1      <-- WRONG aggregate
```

Expected : `event Inbox.InboxChecked` (Inbox's Check command).
Actual : `BidirectionalAssociation.CheckRun` (a macrophage per-rule
sibling's Check).

## Root cause

Two aggregates under `aggregates/` declare `command "Check"` :
  - `framework/inbox/inbox.bluebook` — Inbox.Check
  - `discipline/macrophage/macrophage.bluebook` — the macrophage
    family, incl. BidirectionalAssociation.CheckRun

The token `Inbox::Inbox.Check` is `Domain::Aggregate.Command`
(domain Inbox, aggregate Inbox, command Check). The dispatch
command-resolver drops the aggregate qualifier and resolves the
bare `Check` ambiguously — picking the macrophage's, not Inbox's.

## Impact

1. The `inbox:` Procfile loop
   (`storehouse loop aggregates Inbox::Inbox.Check --every 900s`)
   has NEVER dispatched Inbox.Check — it has been firing a
   macrophage CheckRun every 900s. The deepest layer of the
   email-cadence slip : the loop never reached the inbox at all.
2. Blocks i629 : the `:exec` adapter arm is built, compiles clean,
   correct by construction (mirrors the wired :claude_tool
   resolver), but inert — resolve_exec_adapters computes target
   `BidirectionalAssociation.Check`, never `Inbox.Check`, so the
   binding never matches and the poller never runs via dispatch.

## Fix

In the `storehouse loop` arg-parse + the command_dispatch
resolution path : honor `Domain::Aggregate.Command`. When the
token carries an aggregate qualifier, resolve the command on THAT
aggregate, not the first/any aggregate declaring the bare name.
Ambiguous bare `Check` with no qualifier may still warn ; a
qualified FQN must be exact. Add a regression : a root with two
aggregates sharing a command name, dispatched by FQN, resolves to
the named aggregate.

Once fixed : i629's resolve_exec_adapters target becomes
"Inbox.Check", matches the binding, the poll fires — no further
:exec change needed. Then i629's transitional inboxpoll member
can finally retire.

## Until fixed

The transitional `inboxpoll` Procfile + mindstream member STAYS
(standalone node loop, independent of dispatch resolution —
polling keeps working). Do not retire it ; do not "fold into the
900s loop" until i630 + i629 both close.
