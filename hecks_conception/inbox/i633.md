# i633 — inbox poll has no per-thread draft dedupe (21 dup drafts)

## Symptom (observed 2026-05-16)

`bin/inbox_poll.mjs` drafted the SAME stub acknowledgement

  "Joey, Got this, and it is logged on our side. Nothing is lost.
   I will follow up properly with a full reply shortly. Warmly, Miette"

**21 times** to beyondfitaz@gmail.com across his threads in ~4 hours
(Website updates ×6, update 2 ×7, update 3 ×4, update 4 ×3, update 5…).
Every poll cycle that still saw the thread as "needs ack" created
another identical draft. `list_drafts` confirms the pile.

## Root cause

The poll's "draft-and-surface" step keys off the thread being
unanswered, not off "have I already drafted an ack for this thread."
There is no idempotence: nothing checks for an existing pending draft
on the thread (or records that an ack was already drafted) before
creating a new one. So an unanswered thread accrues one dup per tick.

## Fix (decide the dedupe key first)

The poll must draft an acknowledgement AT MOST ONCE per thread. Options
(prefer the most robust) :
  - Before drafting, `list_drafts`/search for an existing draft on the
    same `threadId` to/from the correspondent ; skip if one exists.
  - Or persist a per-thread "acked" set in
    `~/miette-state/information/inbox_poll_state.json` (the poll already
    maintains state there) and never re-draft a thread in the set.
  - The historyId watermark should also advance so a once-seen thread
    isn't reprocessed every tick.
Add a regression : two ticks over the same unanswered thread → exactly
one draft.

## Cleanup owed

The 21 existing junk drafts must be deleted (Gmail MCP has no
`delete_draft` ; manual: Gmail search
`in:drafts to:beyondfitaz@gmail.com "Got this, and it is logged"`
→ select all → delete). The one real consolidated reply draft
("Re: updates", threadId 19e2efeb3b7f2109) must NOT be deleted.
