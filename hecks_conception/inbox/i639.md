# i639 — Clock as a bluebook driven-adapter (retire the raw-SystemTime class)

## Why this exists
Chris, on the i630 close-out : "Seems like it should all be bluebook.
I don't know why it would require kernel changes." Correct. The i630
fix used the EXISTING hand-written `heki::now_duration()` (#cfg host
vs wasm32). That unblocked VinDiction but is a transitional adapter,
not the domain. i7 (interpreter.rs:402) is not a separate bug — it is
proof the kernel-discipline approach leaks : there is always another
raw `now()` until the clock is a declared capability.

## Design (the bluebook-first shape)
- A `:clock` (Time) **driven-adapter family**, declared in hecksagon,
  sibling to :exec / :mcp / :claude_tool / :llm / :tts.
- Two adapters behind the port :
  - host  → `std::time::SystemTime::now()` (the existing host body)
  - wasm32 → `worker::Date::now()` (the existing wasm body)
- `runtime_shape` fragments + `runtime::interpreter::emit` reference
  the **capability**, never `std::time` or `crate::heki::now_duration`.
- The specializer target-resolves the adapter body per build target
  (same mechanism that already emits host vs wasm worker code).
- Outcome : `heki::now_duration` becomes a generated artifact ;
  the `SystemTime::now()` leak class is structurally impossible
  (not discipline-guarded) ; i7 closes as a side effect.

## Scope / why carded not inline
New adapter-family arc : hecksagon parse + IR + runtime_shape
reference rewrite + specializer target-resolution + byte-identity
goldens (runtime, interpreter). Multi-step, kernel-adjacent. Deserves
a fresh focused session — starting it at the i630 session tail is the
documented lost-hours pattern (i643/i645). Design is locked above ;
implementation is mechanical from here.

## Closes when
`:clock` adapter family lands ; no `SystemTime::now()` /
`now_duration` references remain in runtime_shape frags or
interpreter emit ; host + wasm32 goldens green ; VinDiction worker
+ bin-buddy still dispatch ok ; i7 archived.
