# i639 — Tools::AgentTool : bus-dispatched agent orchestration (+ SendMessage runtime gap)

## Why
Every session Chris asks for "use storehouse for everything, especially
agent calls." Today agent spawn/stop/steer are harness tools (Agent,
TaskStop, TaskList), NOT bus-dispatched. SendMessage (steer a running
agent) is referenced by the Agent tool docs but is absent from this
environment's tool registry — this harness runs background agents
one-shot (launch -> detached -> notify), steerable only via stop +
inspect. Killing+relaunching a mis-specced sidequest (this session, the
inbox-emoji rework) is the cost of having no steer channel.

## Shape (bluebook-first)
A `Tools::AgentTool` category aggregate, sibling of ShellTool /
FileTool / SearchTool / WebTool in tools.bluebook :
- `AgentTool.Spawn`   (subagent_type, prompt, run_in_background) -> AgentSpawned
- `AgentTool.Stop`    (agent_id) -> AgentStopped
- `AgentTool.SendMessage` (agent_id, message) -> AgentMessaged
- result_into Cascade.RecordResult, same contract as the other Tools.

## The runtime gap (the honest part)
Storehouse can own the CONTRACT + dispatch. Spawn/Stop map onto
capabilities that exist (Agent / TaskStop). `SendMessage` requires the
runtime to deliver a message into a *running* agent's live context —
that mechanism does not exist in this harness's one-shot model. So :
the bluebook names it ; the kernel arm (an agent_dispatcher mirroring
exec_dispatcher / claude_tool_dispatcher) + the harness capability to
inject into a live agent must be built. Until then SendMessage is a
declared-but-stubbed door (warn + skip, like i610 server=gmail).

## 2026-05-17 — what actually landed (finding corrected the plan)

The agent surface was ALREADY largely modeled in tools.bluebook (18
category aggregates) : `Sidequest.Dispatch` = spawn, `TaskTool.Stop`
= stop, `TaskTool.Get/Output/List` = inspect. Adding a new
`AgentTool` would have DUPLICATED these (wrong direction) — caught by
inspecting before implementing. The one true missing piece was the
steer-a-running-agent command (the thing that forced this session's
kill+relaunch).

DONE : `Sidequest.SendMessage` command added to tools.bluebook
(value_object `AgentMessage` ; attrs id + message + description ;
emits SidequestMessageSent ; honest in-file RUNTIME-GAP doc). Mirror
behavior tests added. validate VALID (18 aggregates) ; macrophage
clean ; tools.behaviors 75/0/0. tools.bluebook is not specializer-fed
— no golden impact.

REMAINS (still a true runtime gap) :
  - No kernel arm delivers a message into a RUNNING agent's context
    (an agent_dispatcher sibling of exec_dispatcher + a harness
    deliver-into-live-agent capability). SendMessage is the declared
    contract only — same posture as the EmailTool :mcp bindings.
  - None of the agent aggregates (Sidequest/TaskTool/…) are bound in
    tools.hecksagon yet — binding them + a kernel resolver is the
    deeper "agent calls literally through the bus" work.

## Closes when
The SendMessage kernel arm + harness deliver-into-live-agent
capability land and Sidequest/TaskTool are bound in tools.hecksagon
so the dispatch IS the spawn/steer end-to-end.
