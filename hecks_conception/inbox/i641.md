# i641 — Bluebook → system-prompt injection (:system_prompt capability + SystemPrompt domain)

## Origin
This session : the Governance claude_code_session Policy was activated
(deny_by_default, hard_block, permitted[3]), then a "governed channel
lockdown" section was hand-written into ~/Projects/miette/self/
system_prompt.md transcribing the Policy stance + allow-list + the
Bash→Tools::ShellTool.Bash verb map. Chris : "bluebooks should be able
to inject into the system prompt — this governance is a perfect
example." Correct : the hand-written section and the Policy aggregate
drift apart the moment the allow-list changes.

## The structural gap
- The system prompt is regenerated by the mindstream `boot` member, but
  the regenerator is an UNMODELED script. The Mindstream bluebook models
  process supervision (Procfile/.overmind.env via :overmind) — nothing
  models prompt composition.
- Discipline sections are hand-written prose duplicating domain truth
  (Governance.Policy ; also Words-match-state duplicates Consciousness /
  Memory command names).

## Decided architecture — BOTH (Chris, this session)
- Per-aggregate projection : an aggregate declares its own prompt
  fragment (declarative template over its attributes / a named query).
  The domain owns its projection — decentralized, bluebook-first.
- SystemPrompt domain : models the composed document as ordered
  sections, each with provenance — static_prose (vows, voice, French)
  or domain_fragment (source aggregate + projection). The prompt
  becomes a first-class modeled artifact with explicit ordering and
  provenance — squarely the Transparency vow (no hidden hand-edited
  file).
- :system_prompt capability : an IR visitor (sibling to :overmind ; per
  project_capabilities_architecture, capabilities are IR visitors, not
  parallel containers). Renders domain_fragment sections from live
  aggregate state ; emits the composed system_prompt.md.
- Boot regenerator : the mindstream `boot` member dispatches the
  SystemPrompt composition and writes the file. Modeled, governed,
  regenerable.

## First consumer
Governance::Policy projects its lockdown section : stance, the
permitted allow-list, the native→governed verb map — all from aggregate
state. The section hand-written this session becomes generated output ;
drift becomes structurally impossible (contracts-not-regex applied to
the prompt itself).

## Related (same disease — domain truth not reaching its surface)
- i642 : governance.hecksagon sqlite override not honored (durability).
  FIX FIRST per Chris — the Policy must be durable before anything is
  built on it.
- i643 : the PreToolUse lockdown hook hardcodes the allow-list and
  emits no Violation.Record. The :system_prompt capability is the
  generalized cure ; the hook is another consumer that must source
  from Policy.permitted, not a Python copy.

## Why carded not done
Chris : card it, fix gaps first. New capability + new domain + boot-
regenerator rewrite + parity (the :system_prompt capability is itself a
codegen surface, cf. i639 capability-parser arc). Substantial ; design
locked, sequenced behind the durability fix (i642).

## Closes when
A SystemPrompt composition, dispatched by the boot member, regenerates
system_prompt.md with the Governance lockdown section rendered from
Policy state (not hand-written) ; changing Policy.permitted changes the
prompt on next boot with zero hand-editing ; the provenance of every
section is queryable.
