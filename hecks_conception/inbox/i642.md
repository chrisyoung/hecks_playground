# i642 — governance.hecksagon sqlite override not honored (state is process-memory only)

## Empirical finding (this session, not guessed)
Wiring the Governance Policy through mcp__storehouse__storehouse__
dispatch :
- aggregates_dir = the .bluebook FILE → memory-only boot. Policy
  returned id "2" ; state did not survive ; data/ stayed empty.
- aggregates_dir = the DIRECTORY aggregates/framework/governance →
  state coherent across separate dispatch calls : Propose →
  permitted[0], Permit x3 → [1][2][3], Activate → status active,
  EnforcementAdapter Register → registered. Every call ok:true.
- BUT after all of it : ls data/ is EMPTY. No governance.db, no
  .heki anywhere under the domain. governance.hecksagon names
  adapter :sqlite, db:
  "/Users/.../aggregates/framework/governance/data/governance.db".

## Diagnosis
The directory-rooted dispatch keeps state across calls because the MCP
storehouse server is a long-lived process holding it in memory — NOT
because the sqlite adapter is writing. The .hecksagon override is
either not loaded on the MCP dispatch path, or the sqlite write path
silently no-ops. Either way the Policy active status is durable only
for the MCP server process lifetime. Restart = total loss.

## Why this blocks i641
i641 makes the system prompt render from Governance.Policy state. A
source of truth that evaporates on restart cannot be canonical. Per
Chris (fix gaps first) this is sequenced BEFORE the injection feature.

## Investigate
- Does the MCP storehouse build load sibling .hecksagon overrides when
  aggregates_dir is a directory? The CLI `storehouse` on PATH lacks
  dispatch/state/query subcommands entirely — the MCP server wraps a
  different/newer build ; reconcile the two.
- vindiction / bin-buddy (i76) use the same absolute-db hecksagon
  pattern and are reported working — diff their boot path against the
  MCP dispatch path.

## Closes when
A dispatch against the governance directory creates and writes
data/governance.db ; killing and rebooting the MCP storehouse server
and re-reading the Policy returns status active with permitted[3]
loaded from disk, not memory.
