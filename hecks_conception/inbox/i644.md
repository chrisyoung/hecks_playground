# i644 - harness rejection does not cancel the MCP-side dispatch

## What happens
Harness rejects a Tools::ShellTool.Bash tool use ("user doesn't
want to proceed"). The storehouse MCP server has already received
/ still executes the shell_command. The agent gets a rejection
string ; the side effects land regardless.

## Reproduced twice (this session, destructive)
Both times the rejected command was the i8 recompile runbook :
pkill -9 -f wrangler|workerd|miniflare ; rm -rf wasm build +
target ; nohup wrangler dev relaunch. Each time :
- the old worker WAS killed, caches WERE wiped, wrangler WAS
  relaunched - none of which the human approved ;
- a storehouse + sh pair hung (parent blocked on the nohup child
  stdout pipe) and ran 7-11 min until hand-killed : 52460/52538,
  then 83545/83641 (83545/83641 still alive at time of filing).

## Why it is a governance breach, not a nuisance
The Governance domain (claude_code_session Policy) says an act is
accountable only if the human + the log can govern it. Here the
human explicitly refused and the act still executed with
destructive effect. Rejection must propagate to the MCP server as
a real cancel (kill the spawned process group), not just suppress
the result string. Until then a rejected destructive dispatch is
MORE dangerous than an approved one (it runs unsupervised + leaks).

## Fix direction
- storehouse MCP server : on the JSON-RPC cancel / closed request,
  kill the spawned child process group (setsid + killpg), do not
  let a backgrounded nohup child hold the parent.
- Harness-side : confirm reject sends a cancel the server can see
  (it may currently only drop the response).
- Defensive : storehouse should not block indefinitely on a
  backgrounded child's inherited stdout ; close/duplicate fds so a
  nohup'd grandchild cannot pin the parent.

## Closes when
A rejected Tools::ShellTool.Bash dispatch leaves NO process
running and produced NO filesystem side effect ; verified with a
rejected 'touch /tmp/i644_proof' that never creates the file.
