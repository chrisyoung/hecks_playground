# Hecksagon → AWS infrastructure projection

The insight : hecksagons are declarative wiring (which adapters, which providers, which triggers). Bluebooks already project to two runtimes (Ruby + Rust). Hecksagons can project to AWS CloudFormation / Terraform / CDK in the same shape — the napkin diagram becomes infrastructure-as-code.

Example : a hecksagon with `adapter :sqs` + `adapter :lambda` + `adapter :s3` projects to a CloudFormation template wiring an SQS queue triggering a Lambda function reading from S3. The hecksagon's NAME maps to the stack name ; the named adapter instances map to resource logical IDs ; the world file's values map to resource properties (region, instance type, bucket name).

Projection targets to scope :
- AWS CloudFormation YAML
- AWS CDK (TypeScript or Python)
- Terraform HCL
- Pulumi (TypeScript)
- Kubernetes manifests (when adapters are container-shaped)
- Docker compose (local dev)

## Why this matters

The napkin diagram becomes the source of truth across runtime AND infrastructure. Change one hecksagon, project to whichever target. No drift between "what the app does" and "what the infrastructure looks like" — they share the wiring contract.

The parallel : bluebook → Ruby runtime + Rust runtime (proven). Hecksagon → CloudFormation + Terraform + CDK (the same pattern, infra dimension).

## Scope

Major arc. Each projection target is its own sub-card. Start with one (Terraform HCL is a good first because it's the most-common cloud DSL) to prove the projection mechanism, then fan out.
