# Hecksagon IR → bluebook conversion

The Rust file rust/src/hecksagon_ir.rs declares the IR structs (Hecksagon root, TtsAdapter, LlmAdapter, ComputeAdapter, ShellAdapter, McpAdapter, ExecAdapter, ClaudeToolAdapter, WebToolAdapter, etc.) for the hecksagon DSL. Today these are hand-written Rust structs ; they should be DECLARED IN BLUEBOOK so the Rust file becomes a projection, not the source of truth.

## Why

- Bluebook-first principle : every domain concept lives in bluebook first ; code projects from it.
- Today's Rust IR is the de-facto contract for the hecksagon DSL ; making it bluebook closes the meta-loop where the framework describes its own shape.
- Field changes (e.g., adding multi-trigger array support to TtsAdapter) become bluebook edits + parser regen, not coordinated Rust + parser hand-edits.
- Pairs with i693 (hecksagon → AWS projection) — once the IR is bluebook, the cloud projections become "another runtime" of the same IR.

## Shape

New bluebook : `aggregates/framework/hecksagon/hecksagon_ir.bluebook` with one aggregate per IR struct :

- `Hecksagon` (name, persistence, lists of each adapter type)
- `TtsAdapter` (name, provider, voice_id, model, tuning, triggers list_of(String))
- `LlmAdapter` (name, prompt_template, model, max_tokens, trigger_on, response_into, backend)
- `ComputeAdapter` (name, function_name, trigger_on, response_into)
- `ShellAdapter` (name, command, args, output_format, timeout, env, ok_exit)
- `McpAdapter` (name, server, tool, args, result_into)
- `ExecAdapter` (name, command, exec, result_into)
- `ClaudeToolAdapter` (name, tool, trigger, result_into)
- `WebToolAdapter` (name, tool, args, result_into)

Each adapter aggregate's `triggers` field uses `list_of(String)` to express the multi-trigger array form Chris wants ; single-trigger string is the 1-element-list special case.

## Rust catches up

After the bluebook lands : rust/src/hecksagon_ir.rs is generated FROM the bluebook IR walker (or hand-mirrored with parity tests locking the shape). The parser at rust/src/hecksagon_parser.rs and the resolver at rust/src/runtime/mod.rs read the same shape.

## Scope

Major. Each adapter family is its own conversion ; ~6-8 aggregates ; behaviors / .hecksagon / parity tests for each. Multiple-hours focused work — best as a fan-out of sub-sidequests (one adapter per worktree).

## Phase 1 (this card)

Conceive the bluebook skeleton + the Hecksagon root + TtsAdapter (the one we're actively touching). Other adapter families follow in successor cards. Multi-trigger array on TtsAdapter ships in the same phase as the contract change ; Rust parser + resolver update in a parallel sidequest reading the new bluebook as source of truth.
