# Rich pretty-JSON storehouse log

Today storehouse.log is terse single lines : `[ts] dispatch Verb#inv_xxx`. No elapsed time, no args, no result state. Chris wants it RICH and READABLE — pretty-formatted JSON capturing the full execution detail he loved seeing in the dispatch responses.

The shape is already declared : the StorehouseEntry aggregate (framework/session/storehouse_log.bluebook, committed 0c751f9e). The log should emit that shape :

```
{
  "invocation_id": "inv_abc123",
  "command": "Voice::Voice.Speak",
  "summary": "speak the wake greeting",
  "args": { "text": "Good morning" },
  "outcome": "ok",
  "result_state": { "audio_path": ".../miette.mp3", "mode": "live" },
  "elapsed_ms": 14700,
  "dispatched_at": "2026-05-21T19:18:13Z",
  "kind": "sync",
  "parent_invocation_id": null,
  "events": [
    { "kind": "dispatch", "verb": "Voice::Voice.Speak" },
    { "kind": "adapter", "verb": "tts:elevenlabs", "ok": true }
  ]
}
```

Pretty-printed (2-space indent), one JSON object per dispatch, separated by a blank line so `tail -f` reads cleanly.

## Implementation

- rust/src/runtime/storehouse_log.rs : add a `dispatch_detail(entry: &StorehouseEntryView)` emitter that serialises the full struct as pretty JSON. The existing terse `dispatch_entry` / `cascade_step` lines can stay for the live `follow` stream OR be replaced ; Chris wants the LOG rich.
- The elapsed_ms + result_state + args are known at the dispatch boundary (command_dispatch.rs / the MCP dispatch wrapper), NOT inside storehouse_log's current call sites. So the dispatch boundary must thread those into the rich emitter.
- Keep a terse mode (env flag) for high-frequency daemon dispatches (Heart.Beat every 1s, SpeechStream.Advance every 200ms) so the rich log doesn't drown in heartbeats — OR filter daemon-cadence commands to terse, agent/operator commands to rich.

## Backed by

- StorehouseEntry bluebook (framework/session/storehouse_log.bluebook) — the contract.
- i692 dispatch-detail PostToolUse hook — renders the same shape for the conversation surface.

## Scope

~2 hours. Rust serialisation + dispatch-boundary threading + the daemon-noise filter. Antibody-exempt as the impl of the StorehouseEntry contract.

## Additional requirements (Chris, 2026-05-21)

1. **Color coding** — ANSI colors in the live `follow` stream and (where a viewer supports it) the rich render. Color by kind : dispatch (cyan), event (green), cascade ok (green) / fail (red), adapter (magenta), error outcome (bright red), fallback (yellow). The persistent .log can carry an ANSI-stripped copy + a colorized view, or store color codes that `tail` renders and a stripper removes for parsing.

2. **Comprehensive** — the log captures EVERYTHING : every dispatch, every event, every cascade step, every adapter result, every policy reaction, every attribute trace, every fallback. No sampling, no terse-only for daemons — comprehensive. (Daemon-noise filtering becomes a VIEW filter, not a capture filter ; capture everything, filter on read.)

3. **Command metadata** — the storehouse dispatch carries a `summary` field (the MCP dispatch requires it) and may carry other metadata. Surface ALL of it : the summary, the aggregates_dir, the role that's allowed to dispatch the command, the behavior_kind, any declared tags on the command. Make the metadata apparent, not hidden.

4. **Source tags** — tag every entry by WHO dispatched it : `process-manager` (heart, breath, circadian, ultradian, inbox, macrophage, speech_stream), `operator` (Miette via MCP), `hook` (SessionStart/Stop/PostToolUse), `sidequest-agent`, `cascade` (runtime-internal fan-out). Chris specifically wants to filter "show me everything the process managers dispatched." The tag is derived from the dispatch context : the loop/clock workers tag process-manager, MCP dispatches tag operator, etc.

These expand the StorehouseEntry aggregate : add `source_tag` (enum), `metadata_json`, and an `events` list_of(EventTrace) value-object capturing the per-event kind+verb+ok. The bluebook contract grows ; the Rust emitter follows.
