# i80 — cli-routing-as-bluebook

cli-routing-as-bluebook — Most of hecks_life/src/main.rs is hardcoded mappings from CLI-subcommand names to specific aggregate.command dispatches. Lexicon → MatchInput / ListAll, speak → Speech.Speak, status → Heartbeat.ReadVitals, terminal → run_terminal, serve → multi-domain HTTP routing, conceive/develop/behaviors/dump-fixtures/dump-world/dump-hecksagon — all hardcoded routes. The 'now dispatches through the hecksagon' wrappers (speak/status/musings/boot/daemon) explicitly acknowledge they're transitional. The new 'loop' subcommand (i76, PR landing) added one more row to that list. Every CLI route is a name→dispatch mapping that should be DECLARED as data, not hardcoded in Rust. Proposed shape : cli.bluebook (or cli_routes aggregate inside an existing bluebook) declares CliRoute aggregates each carrying name + target_aggregate + target_command + arg_mapping (positional + flags). main.rs becomes a tiny dispatcher : parse argv, look up the route, dispatch. Adding a new subcommand means adding a fixture row, not editing Rust. This is the same pattern as i74 (validator-warning shape), i77 (validator-morphology shape), i78 (specializer-files-as-shape), i79 (inbox.sh-as-bluebook) applied to the CLI layer. The loop subcommand from i76 is the most recent example — tested, working, but a Rust addition that should retire when this arc lands. Companion to i81 if we end up filing 'main.rs argv parsing + routing as bluebook' as its own thing. Acceptance : main.rs shrinks to <200 LoC ; every CLI subcommand is declared as a fixture ; adding a subcommand requires zero Rust edits ; the existing 'now dispatches through hecksagon' wrappers retire alongside their hardcoded routes.
