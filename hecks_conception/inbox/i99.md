# i99 — dispatch-by-id-mismatch-on-multi-record-aggregates

dispatch-by-id-mismatch-on-multi-record-aggregates — DreamWish.MarkFiled dispatched with dream_wish=w20260426T0918Z_1 found and mutated w20260426T0918Z_2 instead. The runtime's command_dispatch.rs find-by-id branch (when self_ref is present and id_val is in attrs) is supposed to look up the record by the passed id and error if not found, but in practice it seems to ignore the passed id and use a different one — possibly the singleton id from next_id() or the first record in HashMap-iteration order. Symptom : multi-record aggregates can't be selectively mutated via dispatch — every MarkFiled hits the wrong row. Workaround : bypass dispatch and use `heki upsert id=<wished-id> ...` directly (same shape inbox.sh now uses for the wish-receipt). Fix : trace the find_self_ref / inject_refs / find-by-id path in runtime/command_dispatch.rs and runtime/repository.rs ; the singleton-id reuse pattern in next_id() (line 67-69 of repository.rs) probably needs to NOT fire when the self_ref attr is present in the dispatch's attrs map. Companion to i93 (find-world-heki-dir-fails-on-relative-path) — same family of multi-record-vs-singleton runtime bugs that all bypass the bluebook surface for collection storage.
