# Runtime as a bluebook — generate runtime/mod.rs from a domain, not hand-maintain it

**Decision (Chris, 2026-06-14) : pursue the TRUE-bluebook path, as its own
deliberate arc — NOT a bolt-on.** Joins the self-hosting cards already
queued (`restarts_inbox/conceiver-as-bluebook-2026-06-13.md`,
`restarts_inbox/kernel-interpreter-2026-06-13.md`).

## The finding that triggered this
`rust/src/runtime/mod.rs` is **3477 lines and hand-maintained**. It is
SUPPOSED to be generated — the machinery exists (`codegen/runtime_shape/`
with 36 snippets, a `specialize runtime` target, and the golden test
`rust_specializer_produces_byte_identical_runtime_rs`). But that golden is
`#[ignore]`d (since the "hecks-rewrite runtime rewrite / Primitive::Process.Spawn
rewrite" landed directly in mod.rs), and the specializer is now badly stale :
`specialize runtime` emits 2357 lines vs the current 3477, **~1496 lines
diverged**. So the kernel file free-drifts with every hand-edit (the i735
`apply_sqlite_persistence` rework + the step-4 `boot_in_memory` additions are
the most recent examples).

This is a standing violation of bluebook-first : the most-consumed file in
the runtime is hand-written imperative Rust with its generate-gate disabled.

## Two senses of "make it bluebook" (the weak one was REJECTED)
- **Weak — re-shard (REJECTED).** Reconcile the 3477-line mod.rs back into
  the 36 `runtime_shape` snippets byte-identical + un-ignore the golden.
  Restores the no-drift gate, but the snippets are still hand-written Rust
  fragments — "generated" by byte-identity, NOT a domain. Chris : not worth
  it ; it's sharding, not bluebook.
- **Strong — Runtime as a domain (CHOSEN).** Describe the Runtime AS a
  bluebook and generate the Rust from it. The pieces that already point the
  way :
  - `command_dispatch` is already a phases-as-rows specializer (the dispatch
    pipeline as ordered Phase rows + snippet bodies) — the template for
    "pipeline as data."
  - Candidate domain shape : a `Runtime` aggregate ; the boot pipeline
    (`boot_with_data_dir` → factory materialise → policy/pm engines →
    projections → apply_sqlite/world dirs) as ordered phases ; dispatch as a
    contract ; `Value` / `RuntimeError` as value objects ; `repo_key` /
    repositories / mailboxes as declared structure.
  - This IS the self-hosting endgame (`project_self_hosting_vision`) — Hecks
    generating its own runtime from its own bluebook.

## Why it's a real arc, not a task
mod.rs is the kernel : Runtime struct + boot pipeline + dispatch surface +
Value/RuntimeError + repo_key/lookup + trigram/mailbox wiring. Lifting it to
a domain that regenerates the current behaviour byte-identical (then un-
ignoring the golden) is a multi-session effort and should be scoped
deliberately alongside the conceiver-as-bluebook / kernel-interpreter work,
not mixed into the persistence arc.

## Done-condition (eventual)
A `.bluebook` (or bluebook + hecksagon) describes the runtime ; `specialize
runtime` regenerates `rust/src/runtime/mod.rs` byte-identical from it ; the
golden is un-ignored and gates ; hand-edits to mod.rs become impossible
(they go through the domain). The same treatment then generalises to the
other `#[ignore]`d kernel goldens.

## Approach DECIDED (Chris, 2026-06-14, scoping session) — strangler-fig, not big-bang

Chris : *"Maybe we can drop out the smallest subst as bluebook and wrap mod in
an adapter? Then we can surgically pull out mod concerns into separate adapters."*
This REPLACES the big-bang byte-identical-rebuild framing of the done-condition
above. We strangle the kernel one concern at a time, each gated independently.

### What the diff sizing found (this session)
- `specialize runtime` emits 2357 lines vs mod.rs 3535 — ~1178 drift.
- The drift is **100% inside the 2878-line `impl Runtime` block** (mod.rs
  324→3202). ~33 methods exist in mod.rs with NO RuntimeMethod row / snippet
  (the Phase-C blockers `apply_sqlite_persistence`, `unwired_aggregates`,
  `dump_backend_map`, `force_memory_repositories` ; plus `boot_in_memory`,
  repository CRUD `save`/`delete`/`count`, the pump/outbox family).
- The **leaves are already snippet-sharded** (snippets 30–42 : Value 30-32,
  RuntimeError 33-34, repo_key 36-37, pascal/trigram 38-39, query helpers
  40-42) — but as hand-written `.rs.frag`, duplicated against the inline
  copies in mod.rs. Extracting leaves buys tidiness, not domain.

### Two INDEPENDENT machinery costs (name them separately)
1. **Structure-from-bluebook** — a new specializer `body_kind` where a
   `value_object` declares the enum/struct and the emitter produces the
   DECLARATION ONLY (variants + fields). Bodies that resist (e.g.
   RuntimeError's bespoke `Display` format strings) stay `raw` snippets —
   the `command_dispatch` precedent (structure in rows, bodies in snippets).
   Works inside today's one-file model. Smallest possible proof. NOT a
   Display-template mini-language — structure only.
2. **Split mod.rs → per-concern files** ("wrap mod in an adapter") — the
   specializer goes one-file → multi-file (each Section → its own output
   path), mod.rs becomes a thin composition root. The "restructure for my
   sanity" win. Bigger change. Staged AFTER the loop is proven.

### The gate (fast inner loop + slow backstop)
- **Inner loop (ms, every edit) :** scoped byte-identity golden in
  `rust/tests/specializer_golden_test.rs` — `specialize <concern> ==
  <file>`. Same harness already green 30× (validator_warnings, dump,
  hecksagon_parser). Subprocess + string compare, no runtime boot. THIS is
  the iteration gate — the first drops regenerate code whose exact target
  already sits in the tree, so correctness is a byte-diff.
- **Backstop (once per concern) :** `cargo test` + 233 behaviors — confirms
  compile + semantic wiring. Run to CLOSE a concern, not to iterate it.
- The two `#[ignore]`d goldens are the big mod.rs byte-identity ones. New
  scoped per-concern goldens are LIVE from day one ; once enough concerns
  carry their own golden, the ignored mega-golden is deleted — the gate
  retires itself.

### Sequence DECIDED (Chris : "leaf warm-up, then C-concern")
- **Step 1 — leaf warm-up.** One leaf (`Value` enum declaration) via
  structure-from-bluebook, one-file model. Builds the new `body_kind` +
  scoped golden. Proves the loop fast and cheap before betting the
  C-blocker on new machinery.
- **Step 2 — the Phase-C unblocker.** The persistence-resolution concern
  (`apply_sqlite_persistence` / `unwired_aggregates` / `dump_backend_map`)
  born in the domain. THIS is what satisfies the "before Phase C"
  prerequisite — leaves alone do NOT unblock C.
- **Later** — file-split / adapter-wrap (machinery cost #2) + remaining
  concerns (Value impls, RuntimeError, repo_key, string-math, the big impl
  methods), each with its own scoped golden, mod.rs shrinking monotonically.

## MECHANISM DECIDED (Chris in go-mode, advisor-reconciled, 2026-06-14) — rows, NOT grammar

**Primary-source finding that forced this :** the bluebook grammar has NO
variant / sum-type concept (`grep variant|enum|one_of` across
`aggregates/language/grammar/` — the only `variant` hits are Rust's own
BlockParser enum). A `value_object` is a PRODUCT type (named attributes).
So `Value` / `RuntimeError` (sum types) CANNOT be `value_object`s without a
grammar extension. The inbox vision's "Value / RuntimeError as value
objects" silently assumed variant support that doesn't exist.

Two paths considered :
- **(A) Grow the core grammar** — add sum-types/variants/raw-type-refs/map-types
  so runtime types become genuine `value_object`s. Touches the PARITY
  CONTRACT (Ruby + Rust parsers, validators, IR, both targets). Bigger ;
  deferred unless explicitly chosen.
- **(B) Describe runtime types as ROWS in `runtime_shape`** (CHOSEN) — a
  `Field` aggregate (structs) + later a `Variant` aggregate (enums) + new
  body_kinds, exactly the `command_dispatch` "pipeline as data" precedent
  (synthetic `dispatch_inner` body_kind walks `Phase` rows ; `runtime_impl`
  walks `RuntimeMethod` rows). NO grammar/parity change. Handles structs
  AND enums — so Value/RuntimeError stay in the plan via a `Variant` table,
  NOT omitted.

### Open tactical decision (surfaced, not yet locked) — scoped golden sub-target
There is NO per-section `specialize` target today — only whole-file
`specialize runtime`, whose golden is `#[ignore]`d by the 33-method drift.
The fast per-concern inner loop needs a sub-target, e.g.
`storehouse specialize runtime --section <name>` (emit one Section's bytes)
or `specialize runtime_section <name>`. Build this as the FIRST machinery
bit so every subsequent concern has a fast scoped golden.

### Step-1 build recipe (BackendInfo via struct_from_fields — executable)
BackendInfo is the chosen first drop : smallest struct (3 fields), ON the
Phase-C path (it's `dump_backend_map`'s return type, cluster 2).
Wrinkle : it's pure drift (NOT in fixtures/snippets) and interleaved with
`use` lines (BackendInfo @200, imports @207, PendingReaction @214, Runtime
struct @220 in `rust/src/runtime/mod.rs`). So Step 1 also CLOSES that drift.
1. **Scoped sub-target** — add `specialize runtime --section <name>` (or
   equivalent) to `rust/src/main.rs` + `specializer/runtime/root.rs` so a
   single Section's bytes can be emitted + diffed. Foundational for ALL
   concerns.
2. **Golden target** — extract the current BackendInfo definition (doc +
   `#[derive(Debug, Clone)]` + struct, lines ~199–205) into
   `codegen/runtime_shape/snippets/02_struct_backend_info.rs.frag`. This is
   the byte-identity target. Resolve the import interleaving : the
   `use crate::ir::Domain;` etc. lines belong in the header section, not in
   the BackendInfo section.
3. **Field aggregate** — add `aggregate "Field"` rows to
   `codegen/runtime_shape/fixtures/runtime_shape.fixtures` :
   `{struct: "BackendInfo", name: "repo_key", rust_type: "String", order: 0}`,
   `{... name: "kind", rust_type: "BackendKind", order: 1}`,
   `{... name: "heki_path", rust_type: "Option<String>", order: 2}` +
   struct-level metadata (derives `Debug, Clone`, doc comment, pub).
4. **Emitter** — add `body_kind: "struct_from_fields"` handling in
   `specializer/runtime/root.rs::emit` (a new `emit_struct_from_fields`
   walking Field rows for the struct), producing bytes identical to step-2
   snippet. Add the Section row at the right `order` (before struct_runtime).
5. **Scoped golden** — add `rust/tests/specializer_golden_test.rs` test :
   `specialize runtime --section backend_info` == the tracked struct bytes.
   LIVE (not `#[ignore]`d).
6. **Backstop** — `cargo test` + 233 behaviors green to CLOSE Step 1.
Then Step 2 reuses the Field machinery for the rest of cluster 2 +
introduces the `Variant` body_kind for the enums.
