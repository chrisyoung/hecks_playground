# i742 — the door redirects to a tool that was removed

> **⚠ READ THE CORRECTION AT THE BOTTOM BEFORE ACTING ON THIS CARD.**
> The symptom described here is exact. The root cause is not. Deleting the
> `deny` array will appear to fix the door — because the door was fixed on
> 2026-08-12 by unrelated commits — and will confirm the wrong diagnosis.

## Symptom (prior session, governed)

Native `Bash` / `Read` / `Edit` / `Write` / `Grep` / `Glob` absent — **removed, not gated**.
Harness wording : *"No such tool available: Bash. Bash is disabled for this session, in
subagents as well as here."* The macrophage's own refusal reads differently —
`GOVERNANCE (macrophage): native … makes no bus event`. Gated = present-and-refused ;
this was absent. Propagated into subagents.

## Why that breaks execution

**The door was never the executor.** `Tools::ShellTool.Bash` carries
`redirects_native: ["Bash"]`, and its own bluebook says outright *"this bluebook names the
contract, not the execution."* The intended flow is :

    native fires → macrophage records the bus event → native still runs

Deny-listing the natives left the redirect **pointing at nothing**. Every dispatch returned
`✓` over a no-op. Confirmed by reading the record back : `{id, shell_command, description}`
— no output anywhere, because nothing ever ran.

## ROOT CAUSE — CONFIRMED 2026-08-12 (ungoverned session, hands back)

Prime suspect `880e1e08c` ("wire governance to a Miette-only settings file") is **confirmed**.
It taught `bin/miette` to pass `--settings /Users/christopheryoung/Projects/miette/self/settings.json`
on the governed launch path. That file contains :

```json
"permissions": {
  "deny": ["Bash", "Read", "Edit", "Write", "Grep", "Glob", "WebFetch", "WebSearch"]
}
```

`permissions.deny` **removes** a tool from the session (and from subagents). The redirect
needs the tool **present**. The commit's own message only ever claimed to wire the settings
file — the deny block predates it in that file and was never load-bearing until `--settings`
started loading it. Two correct pieces, wired together into a break.

**The gate that was wanted already exists in the same file** :

```json
"PreToolUse": [{ "matcher": "*", "hooks": [{ "command": ".../bin/governed-door-hook" }] }]
```

A PreToolUse hook is present-and-refuses — exactly the macrophage semantics. The `deny`
block is therefore both redundant *and* destructive.

### The fix

Delete the `"deny"` array from `~/Projects/miette/self/settings.json`. Let
`bin/governed-door-hook` be the whole gate. **Verify governed** (this session is ungoverned,
so it proves nothing) : launch `bin/miette` without `--ungoverned`, dispatch
`Tools::ShellTool.Bash shell_command='echo OK'` through the door, and confirm the record
carries the output — not just `✓`.

Do not apply blind : the deny list was Chris's explicit call per the commit message
("native-tool governance only applies when a session actually starts as Miette"). The intent
survives with the hook ; only the mechanism changes. Worth one sentence of confirmation first.

Invoke dispatch attrs verbatim."* Two opposite readings :

- **(a)** the overlay is state-only — the adapter path, where
  `resolve_claude_tool_adapters` builds attrs from upstream state ; or

Opposite fixes. Needs `reaction.rs`. First commands with hands :

## IN SCOPE, NOT ADJACENT

`Tools::ShellTool` has no `output` / `exit_code` / `ok` attribute. `Git::Git` models exactly
this with `status_output` / `log_output` / `diff_output`. **If the door ever becomes the
executor, that attribute is what makes results visible** — MCP dispatch returns state JSON,
so a command with no output attribute is structurally incapable of reporting what it did.
That is not a nice-to-have ; it is the difference between `✓` and a result.

# CORRECTION — 2026-08-12, ungoverned session, hands on

## The door is fixed. Not by the cause on this card.

Branch `fix/door-execution-port` : `dacadbecc`, `9ce17b409`, `e486e901a`.

**Real cause.** `Bluebook::DSL::HecksagonBuilder#adapter(kind, **opts)` with no
block collects into `@raw_adapters` ; `#build` constructs `IR::Hecksagon` from
`binds / subscriptions / framework_members / driving_handlers` and **never
passes `@raw_adapters`**. All seven `adapter :claude_tool, …` bindings in
tools.hecksagon were parsed and dropped at boot. The Rust runtime's
`resolve_claude_tool_adapters` used to execute them ; vendoring hecksagain
replaced that runtime and nothing carried the edge across.

**Proof this card's cause was not it.** This session ran UNGOVERNED — every
native tool present, no deny-list in effect — and `Tools::ShellTool.Bash` still
executed nothing. A dispatch of `echo proof > /tmp/probe` returned `✓`, emitted
`BashRan`, and the file did not exist. The deny-list governs which tools *I* may
call directly. It has no bearing on whether the door's own adapter runs. Two
independent problems, one identical symptom — which is exactly why the prior
session's reasoning was sound and still landed wrong.

**The fix.** Ports and adapters, in hecksagain's own idiom :
`ports/execution.port` (verb `executed_by`, signal `:reply`), adapters
`Shell` / `Filesystem` / `Search`, and three ordinary binds in tools.hecksagon.
Being real `IR::Bind`s, they now pass `Registry::Verification#check_verb` at
boot — a wrong adapter fails LOUDLY at wiring. The invisible-failure mode is
structurally unreachable for this family now.

## Two sections of this card are OVERTAKEN

- **"IN SCOPE, NOT ADJACENT"** (ShellTool has no output attribute) — resolved
  differently and better. No new attribute was added. `Cascade` already declared
  the outcome chain (`id / tool_kind / output / exit_code / ok_status`), so the
  dispatcher re-enters `Cascade::Cascade.RecordResult` off the port's reply, and
  the reply also rides out on `Dispatcher::Result` → the MCP renderer's `Output`
  block. The domain needed no change ; it was right all along.
- **"OPEN JOINT"** (`Primitive::ClaudeTool.Invoke` arity) — moot for this path.
  `:claude_tool` is retired from tools.hecksagon. Reading (a) was right : the
  overlay was the adapter path, and that adapter no longer exists here.

## Still true and still open

The **"TRAPS CONFIRMED"** list holds — re-read it, it is the best part of this
card. **"ALSO OPEN"** (system_prompt regen) is still open and now has a likely
explanation : `HecksagainRuntime.validate("~/Projects/miette")` returns

The **deny-list finding itself is real and unverified either way.** Whether the

## The deny-list finding — resolved as VESTIGIAL, not applied

The card left this genuinely open. It is now settled by reading, not restart :

- `redirects_native` has exactly ONE non-bluebook consumer in the whole tree :
  `hecksagain_runtime/lib/hecksagain_runtime/governed_door.rb`, and there it is
  a *lookup* — which door does this native map to — never an executor.
- `bin/governed-door-hook` is data-driven off that same lookup. `mcp__storehouse__*`
  resolves to no door, so the hook exits 0 and the door tool passes through
  under governance. The execution itself is a `hecksagain-cli` subprocess,
  which no session-level permission set can reach.

So the deny list removes tools from *my* toolbelt and has no bearing on whether
the door's adapter runs. **Do not delete it.** Chris's original intent stands
intact, and the fix proposed in "### The fix" above is unnecessary.
