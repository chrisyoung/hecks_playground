# i743 — every `adapter :kind, opts` binding is silently discarded at boot

## The one-line cause

`Bluebook::DSL::HecksagonBuilder#adapter(kind, **opts)` with no block does:

```ruby
return @raw_adapters << { kind: kind.to_s, opts: opts } unless block
```

and `#build` constructs:

```ruby
IR::Hecksagon.new(domain:, binds:, subscriptions:, framework_members:, driving_handlers:)
```

**`@raw_adapters` is never passed.** Parsed, collected, dropped. No warning, no
validation error — the binding simply ceases to exist the moment boot finishes.

## Why nothing caught it

Nothing *could*. A dropped `@raw_adapters` entry produces no bind, so
`Registry::Verification#verify!` — which walks `hexagon.binds` and type-checks
every one against its port — has nothing to check. The gate is real and it
works; the declaration never reached it. Every dispatch then succeeded, mutated
state, emitted its event and returned ✓, because the domain half was always
correct. Only the world stayed untouched.

That is the shape to remember: **the failure was invisible precisely because
the domain was right.**

## Correction to i742

i742 described the symptom exactly ("every door dispatch returns ✓ over a
no-op") and attributed it to `permissions.deny` removing the native tools that
`redirects_native` points at. That is a real and separate issue about the
*governance* path, but it is not why the door did nothing. Proven this session:
with governance OFF and every native tool available, `Tools::ShellTool.Bash`
still executed nothing, because there was no adapter on the far side to
execute. The deny-list governs which tools *I* may call directly; it has no
bearing on whether the door's own adapter runs. Two different problems that
produced one identical symptom.

## Fixed (commits dacadbecc, 9ce17b409, branch fix/door-execution-port)

The `:claude_tool` family — the door itself. Replaced with a real port:

- `ports/execution.port` — verb `executed_by`, signal `:reply`
- `adapters/driven/{shell,filesystem,search}` — Bash / Read·Write·Update·Edit / Grep·Glob
- `Tools::{ShellTool,FileTool,SearchTool}.executed_by(...)` in tools.hecksagon

Because those are ordinary `IR::Bind`s, they now pass through `check_verb` at
boot — a wrong or missing adapter fails LOUDLY at wiring. The invisible failure
mode is structurally unreachable for this family now.

## Still dead — 35 bindings, 10 files

| family | count | what is inert |
|---|---|---|
| `:exec` | 28 | sub-process edges — sidequest spawn, inbox poll, cargo, git, fibroblast, plan |
| `:mcp` | 4 | EmailTool → Gmail (SearchThreads, GetThread, CreateDraft, ListDrafts) |
| `:web_tool` | 3 | WebTool.WebFetch / WebSearch, EmailTool.GetAttachment |

Files: `framework/tools/{cargo,git,filesystem,tools}.hecksagon`,
`framework/inbox/inbox.hecksagon`, `framework/process_health/…`,
`framework/session/…`, `plan/…`,
`discipline/immune_system/repair_cell/fibroblast/…`,
`discipline/immune_system/macrophage/artifact_claim.hecksagon`.

Note `tools.hecksagon` appears twice over: its `:claude_tool` lines are fixed,
its own `:exec` (sidequest) and `:mcp` (Gmail) lines are still inert.

Several of these carry comments asserting the runtime arm has landed — e.g.
*"i594 has landed — the runtime auto-fires these :mcp bindings via
`Runtime::resolve_mcp_adapters`"*. That was true of the **Rust** runtime. It has
not been true since the vendoring, and the comments now read as false
reassurance. They should be corrected as each family is ported.

## The shape of the remaining work

`ports/execution` is the template and it generalises cleanly — each family is
one `.port`, one or more `.adapter` + implementation, and per-aggregate binds
replacing the `adapter :kind, opts` lines. `:exec` is nearly free (it is
`Shell` with a fixed command from the binding rather than from the dispatch).
`:web_tool` needs an HTTP adapter. `:mcp` is the genuinely hard one — the
Claude harness owns the MCP transport, and `tools.hecksagon`'s own comment
already names that gap honestly.

## Open question worth deciding once

Should `HecksagonBuilder#adapter` **refuse** an unknown no-block form rather
than collecting it into a field nobody reads? Every argument for keeping
`@raw_adapters` is an argument for a silent no-op, and this session is what
that costs. If the corpus needs a transitional period, it should at minimum
warn at boot — a declaration that reads as wiring and isn't is worse than no
declaration at all.
