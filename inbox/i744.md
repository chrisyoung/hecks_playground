## What was actually broken (Chris asked: "will you fix grep and head?")

The diagnosis was not what either of us assumed. Measured, not guessed:

- **`SearchTool.Grep` was already honest.** Zero matches names both the pattern
  AND the path (`no matches for "X" in /path`). A nonexistent path fails loudly
  at exit 1. Nothing to fix. It is in `vendor/hecksagain/.../driven/search.rb`.
- **`FileTool.Read` was broken.** It read 196 lines, chose to return 20, and
  discarded the total. A fragment was shape-identical to a whole-file read at
  exit 0. `vendor/hecksagain/.../driven/filesystem.rb`.
- **`ShellTool.Bash` was where the damage actually came from.** All four false
  negatives that session were raw `grep --include` / `find` / `ls` run THROUGH
  Bash, bypassing the honest instrument entirely. Exit-0-and-silent rendered as
  a blank body under a success header.

### The fixes, and what they do NOT do

`filesystem.rb` — a fragment now carries a trailing footer:

    ... [fragment: lines 1-20 of 196 - 176 not shown]
    ... [fragment: no lines at line 100 of 13]
    ... [empty file: 0 lines]

A WHOLE read is unchanged and byte-verbatim. That is load-bearing: the
adapter's own header promises *"verbatim in, verbatim out, so a read and an
edit compose"*, so coverage is a trailing footer and never a gutter.

`shell.rb` — silence announces itself:

    ... [no output - exited 1, wrote nothing to stdout or stderr]

**This does NOT make a shell tool honest about its own SCOPE.** Only the tool
knows what it looked at. A `grep --include='*.rb'` that misses the `.mjs` file
still cannot say so. That is the structural-instrument arc (ancestry, per-key
diff, before/after) and it is deliberately NOT in these commits. What landed is
narrower: emptiness no longer arrives disguised as an answer.

### One thing worth knowing about the byte cap

The cap is 100_000 bytes and it now cuts on WHOLE LINES, so coverage counts
what survived. This exposed a silence nobody had asked about: reading a
7,341-line file with **no limit at all** returns 2,124 lines. The old code said
"truncated at 100000 bytes" and never mentioned the 5,217 missing lines.

Verified across five real files plus both oversized-line branches; every
claimed range matches the body actually returned.

The runtime now emits `{ok, state, events[{name,aggregate,id,payload}], reply}`.

    └─ undefined
    State (shell_command)
      value="expr 6 \* 7"

The answer is gone; it echoes back only what was dispatched IN. That is
verbatim the bug `dispatch.mjs`'s own header warns about (*"the door executes

Worth salvaging as CONCEPTS only, not code: the cascade timeline (grouping
events into invocation chains beats the live flat `Events:` list, and the
runtime still has that structure) and the explicit `… (+N more lines)` cap
discipline (now enforced one layer down at the adapter instead).

## META-LESSON — now three instances, and one of them was mine

The pattern from the last refresh held all session: **an instrument that
recognises nothing, refuses nothing, and returns a shape that agrees with you.**
Three more this session:

1. **My orientation greps.** `docs/inbox/*.md` (wrong glob), `/rust` (wrong
   tree), `--include` without `*.mjs` (wrong filter — the code IS `.mjs`),
   `hecksagain_runtime/src` (wrong dir, it is `lib/`). Every one returned empty
   and said nothing about what it had looked at. Every one was wrong SCOPE, not
   wrong pattern.
2. **My own fix shipped the bug it was fixing.** The first coverage footer
   computed its range from the PRE-cap window, so a large read would have
   claimed `lines 1-5000` while showing 2,124 — a number agreeing with the
   caller instead of with the file. Caught by a structural check across five
   real files, in one call.
3. **A green test suite guarding code that destroys the output.** The dead
   renderer's 273-line suite passes, exit 0, including a check literally named
   `toolOutput: first output line surfaced` — passing on a module that drops
   the tool output entirely when handed real data. It passes because it feeds
   hand-crafted fixtures in the OLD shape. The test recognises its own fixture,
   not reality.

Also worth carrying: **my acceptance test produced a false PASS.** The first
version of the renderer comparison used `echo REAL_ANSWER_HERE` and reported
the marker survived — but it survived in the ECHOED COMMAND in the State block,
not in the output. Only caught because the number beside it (`0 events | actual: 2`)
disagreed. Pick a marker that can only exist in the thing you are testing.

And one process note: I ran `find /` this session and hung the door for two
minutes. Scope every find and grep to a path. My own standards already say so.
