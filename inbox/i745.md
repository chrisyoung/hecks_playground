## There are THREE parsers, not two

| reader | lines | status |
|---|---|---|
| `vendor/hecksagain/lib/hecksagain/bluebook` | 9,085 | **LIVE** — the MCP door, every dispatch |
| `ruby/hecks/{dsl,bluebook_model}` | 8,250 | no caller outside `parity/` + `spec/` |
| `rust/src/*parser*` | 6,535 | retired as authoritative, **still a blocking pre-push gate** |

The first two are Ruby interpreters (`Kernel.load` + builder-record). Only the
Rust one is a real text parser. Namespaces are isolated in both directions
(verified by grep, no cross-requires).

## Where hecksagain is RIGHT and Rust is wrong

This is why the cutover was correct. `identified_by { field.value }`:

    RUST        storehouse dump bin-buddy/route.bluebook -> identified_by=[]
    HECKSAGAIN  describe Tools::FileTool               -> identified_by=["id.value"]

The corpus uses the block form at **267 sites** vs 25 symbol-form. Rust reads
none of them and says nothing — it counter-mints ids instead of upserting on
the natural key. That is the silent-drop bug the cutover commit (`f73a34567`)
describes, confirmed live here against a real client bluebook.

## Where hecksagain CANNOT read what Rust reads

### 1. `family` on adapters — blocks 35 of 58 domain roots, including PIZZAS

    $ hecksagain-cli validate examples/pizzas
    {"ok":true,"valid":false,
     "error":"undefined method `family' for AdapterBuilder"}

`AdapterBuilder` (`bluebook/dsl/adapter_builder.rb`) implements `port`, `field`,
`secret`. The corpus says `family`. **11 of 11 `.adapter` files use `family` ;
zero use `port`.** The canonical form — the one in Miette's own system prompt — is

    Hecks.adapter "Heki" do
      family "persistence"
    end

So the vendored parser is one vocabulary rename behind the corpus. This is ONE
missing DSL method standing between 35 roots and green. It is a rename decision
(`port` -> `family`, or both) so it is Chris's call, not a silent patch.

### 2. `on:` / `success` / `failure` on binds — structurally unrepresentable

    Bind = Struct.new(:aggregate, :verb, :adapter, :role, keyword_init: true)

No `on`, no `success`, no `failure`. Not stubbed at the edge — absent from the
IR. `HecksagonBuilder` carries `def success(*) = nil` / `def failure(*) = nil`
with an honest comment calling itself "NOT a real fix" and "the single
highest-value remaining gap this migration surfaced."

Rust reads it correctly, today:

    Pizzas::Order.charged_by(Stripe) on="OrderPlaced"
      success="Order.Authorize" failure="Order.Decline"

This is the async verdict re-entry — the entire Pizzas payment narrative, the
reference pattern every hexagon in the corpus is written against. **Deleting the
Rust parser deletes the only reader of it.**

### 3. Inline aggregate `fixture` blocks — 328 occurrences, silently discarded

`AggregateBuilder::InlineFixtureFieldStub` — `def method_missing(*, **, &) = nil`.
The comment is honest: "Accepted so the file boots … NOT stored or seeded
anywhere." 328 occurrences across 32 files in hecks_nursury parse clean and
produce nothing.

### 4. bin-buddy portal `.hecksagon` content — absorbed by a catch-all

`HecksagonBuilder#method_missing(*) = nil`. Branding/UI config for
driver/admin/homeowner portals: parsed, discarded, no complaint.

## UPDATE — the .behaviors runtime, built (Chris: "yes do that")

Chris confirmed the plan from the parser-correctness read: don't hand-write the
44% of `.behaviors` content that only restates the bluebook ; build the missing
CONFORMANCE RUNTIME first, since it's the only executable check left that the
Ruby runtime does what a bluebook declares, now that parity is retired.

**Built, 3 commits** (`5fa738cb1`, `26ea8d003`, plus the qualify-fix folded into
the first): IR (`bluebook/ir/behaviors.rb`), DSL (`bluebook/dsl/
behaviors_builder.rb`, mirrors WorldBuilder exactly), runner (`hecksagain_runtime/
lib/behaviors_runner.rb` + `behaviors_runner/expectations.rb`), wired into
`hecksagain-cli behaviors <path>` (file or directory sweep, always reports
`files_swept` + a real summary). Ported from the Rust reference
(behaviors_parser.rs / behaviors_runner.rs), not invented — same grammar, same
per-test isolation (fresh in-memory runtime per test), same domain-scope rule.

**Real simplification vs the Rust port**: a `.behaviors` file is RUBY here,
executed the same way every other bluebook format already is. No hand-rolled
line parser, no string-to-value coercion — confirmed by grepping
`vendor/hecksagain/lib` myself for `.behaviors`/`TestSuite`/`behaviors_parser`
(zero hits, matching the CLI stub's own claim) before writing a line.

**Disclosed deviation**: hecksagain's `Dispatcher#dispatch` has no cascade-off
mode (checked directly, `runtime/dispatcher.rb` always pumps
`@policies.react`/`@sagas.advance`). Every dispatch — setups included — runs
with cascades ON. Documented in the runner's own header, not papered over.

**Two real bugs found and fixed DURING build, before shipping**:
1. Live state fields come back as `Hecksagain::Runtime::Value` objects, not
   plain Ruby — `sweeper_id: "fleet"` compared false against a bare string.
   Fixed via `Value.materialize_unwrapped`.
2. A `setup` command was assumed to act on the test's own `on:` aggregate.
   Wrong for a genuine cross-aggregate cascade (`tests "Add", on: "Task"`
   seeding `setup "Capture"`, which actually creates the owning Story — found
   live in plan.behaviors). `qualify()` now searches every aggregate the
   domain declares for the one that owns the command.
3. (Found sweeping the REAL corpus, not the 3 reference examples) : the corpus
   writes VO-typed `expect` values BOTH bare (`sweeper_id: "fleet"`) AND
   wrapped (`repo: {value: "..."}`). Unwrapping only the live-state side broke
   every wrapped expectation — 104 fails, shape `expected repo: {:value=>X},
   got X`. Fixed by normalizing BOTH sides before comparing.

### Error/fail causes, categorized (not 561 independent problems)

- **145 of 561** — ONE file, `catalog/bluebook/appeal.behaviors` : a boot-time
  `Malformed` ("Explorer.ByKind asks about kind, which Explorer never
  declares") repeated across every test in that file. One root cause.
- **~52** — `attribute :status, Status, default: "pending"` (bare-string
  shorthand for a VO-typed default) refused as `Malformed` : "a default fills
  its FIELDS". **The canonical pizzas.bluebook uses this EXACT shorthand**
  (`attribute :status, OrderStatus, default: "pending" do ... end`, confirmed
  by reading the file directly) — so hecksagain's meta-validator is stricter
  than the corpus's own canonical convention. Real drift, distinct from the
  parser-correctness findings above ; worth its own decision.
- **~29** — `Conductor is not a well-formed bluebook ... no Aggregate with
  bluebook_id` : a referential-integrity check firing during my ISOLATED
  single-file boot, likely because Conductor references a sibling aggregate
  the isolation deliberately excludes. Possibly a limit of the isolation
  strategy itself, not a hecksagain defect — not chased further.
- **36** — `Acl has no aggregate X`, an `UnknownVerb` surfacing from inside a
  POLICY reaction (an `across` cross-domain policy), not the dispatched
  command itself. `runtime/errors.rb`'s own comment says a cross-domain
  reaction failure should be RECORDED as undelivered, never raised — if that
  contract doesn't actually hold for a policy target that's absent entirely
  (not just "deployment lacks that domain"), that's a real interpreter
  question. Not chased further this pass.
- **Remaining hundreds** — `AbsentArgument`/`NotFound` refusals for commands
  missing an attribute the test never supplies (`id:`, `worker:`,
  `stale_after:`, `project:`, `description:` ...). Same shape as the
  `AgentMessage.Send` finding above : machine-generated `.behaviors` files
  that never learned to synthesize the one attribute (usually the
  caller-minted `id`) the conceiver didn't know a command needed. A corpus
  gap, not a runner defect — confirmed on `AgentMessage.Send` by dispatching
  the SAME call with `id:` added by hand : it succeeds.

### What this means for the deletion decision

The runtime now EXISTS and largely AGREES with the domain (346 clean passes
across real corpus files, including the full multi-step `setup` chain +
`expect refused:` reference case). The errors are overwhelmingly corpus
authoring gaps (missing attributes) and a handful of concentrated, named
findings — not a runner that doesn't work. Still not a green light to delete
Rust : the parser-correctness gaps from the top of this card (`family`,
`on:`/`success`/`failure`) are unrelated to behaviors and still open, and 51
files + the pizzas/banking canon are still unswept.
