# i746 — hecksagain has no effect-port execution (on:/success/failure)

Split off the parser-removal plan (`~/.claude/plans/fully-plan-the-removal-
velvety-chipmunk.md`) at Chris's explicit choice : this is a real subsystem
port, not something to fold into that plan's Phase 1. Filed with full
citations so nobody has to re-derive them.

## Where it breaks, exactly

`vendor/hecksagain/lib/hecksagain/bluebook/ir/hexagon.rb:15`

    Bind = Struct.new(:aggregate, :verb, :adapter, :role, keyword_init: true)

No `on`, `success`, `failure` fields.

**`on:` dies in `BindingProxy#method_missing`**
(`vendor/hecksagain/lib/hecksagain/bluebook/dsl/binding_proxy.rb:73-114`).
`Order.charged_by("Stripe", on: "OrderPlaced")` arrives as `kwargs={on: "..."}
`; only `kwargs[:role]` is ever read (lines 99, 110). `on:` is captured, then
dropped.

**The do-block runs against the wrong receiver.** `block&.call` at
binding_proxy.rb:112 is a plain call, not `instance_eval` — it runs in the
block's ORIGINAL lexical scope, which is `HecksagonBuilder`'s own
`instance_eval` context (hecksagon_builder.rb:249). So `success "Order.
Authorize"` resolves to `HecksagonBuilder#success` — the no-op stub at
hecksagon_builder.rb:214-215 (`def success(*) = nil; def failure(*) = nil`).

**The mechanical crux**: the builder receiving `success`/`failure` has no
reference to the Bind minted two calls earlier in a DIFFERENT object
(`BindingProxy`). Recommended fix : `BindingProxy` sets `builder.current_bind
= bind` around `block&.call`; `HecksagonBuilder#success`/`#failure` write onto
`current_bind` instead of no-opping. Preserves existing lexical scoping
(needs `BindingProxy` to hold a `builder` reference — it currently holds only
`@collector`, binding_proxy.rb:13-16, so `.namespace`/`.new` call sites need
updating too).

## Runtime execution — confirmed absent, not just unwired

- `Port#effect?`/`#reply?` (hexagon.rb:6) defined, never called anywhere.
- `Registry::Verification#check_verb` (runtime/registry/verification.rb:
  47-55) only checks `bind.verb == port.verb` ; never branches on
  `port.signal`/`.effect?`.
- `Dispatcher#dispatch` (runtime/dispatcher.rb:74-131) has zero references to
  `charged_by`/`OutboundEvent`/any effect concept. After events announce, it
  only runs `@policies.react` + `@sagas.advance` — no adapter dispatch on
  events at all.
- `Ports::Execution`'s own header (ports/execution.rb:32-38) says so directly:
  *"SIGNAL IS :reply, deliberately. The effect-family shape the Pizzas example
  documents... has no implementation anywhere in hecksagain."*

## The good news : this is a port, not new design

A fully-built Rust reference exists, never carried into hecksagain during the
migration:

- **IR shape to copy**: `rust/src/hecksagon_ir.rs:187-209` — `Binding
  {aggregate, verb, adapter, on, success, failure}`. Exactly the 3 fields
  `IR::Bind` needs.
- **The producer**: `rust/src/runtime/effect_outbound.rs:26-134`,
  `record_effect_outbound`. Called from the dispatcher right after commit
  (`rust/src/runtime/dispatch_core.rs:138`). For each binding whose `on`
  matches the just-emitted event, whose adapter's port/family carries the
  bind's verb, build a delivery record (`delivery_id = source_type::
  source_id::event::adapter` for idempotency), re-enter `OutboundEvent::
  OutboundEvent.Record`.
- **The adapter→family→verb attach check Rust needs already exists in Ruby**:
  `Registry::Verification#port_for`/`check_verb` (verification.rb:47-55,
  70-75) already computes `@adapters[bind.adapter].port → @ports[...] →
  port.verb == bind.verb`. The Ruby port of `record_effect_outbound` should
  call that plus `port.effect?` — genuinely simpler than the Rust source.
- **The target bluebook is already fully designed, in the live corpus, zero
  callers**: `hecks_conception/aggregates/framework/hexagon/bluebook/
  outbound_event.bluebook` — `Record`/`Claim`/`MarkDelivered`/`MarkFailed`
  commands, `Pending`/`AllPending` queries, its own vision text describing
  exactly this mechanism. Confirmed present in `hecksagain-cli catalog
  hecks_conception`'s bluebook list. Nothing calls `.Record` on it anywhere.
- **A generic consumer already exists**: `bin/adapter-host` — polls
  `OutboundEvent::OutboundEvent.pending(adapter)`, claims, execs a thin
  handler subprocess on stdin/exit-code, dispatches `success_command`/
  `failure_command`, marks delivered. Real, not a stub — **but its discovery
  step still shells to the Rust binary** (`bin/adapter-host:39`, `"$SH"
  dump-hecksagon "$ADAPTER_FILE" | jq -r '.adapters[0].handler'` —
  `hecksagain-cli` has no `dump-hecksagon` subcommand, and `IR::Adapter`/
  `AdapterBuilder` have no `handler` field at all today). Confirmed
  `~/.local/bin/storehouse` symlinks straight to `rust/target/release/
  storehouse` — the working end-to-end demo still depends on the Rust binary,
  never exercised against the Ruby CLI.

## Prerequisite, separate from the DSL gap

`examples/pizzas/bluebook/stripe.adapter` uses the OLD `family "payment" /
handler "..."` shape — confirmed crashes hecksagain boot with a hard
`NoMethodError` (no `method_missing` on `AdapterBuilder`). Fixed as part of
the parser-removal plan's Phase 1a (family→port migration) — that fix adds a
no-op `handler(*) = nil` stub so this file boots ; REAL handler support
(step 7 below) is this card's job, not Phase 1a's.

## Scoped build list, in order

1. (Handled by Phase 1a, not this card) Fix `examples/pizzas/bluebook/
   stripe.adapter` so Pizzas boots under hecksagain at all.
2. `IR::Bind`: add `:on, :success, :failure` (hexagon.rb:15). Trivial.
3. `BindingProxy#method_missing`: thread `kwargs[:on]` onto the new Bind
   (binding_proxy.rb:106-111). Trivial.
4. The scoping fix above (`builder.current_bind`) — small, contained, but a
   real decision.
5. Port `record_effect_outbound` (~196 lines Rust) into Ruby (~60-80 lines,
   simpler — `Verification#port_for` is reusable), hooked into
   `Dispatcher#dispatch` after `announced` events are known (dispatcher.rb,
   near line 124-128), calling `reenter("OutboundEvent::OutboundEvent.
   Record", ...)`. Verified safe against the `role "System"` gate :
   `Caller.without` (caller.rb) nils the ambient caller, and
   `refuse_role_mismatch` (`command_rules/authorization.rb:17-20`) is
   unchecked when caller is nil — exactly like `PolicyInterpreter#deliver`
   already relies on.
6. Decide + implement framework attachment: either Pizzas gets
   `uses_framework "OutboundEvent"` (hecksagon_builder.rb:122-125, 1 line —
   recommended for this MVP) or the runtime always loads the outbox (Rust's
   bigger, boot-wide choice, effect_outbound.rs:31-35).
7. Add `handler` to `IR::Adapter`/`AdapterBuilder`, and a
   `dump-hecksagon`-equivalent (or a dedicated `hecksagain-cli
   adapter-handler <root> <name>`) subcommand so `bin/adapter-host` can
   resolve its handler against the Ruby CLI instead of the still-installed
   Rust binary. ~20-30 lines — confirm scope by re-running `bin/adapter-host`
   pointed at `STOREHOUSE=hecksagain_runtime/bin/hecksagain-cli` once step 6
   lands.

## Estimate

Not a genuine new subsystem — a scoped port of an already-designed,
already-shipped Rust mechanism, plus one small missing CLI facility.
**Closer to 1-2 days than a week**, if steps 5-6 go cleanly. Step 7 could push
toward the high end if other parts of the migration plan also need
`dump-hecksagon` parity — worth checking against the rest of the migration
plan before committing to a number.
