# i748 — `Hecks.behavior_kind` / `Hecks.adapter_family` : undefined DSL entrypoints, invisible to both gates

Found while chasing an unrelated caching bug during i745 Phase 2 (CI
migration). Filed separately per i745's own precedent for real,
self-contained parser-completeness gaps (see i746, i747) — this is the
same shape (a DSL verb the corpus uses that vendor/hecksagain's `Hecks`
module never defines), a different location.

## Where it breaks

`vendor/hecksagain/lib/hecksagain.rb` defines exactly these top-level
entrypoints on `Hecks`/`Hecksagain`: `bluebook`, `hecksagon`, `port`,
`adapter`, `world`, `data_translation`, `behaviors`. No `behavior_kind`,
no `adapter_family`.

Full sweep run this pass (`grep -rln 'Hecks\.behavior_kind\|Hecks\.adapter_family\|Hecks\.provider' hecks_conception`) — three sibling directories, three undefined verbs, 21 files total:

    aggregates/framework/behavior_kinds/    (7 files) — Hecks.behavior_kind
      back_aggregate_storage.hecksagon    invoke_claude_tool.hecksagon
      invoke_mcp_tool.hecksagon           perform_exec.hecksagon
      perform_web_fetch.hecksagon         perform_web_search.hecksagon
      render_report.hecksagon

    aggregates/framework/adapter_families/  (10 files) — Hecks.adapter_family
      claude_tool.hecksagon  exec.hecksagon    heki.hecksagon   html.hecksagon
      markdown.hecksagon     mcp.hecksagon     memory.hecksagon sms.hecksagon
      sqlite.hecksagon       web_tool.hecksagon

    aggregates/framework/providers/         (4 files) — Hecks.provider
      duckduckgo.hecksagon  gmail.hecksagon  http_get.hecksagon  twilio.hecksagon

Each opens with `Hecks.<verb> "<name>" do ... end`. The moment any of
these loads, it raises the matching `NoMethodError: undefined method
'<verb>' for module Hecksagain`.

**This is not a guess about intent** —
`hecks_conception/aggregates/framework/hecksagon/bluebook/hecksagon_ir.bluebook:96-106`
describes the exact IR field these three verbs are meant to populate:

    # FrameworkKind — the meta-layer discriminator. Plain
    # `Hecks.hecksagon` files leave this empty ; files declared
    # via `Hecks.adapter_family` / `Hecks.provider` /
    # `Hecks.behavior_kind` carry the family-kind string here.
    # The kernel framework_registry walks framework/* and indexes
    # by this value.

So this is fully-designed functionality — a real `Hecksagon::FrameworkKind`
value object already modeled in the corpus's own IR bluebook — that was
never ported into `vendor/hecksagain`'s DSL, same shape as i746's
`on:`/`success`/`failure` gap (design exists, port doesn't).

## Why neither gate catches it

- **Gate 2b / `hecksagain-cli validate`**: discovers its 63 roots by
  walking for directories, and (per i745's own Phase 1b work) treats a
  root as valid input only when it resolves through `Adapters::Folder`'s
  `bluebook/`-subdir convention or one of `stage_flat_corpus`'s three
  known project shapes. `framework/behavior_kinds/` has no `bluebook/`
  subdir — files sit bare — so a scoped validate of that directory finds
  nothing to check (confirmed live: `hecksagain-cli validate
  hecks_conception` lists 63 roots ; `framework/behavior_kinds` is not
  among them).
- **`.behaviors` sweep**: `hecksagain-cli behaviors
  hecks_conception/aggregates/framework/behavior_kinds` returns
  `files_swept: 0` — there are no `.behaviors` files in that directory
  (only `.hecksagon`), so the sweep has nothing to walk and reports
  clean by omission.
- Only a **scattered-project full-corpus flatten** (`stage_flat_corpus`
  falling into its `scattered_project?` branch, the broad
  `root/**/*.{bluebook,hecksagon,world,fixtures,behaviors}` glob with no
  `bluebook/` segment requirement) ever actually loads these files —
  and that branch is not what either gate normally takes for
  `hecks_conception` (which usually matches `CANON_SUBDIRS` instead).
  This is the exact "THE GATE IS GREEN BECAUSE IT IS NOT LOOKING" shape
  i745 already catalogued twice for other roots (Conductor,
  catalog/Explorer.ByKind) — a third instance, same root cause : a
  gate's coverage is part of the gate, and coverage here is zero on
  this whole directory.

## What these files are trying to declare

Per `back_aggregate_storage.hecksagon`'s own vision text, `behavior_kind`
looks like a **framework meta-layer declaration** distinct from an
ordinary `hecksagon` (hexagon/bind) file — it describes a *kind* of
kernel behavior ("what the kernel does when a `:claude_tool` adapter
fires", "the persistence PORT resolved at repository-mint time"), not a
domain's own bind wiring. It reads as a real, distinct DSL concept that
was designed and written against but never implemented in
vendor/hecksagain — same shape as i746's `on:`/`success`/`failure` (a
Rust-era concept that never got ported), not obviously a rename
collision like `family`→`port` was.

## Recommended next step

1. Decide, Chris's call: add a `FrameworkKind`-aware DSL entrypoint set
   to `Hecksagain`/`Bluebook::DSL` — `behavior_kind`, `adapter_family`,
   `provider` each mirroring how `port`/`adapter`/`world` are a
   `Bluebook::DSL::XBuilder.build` call — and wire `Hecksagon::
   FrameworkKind` + the `framework_registry` walk the IR bluebook
   already documents. This is a port of designed-but-unbuilt behavior,
   not new design from scratch.
2. Whichever gate discovery convention gets fixed for this (walking for
   `bluebook/` subdirs), also reconsider whether it should widen to
   catch bare-directory `.hecksagon`/`.bluebook` files in general — this
   is the third time a bare, non-`bluebook/`-nested directory has hidden
   real content from both gates this month.
3. Worth doing alongside i746 (same session found both, same shape:
   design fully exists in the corpus/IR, port to vendor/hecksagain
   doesn't) — not necessarily the same commit, but the same investigation
   context applies.
