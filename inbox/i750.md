## The correction (own this plainly, it's the actual finding)

I claimed "nothing today takes a hecksagain domain and emits a compilable
Rust or WASM crate" -- based entirely on searching `~/Projects/hecks`'s own
`codegen/` (Ruby-target generators only) and `vendor/hecksagain/`'s
contents. That claim was false, and the way it was false is worth naming:
**`vendor/hecksagain/VENDORED_FROM.md` says vendoring only ever covered
`lib/` + the gemspec** -- so `rust/`'s absence from the vendored copy was a
vendoring SCOPE decision made 2026-08-11, not evidence the ecosystem lacks
it. I read absence-in-a-subset as absence-in-the-whole. Same shape of
mistake as this session's earlier "only bin-buddy depends on rust/src"
error -- a confident negative built on a search that was never widened past
the local repo.

**What actually exists**: `~/Projects/hecksagain` (a separate, real,
actively-developed repo -- own `origin` at `github.com/chrisyoung/
hecksagain`, HEAD `d3bb07724` dated 2026-08-12) has a working generator
under `rust/`:

- `bin/project_rust <domain>` -- bluebook IR -> a generated Rust module
  tree (`rust/src/generated/<domain>/*.rs`, `ir.json`, `manifest.json`,
  `merged.rs`), a whole Ruby pipeline behind it (`rust/project/
  domain_generator.rb`, `expr_emitter.rb`, `mutations.rb`, `queries.rb`,
  `reactions.rb`, `read_models.rb`, etc.)
- `bin/project_wasm <domain>` -- cross-compiles to `wasm32-wasip1`,
  confirmed working (`rust/dist/pizzas.wasm`, `banking.wasm`,
  `embryonaut.wasm`, `embryonautfoundersapp.wasm` all already built)
- `bin/project_wasm_browser <domain>` -- builds a `wasm-bindgen --target
  web` ES module (`rust/dist/browser/banking/` already populated)

Domains already projected: banking, compliance, embryonaut, governance,
identity, pizzas, plus the self-hosted grammar itself (`meta/`).
