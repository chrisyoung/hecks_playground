# 2026-08-13 -- both open questions answered

## Q1: the fork HAS the projector. Nothing to reconcile.

`~/Projects/hecks-hecksagain` (the fork vendored into hecks_playground) carries the
whole subsystem:

    rust/src/{kernel,generated,exemplar}   rust/host/   rust/web/   rust/project/
    bin/project_rust  bin/project_wasm  bin/project_wasm_browser  bin/rust_conformance

with generated trees already on disk for banking, embryonaut, governance,
identity, meta, pizzas. Verified live rather than inferred: `bundle exec
ruby bin/project_wasm examples/pizzas` in the fork produced
`rust/dist/pizzas.wasm` (release, wasm32-wasip1, 10.3s). Fork tree
reverted afterward.

The fork contains upstream `77b3dc2` (2026-08-11), well after the
projector landed, so the ten hecks_playground-specific fixes sit on a base that
already had it. No rebase, no re-fork, no diverged-lines problem.

**What the fork lacks vs. upstream**: `rust/parser`, `rust/codegen`,
`rust/build` -- the Rust-native pipeline (`hecks_playground-parse`/`hecks_playground-codegen`/
`hecks_playground-build`, "no Ruby at build time") that landed upstream AFTER the
fork point. Not needed to emit WASM: `bin/project_wasm` is Ruby-driven
and is what produced every `.wasm` in existence, including the one above.
A later nice-to-have, not a blocker.

**Why the vendored copy has none of it**, which is the actual mechanism
this card was groping for: `bin/vendor-hecksagain` runs

    git archive <sha> -- lib hecksagain.gemspec

Two hardcoded paths. That single line -- not any fork/upstream
divergence -- is why `hecks_playground/vendor/hecksagain` has no projector while the
fork it was cut from does. Widening it to include `rust/` and the
`bin/project_*` scripts (excluding `rust/target/` and probably
`rust/src/generated/`) is close to the entire delivery mechanism.

## Q2: hecks_playground_conception is a project, not a swap -- but four causes, not hundreds

Tested at `db253cd` (the exact commit hecks_playground vendors, not fork HEAD) in a
throwaway worktree, since fork HEAD's newer DSL guards would have
confounded the result.

**Layout blocks most of it before parsing starts.** `bin/project_rust
<domain>` requires `<domain>/bluebook/<basename(domain)>.bluebook` -- one
chapter, named after its directory. hecks_playground_conception is 138 bluebook
files / 135 distinct chapters across ~40 nested `*/bluebook/` dirs, several
chapters per dir (`aggregates/language/grammar/bluebook` has 11). Of 14
aggregate groups, 5 match the convention.

| domain | generate | compile |
|---|---|---|
| `storehouse` | yes | **31 errors** |
| `plan` | yes (34 skips) | **465 errors** |
| `demo` | yes (20 skips) | not built |
| `drafting` | yes (21 skips) | not built |
| `framework`, `conductor` | **LoadError** | -- |

Skips are the generator's own "not generated yet" refusals (e.g.
"optional argument feeds a non-optional target"), 20-34 per domain.

### The four defect classes

1. **No namespacing for value objects -- the big one.** `plan` declares
   `aggregate "Story"` and, separately, `value_object "Story"` five times
   inside different aggregates. All emit `pub struct Story` into one flat
   `story.rs`: line 47 is the value object (`pub value: String`), line
   1402 the aggregate. Conflicting `Clone`/`Debug`/`Fielded`/`PartialEq`
   impls, then 143 `E0609` + 84 `E0560` + 93 `E0308` cascading off it.
   Essentially all 465 errors are this one gap. The examples corpus never
   collides, so it was never exposed. Real generator design change:
   namespace value objects per aggregate, or refuse the collision.

2. **`status` collides with the generator's own state field.** An
   aggregate declaring a `status` attribute while also having states
   emits both `pub status: Option<Status>` and `pub status: String`.
   16 of storehouse's 31 errors.

3. **Inline `one_of` inside a `value_object`.** Emits `value:
   Value::from_json(...)` referencing a `Value` type never generated.
   4 errors. Same construct fork HEAD now refuses outright -- its guard
   says the old behavior "loads clean and is silently broken." The
   projector reaches that verdict independently, by failing to compile.
   33 sites in 19 corpus files. **Already being fixed** -- the working
   tree carries that migration (inline form to block form) as of this
   writing.

4. **Ruby `nil` leaking into generated Rust.** `primitive.rs:328` ->
   `from_states: &[nil]`. No emitter case for a transition from an absent
   state. One error, trivially fixable.

# 2026-08-14 -- 465 -> 5, via fixes made for a DIFFERENT reason (bin-buddy)

## What happened

The bin-buddy/hecksagain-WASM recompile plan (`i745`/`i749`'s own sibling
effort, all 6 approved phases now complete and committed) hit the EXACT
SAME defect class 1 shape independently, in bin-buddy's own `AddOn`
aggregate: `value_object "AddOn"` declared *inside* the `AddOn` aggregate
itself, for an identical self-referencing-VO reason to `plan`'s `Story`
(a local identity-string wrapper the SME reaches for repeatedly across
this whole corpus -- see the `conductor/claim.bluebook`-derived comment
this card already quoted). Fixed narrowly in
`vendor/hecksagain/rust/project/domain_generator.rb` as
`disambiguate_self_named_value_object!` -- renames a VO to `#{name}Ref`
and retypes every reference to it, but ONLY when the VO's name equals its
OWN owning aggregate's name (not any other aggregate's).

Separately, a boolean-scalar codegen gap surfaced regenerating `plan` as a
bonus regression check today: `json_codec.rb`'s `SCALAR_JSON_ACCESSOR` (and
two sibling scalar-type case tables) never got the `FalseClass` entry
`naming.rb`'s own `SCALAR` map already had, so ANY boolean-typed attribute
crashed `project_rust` with a raw Ruby `KeyError` -- and because
`project_rust` generates `meta` (the self-hosted grammar) before the
requested domain and aborts the WHOLE run on the first uncaught exception,
this masked itself as `plan` never even starting, surfacing downstream as
a misleading `E0583: file not found for module plan` (the crate's own
`mod.rs` referenced a domain whose generation had silently aborted
upstream). Fixed: `kernel/json.rs` gained `Json::as_bool`, `json_codec.rb`
gained the `FalseClass -> as_bool` accessor entry plus the two missing
`to_json` case branches. Verified zero regression: regenerated bin-buddy
(the canonical default domain) after both fixes, `cargo build` clean,
`Cargo.toml`'s default feature restored to `bin_buddy`.

## `plan`'s error count with both fixes applied: 465 -> 5

Neither fix targeted `plan` -- both were made for bin-buddy/shared-codegen
reasons and happened to apply here too, which is the actual news: **most
of `plan`'s 465 errors were the self-referencing occurrence of defect
class 1** (`Story`'s own `value_object "Story"` declared inside the
`Story` aggregate itself, for a self-ref -- exactly the pattern the
"line 47 vs line 1402, same file" example in this card's original write-up
described). That ONE occurrence caused an in-file duplicate-struct
definition, which is what cascades into ~450 errors (conflicting
`Clone`/`Debug`/`Fielded`/`PartialEq` impls, then E0609/E0560/E0308 off
every use site) -- not the other 4 non-self-referencing `value_object
"Story"` declarations (inside `Sprint`, and two others), which live in
their OWN files/modules and never collided in-Rust to begin with. Defect
classes 2 (`status` field collision) and 4 (`nil` leaking into
`&[states]`) also read as resolved in this run -- 0 errors of either shape
survived. Class 3 (inline `one_of`) wasn't re-confirmed explicitly but no
`Value::from_json` error surfaced either; worth a real recheck before
closing this card, not assumed clean here.

## The 5 remaining errors -- two genuinely distinct causes, neither touched

**4 errors -- defect class 1's own non-self-referencing residue, exactly
as this card's "namespace value objects per aggregate, or refuse the
collision" recommendation already named.** `Plan::Board.PlaceCard` /
`RemoveCard` (`card_ref: Story`) and `Plan::Story.Start`
(`worker: Worker` -- see below) reference a bare aggregate/VO name as an
attribute type -- a WORKING pattern elsewhere in this same domain
(`sprint_ref: Sprint`, `queued_sprints: Sprint` compile fine) precisely
because `Sprint` is declared exactly once. `Story` is declared as a VO
independently in 4 different sibling aggregates' own files, none of which
`board.rs` can see or import -- board.rs ends up emitting a bare, unqualified
`Story`/`Worker` identifier the compiler can't resolve (`E0425`/`E0433`,
`cargo`'s own diagnostic literally lists 4-5 same-named candidates across
different modules). This is not a new defect class -- it's `plan`'s own
proof that a real design fix is needed, now that the self-referencing
case dominating the count is gone. Chris's own answer to the "Naming
collision" question during the bin-buddy plan-mode conversation this
session -- **"qualify generated type names by owning aggregate"** -- is
direct prior art for the fix here too, even though that conversation was
scoped to bin-buddy. Not implemented in this update -- deserves its own
session, this is a real generator design change touching type resolution
domain-wide, not a narrow patch.

**1 of those 4 (`Worker`) is ALSO a second, distinct problem worth
separating out**: `storehouse describe Plan::Story` shows `Start`'s own
`worker` attribute resolved to literal type `"Worker"` by hecksagain-cli's
own Ruby DSL at validate time -- but `value_object "Worker"` does not
exist ANYWHERE in `plan.bluebook` (confirmed: zero matches for the
literal string). Ruby's own DSL accepts an attribute type referencing an
undeclared constant name and silently carries it through as an opaque
type-name string, with no validation catching it -- the defect only
surfaces later, downstream, when the Rust projector tries to actually
resolve that name as a real type. This is NOT a rust-projector bug at
all: it's (a) very likely a genuine content defect in `plan.bluebook`
itself (SME probably meant something else here -- not mine to guess or
fix), and (b) a real gap in hecksagain-cli's own DSL validation --
`Registry#verify!`-time wiring checks don't currently catch an
unresolvable attribute type. Filed separately as its own card
(`i764`) since it's a validator gap, not a projector gap, and touches a
domain owner decision (what `Worker` should actually mean here) I
shouldn't make unilaterally.

**1 error, unrelated to either of the above**: `usecase.rs:769` --
`record.steps = "[]".to_string()` assigned into a `Vec<Step>`-typed field
(`E0308`). A `list_of(Step)`-typed attribute's default apparently emits a
bare JSON-string-literal default (`"[]"`) instead of an empty-`Vec`
construction -- looks like a list-attribute default-value codegen gap,
not investigated further here. Not the same root cause as the FalseClass
fix above (that was a missing accessor entry, not a default-value
emission bug) or defect class 1 (naming, not defaults).
