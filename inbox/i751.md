# i751 -- catalog/Explorer.ByKind validate failure

## What's failing

`hecksagain-cli validate hecks_conception` reports `hecks_conception/catalog`
invalid :

    Explorer.ByKind asks about kind, which Explorer never declares — a
    query over a field that does not exist matches nothing and refuses
    nothing

## Status when filed

The ONLY remaining invalid root out of 63 (was 2 -- conductor -- of 63
at the start of this session ; conductor's multi-file boot-ordering bug
was found and fixed for real this session, see the `fix(hecksagain):
defer MetaValidator.call...` commit). This is now the sole blocker on
the pre-commit validate gate for ANY bluebook-touching commit, corpus-
wide (the gate is zero-tolerance, not diff-scoped) -- landed past it via
`VALIDATE_SKIP=1` with Chris's explicit sign-off, same discipline as
conductor's own prior bypass earlier in the session (never pre-empted,
reported and asked each time).

## Confirmed root cause (investigated this session, before filing)

NOT a multi-file ordering bug like conductor's -- checked, ruled out.
`Explorer` (aggregate + its query both live in ONE file, `catalog/
bluebook/appeal.bluebook`, lines 70-169) declares:

    attribute :aggregate_names, list_of(ExplorerEntry)

    value_object "ExplorerEntry" do
      attribute :name, String
      attribute :kind, String
    end

    query "ByKind" do |kind|
      where(kind: kind)
    end

`kind` exists only NESTED inside `ExplorerEntry`, one level down inside
the `aggregate_names` list -- `Explorer` itself has no top-level `kind`
field. `ByKind`'s `where(kind: kind)` asks for a field at the Explorer
level that was never declared there. The validator is correct to refuse
this ; it is not a false positive.

## Why this isn't a quick fix

The real question is INTENT, not syntax : should `ByKind` filter entries
WITHIN `aggregate_names` by their nested `kind` (a list-element field
match -- unclear whether the query DSL supports this at all today), or
should `Explorer` grow its own top-level `kind` field that means
something different from `ExplorerEntry`'s? Fixing this blind (e.g.
deleting the query, or bolting on a same-named top-level attribute just
to satisfy the validator) risks quietly breaking whatever calls `ByKind`
today expecting list-filtering semantics. Needs the caller/intent
understood first.

## Next step

Find what calls `Explorer.by_kind` (or wires to `ByKind`) to learn the
intended semantics, THEN decide: extend the query DSL to filter list
elements by a nested field, or give `Explorer` its own top-level field.
Not a generated-validator-deferral question like conductor was -- this
is real design work on the query.
