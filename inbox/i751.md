# i751 -- catalog/Explorer.ByKind, then the whole corpus behind it

## Resolution : Explorer.ByKind removed, not redesigned

Investigated the two options the original card posed (nested list-filter
semantics vs. a new top-level field) before picking either. No real
caller anywhere in the repo (grepped clean -- only the declaration
itself, its own generic behaviors smoke test, and doc/template copies
of the same file elsewhere in the tree). And moot regardless:
`aggregate_names` -- the list `kind` lives inside -- is never populated
by ANY command on Explorer (`LoadDomain` emits `DomainLoaded` with no
`then_set` at all). A where-clause over a field that both doesn't exist
AND has no real data behind it is dead code twice over. Removed, with
the full investigation left as a comment in appeal.bluebook so the next
person doesn't have to redo it.

The query DSL DOES support dotted paths into a `list_of` attribute at
the declaration/validator level (`QuerySpecification::FieldPath.leaf_attribute`
walks through fine) but NOT at the value-read level (`FieldPath.dig`
reduces a dotted path via plain Hash reads, which can't descend into an
Array) -- so even the "real" fix would have been unverifiable today.
Noted for whoever eventually wants real nested-list query filtering.

## What the fix unmasked, one validate run at a time

Each fix below was found ONLY by re-running the full-corpus
`storehouse__validate` after the previous fix -- the gate stops at the
first error per root, so a 2389-line file like appeal.bluebook can hide
an arbitrary number of independent defects behind each other.

1. **Explorer.ByKind** (above) -- dead query, removed, its orphaned
   behaviors test removed too.
2. **Playground.RecentEvents** -- identical shape: `where(timestamp:
   "recent")` asked for a field that only existed nested inside
   `PlaygroundEvent`. Doubly dead -- appeal.behaviors' OWN comment
   already said as much ("ExecuteCommand doesn't set timestamp to
   'recent' so the record doesn't match"), and ExecuteCommand doesn't
   even append to `events` in the first place. Removed the same way,
   comment + orphaned test both.
3. **11x bare-literal defaults on named VO-typed attributes** --
   `attribute :status, Status, default: "pending"` refuses every
   create (a VO default must fill its fields: `default: { value: ... }`).
   Found across `catalog.bluebook`, `none_in_state_gate.bluebook` (x2),
   `boot.bluebook`, `appeal.bluebook` (x3), `law.bluebook` (x2),
   `pizzas.bluebook`, `court.bluebook` -- all confirmed simple
   single-field `attribute :value, String` VOs before fixing, so the
   `{ value: ... }` wrap was safe in every case, not guessed.
4. **A typo'd policy verb** -- `defaults tab: "editor"` inside
   `policy "SwitchToEditorOnFileOpen"` isn't a real `PolicyBuilder`
   method (`NoMethodError`, not even a validator-caught Malformed).
   The real verb with matching kwarg-merge semantics is `map` --
   fixed to `map tab: "editor"`.
5. **2x bare-symbol `identified_by`** -- `identified_by :ref` /
   `identified_by :slot` in `none_in_state_gate.bluebook`, same class
   as the Kitchen bug found earlier this session in examples/pizzas
   (i760): `identified_by` takes zero positional args, only a block.
   Fixed to `identified_by { ref.value }` / `identified_by { slot.value }`.
   Proactively grepped the WHOLE hecks_conception tree afterward for
   any other bare-symbol `identified_by` -- everything else left was
   prose/comments, confirmed clean.
