# i754 -- generated Rust: codegen assumes every lifecycle field is a bare String

## What's actually wrong (revised from this card's original scope)

The original framing ("the generic field-reflection accessor assumes
String") was correct as far as it went, but investigation this session
found the assumption runs much deeper and the true error surface is
much larger than first measured -- the original card was written
testing `framework/agent` BEFORE i752's multi-file-loading fix landed,
which meant only ~1-2 errors were visible (AuthIdentity and Role's own
`.bluebook` files were being silently dropped, per i752). Once i752
was fixed and all three of framework/agent's co-located domains
(Agent, AuthIdentity, Role) generate and compile together, the same
underlying bug surfaces 37 errors across three Rust error classes:

    9 error[E0062]: field `status` specified more than once
    3 error[E0124]: field `status` is already declared
   35 error[E0308]: mismatched types  (0 unrelated to this bug, of the ones checked)

Concretely, in `role.rs`:

    #[derive(Debug, Clone, PartialEq)]
    pub struct Role {
        ...
        pub status: Option<Status>,   // <- from the ATTRIBUTE-driven emission (correct)
        pub status: String,           // <- from the LIFECYCLE-specific emission (wrong, duplicate)
    }

## The real root cause

`Agent.status` / `AuthIdentity.status` / `Role.status` are each declared
exactly ONCE in their source `.bluebook` -- as a normal `attribute
:status, Status` (Status being a one_of long-form value object) that
*also* happens to be the field the aggregate's `lifecycle` block
transitions:

    attribute :status, Status, default: "active" do
      transition "Retire" => "retired"
    end

hecksagain's own IR reflects this correctly: `status` appears exactly
once in `attributes` (VO-typed, with a default), and `lifecycle.field`
just *names* that same attribute -- it is metadata pointing at an
existing field, not a second field declaration. Confirmed directly via
`storehouse__catalog` against `framework/agent`.

The Rust generator, however, treats "the lifecycle field" as its own
separate thing that is always a String, and does so in (at least) six
places:

- `rust/project/fielded.rb:115-118` -- `emit_fielded_record`'s
  `fielded_lifecycle_arm` (reflection accessor: `Value::Str(self.status
  .clone())`)
- `rust/project/types.rb:173,181-189` -- `emit_entity`'s own parallel
  lifecycle-arm logic for entity elements (same shape, different code
  path, `TmplFieldType => "String"` hardcoded)
- `rust/project/types.rb:213` -- another `TmplFieldType => "String"`
  hardcode, aggregate-side
- `rust/project/mutations.rb:260` -- default-fields-assignment for a
  record's own lifecycle field: `#{default.inspect}.to_string()`
- `rust/project/commands.rb:13` -- `target_type_for`: `target ==
  lifecycle_field ? "String" : ...` (used to typecheck `then_set`
  targets against source types)
- `rust/project/commands.rb:303` -- default lifecycle field on a
  freshly-created record: `#{default.inspect}.to_string()`
- `rust/project/domain_generator.rb:24-28` -- `lifecycle_extra_field`
  (JSON serialization: `Json::Str(self.#{field}.clone())`)

None of these ask "is the lifecycle field's *declared attribute type* a
value object?" -- they all just emit `String` / `.to_string()` /
`Value::Str` unconditionally. This design predates VO-typed lifecycle
fields being expressible in the source grammar (or was written before
any corpus domain exercised the combination) and was never updated
once one_of long-form VOs became a normal lifecycle-field type
(this session's own i745/i750 migration made this MORE common, not
less -- 18 files moved to the long form).

**The deciding question the advisor flagged -- answered**: does the
runtime treat a VO-typed lifecycle field as a raw string internally, or
keep it wrapped? Confirmed via a real dispatch this session
(`Conductor::Worker.Register`) that the runtime returns the lifecycle
field wrapped (`:status=>#<Value ... @fields={:value=>"alive"}>`), not
as a bare string. **VO wins.** The fix direction is therefore: teach
the generator that the lifecycle field can be VO-typed and handle it
correctly wherever it currently hardcodes String -- not the reverse
(downcasting the domain model to always store lifecycle as a string
would contradict the runtime's own actual behavior).

## Shape of the real fix (not implemented this session)

1. **Stop emitting a duplicate struct field.** The lifecycle field is
   already emitted once by the normal attribute-driven struct-field
   loop, with its correct type. The lifecycle-specific code paths
   (fielded.rb's `fielded_lifecycle_arm`, types.rb's `lifecycle_arm`)
   should never emit a second `pub <field>: TYPE` -- they exist to
   generate the transition/reflection *behavior* around an existing
   field, not to declare the field itself.
2. **Make the reflection/JSON-serialization arms VO-aware.** Where they
   currently do `Value::Str(self.status.clone())` /
   `Json::Str(self.status.clone())` unconditionally, branch the same
   way the normal per-attribute reflection codegen already does for
   any other VO-typed field (need to locate that existing correct
   branch and reuse it, not reinvent it -- it's proven correct for
   every non-lifecycle VO field already, including Agent's own `Kind`).
3. **Wrap literal state-transition assignments.** `record.status =
   "pending".to_string();` and the default-fields-assignment sites
   (`mutations.rb:260`, `commands.rb:303`) need the SAME
   `scalar_literal_rhs`-style wrapping i753 just added for defaults --
   likely literally reusable, since it's the identical shape (a bare
   string literal headed at a VO-typed target).
4. **Fix `target_type_for` in commands.rb:13** so `then_set` type
   checking against the lifecycle field uses its real declared type,
   not a hardcoded `"String"`.

This touches five files and needs a real regression pass (agent,
authidentity, role, conductor, and a plain-String-lifecycle domain
like demo/pizzas as a control, to confirm the non-VO lifecycle case
still emits exactly as before). Scoped as a real fix, not attempted
this session -- reporting to Chris to choose whether it lands now or
later.
