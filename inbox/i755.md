# i755 -- generated Rust: unconstrained lifecycle transition emits a bare `nil`

## What's wrong

    error[E0425]: cannot find value `nil` in this scope
       --> src/generated/agent/agent.rs:337:79
        |
    337 |         Some(crate::kernel::TransitionCheck { field: "status", from_states: &[nil] }),
        |                                                                               ^^^ not found in this scope

`Agent.Retire` (and `Role.Retire`) declare `transition "Retire" =>
"retired"` with no `from:` clause -- meaning, at Ruby runtime, the
transition applies regardless of the record's current state. hecksagain's
IR represents that as `from_state: nil` on the transition row.

`rust/project/mutations.rb#lifecycle_transition_for` collects every
matching row's `from_state` into a `from_states` list, `.uniq`'d:

    { field: ..., to_state: ..., from_states: rows.map { |r| r[:from_state] }.uniq }

`rust/project/commands.rb`'s `transition_arg` then `.inspect`'s every
entry into the generated `&[...]` slice:

    "from_states: &[#{transition[:from_states].map(&:inspect).join(', ')}] }"

`nil.inspect` in Ruby is the STRING `"nil"` -- which lands in the
generated Rust source as the bare identifier `nil`, not a string
literal and not Rust's `None`. Rust has no `nil`; this is a straight
compile error, not a type mismatch this generator's usual VO-bridging
machinery has any hook into.

## Why this wasn't caught before

`vendor/hecksagain/rust/src/kernel/dispatch.rs`'s `TransitionCheck`:

    pub struct TransitionCheck {
        pub field: &'static str,
        pub from_states: &'static [&'static str],
    }
    ...
    if !check.from_states.contains(&current.as_str()) { ... refuse ... }

`from_states` is a plain, required slice -- there is no existing
representation for "no constraint, match any current state." An EMPTY
slice would be WRONG (an empty slice `.contains(...)` is always false,
so it would refuse every transition instead of allowing every one) --
this needs either a real design change to `TransitionCheck` itself
(e.g. `Option<&[&str]>`, `None` meaning unconstrained) or a generation-
time trick (enumerate every member of the lifecycle field's closed-set
VO, if it has one, and populate `from_states` with all of them --
doesn't generalize to a free-form String lifecycle field, which has no
fixed member list to enumerate).

Every domain exercised before this session's work (demo, pizzas,
conductor) happens to declare an explicit `from:` on every transition,
so this gap was real but dormant -- framework/agent's Agent.Retire /
Role.Retire are the first `hecks_conception` transitions this
generator has ever actually rendered without one.

## Where to look

- `vendor/hecksagain/rust/src/kernel/dispatch.rs:55-57` (`TransitionCheck`
  struct) and its two `from_states.contains(...)` call sites
  (~lines 141, 277) -- the real fix likely changes this struct's shape.
- `vendor/hecksagain/rust/project/mutations.rb#lifecycle_transition_for`
  (collects `from_state` rows, `nil` included, unfiltered)
- `vendor/hecksagain/rust/project/commands.rb` (`transition_arg`, both
  the aggregate and entity-command emit sites -- same `.inspect.join`
  shape lives in two places, mirroring i754's own aggregate/entity
  duplication)

    rm -rf rust/src/generated rust/target
    ruby bin/project_rust /path/to/hecks_conception/aggregates/framework/agent

Also re-check demo/conductor (explicit from: states, currently 0

an unconstrained transition should still be reachable from every state
