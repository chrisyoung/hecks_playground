# i757 -- :mcp / :web_tool adapters are declared but never actually execute

## What's wrong, confirmed live

Twice this session, dispatching a command bound to a `:mcp` or
`:web_tool` adapter succeeded, emitted its event, recorded state --
and the real external effect never happened:

1. `Tools::EmailTool.GetAttachment` (bound `:web_tool`, `tool:
   "gmail_attachment"`) -- dispatched clean, `AttachmentFetched`
   emitted, but `/tmp/joey_screenshot.png` never got written. Had to
   run the transitional script (`~/.config/miette/
   fetch_gmail_attachment.py`) directly to get real bytes.
2. `Tools::EmailTool.CreateDraft` (bound `:mcp`, `server: :gmail`,
   `tool: "mcp__claude_ai_Gmail__create_draft"`) -- dispatched clean,
   `DraftCreated` emitted, but `list_drafts` showed nothing. Had to
   call `mcp__claude_ai_Gmail__create_draft` directly to actually
   create the draft.

Both times the dispatch's own JSON response gave no signal anything
was wrong -- `ok: true`, a real event, real-looking state. Nothing
told the caller the adapter never ran.

## Why this matters more than a normal bug

Chris flagged directly: **once dispatch runs governed, calling the
underlying tool manually as a fallback is not an acceptable
workaround** -- it's exactly the kind of bypass governance exists to
catch. So this can't stay "known gap, route around it by hand." The
dispatcher needs to either (a) actually perform the effect, or (b)
make the gap loud and actionable in-band, not silent.

## Root cause

Every `:claude_tool`-family adapter proven working this session
(`ShellTool.Bash`, `FileTool.Read/Edit/Write`, `SearchTool.Grep`) does
something a bare `hecksagain-cli` subprocess can perform itself --
shell out, read/write a file. No bridge to an agent needed.

`:mcp` (Gmail) and `:web_tool` (gmail_attachment, web_fetch,
web_search) are different in kind : they require capabilities that
live ONLY in the calling agent's own connected session -- an
authenticated Gmail MCP connector, WebFetch/WebSearch, whatever else
is wired into that specific Claude session. A background Ruby process
started from a CLI has no access to any of that. The hecksagon
comments' claim that "the runtime resolves this" (i594 "landed") is
false -- grepped clean across both `hecksagain_runtime` and
`vendor/hecksagain`, no `resolve_web_tool_adapters`,
`web_tool_dispatcher`, `mcp_dispatcher`, or `gmail_attachment` handling
exists anywhere in the live code.

## Shape of the real fix

This is the SAME shape i746 already built this session for the
`charged_by`/payment effect-port pattern -- a domain event that an
external adapter picks up asynchronously and reports back on via a
verdict command. Generalize it:

1. When the dispatcher resolves a command to a `:mcp` or `:web_tool`
   adapter bind it cannot itself execute (no local `:exec`/file/shell
   primitive backs it), don't silently record the event and stop.
   Surface a structured pending-effect payload in the dispatch
   response : `{tool: "mcp__claude_ai_Gmail__create_draft", args:
   {...interpolated from the command's own attrs...}, result_into:
   "Hecks::Framework::Cascade::Cascade.RecordResult", invocation_id:
   ...}`.
2. The calling agent (Miette, via the storehouse MCP door) sees this
   in the dispatch result, performs the real tool call itself (the
   ONLY party that legitimately can), and reports the outcome back
   via an explicit follow-up dispatch to the named `result_into`
   command -- auditable, in-band, no bypass.
3. This closes the loop for every `:mcp`/`:web_tool` binding in one
   mechanism -- EmailTool's four Gmail commands, WebTool's
   WebFetch/WebSearch, and any future MCP-backed tool -- rather than
   hand-patching each one.

## Where to look

- `framework/adapter_families/mcp.hecksagon`, `web_tool.hecksagon`,
  `claude_tool.hecksagon` -- the family contracts already declare
  `:result_into` as a field; the execution arm is what's missing.
- `hecks_conception/aggregates/framework/tools/bluebook/tools.hecksagon`
  -- every `:mcp`/`:web_tool` binding (GetAttachment, SearchThreads,
  GetThread, CreateDraft, ListDrafts, WebFetch, WebSearch) needs this.
- The i746 effect-port work this session (`Dispatcher#record_effect_
  outbound`, `vendor/hecksagain/lib/hecksagain/runtime/dispatcher.rb`)
  is the closest existing precedent -- read it before designing this,
  the shape may transplant directly.
- `vendor/hecksagain/lib/hecksagain/runtime/dispatcher.rb`'s main
  dispatch path -- confirm exactly where a `:claude_tool` adapter's
  local execution currently happens, to see why `:mcp`/`:web_tool`
  binds fall through silently instead of erroring or surfacing.

## Verification once fixed

Re-dispatch `Tools::EmailTool.GetAttachment` and `Tools::EmailTool.
CreateDraft` against real data and confirm the dispatch response
itself carries the pending-effect instruction (not silent success),
then confirm the follow-up `Cascade.RecordResult` dispatch actually
lands the real Gmail draft / attachment bytes -- no manual tool call
outside the door.
