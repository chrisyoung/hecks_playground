# i758 -- closed-set lifecycle fields had no reflection arm, breaking every real transition

## What was wrong

`kernel::dispatch`'s (and `dispatch_entity`'s) `TransitionCheck` guard
reads the lifecycle field's CURRENT value generically:

    match record.field(check.field) {
        Some(Field::Value(Value::Str(current))) => { ... }
        _ => return Err(Refusal::TypeMismatch(format!(
            "{command_name}: lifecycle field {:?} missing or not a
             string -- a codegen bug", check.field
        ))),
    }

i754's fix correctly stopped the generator from emitting a SECOND,
wrongly-typed reflection arm for a closed-set lifecycle field (the
duplicate/mismatch that caused E0308/E0062/E0124). But it did so by
simply skipping the lifecycle-specific arm whenever the field was
already a declared attribute -- without checking whether the NORMAL
per-attribute reflection loop actually covers it. It doesn't, for
closed-set types: `emit_fielded_record`'s own per-attribute loop
explicitly skips every closed-set field (`next nil unless nested &&
!nested[:closed_set]`), a deliberate, harmless gap for a field like
`Kind` that nothing reads reflectively. The lifecycle field is the ONE
exception -- `TransitionCheck` reads it unconditionally -- so leaving
it with zero reflection arm meant `record.field("status")` returned
`None`, which the match above turns into a hard refusal on EVERY
lifecycle-transition dispatch, for every domain with a closed-set
lifecycle field (Agent, AuthIdentity, Role).

This compiled cleanly. `cargo build` gave no signal anything was
wrong -- the bug only manifests when a command with a `transition`
actually dispatches.

## The fix

New `Projector.lifecycle_reflection_arm(key, ident, target_type,
value_objects_by_name, optional:)` in bridging.rb: for a closed-set
target type, builds a match arm over the generated enum's variants,
mapping each back to its raw state string (`Status::Active =>
"active".to_string()`, ...), Option-aware (aggregate records) or plain
(entities, matching each shape's own struct-field convention). Falls
through to the original unwrapped `Value::Str(self.field.clone())`
shape for a plain String-backed field.

Wired into the two sites that previously guarded on
`lifecycle_field_declared?` alone: `fielded.rb#emit_fielded_record`
and `types.rb#emit_entity`'s own local `lifecycle_arm`. Both now also
check whether the resolved type is closed-set -- only skip when the
normal per-attribute loop already covers the field (declared AND
non-closed-set); emit the new type-aware arm in every other case
(closed-set, or the defensive not-a-declared-attribute fallback).

## How this was found

Not by `cargo build` -- by actually dispatching a command through the
compiled binary, per this session's own standard ("verify state
before guessing," "run the runtime to learn behaviour"). i755's own
verification step (confirming an unconstrained transition compiles
AND runs) surfaced this immediately: `Agent::Agent.Retire` compiled
clean, then refused at dispatch time with exactly the "codegen bug"
message this bug produces. A build-only verification pass -- which is
what i754's own closure had done -- would never have caught it.

## Verification

    Agent::Agent.Birth {name, description, kind: human}
      -> AgentBorn, status defaults to {"value":"active"}
    Agent::Agent.Retire {id: TestAgent}
      -> Retired, status correctly becomes {"value":"retired"}
    zero refusals

Run through the independently-compiled `rust/target/release/rust`
binary, piped `{"steps": [...]}` on stdin -- no Ruby runtime involved
at all. demo and conductor regression-checked clean, 0 errors, both
before and after.

## Lesson for future rust/ projector work

A clean `cargo build` proves the generated CODE TYPE-CHECKS. It does
NOT prove the generated code is semantically correct -- this bug is
proof: it compiled perfectly and was wrong every single time it ran.
Any future fix in this generator that touches a REFLECTION or GUARD
mechanism (anything `kernel::dispatch` itself reads back off a
generated type, not just what Rust's type checker verifies) needs a
real dispatch through the compiled binary as part of its own
verification, not just a clean build.
