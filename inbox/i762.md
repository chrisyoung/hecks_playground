# i762 -- bin-buddy's expects/given/guarantees use Ruby constructs the canonical evaluator never learned

## Found while

Piloting bin-buddy through `bin/project_rust` + `bin/project_wasm_browser`
(the plan to recompile bin-buddy against hecksagain's own wasm-bindgen
projection instead of the old hecks_playground/rust/src parser). Real dispatches
through the compiled binary refused on commands whose `expects` block
couldn't actually be evaluated.

## Confirmed root cause, not guessed

Every one of these constructs was checked directly against
`Hecksagain::Bluebook::Expression::Resolver.parse` in a live Ruby session
-- not inferred from the Rust side alone:

    Resolver.parse('Plan.find_by_code(plan_code).nil?')
    # => #<struct ... Lookup path="Plan.find_by_code(plan_code).nil?">

A cross-aggregate query call (`Aggregate.find_by_x(...)`) isn't a
recognized construct in the grammar AT ALL -- by design, the evaluator
only resolves against `state`/`attrs` (the current command's own args and
the aggregate's own current instance), no query-engine access. The parser
falls through to its own `Lookup.new(path: expr)` catch-all (same
fallback the multi-arg `start_with?` bug used, see photo.bluebook's own
fix this session) -- the ENTIRE literal call text becomes a bogus lookup
path, which then refuses at dispatch ("cannot resolve X") since no
attribute is ever named that.

A second, distinct shape hits the SAME wall without even needing a parse
failure: `subscription.operational_status` (service_task.bluebook's
Generate command) parses fine as an ordinary dotted lookup -- but
`subscription` is a reference-WRAPPER value_object (just `{value:
"sub_id_string"}`, the Aug 11 migration's own cross-domain-reference
pattern), which has no `operational_status` field at all. Confirmed live:

    {"verb":"ServiceTask::ServiceTask.Generate", ...}
    -> refusal: "cannot resolve \"operational_status\" on \"subscription\""

This is architecturally a DIFFERENT, bigger gap than the first --
"resolve a field on the LIVE, CURRENT state of the aggregate a reference
points at," not just "call a query method." Neither Ruby nor Rust has
any mechanism for either today.

    Date.today.iso8601                                      -- add_on.bluebook
    Time.now.iso8601                                        -- somewhere in the corpus (grep hit, file not pinned)
    %w[admin_manager owner]                                 -- somewhere in the corpus (role-check, file not pinned)

Plus the separate live-field-dereference shape (`subscription.
operational_status`, and likely others sharing the same reference-wrapper
pattern -- not exhaustively swept, only the one hit live).

## Why this wasn't fixed in this pass

Genuinely out of scope for "pilot-compile bin-buddy" -- these are TWO
real, separate FEATURE gaps in the shared canonical expression grammar
itself (cross-aggregate query resolution ; cross-aggregate live-field
dereferencing through a reference), not something a Rust-projector-only
fix can close, and not something safe to rush. `unit_price.amount_cents *
quantity` (plain multiplication) is the one exception that's probably a
small, safe grammar addition on its own -- everything else here is a real
design question (how does a stateless-per-call expression evaluator reach
across to another aggregate's live state at all?).

## Where to look

- `vendor/hecksagain/lib/hecksagain/bluebook/expression/resolver.rb` --
  `Resolver.parse`'s own regex-cascade (grep `Regexp.last_match`), where
  every one of the working constructs (`.present?`, `.match?`, `.start_
  with?`, `.split`, `.size`) was added the SAME way -- a new `elsif expr
  =~ /.../ ` clause and a new resolver Struct. Cross-aggregate query calls
  and live-field dereferencing don't fit this pattern at all -- they need
  the evaluator to have access to something beyond `state`/`attrs`
  (a live repository/query interface), a much bigger interpreter change.
- `vendor/hecksagain/lib/hecksagain/bluebook/expression/resolver.rb`'s
  own `interpret` case statement + `vendor/hecksagain/rust/src/kernel/
  expr.rs`'s `interpret` -- BOTH sides need it if it's ever built, same
  as every fix this session.
