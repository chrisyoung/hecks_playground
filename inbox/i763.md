# i763 -- migrate summer/ (Spring's CLI) off hecks/rust/src, the last blocker on rust/src/*parser* deletion

## What summer actually needs, confirmed live

    use storehouse::{heki, boot};
    storehouse::parser::parse
    storehouse::runtime::...
    storehouse::ir::...

Four real modules, not one -- `boot::run` (indexes + boots an arbitrary
domain directory), `parser::parse` (the actual bluebook parser this
whole plan retires), `heki` (the old native persistence format),
`ir`/`runtime` (the old IR + dispatch machinery). `domain_index.rs`
(393 lines) and `tools.rs` (338 lines) are real, substantial supporting
modules built on top of these -- this isn't a thin CLI shim over a
library, it's Spring's own real, working tool.

## Why this is a DIFFERENT shape of migration than bin-buddy's

bin-buddy (this session's whole plan) worked because it's ONE FIXED
domain : compile it once, ahead of time, via hecksagain's Ruby codegen
pipeline (`bin/project_rust`/`bin/project_wasm_browser`), ship the
generated Rust/WASM as a build artifact. Summer's whole point is the
OPPOSITE : `spring boot <any-dir>`, `spring exec "Domain.Agg.Cmd"`
against WHATEVER domain the caller points it at, decided at RUNTIME, not
baked in ahead of time. hecksagain's own live parsing path -- the one
every fix this session actually exercised -- is `hecksagain-cli` itself
(Ruby, `vendor/hecksagain/lib/hecksagain/bluebook/dsl/*`), not anything
Rust-native. There is no existing "parse an arbitrary domain at runtime"
capability on the Rust side at all -- the whole rust/ projector
(vendor/hecksagain/rust/) works by CODE-GENERATING one domain's own
Rust source ahead of time in Ruby, the opposite shape summer needs.

## Real options, not investigated further here -- a real design pass, not a quick fix

1. **Retire summer as a Rust binary ; replace with a thin wrapper over
   `hecksagain-cli`** (Ruby, already the live door everywhere else this
   session touched). Loses whatever performance/standalone-binary
   property made summer a compiled Rust tool in the first place --
   worth checking why it was built that way before assuming this is fine.
2. **Give summer a REAL runtime bluebook parser on the Rust side** --
   port `vendor/hecksagain/lib/hecksagain/bluebook/dsl/*`'s actual
   parsing logic to Rust for real (not code-generation -- a genuine
   interpreter, parsing arbitrary bluebook text at runtime the way the
   OLD `rust/src/parser.rs` did). A much bigger lift than anything this
   session's plan needed -- this is building a second real
   implementation of hecksagain's own DSL parser, the exact duplication-
   of-truth problem the whole parser-removal plan exists to END, just
   inverted (a real Rust parser this time, not a stale one).
3. **Some hybrid** -- summer shells out to `hecksagain-cli` for parsing/
   validation but keeps its own fast interactive/tab-complete UX layer
   in Rust, IPC'd somehow. Not sketched further here.

## Where to look

- `summer/src/main.rs`, `summer/src/domain_index.rs`,
  `summer/src/engine.rs`, `summer/src/tools.rs`, `summer/src/harness.rs`
  -- the whole tool, 1234 lines, all four files.
- `summer/Cargo.toml` -- the exact dependency : `storehouse = { path =
  "../rust" }`.
- This session's own bin-buddy work (inbox, this same posted_at date) --
  the closest real precedent for "what does migrating a rust/src
  consumer onto hecksagain actually take," even though the shape differs.

## Verification once picked up

`grep -rn 'storehouse::' summer/src/*.rs` returns nothing ; `summer/
Cargo.toml` no longer path-depends on `../rust` ; every one of
summer's own commands (`spring boot`, `spring list`, `spring exec`)
still works against a real domain, dispatched and confirmed, not just
compiled.
