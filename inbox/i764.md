# i764 -- undeclared attribute type silently passes hecksagain-cli's own validation

## What happened

Investigating i750's own residual error count (bonus regression work
alongside the bin-buddy/hecksagain-WASM plan, unrelated to it), found via
`storehouse describe Plan::Story` that `Story.Start`'s own `worker`
attribute -- `attribute :worker, Worker` in
`hecks_playground_conception/aggregates/plan/bluebook/plan.bluebook` -- resolves at
Ruby DSL validate time to attribute type `"Worker"`. But `value_object
"Worker"` does not exist anywhere in `plan.bluebook` (confirmed: zero
matches for the literal string `value_object "Worker"`, and zero matches
for `"Worker"` as a quoted string at all outside that one attribute
declaration). `storehouse validate` on the `plan` domain reports no error
for this -- the DSL happily builds a Registry carrying an attribute whose
declared type resolves to nothing.

## Why this matters

Two separate things are true here, and this card is about the SECOND one:

1. `plan.bluebook`'s own content is very likely wrong -- the SME
   (Chris) probably meant to reference an actual declared type here, or a
   plain untyped value, not a capitalized constant that happens to have no
   backing declaration. **Not this card's business to fix** -- that's a
   domain-content decision, not a framework bug, and I don't know what
   `Worker` was supposed to mean.
2. **hecksagain-cli's own DSL should have caught this and didn't.**
   `Registry#verify!` checks wiring at boot time (per this project's own
   `storehouse validate` tool description: "hecksagain's DSL builders
   raise inline, Registry#verify! checks wiring at boot time") -- an
   attribute type that resolves to a name backed by no `value_object`,
   no `Reference<...>`, and no scalar in the domain's own vocabulary
   should be exactly the kind of wiring defect that check exists for.
   Instead it passes through silently as an opaque string, and the only
   place it ever surfaces is a downstream consumer that actually tries to
   resolve the type into something concrete -- in this case, the Rust
   projector's own codegen, which emits a bare unresolvable `Worker`
   identifier into generated Rust and fails at `cargo build`, several
   steps and a context-switch away from the actual mistake.

Per this project's own "Validators before manual testing" standard: a
validation rule here protects every future bluebook that makes the same
typo/oversight, catching it at `storehouse validate` time (or even at
DSL-build time) instead of relying on a downstream Rust-specific tool to
notice much later.

## Where to look

- `hecksagain-cli`'s attribute-type resolution -- wherever `attribute
  :name, ConstantName` resolves `ConstantName` into the IR's own
  `"type"` string (likely `attribute_collector.rb` or a sibling DSL
  builder, same family as `normalize_boolean_alias`).
- Whatever backs `Registry#verify!`'s wiring checks -- the natural home
  for "does this attribute's declared type actually exist as a
  value_object / known scalar / reference target in this domain" as one
  more check alongside whatever it already verifies.

## Not investigated here

- Whether this is Ruby's own `const_missing`/lazy-constant mechanism at
  work, or a deliberate DSL design choice to accept any bare identifier
  as an opaque type tag. Either way the gap is the same: nothing checks
  it resolves to something real.
- Whether other bluebooks in this corpus have the same latent issue --
  only found via `plan`'s own residual Rust-projector error count, not
  via a sweep.
