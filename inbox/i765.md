# i765 -- generated/<chapter> is keyed by bare name only, so unrelated same-named domains clobber each other

## What happened

Hit repeatedly this session (2026-08-13/14) investigating both bin-buddy's
own recompile (i745/i749's plan) and, as a separate bonus regression check,
`hecks_playground_conception`'s own `plan` domain (i750). Both regenerate into
`vendor/hecksagain/rust/src/generated/plan/` -- bin-buddy has its own
`Plan` aggregate (chapter name `plan`), and `hecks_playground_conception` has its own
unrelated `plan` bluebook (Sprint/Story/Task/Board/...). Whichever one ran
`bin/project_rust` most recently overwrites the other's directory
wholesale. The next `cargo build` (against whichever domain Cargo.toml's
`default` feature currently points at) then fails with spurious `E0433:
could not find X in 'plan'` errors referencing types that belong to the
OTHER domain entirely -- looks exactly like a real generator defect until
you notice the directory's contents don't match the domain you meant to
build.

Worked around ad hoc during this session with `rm -rf
generated/{plan,bin_buddy,binbuddy}` before each isolated re-test -- test
hygiene, not a real fix, and easy to forget (this is genuinely the second
time in one session the same collision was hit and re-diagnosed from
scratch).

## Root cause

`rust/src/generated/` is a single flat directory tree keyed only by the
domain's own bare, lowercased chapter basename
(`domain_generator.rb`/`bin/project_rust`'s own path derivation) --
nothing distinguishes WHICH source root a same-named chapter came from.
`generated/` is gitignored (`vendor/hecksagain/rust/.gitignore:6`), so
this never shows up as a committed conflict -- it's purely a local,
silent, same-machine collision between whichever two domains a developer
happens to have generated most recently.

## Why this matters

Not a blocker for anything shipped (the committed WASM/native artifacts
this session produced are unaffected -- verified byte-identical to a
regen from current HEAD). But it's a real footgun for anyone using
`bin/project_rust`/`bin/project_wasm`/`bin/project_wasm_browser` across
more than one domain locally, and the failure signature (spurious E0433s
in a domain you didn't touch) actively misleads -- it looks like a
codegen bug, costs real diagnosis time, and will recur for the next
person who generates two same-named domains back to back without knowing
this card exists.

## Candidate fixes, not decided here

- Key `generated/<root-basename>-<chapter>/` or similar, so two
  same-named chapters from different roots land in different
  directories -- most direct, but changes every generated path
  `mod.rs`/`Cargo.toml`/`kernel::cli` reference by convention.
- `bin/project_rust` refuses to overwrite an existing `generated/<chapter>/`
  whose own `ir.json` fingerprint (source root path, or a hash of it)
  doesn't match the domain currently being generated -- loud failure
  instead of silent clobber, cheaper to add, doesn't rename anything.
- Simplest: `bin/project_rust` prints a warning when it's about to
  overwrite a `generated/<chapter>/` that already exists and whose
  `ir.json` source root differs from the one just requested. Not a fix,
  but turns a silent clobber into a loud one.

## Not investigated here

Whether this collision is possible in the two other consumers
(`bin/project_wasm`, `bin/project_wasm_browser` -- both call
`bin/project_rust` first, so they inherit the same issue) beyond what's
already described above.
