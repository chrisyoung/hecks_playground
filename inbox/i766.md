# i766 -- bin-buddy/hecksagain-WASM cutover done + verified locally ; PR #19 open, not merged, not deployed

## CLOSED 2026-08-14 -- merged, deployed, verified live against real production R2

Picked back up same day. Sequence:

1. **`gh pr merge 19 --merge`** -- clean fast-forward (`origin/main` was
   already an ancestor of the branch, confirmed via `git merge-base
   --is-ancestor` before merging, not assumed). Merge commit `7cbf5d2`.
2. **`bin/deploy-worker.sh`** (after a `DRY_RUN=1` pass to catch bundling
   issues first) -- real `wrangler deploy`, `https://bin-buddy-worker.
   belleboche.workers.dev`, `Worker Startup Time: 17ms`. `/health`,
   `/`, `/ir` all verified directly against the deployed URL.
3. **Bug found #1**: authenticated dispatch returned `{"error":
   "unauthorized"}` against production even with the locally-saved
   `.dev.vars` key -- `wrangler dev --local` reads `.dev.vars` directly,
   completely independent of whatever `wrangler secret put` had set in
   production at some earlier point; the two had drifted. Fixed by
   piping the local key into `wrangler secret put BIN_BUDDY_API_KEY`
   (value never printed to any tool output, piped straight through) so
   both agree, going forward.
4. **Bug found #2, the real one**: after rotating the Worker's secret,
   also rotated the Pages project's own `BIN_BUDDY_API_KEY` (README is
   explicit both sides must match) -- but Cloudflare Pages secrets only
   apply to the NEXT deployment, not the currently-live one, so this
   opened a real window where Pages' authenticated proxy path was
   broken in production. Triggered a redeploy to close it
   (`wrangler pages deploy homeowner_portal/public` from the repo root)
   -- which turned out to be the WRONG invocation: it uploaded only the
   10 static asset files and silently dropped the Functions bundle
   entirely, so `/api/*` 404'd across the board (caught immediately via
   a direct health check, not assumed fixed). Root cause: `functions/`
   lives at `homeowner_portal/functions`, a sibling of
   `homeowner_portal/public` -- passing `homeowner_portal/public` as an
   explicit path from repo root bypassed wrangler's directory-relative
   functions-dir detection. Fixed by re-running from inside
   `homeowner_portal/` (`cd homeowner_portal && wrangler pages deploy
   public ...`), which logged "Uploading Functions bundle" and actually
   included it.
5. **Verified for real, not assumed**: `bin/smoke-api-health.sh
   https://bin-buddy-2pf.pages.dev` green. An authenticated `POST
   /api/route` through the Pages proxy returned `{"ok":true,"stage":
   "appended-to-r2","key":"route-log/..."}`, then fetched straight back
   with `wrangler r2 object get bin-buddy-heki/<key> --remote --pipe`
   (the `--remote` flag matters -- without it the CLI silently reads a
   local simulated bucket and reports "key does not exist," which is
   its own small trap, not a real bug) -- content byte-identical to
   what was POSTed. This is the actual end-to-end proof: Pages proxy ->
   Worker -> WASM kernel -> R2, in production, on the new stack, with no
   Rust/Cargo build anywhere in the path anymore.
