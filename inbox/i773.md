# i773 -- storehouse establish: missing-file crash fixed, Procfile-regen goal still blocked (i771/i772 misdiagnosed the boot.bluebook as dead)

## What Chris asked

"fix storehouse establish" -- following up on i772's filed-not-chased finding #1.

## Root cause (corrects i771/i772)

i771 and i772 both concluded `runtime/boot/bluebook/boot.bluebook` was a
"superseded, unreferenced concept." That conclusion was wrong -- neither
session git-blamed the deletion. It traces to commit `99803ed99`
(`chore(hecksagain-cutover): delete top-level runtime/ (i768 slice 5.1)`),
part of a large sweep in the top-level `hecks` repo that deleted `spec/`,
`tools/`, `discipline/` (except antibody/), `adapters/`, `cli/`, `codegen/`,
`bluebook/`, and `runtime/` in full -- retiring the OLD Ruby runtime tree as
part of the hecksagain (Rust) cutover. `runtime/boot/bluebook/boot.bluebook`
happened to live under that directory name, so it was deleted by the sweep's
directory-level `rm`, not by anyone checking whether anything still pointed
at it. Three live things did:

- `mindstream.bluebook` line 196, the `boot:` Procfile member
- `mindstream.bluebook` line 206, the `establish:` Procfile member
- `bin/miette` line 9 (doc comment reference)

The Rust source (`storehouse/src/run_boot/complete.rs`) documents the whole
keystone design in detail -- `FINDING-keystone-dead-path` (2026-07-03),
`establish_keystone_test.rs` -- all pointing at this exact file as load-
bearing, not dead. i771/i772 never read that file.

## What I restored

NOT a verbatim restore of the deleted 277-line, 9-phase pipeline bluebook.
Advisor review caught two live hazards in the original before I wrote
anything:

1. The original chains nine phases via policies, ending in
   `policy "StartStudioOnComplete" { on "BootCompleted"; trigger "StartStudio" }`.
   Because `merge_boot_into_corpus` extends the corpus's policies with boot's,
   and `drain_policies` is synchronous on the `BootCompleted` emit, a verbatim
   restore would make every `storehouse establish` also try to dispatch
   `StartStudio` inside the establishment cascade.
2. The original hecksagon declares
   `adapter :daemon, name: :mindstream, command: "{hecks} run-loop ..."`.
   `establish` never walks daemons, but restoring the file re-arms the `boot:`
   Procfile member -- which would spawn a SECOND mindstream run-loop
   alongside the one i772 already found alive (pid 8748) on the next
   `overmind restart`.

Wrote a minimal `BootRun` aggregate instead: one `phase` field, one
`CompleteBoot` command emitting `BootCompleted`, gated behind
`from: "completing"` (kept deliberately -- without it `stage_pipeline_settled`
no-ops and the exact code path `FINDING-keystone-dead-path` was written for
goes unexercised again). Sibling hecksagon carries only the persistence bind
(`Boot::BootRun.persisted_by("Memory")`). No pipeline commands, no chaining
policies, no daemon adapters, no `entrypoint`.

Files:
- `/Users/christopheryoung/Projects/hecks/runtime/boot/bluebook/boot.bluebook`
- `/Users/christopheryoung/Projects/hecks/runtime/boot/bluebook/boot.hecksagon`

`storehouse validate` on the new domain: valid. Two DSL-shape catches from
the validator itself (not carried over from the original, which predates a
VO-default rule tightening): a value-object-typed attribute's `default:`
must fill the VO's fields (`default: { value: "..." }`), not a bare scalar.

## Bigger finding: establish is only HALF fixed, and my fix switches on a live cost

i772's finding #1 wasn't just "establish exits 1" -- it was "the Procfile
can't be regenerated through the documented pipeline." I checked that
directly : `storehouse project procfile hecks_conception` still bails --
`no Mindstream/MindstreamMember records established at ... -- nothing to
render`. So the actual downstream goal i772 cared about is STILL blocked,
even though `establish` itself now exits 0.

What I found digging in : `establish`'s `BootCompleted` dispatch fires
authorization.bluebook's `on "BootCompleted"` policies (confirmed --
RoleAssignment/Policy counts grew) but does NOT appear to fire
mindstream.bluebook's 14 `on "BootCompleted"` policies (`EstablishBootMindstream`,
`EstablishBootMember`, ... `EstablishConsolidateMember`) -- no new
MindstreamMember/Mindstream records land from my dispatch. Reading the raw
heki stores directly (`mindstream.heki`, `mindstream_member.heki`) shows
they're NOT empty -- they're full of HISTORICAL records from past sessions,
including many still carrying the dead `hecks/rust/target/release/storehouse`
path i771/i772 fixed in the bluebook source tonight. Those never got
re-established with the corrected path, and my `establish` run added none
either. Why authorization's policies fire but mindstream's don't, inside
the same `BootCompleted` cascade, is unexplained -- didn't chase it further,
it's a separate root cause from the missing-file bug I was asked to fix.

**And it compounds live, per run.** Before today `establish:` failed fast
and wrote nothing. Now it succeeds -- and every success costs +7
RoleAssignment duplicates (confirmed : 68 -> 75 from the ONE verification
run I did ; `project procfile` also internally dispatches CompleteBoot again,
so even a read-only diagnostic adds more). i772 already left an
`overmind restart` pending Chris's timing call, specifically because it
touches the live `establish:` Procfile member. That restart now means every
boot silently grows the live RBAC roster. This wasn't true before my fix --
the member failed closed. It's Chris's call whether the restart happens
