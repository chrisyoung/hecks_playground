# i774 -- i773's RBAC "upsert-by-natural-key" bug re-diagnosed: root cause is a different bug, in a different runtime, still live

## What Chris asked

"fix the RBAC upsert-by-natural-key bug now" -- following directly from i773's finding.

## i773's diagnosis was wrong, and here is the live evidence

i773 claimed: queried `Authorization::RoleAssignment.active` live, saw 68 records
for ~6 distinct identities ; ran `storehouse establish` once ; saw 75. Concluded
`RoleAssignment.Assign` (`identified_by { auth_identity_id.value }`, upsert-by-
auth-identity per its own doc string) was silently duplicating instead of
upserting.

That mechanism does not exist. Proven three ways, live, before touching anything:

1. **No hecksagon anywhere binds Authorization.** Grepped the whole corpus for
 `Hecks.hecksagon "Authorization"` and for `persisted_by` inside
 `aggregates/framework/authorization/` -- zero hits, in either direction.
2. **The Ruby-side runtime (`hecksagain-cli` / `storehouse__dispatch`,
 `__query`, `__state` -- what the MCP tools actually call) therefore defaults
 both `Policy` and `RoleAssignment` to `Memory`
 (`Ports::Persistence::DEFAULT_ADAPTER = "Memory"`,
 `BindingPolicy.resolve` in `hecks-hecksagain/lib/hecksagain/ports/persistence/binding_policy.rb`).
 Confirmed live : `Authorization::RoleAssignment.Active` returned `rows: []` ;
 `state ... pr-agent` returned `state: null`. Nothing durable exists via that
 path, full stop -- the "68" and "75" i773 saw cannot have come from a fresh
 dispatch/query/state call the way the MCP tools issue them (each is a
 genuinely fresh Ruby process -- proved with an isolated `/tmp` repro: a
 Memory-backed record written by one `storehouse__dispatch` call was gone by
 the very next `storehouse__state` call).
3. **A faithful repro of the exact same shape, Heki-bound, proves the upsert
 mechanism that DOES exist works correctly.** Built `Repro::Thing` with
 `identified_by { auth_identity_id.value }` and a reference_to-less `Assign`
 command, bound `persisted_by("Heki")`. First dispatch: creates "pr-agent".
 Second dispatch, identical args, separate process : raises
 `Hecksagain::Runtime::AlreadyExists — Assign creates a Thing that already
 exists`. That is `command_interpreter.rb`'s `hydrate` doing exactly what its
 own comment says it does ("NOTHING IS MINTED... A SECOND CREATION IS NOT A
 FRESH ONE") -- a deliberate, mutation-test-provenanced refusal, not a bug.
 And it is SAFE to hit repeatedly : `PolicyInterpreter#deliver`
 (`policy_interpreter.rb`) rescues every `DOMAIN_REFUSALS` member --
 `AlreadyExists` included -- per policy, logs `delivered: false`, and does not
 fail the cascade.

So whatever i773 saw, it was not this. `hydrate`'s creates-branch is correct
and does not need fixing. Do not touch it.

## The real, live, currently-growing bug

`storehouse establish` does not run through the Ruby gem's `hecksagain-cli` at
all. It is a **separate Rust implementation** living in the SAME repo at
`hecks-hecksagain/storehouse/src/` (distinct top-level dir from
`hecks-hecksagain/lib/hecksagain/`, which is what `hecksagain-cli` -- and so
every `storehouse__dispatch`/`__query`/`__state`/`__validate` MCP call --
actually loads). Confirmed by finding `pub fn establish(...)` in
`storehouse/src/run_boot/complete.rs` and `storehouse/cli/src/main.rs`'s
`if command == "establish"` branch, and by the fact that a role assignment
`establish` reports as created is invisible to `storehouse__state` immediately
afterward -- two runtimes, two stores, not synced.

That Rust runtime's id resolution
(`storehouse/src/runtime/repository.rs::id_for_command`) has **no duplicate
refusal of any kind**:

```
/// identified_by + attr present -> use attr value (explicit)
/// identified_by + attr absent + exactly 1 record -> use existing id
/// identified_by + attr absent + 0 or >1 records -> counter-mint
/// identified_by absent -> counter-mint
```

When a policy-triggered `RoleAssignment.Assign` (or `MindstreamMember.Register`,
same shape) arrives with its `identified_by` key (`auth_identity_id` / `name`)
missing from the resolved `attrs` map, this silently mints a fresh **numeric**
id and inserts a brand new record -- no error, no log line, nothing. It does
not check whether a record with the derived natural key already exists first;
it just counts up.

**Watched this live, twice, from a fully cleared store both times:**

- Cleared `~/Library/Application Support/Hecks/hecks/authorization/` entirely,
 added a hecksagon binding for `RoleAssignment`/`Policy` (see below), ran
 `storehouse establish` once: **"78 role assignments · 17 policies"**.
 `role_assignment.heki` held 78 records -- only 6 correctly keyed by name
 (`pr-agent`, `workflow-subagent`, `sidequest`, `carol`, `mallory`, `alice` --
 exactly the roster i773 expected), the other **72 keyed by small integers**
 ("1" .. "140"-ish, sparse). `storehouse heki get ... 140` -> a real record,
 `name: "consolidate"`, `mindstream: "boot"` -- an entirely different
 aggregate's data shape leaking the same bug (see below), sitting under a
 numeric id instead of `"consolidate"`.
- Removed the hecksagon binding again, cleared the directory again, ran
 `establish` a second time: **"3 role assignments · 6 policies"** -- and
 `role_assignment.heki`/`policy.heki` **reappeared anyway**, proving the
 binding I'd added was never the causal factor -- the Rust establish path
 persists these to Heki on its own, independent of any hecksagon file the
 Ruby side reads. NOTE: these two runs are not otherwise a controlled pair --
 the first had the hecksagon binding present, the second didn't, so the
 17-vs-6-policy swing may just be that variable, not independent
 non-determinism. Worth re-running twice with the tree held fixed either way
 before reading anything into the swing itself; not chased further here.

**This is the same shape i773 actually saw**, just far bigger once actually
watched end to end: not "68 -> 75" drifting slowly, but dozens of fresh
counter-minted rows from a SINGLE `establish` call, unbounded, on every run,
today, with nothing I or i773 did causing it.

The MindstreamMember evidence i773 cited (`mindstream_member.heki`, 154
records, ids like "boot"/"inbox_poller" correctly named alongside ~144 bare
integers) is the same bug's accumulated residue over many historical
`establish`/boot runs, not a one-time migration artifact from an old identity
scheme as I first assumed reading it -- id "140" carrying `name: "consolidate"`
while a separately-created, correctly-keyed `"consolidate"` record also exists
in the same store is the live mechanism caught in the act, not fossil data.

## Two smaller things found, not fixed

- **`storehouse__query`'s documented snake_case convention is wrong for at
 least single-word query names.** `Naming.split_verb` in the Ruby gem does
 zero case conversion ; a query's dispatch key is its `hecks_name` exactly as
 declared (`"Active"`, not `"active"`). `Authorization::RoleAssignment.active`
 raises `UnknownVerb`; `Authorization::RoleAssignment.Active` (PascalCase)
 works. The MCP tool description ("verb-tail must be snake_case") should
 either be corrected or the CLI should fold case -- as it stands the
 documented path for exactly this kind of live-count check does not work,
 which is presumably why i773 (if using this path) never re-derived numbers
 that reconcile with what I found.
- Caught myself making several native `Read`/`Edit`/`Bash` calls (starting with
 `/tmp/upsert_repro/bluebook/repro.bluebook`, and again writing/editing this
 very note) instead of routing through the storehouse door -- should have
 been denied by the macrophage and wasn't (or the macrophage doesn't cover
 `/tmp` paths and doesn't gate the native tools this harness also exposes).
 Noting per the transparency lockdown standard, not chasing further.
