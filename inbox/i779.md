# i779 — :sprint dispatch bug root-caused and fixed (i778 item #3 closed)

*Continuation of i776 -> i777 -> i778 (2026-08-17, next session).*

## What was wrong

`aggregates/plan/hecksagons/activate_sprint_on_project.hecksagon`:

```ruby
driven on "HecksPlayground::Plan::Project.SprintActivatedByProject" do |event|
  dispatch "HecksPlayground::Plan::Sprint.Activate", sprint: "{sprint_ref}"
end
```

`Hecksagain::Bluebook::DSL::DrivingAdapterBuilder::DrivenCapture#dispatch` is
declared `def dispatch(command, with: {})` -- the only keyword it accepts is
`with:`. Passing `sprint:` directly raises `ArgumentError: unknown keyword:
:sprint`.

**Why it only broke a full-root catalog/dispatch, never an isolated
`aggregates/plan` catalog or `storehouse__validate`:** `DrivingAdapterBuilder
#driven` calls `capture.instance_eval(&block)` immediately while the
hecksagon is being *parsed* (confirmed with a `TracePoint(:raise)` planted
temporarily in `hecksagain-cli`, reverted after -- see backtrace bottoming
out at `hecksagain_runtime.rb:554:in 'catalog'` via a staged temp copy of
the tree, `.../hecksagons/134_activate_sprint_on_project.hecksagon:9`).
So this is a **load-time** bug, not a deferred runtime one -- any process
that walks far enough into loading this hecksagon dies here. Isolating
`aggregates/plan` alone hit a *different*, earlier category-2 failure
first and never reached this file; `storehouse__validate` sweeps each of
the 64 roots independently with its own rescue, so a category-2 failure
elsewhere in Plan short-circuited before this line too. Only a *full-tree*
`catalog`/`dispatch` (the storehouse-mcp convention, `aggregates_dir` =
the whole `hecks_playground_conception` root) walked far enough to hit it.

## Fix

```ruby
dispatch "HecksPlayground::Plan::Sprint.Activate", with: { sprint: "{sprint_ref}" }
```

One line. `sprint` was already the semantically correct key
(`snake_case(Sprint)`, the self-ref convention) -- it just needed wrapping
in `with: { ... }` to match the current pinned gem's grammar.
