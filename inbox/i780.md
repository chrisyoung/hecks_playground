# i780 — design proposal: the `:exec` adapter family, re-expressed on the effect port

*Continuation of i776 → i777 → i778 → i779 (2026-08-17, same day, later in the
session). Category-2 scoping, the `:exec` branch specifically — see i778/i779
for the full 11-root map. This card is a DESIGN PROPOSAL, not a change —
nothing described here is built yet.*

## Where this came from

Chris picked "build the effect-family adapter fresh" for the 10 files on the
retired `adapter :exec, name:, command:, exec:, result_into:` form (git,
cargo, filesystem, tools/sidequest, inbox, process_health ×3, session,
plan ×4, macrophage/artifact_claim ×2, fibroblast — 7 roots). Two corrections
surfaced immediately after, both worth recording so the next session doesn't
re-derive them:

1. **`:exec` never branched.** `exec.hecksagon`'s own vision text: "routes
   the result into `:result_into` as a follow-on dispatch" — one
   unconditional target, no success/failure distinction. My first preview to
   Chris borrowed `charged_by`'s branching shape by reflex; that's the wrong
   spec. Building branching support the domain never asked for is exactly
   the "confession the domain wasn't reached for first" the bluebook-first
   standard names.

2. **The gap is narrower than "a new subsystem."** Re-reading
   `hecks-hecksagain/lib/hecksagain/bluebook/hexagon.rb`'s own `Bind` struct
   comment turned up two things that change the shape of the work:
   - `on`/`success`/`failure` DSL-capture is **already real** — landing on
     the correct `Bind` at build time, not the runtime consumer. What's
     missing is only the runtime piece that watches for the event and acts.
   - That runtime piece (`record_effect_outbound`) is documented as needing
     "an `OutboundEvent` framework bluebook this gem's own corpus does not
     declare; a consuming corpus's own is where that half belongs." **hecks_
     conception already has exactly that domain** —
     `aggregates/framework/hexagon/bluebook/outbound_event.bluebook`, a
     durable outbox (Record → Claim → MarkDelivered, `pending → claimed →
     delivered | failed`) — and I fixed its one live bug this session
     (`.event_sourced` → `persisted_by("AppendLog")`, see i779). It reads
     purpose-built for this, not a coincidence.

## The open question that mattered, and why it's not open anymore

`plan.hecksagon` binds four different scripts to the *same* command
(`Story.RunCheck`). Moving `:exec` onto Bind's event-triggered model means
four binds would all key off whatever `RunCheck` emits — does the runtime
pick one, refuse ambiguity, or fire all four?

`OutboundEvent.Record`'s own goal text answers this directly: *"the runtime
records ONE OutboundEvent per subscribing adapter."* Fan-out isn't an edge
case to design around — it's the documented default. Four adapters
subscribing to one event get four independent outbox rows, each claimed and
delivered on its own. This is the single finding that turned this from "an
open design question" back into "a spec that already exists, needs building."

## The proposed shape

Two pieces, both currently unbuilt anywhere (`grep -rn
"record_effect_outbound\|bin/adapter-host"` across the fork and
hecks_conception turns up only the one comment in `hexagon.rb` referencing
both by name):

**1. `record_effect_outbound` (new, in `hecks-hecksagain`)** — a dispatcher
hook: after a command emits an event, for every Bind whose `on:` names that
event, dispatch one `OutboundEvent::OutboundEvent.Record` — `delivery_id`
(fresh), `adapter` (the bind's adapter name), `event`, `source_type` /
`source_id` (the emitting aggregate + id), `payload` (the event's data),
`success_command`, `failure_command`. For `:exec`'s unconditional semantics,
`success_command` and `failure_command` are simply **the same** FQN (e.g.
`Cascade.RecordResult`) — no new IR field needed, `OutboundEvent` already
carries both.

**2. `bin/adapter-host` (new, standalone process)** — polls `OutboundEvent`
for `pending` rows, `Claim`s one, looks up the named adapter's `handler`
field (already a real `Adapter` struct field — see `stripe.adapter`'s
`handler "examples/adapter_host_demo/stripe-handler"` for the existing
precedent), execs it, dispatches `success_command`/`failure_command` with
the captured `{output, exit_code, ok}`, then `MarkDelivered`.

**Each old `:exec` binding becomes its own small named adapter**, mirroring
how `Stripe` is one adapter with one `handler` — not one generic `LocalExec`
adapter carrying per-binding config. e.g.:

```
# git.hecksagon, git_status binding, re-expressed:
Hecks::Framework::Tools::Git.reported_by("GitStatus", on: "StatusRequested") do
  success "Hecks::Framework::Cascade::Cascade::Cascade.RecordResult"
  failure "Hecks::Framework::Cascade::Cascade::Cascade.RecordResult"
end
```
```
# GitStatus.adapter (new, one per old :exec binding):
Hecks.adapter "GitStatus" do
  family "execution"    # verb TBD -- see open questions
  handler "bin/git_status"
end
```

This needs no new Bind/Port/Adapter fields — every piece it touches
(`on`/`success`/`failure`, `handler`, `OutboundEvent`'s full lifecycle)
already exists in the IR. The work is the two runtime pieces above, plus one
small adapter file per binding, plus re-expressing each `:exec` line as a
`driven`-adjacent bind on whatever event the source command now needs to
emit (several of the 10 files' commands don't currently emit anything to
trigger on — that audit is still per-file work, same as i778 originally
scoped).

## Open questions before any of this gets built

1. **Family/verb naming.** `charged_by` (payment) and `executed_by`
   (Ports::Execution, synchronous reply) are both taken and both wrong
   shape. Needs its own verb — `reported_by`? `spawned_by`? — and its own
   `.family` declaration (signal `:effect`, matching `charged_by`'s shape,
   but explicitly documented as never branching for this family).
2. ~~Does every source command already emit an event to trigger on?~~
   **ANSWERED (2026-08-17, full pass) — yes, all 14 bindings, zero gaps.**
   No command needs a new `emits` added. Full table:

   | file | command | emits |
   |---|---|---|
   | inbox.hecksagon | `Inbox.Check` | `InboxChecked` |
   | process_health.hecksagon | `ProcessMacrophage.Sweep` (2 bindings: reap + sweep) | `Swept` |
   | process_health.hecksagon | `ProcessMacrophage.Heal` | `HealRequested` |
   | fibroblast.hecksagon | `Fibroblast.Sweep` | `SweepRan` |
   | artifact_claim.hecksagon | `NoPromisesSweep.Scan` | `ScanRequested` |
   | artifact_claim.hecksagon | `NoPromisesSweep.Verify` | `VerifyRequested` |
   | session.hecksagon | `Session.RebuildContext` | `ContextRebuilt` |
   | plan.hecksagon | `Story.RunCheck` (4 bindings) | `StoryChecksRequested` |
   | tools.hecksagon | `Sidequest.Dispatch` | `SidequestDispatched` |
   | git.hecksagon | `Git.Status`/`Log`/`Diff`/`CurrentBranch`/`WorktreeList` (5) | `StatusChecked`/`LogRead`/`DiffRead`/`CurrentBranchRead`/`WorktreeListRead` |
   | cargo.hecksagon | `Cargo.Build`/`Test`/`Check`/`Clippy` (4) | `BuildCompleted`/`TestsRun`/`CheckCompleted`/`ClippyCompleted` |
   | filesystem.hecksagon | `Filesystem.File.Move`/`Remove`/`ReadRange`, `Directory.Create`/`Remove`/`List` (6) | `FileMoved`/`FileRemoved`/`FileRangeRead`/`DirectoryCreated`/`DirectoryRemoved`/`DirectoryListed` |

   The two multi-binding files resolve cleanly through the SAME fan-out
   OutboundEvent already documents: `process_health.hecksagon`'s two execs
   (reap + sweep) both subscribe to `Swept`; `plan.hecksagon`'s four checks
   all subscribe to `StoryChecksRequested`. `RunCheck` genuinely emits ONE
   event (confirmed reading `plan.bluebook`) — no splitting into four
   distinct emits needed, "one OutboundEvent per subscribing adapter"
   handles it as designed.

   One more thing this closes: `fibroblast.bluebook` has its own comment
   explaining `Sweep` emits `SweepRan`, not `Swept`, specifically *"because
   the latter collides with ProcessSentinel.Swept ... whose
   MarkHangedOnMissingHeartbeat policy would mis-fire."* That's the exact
   collision `primitive.bluebook`'s gap #1b named as blocking 3 of these
   bindings under the OLD Rust runtime. It doesn't block the NEW design:
   that collision is a **bluebook-policy** concern (global bare-name
   matching, process-wide) — a **Bind**'s `on:` is scoped to one aggregate
   (`ProcessMacrophage.reported_by(..., on: "Swept")` only ever matches
   `ProcessMacrophage`'s own emit, never `ProcessSentinel`'s, even if both
   happen to be named `Swept`). The reason gap #1b existed doesn't carry
   over to this mechanism — worth Chris confirming this reading, but it
   looks like a real, not just convenient, resolution.
3. **`bin/adapter-host` runtime shape** — one long-running poller for all
   adapters, or one per adapter (mirrors the Procfile-as-projection-of-
   Drivers pattern from `driving.bluebook`, worth checking for a Host-side
   analog before inventing a second shape)?
4. **Does this replace `Ports::Execution`/`executed_by` for any of the 10
   files**, or do the genuinely-synchronous ones (git status, cargo build —
   arguably want an immediate reply, not a durable async round-trip) stay
   on `executed_by` instead? Not every `:exec` site obviously wants the
   async outbox treatment.

## Not done in this pass, still true

`interval` (and, on closer read of `DrivingHandler`'s own comment, `cron`
too — "no DSL yet builds one... driving on cron/interval grammar and its
runtime scheduler are their own, still-pending unit") and the `storehouse`
`:fs`/`:shell` forms (i778's own "until i493 lands" call) are unrelated gaps,
separately scoped, untouched by this proposal.
