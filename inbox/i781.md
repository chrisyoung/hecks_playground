## A real infrastructure discovery, not specific to this task

`.port`/`.adapter` file visibility for a *scoped* (single-domain) boot is
**non-recursive and directory-local** — `Adapters::Folder#load_domain` globs
`*.port`/`*.adapter` only in the exact directory it's given, no relative-hop
resolution to a sibling `adapters/` folder. `framework/adapters/appendlog.
adapter` only reaches `event_sourcing`/`hexagon` because of how the FULL
`hecks_playground_conception` boot flattens everything into one directory
(`stage_flat_corpus`, triggered only when a root has the exact
`aggregates`+`storehouse`+`adapters` sibling signature) — a scoped subroot
boot (what `storehouse__validate`'s 64-root sweep actually runs) never gets
that flatten. Confirmed empirically: `spawn.port` at `framework/adapters/`
was invisible to `fibroblast`'s own scoped validate until co-located
directly in its `bluebook/` dir. Fix applied: local copies in every domain
that needs `spawn.port`, not one shared file. Worth knowing for any future
consumer-corpus-level `.port` declaration, not just this one.

## UPDATE 2 (same day, later still) — bin/adapter-host built, fixed, and PROVEN end to end

**It already existed.** `~/Projects/hecks_playground/bin/adapter-host` — I missed it
earlier because my `find` for "adapter-host*" only searched the fork and
`hecks_playground_conception`, never `hecks_playground/bin/`. Good design already there (the
generic claim/handle/dispatch/ack loop, `--once`/loop modes, declarative
handler resolution via `adapter-handler`). It was written against the OLD
Rust `storehouse` CLI's shape and needed real fixes, not a rewrite:

- `STOREHOUSE` defaulted to bare `storehouse` (doesn't exist) — now
  defaults to `hecksagain_runtime/bin/hecksagain-cli`.
- Every `dispatch` call was missing the literal `dispatch` subcommand word
  (`"$SH" "$ROOT" Verb ...` → `"$SH" dispatch "$ROOT" Verb ...`).
- `query`'s rows live under `.rows`, not `.state` (`.state` is `dispatch`'s
  field). Fixed `poll()`.
- The query name was `.pending` (lowercase) — the bluebook declares
  `Pending` (exact PascalCase, confirmed live — hecksagain query names are
  NOT snake_cased, contra the CLAUDE.md note I was carrying).
- **Every VO-typed field comes back `{"value": ...}` wrapped**, confirmed
  empirically — the script's `jq -r .delivery_id` etc. were reading the
  wrapper object, not the string. Fixed to `.delivery_id.value` etc.
- `$HANDLER` is a full SHELL COMMAND STRING (i780's exec-string convention
  — "bash bin/fibroblast_sweep.sh", "node bin/inbox_poll.mjs" — not a bare
  executable path like the Stripe example). Was being `exec`'d directly
  with an `-x` executable check ; now runs via `/bin/sh -c "$HANDLER"`,
  matching hecksagain's own Shell execution adapter convention exactly
  (CWD inherited from the launching process, not the registry root).
- Verdict dispatch now ALWAYS carries `id`/`tool`/`output`/`exit_code`/`ok`
  (what `Cascade.RecordResult` needs), computed by the host from the
  captured run (stdout+stderr+exit code, captured to temp files so both
  are available alongside the real exit code under `set -e`) — not left to
  the handler's own stdout, which was the previous design's only source
  and doesn't fit `:exec`'s unconditional shape. A handler's own
  `key=value` stdout lines still layer on top, for a future adapter (a
  real Stripe-style one) that wants extra structured verdict fields.

**Two more real, previously-undiscoverable bugs found chasing the live
proof, both fixed:**

1. **`OutboundEvent.Claim` / `MarkDelivered` / `MarkFailed` were
   mis-classified as CREATORS.** `Hecksagain::Bluebook::Behaviour::Command
   #creates? = @references.nil?` — these three commands declared
   `attribute :delivery_id, DeliveryId` directly instead of `reference_to
   (OutboundEvent)`, so the runtime tried to CREATE a second record with
   the same id on every Claim/MarkDelivered/MarkFailed call and refused
   with `AlreadyExists`. This blocked the WHOLE effect-port mechanism, not
   just `:exec` — `charged_by`/Stripe would have hit the identical wall the
   moment anyone tried it live. Fixed : all three now `reference_to
   (OutboundEvent)`, same pattern `Sprint.Activate` already uses for its
   own self-ref transition. Dispatch key is `id=`, not `delivery_id=` —
   updated `bin/adapter-host` to match.
2. **The Cascade FQN baked into every `:exec` binding was stale.**
   `"HecksPlayground::Framework::Cascade::Cascade::Cascade.RecordResult"` — copied
   verbatim from the old (never-actually-fired, since :exec never parsed
   under hecksagain) `result_into:` fields into all 27 of i780's
   `spawned_by` conversions. The real FQN, confirmed by the gem's own
   hardcoded `Dispatcher::CASCADE_VERB` constant AND a live dispatch test,
   is `"Cascade::Cascade.RecordResult"` — domain names aren't affected by
   file-path depth, only by the bare string in `HecksPlayground.bluebook "X"`. Fixed
   across all 10 files (27 occurrences) with a scoped, verified exact-
   string replace.
