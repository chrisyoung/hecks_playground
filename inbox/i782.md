### Thread 1 — `for_each:` in `driven` blocks (8 sites)

**Confirmed completely unwired, not a config gap.** Read
`DrivingAdapterBuilder::DrivenCapture#dispatch` and `Dispatcher
#record_driven_dispatches` in the real bundler-pinned gem
(`hecks-hecksagain-74ea7dacd85a`) directly: `dispatch` stores `for_each:`
as an ordinary kwarg with no special handling ; `record_driven_dispatches`
fires the dispatch command **exactly once** per matching event, no row
iteration, no query resolution — the `for_each:` hash is passed straight
through as a dead literal argument. All 8 sites (`reset_story_tasks`,
`resolve_deps` x2, `seed_sprint_active` x2, `worker_died_reclaim` x1
binding/2 dispatches, `liveness_sweep`, `expiry_sweep`,
`claim_next_on_claim_released`, `claim_next_on_worker_registered`) are
real production reactions — task reopening on story reset, dependency
resolution, sprint-active propagation, worker-death lease/claim reclaim,
liveness + expiry sweeps, claim-next-on-release/registration — and every
one is silently non-functional or erroring today.

**The design call i781 posed is already answered, on record, by the
codebase itself**: `sweeper.bluebook`'s own comment states *"for_each
fan-out is driven-adapter-only"* — i.e. for_each was always meant to live
on `driven` blocks, never Policies, for this corpus's convention. And the
REAL, wired implementation already exists one layer over:
`PolicyInterpreter#deliver_for_each` (resolves `spec[:from]` as a query,
interpolates `where:` tokens against the event payload, iterates every
row, re-enters `policy.trigger_command` once per row) and
`SagaInterpreter#deliver_saga_dispatch` (same shape for
`ProcessManagerBuilder`). **The fix is to give `DrivenCapture#dispatch` /
`record_driven_dispatches` the identical treatment** — not a design
question for Chris, a scoped implementation task.

**The cost, which IS Chris's call**: this means patching the
Bundler-pinned `hecks-hecksagain` gem — a fork PR + Gemfile re-pin, i780's
exact loop (fork branch -> spec coverage -> Chris reviews -> merge to
main -> real pin). Not a same-session mechanical fix.

### Thread 2 — bare `run "shell cmd"` in `driven` blocks (5 sites)

**Also confirmed completely unwired**: `DrivenCapture#run(_cmd,
result_into: nil) = nil` is a hard no-op in the real gem, with its own
comment stating `record_driven_dispatches` "has no execution path for a
`run` leaf yet." **None of these 5 shell commands have ever actually
executed through this runtime.** Verbatim sites (full survey in the
Explore agent transcript, not reproduced here):
- `pr_delivery.hecksagon` (3rd binding) — `gh pr merge sq/{story_ref}
  --squash --delete-branch`, no `result_into`, unconditionally dispatches
  `CompleteMerge` right after regardless of outcome (a documented gap in
  the file's own comment).
- `pr_mergeable_check.hecksagon` — `gh pr view ... --jq ...`, WITH
  `result_into: "...RecordPrMergeableCheckResult"` (read-only).
- `main_uptodate_check.hecksagon` — `git diff --quiet main origin/main`,
  WITH `result_into: "...RecordMainUpToDateCheckResult"` (read-only).
- `worktree_create.hecksagon` — `git worktree add --detach
  {worktree_path}`, no `result_into`, no downstream dispatch (mutating).
- `worktree_remove.hecksagon` — `git worktree remove --force {id}`, no
  `result_into` (mutating).

**None of the five need a synchronous capability `spawned_by`+`success`/
`failure` structurally lacks** — `plan.hecksagon` already converted 4
sibling reactions on the SAME `StoryChecksRequested` event to `spawned_by`
today (i780), and `result_into:`'s "run, examine exit code, decide next
dispatch" shape is exactly what `spawned_by`'s success/failure ports
already model. These 5 read as **unconverted leftovers** of the pre-i780
`:exec`/`run` era, not a deliberate sync-vs-async split.

**But converting them has real teeth, and this is the part i781 never
flagged**: because `run` is currently dead, `gh pr merge --squash
--delete-branch`, `git worktree add`, and `git worktree remove --force`
have never fired. **Converting to `spawned_by` wakes up dormant automation
that mutates the real repo and merges real PRs** — this is not a
refactor, it's turning on a feature. Split the thread:
- `pr_mergeable_check` + `main_uptodate_check` — read-only probes, safe
  to convert and verify once the verdict-signature check below passes.
- `pr_delivery` (3rd binding) + `worktree_create` + `worktree_remove` —
  mutating. **Convert only with Chris's explicit sign-off**, and he needs
  to be told plainly what landing them means (PRs start auto-merging on
  approval, worktrees start getting created/destroyed automatically).

**Verdict-signature check — DONE, and it's negative: conversion is not
mechanical.** `RecordPrMergeableCheckResult` / `RecordMainUpToDateCheckResult`
declare only `reference_to(Story)` (i.e. `id`) + `attribute :ok, CheckOk`.
adapter-host unconditionally sends 5 keys (`id`/`tool`/`output`/
`exit_code`/`ok`). `CommandInterpreter#step_refuse_unknown_arguments` (real
gem, `command_interpreter.rb`) refuses any dispatch carrying an attribute
the command doesn't declare — so pointing `success`/`failure` directly at
either command **will be refused** on `tool`/`output`/`exit_code`. Two real
options, a decision not a mechanical fix: (a) widen both commands to accept
(and likely `logged: false`) the extra 3 keys, or (b) target
`Cascade::Cascade.RecordResult` like all 6 sibling checks already do.

**Followed (b) one layer further and found a bigger, adjacent gap — stated
carefully, because two earlier claims this session came from an incomplete
search and this one almost did too.** All 6 spawned_by-converted checks on
`Story` (`CheckWorktree`/`CheckMerged`/`CheckTests`/`CheckVerbResolves`,
plus the 2 unconverted `run` ones if converted the same way) target
`Cascade::Cascade.RecordResult` as success/failure. Cascade emits
`ResultRecorded` "so downstream policies can react" (its own goal text).
**Searched thoroughly for a consumer — `.bluebook` policies, `.hecksagon`
driven blocks, saga/process-manager declarations, corpus-wide — found
none.** Also checked `dispatcher.rb#record_outcome` directly (the one
non-declarative path advisor flagged as unchecked): it's a *different*
mechanism, firing only off the synchronous `executed_by` port
(ShellTool/FileTool/SearchTool's `perform_execution` path), never the
async `spawned_by` port these 6 checks use — so it doesn't bridge this
gap either. **Net: as far as this search reached, nothing currently
re-dispatches a Cascade-recorded check outcome back into Story's own
`Record*CheckResult` commands, which means the sprint-14 done-is-done
gate's 6 individual checks may never actually arm their flags on Story
even once converted to `spawned_by`.** Framing this as a well-searched
open question, not a certainty — a saga or interpolation path neither the
Explore agent nor I read line-by-line could still exist. Whoever picks
this up should re-verify with a live probe (dispatch a check, run
adapter-host, then query Story's own `pr_mergeable`/`worktree_clean`/etc.
fields) before trusting either this note or its absence.

## A fourth, NEW finding — not one of i781's three threads, found while

**`adapter :memory` (the bare, blockless form) is dead in the current
gem — not a persistence shortcut.** `HecksagonBuilder#adapter(name,
&block)` (the real method, confirmed by reading
`hecks-hecksagain-74ea7dacd85a/lib/hecksagain/bluebook/dsl/
hecksagon_builder.rb`) takes `name` positionally and builds a
DRIVEN-adapter registration via `DrivingAdapterBuilder.build(name,
&block)`. Called bare with no block (`adapter :memory`), it registers an
empty, no-op driven-adapter entry named `:memory` — it does NOT wire
persistence for anything. The comment in `tools.hecksagon` describing this
as a working domain-wide default ("When i728 made :memory actually select
Backend::Memory, the declaration finally took effect") describes an OLDER
DSL/runtime version ; the method has since been repurposed exclusively for
`adapter "Name" do driven on ... end end` blocks, and the comment is
stale.

**Verified this isn't corpus-wide** (falsification check, not assumed):
only 2 files in the entire `hecks_conception` tree use the bare form —
`tools.hecksagon` and `git.hecksagon`, both in `framework/tools/bluebook/`,
the one domain that has never successfully booted this whole session.
Checked a passing domain (`demo.hecksagon`) uses explicit `persisted_by`,
confirming the bare form isn't how anything else in the corpus wires
persistence.

**Blast radius, checked directly**: of 21 aggregates declared in

## Two false alarms this session, both caught by advisor before being

   `$LOAD_PATH.unshift`'d `vendor/hecksagain/lib` directly (instead of
