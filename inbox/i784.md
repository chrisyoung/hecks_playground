**Isolated reproduction (safe, no live processes touched).** Built a

   `maybe_capture_snapshot` in `es_replay.rs` before it does any work) :

5. `sample`'d the reproduction 2s into a fresh run : **physical

   re-materializing a large structure EVERY tick rather than genuinely

**Where the bug most likely lives** (not yet confirmed to the exact

**RESOLVED — do NOT remove `HECKS_PLAYGROUND_EVENT_SOURCING=1`.** Checked : only 2
aggregates (`Tools`, `OutboundEvent`) declare `event_sourced`
individually, and nothing today queries the Log for any other
aggregate. Looked safe on those two facts alone — but
`docs/designs/event-sourcing-lineage.md` (Chris, 2026-06-16, DESIGN
ONLY / locked) makes the blanket override a deliberate strategic
choice, not dead config : *"make the event the unit of an
attributable, persisted, causally-linked audit log"* ; *"Storehouse →
the EMBRYONAUT ADVANTAGE... the thing that RUNS an enterprise on one
governed event-sourced bus is the product."* Every aggregate is meant

That SAME doc already names the exact failure mode as a hard

persistence as a tail, not a barrier."* So this isn't "an unwanted
feature causing a side effect" — it's that constraint being violated
by a bug. **The fix belongs in the Rust caching**, not `.overmind.env`.

## FOUND AND FIXED (2026-08-18 night)

Traced with a symbolicated debug-build `sample` profile against an
isolated reproduction (real ~5MB `event.heki` copied into a throwaway
scratch corpus, zero contention with live processes) : `heki::read` was
the hot leaf, inside `repo_hydrate`/`Repository::new_with_context` —
the GENERIC Heki backend, not the AppendLog shard writer the design
calls for.

Root cause : `framework_mut()`
(`hecks-hecksagain/storehouse/src/runtime/framework_substrate.rs`)
boots the framework collaborator (the second, crate-internal `Runtime`
that actually owns `EventSourcing::Event`, `Governance::Violation`,
`OutboundEvent`) via `Runtime::boot_with_data_dir` directly. That
constructor is the SAME one every domain boot uses, but
`apply_hexagon_persistence` — the ONLY code that reads a
`persisted_by("AppendLog")` hexagon binding and rebuilds the matching
repository on the AppendLog backend — only ever runs from
`boot_with_hecksagons`, never from `boot_with_data_dir`. The
collaborator never sees it, so `EventSourcing::Event` silently stayed
on the default Heki repo `boot_with_data_dir` builds for every
aggregate, and every single event-sourced dispatch paid a full
compressed-whole-file read-modify-write against the growing global
`event.heki` — proportional to its size (confirmed empty-log = 0-2ms,
real 5MB log = 6-8.5s, deleting just `event.heki` and nothing else
flips it back to fast).

Fix (committed, `hecks-hecksagain` branch
`fix/i784-framework-collaborator-appendlog-wiring`, `339ceb5`) :
`framework_mut()` now explicitly rebuilds the collaborator's
`EventSourcing::Event` repo on `LazyRepository::new_appendlog` right
after boot. Crate-owned kernel substrate, not corpus-configurable, so
this hardcode is consistent with how `OUTBOX_SUBSTRATE` /
`EVENT_SOURCING_SUBSTRATE` / `GOVERNANCE_SUBSTRATE` are already
crate-embedded rather than corpus-resolved.

Two follow-on fixes the change surfaced (both included in the same
commit) :
- `event_sourced_faithful_delta_test.rs` and `causation_e2e_tests.rs`
  were passing ONLY because the bug made the collaborator's Event repo
  and the test's OWN top-level Event repo silently share the same
  live-rewritten Heki file — a same-process read saw a same-process
  write purely by accident. Post-fix, the collaborator's write goes to
  a private per-process AppendLog shard (by design — shard-then-merge,
  folded by the separate `storehouse drive --adapter LogConsolidation`
  daemon), so a same-process read needs to combine the merged view
  with `unconsolidated_log_tail()` — the exact pattern
  `fold_event_log`'s own doc comment and `verify-projection` already
  establish. Updated both tests to do that combination.
- `unconsolidated_log_tail()` itself had a real, separate bug : it
  built every tail record with `AggregateState::new("")` instead of
  the record's actual `event_id`, so every tail record collapsed onto
  one blank-id state. Fixed to use `rec.event_id`.

**Verified** : isolated reproduction went from 6-8.5s/tick to 0-1ms/tick
on the identical scratch corpus + identical 5MB `event.heki`, using a
binary built from the fixed source (checksummed to confirm the
PRE-fix deployed `~/.local/bin/storehouse` was NOT stale — it was
built from this exact source tree, the bug was real and live). Full
workspace suite : 438/438 lib tests pass ; the only remaining failure
(`board_activation_guard_test`) is confirmed pre-existing and unrelated
(fails identically on the branch's base commit, before any of these
changes).
