# i784 — miette pre-push gate: 22 failures root-caused into 6 clusters, 1 fixed+shipped, 5 tracked here

*Surfaced while pushing two small miette commits (a body_pulse Procfile
fix + a pre-push hook binary-path fix, both already committed/pushed on
miette main). The pre-push gate blocked on 22/169 `.behaviors` files
unrelated to either commit. Chris asked to investigate before deciding
whether to push past it. This card is the parking lot for what didn't
get fixed today.*

## Fixed + shipped

**Cluster 1 — VO `one_of` validation stringifies the whole hash instead of
its discriminant.** `storehouse/src/runtime/payload_gate.rs:110-142` in
`hecks-hecksagain` compared the vocabulary against `raw.to_string()` for
the whole incoming payload; for a VO-typed attribute that's a `Value::Map`,
and `Value`'s `Display` renders any map as `"{N fields}"` — never equal to
a vocabulary string. Every VO-typed `one_of` attribute refused
unconditionally the moment a real dispatch sent the full hash shape.
Fixed by resolving the VO's discriminant (first declared attribute) and
reading that field out of the map first. Shipped as
[hecks-hecksagain#2](https://github.com/chrisyoung/hecks-hecksagain/pull/2)
(branch `fix/payload-gate-vo-one-of-hash-unwrap`, not yet merged).

Fixed 3 of 5 affected files outright: `mindstream.behaviors`,
`macrophage.behaviors`, `hecksagon_ir.behaviors`. The other 2
(`storehouse_log.behaviors`, `capabilities.behaviors`) each have exactly
one remaining failure that cluster 1 was masking — see below, these are
new findings from today, not previously catalogued.

**Build gotcha hit along the way**: `cargo build --release` from
`hecks-hecksagain/storehouse/` silently rebuilds only the lib, not the
`storehouse` CLI binary — that binary is the `storehouse-cli` package
under the `storehouse/cli` workspace member. Needs
`cargo build --release --workspace`. (Matches the existing
`project_workspace_build_gotcha` memory, but that was about the retired
`hecks/rust` tree — this is the same footgun in the new `hecks-hecksagain`
repo.) Also: installing the new binary to `~/.local/bin/storehouse` via
`cp -f` while ~7 miette daemons had the old binary memory-mapped and
running produced `SIGKILL(137)` on every subsequent exec of that exact
path (byte-identical content, confirmed via checksum, ran fine from any
other path) — macOS invalidates code-signing validation for a vnode
overwritten in place while mapped executable. Fixed by writing to a temp
path and `mv`-ing atomically over the destination instead (new inode,
old mappings undisturbed).

## Not fixed — tracked here

**Cluster 2 — cross-domain policy cascades never fire. FIXED + SHIPPED
(corrected root cause).** First diagnosis (above, in an earlier version of
this card) blamed `hecksagain/lib/hecksagain/runtime/policy_interpreter.rb`
(the Ruby gem) — wrong runtime. `~/.local/bin/storehouse` (what the
Procfile daemons and the pre-push hook actually invoke) is a compiled
Rust binary from `hecks-hecksagain/storehouse`, not this Ruby gem.

The REAL root cause: `behaviors_aggregates_root()` in
`hecks-hecksagain/storehouse/cli/src/main.rs` resolves a `.behaviors`
file's combined-domain root by walking UP looking for a sibling
`hecks/hecks_conception/aggregates` — an i117-era heuristic from before
miette became her own repo (2026-08-14 cutover, slice 3.1), never
updated. Two consequences: (a) a STALE pre-migration duplicate of
`world/conception/bluebook/domain_cell.bluebook`, still sitting
un-deleted in `hecks_conception` (old `sets`/`goal` DSL dialect),
organ-won over miette's own live copy — the fixed cross-domain policy
never got a chance to fire; (b) the isolation gate that decides whether
to merge in `HECKS_ADDITIONAL_CORPUS_ROOTS` + the framework's own
buckets checked only "is this path textually inside the hecks repo",
which stopped being the only shape of "a being dispatching against her
own conception" once her corpus moved out.

Fixed in [hecks-hecksagain#3](https://github.com/chrisyoung/hecks-hecksagain/pull/3)
(branch `fix/behaviors-root-recognizes-decoupled-being-repos`, not yet
merged): `behaviors_aggregates_root` now recognizes any ancestor
directory containing a `*.world` file (the being-repo marker
`deploy/.env.storehouse.template` already documents) and returns it
directly; the isolation gate now also treats a root that IS one of
`additional_corpus_roots()` as "her own conception".

Verified against the live corpus: fixed 6 of 7 "cascades through policy
chain" failures outright — `gut.behaviors`, `fine_tune.behaviors`,
`training_corpus.behaviors`, `composition.behaviors`, `acl.behaviors`,
`sentence.behaviors`. `conception.behaviors` still has ~9 unrelated
attribute-not-set failures and one wrong-events-fired cascade
(`DevelopDomain`) — unchanged, still needs separate follow-up.

3 previously-passing tests newly fail as a SIDE EFFECT of correctly
finding content that was never reachable before — not regressions in
the fix's own logic, each independently root-caused, none chased
further today:
  - `self/memory/bluebook/memory.behaviors`'s `StoreMemory` test was
    accidentally passing against an unrelated, same-named `Store`
    aggregate that only ever existed in
    `hecks_conception/aggregates/library/stores` — a genuinely foreign
    concept (miette's own `Store`, in `body/sleep/consolidation/`, only
    has `PromoteSignal`), now correctly unreachable. The test needs
    retargeting, not the runtime.
  - `self/system_prompt/system_prompt_assembly/bluebook/system_prompt_assembly.behaviors`
    newly discovers its own sibling `.hecksagon` file (never reachable
    from the old root), which wires `ResolveOutputPath` to a real `:fs`
    adapter — that adapter binding doesn't behave cleanly inside the
    pure in-memory `.behaviors` test harness. Worth its own thread : does
    the behaviors runner need an adapter-mocking story for hexagon-bound
    commands?
  - `body/organs/bluebook/proprioception.behaviors` surfaces the SAME
    pre-existing event-name-collision bug already visible on
    `conception.behaviors`'s `DevelopDomain` cascade (extra unexpected
    events — `DomainDeveloped`, `VersionSnapshotted`, `IndexRebuilt`, …
    — leaking into an unrelated cascade's emit list), now reachable
    because `DomainCell` is no longer shadowed. Same bug, two sightings.

Net so far: 22 → 15 of 169 failing (cluster 1 fixed 3, cluster 2 fixed 6,
3 newly surfaced).

**Minor, unrelated to the actual gate**: the Ruby `hecksagain` gem's
`policy_interpreter.rb` has the identical same-shaped bug (domain-scoped
`policies_for`) independently — confirmed by reproducing the scenario
directly against `Runtime::PolicyInterpreter`. Fixed on its own merits
(whatever consumes that gem as the parity reference) in
`hecksagain` branch `fix/policy-interpreter-cross-domain-reaction-scan` —
doesn't touch anything on the actual miette gate's path.

**Cluster 3 — aggregates identified by a plain `attribute` (no
`reference_to`) aren't loaded on redispatch.** Every redispatch acts like
fresh creation instead of loading existing state. Breaks mutex-refusal
(`claim.behaviors` — Acquire doesn't refuse a second holder), idempotent-declare
(`storehouse.behaviors` — Declare produces 2 records instead of 1), and
fold/accumulate (`event_sourcing.behaviors` — 3 chained Apply calls land
at `events_applied: 1` not `3`). Root cause not yet pinned to file:line —
whichever code path resolves an aggregate instance by identity needs to
handle plain-attribute `identified_by` the same way it handles
`reference_to`. Note: there's an untracked
`hecks-hecksagain/spec/runtime/driven_dispatch_identity_spec.rb` already
sitting in that repo's working tree (not mine, left alone) — may be
someone already mid-investigation on this exact cluster; worth checking
before starting fresh.

Also likely the same family: `framework/capabilities/bluebook/capabilities.behaviors`
now fails on `AddProvider`/`Activate`/`Deactivate` with `missing attribute:
capability` (a `reference_to(Capability)`-shaped field) — newly visible
today once cluster 1 stopped masking it. Worth checking against cluster 3
before assuming it's a 4th thing.

**Cluster 4 — bulk `list_of` commands only process the first row.**
`antibody.behaviors` — `RegisterExemptions` given a 2-row `specs` list
emits only 1 `ExemptionRegistered` instead of 2. Independent bug in
Many-form fan-out iteration, not yet traced to source.

**Cluster 5 — VO defaults `{ value: X }` don't unwrap to scalar `X`.**
Sibling of cluster 1 but a different code path (default resolution /
`where`-clause comparison, not `one_of` validation). `plan.behaviors`
(`unresolved_dep_count` reads back as literal `"{"`, gating 18 other tests
behind the one broken `Start` precondition), `process_health.behaviors`
(`runaway_after_seconds` same shape), `correspondence.behaviors`
(`where awaiting_reply: true` still matches after it's cleared to
`false`), `none_in_state_gate.behaviors` (cross-aggregate `none_in_state`
predicate still includes an excluded slot). 4 files.

**New today, not yet clustered**: `framework/session/bluebook/storehouse_log.behaviors`
still fails 2 of 5 after the cluster-1 fix — `must be one of: dispatch,
event, cascade, adapter, policy, attr, error, fallback — events = [0 items]`
/ `[2 items]`. Looks like the `one_of` gate's `Value::List` case has the
same unwrap gap the `Value::Map` case just got fixed for (a `list_of`
attribute's vocabulary check comparing against the whole list instead of
validating per-element). Same family as cluster 1, same file
(`payload_gate.rs`), not included in today's fix — scoped that one
narrowly to the Map case that was actually diagnosed.

**Stale test, no runtime bug**: `world/infrastructure/bluebook/change_tracker.behaviors`
references a `RunBatch` command (`setup "RunBatch", ...`) that has never
existed anywhere in the corpus or git history — the file was created
whole-cloth in the migration commit `c54fba4`, aspirational and never
backed by an implementation. Either implement `RunBatch` or delete/skip
this test; not a regression to chase.
