### 1. `for_each:` in `driven` blocks (8 sites)

Confirmed completely unwired in the vendored `hecksagain` gem: `dispatch`
stores `for_each:` as an ordinary kwarg with no special handling ;
`record_driven_dispatches` fires the dispatch exactly once per matching
event, no row iteration. Sites: `reset_story_tasks`, `resolve_deps` x2,
`seed_sprint_active` x2, `worker_died_reclaim` (1 binding/2 dispatches),
`liveness_sweep`, `expiry_sweep`, `claim_next_on_claim_released`,
`claim_next_on_worker_registered` -- all real production reactions,
silently non-functional today.

**The design call is already answered, on record**: `sweeper.bluebook`'s
own comment says for_each fan-out is driven-adapter-only. The wired
reference implementation already exists one layer over: `PolicyInterpreter
#deliver_for_each` (resolves `spec[:from]` as a query, interpolates
`where:` against the event payload, iterates every row, re-enters
`policy.trigger_command` once per row). The fix is to give
`DrivingAdapterBuilder::DrivenCapture#dispatch` /
`Dispatcher#record_driven_dispatches` the identical treatment.

**What makes this Chris's call, not just implementation**: it means
patching the Bundler-pinned `hecks-hecksagain` fork -- a fork PR + Gemfile
re-pin, same playbook i780/i781 already proved out for the `spawned_by`
work. Confirm he wants that cost paid before opening the PR.

### 2. `run "shell cmd"` inside `driven` blocks (5 sites)

Confirmed a hard no-op in the vendored gem -- `run` is an undefined method
inside a `driven` block, so these silently never fire. Sites: `pr_delivery`,
`pr_mergeable_check`, `main_uptodate_check`, `worktree_create`,
`worktree_remove`.

**3 of 5 are MUTATING** (`gh pr merge --squash --delete-branch`,
`git worktree add`/`remove`) -- converting them to a working effect port
wakes up dormant automation that has never actually run. Needs explicit
sign-off from Chris before touching these three specifically, independent
of the mechanical question of how to wire `run`.

**The 2 read-only ones have a verdict-signature mismatch**
(`refuse_unknown_arguments`) so conversion isn't mechanical either --
needs a widen-or-build-bridge decision that likely also affects the 4
ALREADY-converted sibling checks from i782's execute pass. i782 searched
thoroughly and found no `Cascade.ResultRecorded` consumer anywhere in the
declarative layer -- framed as an open question, not a certainty. Re-check
that before assuming it's still true.

### 3. The `:memory` / `interval` gap (4 roots: tools, storehouse, agent_inbox, event_sourcing)

Two distinct unbuilt-capability gaps, not one:

- **`tools`, `storehouse`** fail with `ArgumentError: wrong number of
  arguments` -- traced to bare `adapter :memory`, which is dead in the
  current gem (not a persistence shortcut it once was). i782's own
  explicit warning: fixing `:web_tool` alone will NOT make `tools` boot --
  ~20 more missing binds surface immediately after `:memory` is addressed.
  Needs a real design decision on what `:memory` becomes, not a patch.
- **`agent_inbox`, `event_sourcing`** fail with `NoMethodError: undefined
  method 'interval'` -- `driving on interval` is unbuilt in the vendored
  gem, confirmed by reading gem source directly in i781. The `cron_adapter`
  and `interval_adapter` parity fixtures both fail to load the same way,
  matching `DrivingHandlers`' own comment that this was never built.

Full 64-root validate sweep was 60/64 as of `e4c1e4dd9` -- these 4 roots
are the entire gap. Closing all three threads above should bring the sweep
to 64/64, but confirm by re-running the sweep, don't assume:
