## 2. The `:memory` gap — root cause is narrower than previously stated

**Correction to i782/i786/i787**: those cards traced the `tools`/`storehouse`
ArgumentError "to bare `adapter :memory`." Read the gem source
(`hecksagon_builder.rb#adapter`, real signature `def adapter(name, &block)`)
and pulled the actual backtrace for both failing roots — **the bare,
no-comma, no-block form (`adapter :memory`) never raises**. Called with one
positional arg and no block, it builds an empty `DrivingAdapterBuilder` and
returns cleanly. Proof: `git.hecksagon` has *only* a bare `adapter :memory`
line and loads fine as part of the same `tools` root boot (alphabetically
before `tools.hecksagon` in the non-recursive glob) — it never contributes
to the crash.

The real crash sites, confirmed via full backtraces:

- **`tools`** crashes at `tools.hecksagon:84` —
  `adapter :web_tool, command: "...", tool: :web_fetch, result_into: "..."`
  (and its `:web_search` sibling at line 85). These pass keyword arguments;
  `adapter(name, &block)` has no `**kwargs` parameter, so Ruby 3's
  positional/keyword split turns them into 2 positional args against an
  arity-1 method → `ArgumentError (given 2, expected 1)`.
- **`storehouse`** crashes at `command_bus.hecksagon:50` —
  `adapter :fs, root: "information"` (same shape). If that line were fixed,
  the *next* crash would be `command_bus.hecksagon:63`
  (`adapter :shell, name: :delegate, command: "storehouse", args: [...],
  output_format: :text, timeout: 60`), then the same `:fs, root:` shape in
  `lexicon.hecksagon`, `query.hecksagon`. `dispatch.hecksagon` has both
  `:memory` bare (harmless) and `adapter :shell, name: :invoke, ...`
  (also crashes).

**So there are 3 distinct legacy `adapter`-kwargs call shapes across the two
roots, all dead the same way, only one of which (`:memory` bare) is actually
harmless:**
1. Bare `adapter :symbol` — no-op, never crashes (2 sites: `git.hecksagon`,
   `tools.hecksagon:37`; plus 4 in storehouse's files).
2. `adapter :web_tool, command:, tool:, result_into:` — crashes (2 sites,
   `tools.hecksagon:84-85`).
3. `adapter :fs, root:` / `adapter :shell, name:, command:, args:,
   output_format:, timeout:` — crashes (5 sites across storehouse's 4
   files).

Fixing only shape 2/3 (removing or converting the crashing lines) would let
both roots' *boot* succeed, but per i782's already-confirmed finding, ~19 of
21 `tools.bluebook` aggregates still have no `persisted_by` bind at all once
the crash is gone — the domain would boot but the wiring-verification pass
(`Registry::Verification`) would then fail those aggregates one by one. Both
halves (crash + missing persistence) need addressing for a real fix.

### 2a. What the bare `adapter :memory` line was ACTUALLY trying to say — read from the file's own comment

`command_bus.hecksagon`'s trailing comment (storehouse, not previously
quoted in i782/i786) states the OLD behavior directly:

> bare `adapter :memory` (no opts, no block) already triggers
> HecksagonBuilder's domain-wide-default sugar (`domain_wide_persisted_by`),
> synthesizing `CommandBus::CommandBus.persisted_by("Memory")` on its own.

That sugar is gone — `adapter` is now a real defined method, not
`method_missing`, so it never reaches the domain-wide-default path anymore.
**But the domain-wide-default path itself is alive and well for a DIFFERENT
verb.** `HecksagonBuilder#method_missing` (still real, still called for any
verb `adapter` doesn't shadow) does exactly this:

```ruby
def method_missing(verb, *args, **kwargs, &block)
  return super unless args.first
  bind = Bind.new(aggregate: nil, verb: verb.to_s, adapter: args.first.to_s, ...)
  @binds << bind
  ...
end
```

and `Hecksagon::Behaviour#bind_for` (real gem code) falls back to
`@binds.find { |b| b.aggregate.nil? && b.verb.to_s == verb.to_s }` whenever
an aggregate has no bind of its own. **This means a bare, domain-level
`persisted_by "Memory"` line does today, mechanically, exactly what the
comment says `adapter :memory` used to do** — one line, applies to every
aggregate in the domain lacking its own override.

**Verified live**, not just read: built an isolated probe domain
(`/tmp/i788_probe`, outside `hecks_conception`, deleted findings not
committed anywhere) with `persisted_by "Memory"` bare at the top of a
2-aggregate hecksagon, one aggregate with its own `persisted_by("Heki")`
override. `Hecksagain.boot` succeeds with no error — confirms the sugar
path is live and doesn't collide with a real per-aggregate override.

### 2b. Is "Memory" even the right semantic default, vs "Heki"?

Read all 19 uncovered `tools.bluebook` aggregates in full (`SearchTool`,
`WebTool`, `AgentTool`, `EmailTool`, `TaskTool`, `Sidequest`, `WakeupTool`,
`CronTool`, `MonitorTool`, `NotifyTool`, `PlanTool`, `WorktreeTool`,
`AskTool`, `SkillTool`, `LspTool`, `MetaTool`, `RemoteTriggerTool`,
`GitTool`, `GitHubTool`). Nearly all of them are the identical shape to
`ShellTool`/`FileTool` — "invocations as first-class dispatched commands,"
one stable invocation `id`, no lifecycle, description text — which is
exactly the shape `ShellTool`/`FileTool` already bind to
**`persisted_by("AppendLog")`**, not `"Heki"`. Their own comment (already
in `tools.hecksagon`) explains why: "A tool call is an EVENT, not an
entity : it has no lifecycle and nothing to update... What matters is that
the act HAPPENED... so it belongs in the Log, not in a store." `AppendLog`
is a real, distinct backend (`lib/hecksagain/adapters/driven/append_log.rb`
+ `.adapter` file in the gem), so "the only proven pattern is
`persisted_by("Heki")`" (i782's framing, from `demo.hecksagon`) is not the
full picture — there are at least 2 proven backends in active corpus use
(`Heki`, `AppendLog`), plus `Memory` used domain-wide elsewhere
(`HecksagonIr::TtsAdapter/ComputeAdapter/LlmAdapter.persisted_by("Memory")`).

**3 of the 19 look like real exceptions, not append-log-shaped:**
- `TaskTool` — has a `status` field, verbs Create/Get/List/**Output**/Stop/
  **Update** — genuinely mutable current-state, not write-once.
- `CronTool` — Create/**List**/Delete, a registry that must be enumerable
  and survive process restarts (a scheduled cron job losing its
  registration on every boot would silently stop firing).
- `WorktreeTool` — Enter/Exit lifecycle tracking `branch`/`path`, similar
  restart-durability concern.

These three plausibly want `Heki` (or per-aggregate override), not a
domain-wide `Memory`/`AppendLog` default; the other 16 look genuinely
append-log/ephemeral-shaped.

### 2c. The `:fs, root:` / `:shell, command:/args:` shapes have no 1-line replacement

Checked `Bind` (the only carrier a per-aggregate or domain-level bind has)
and `BindingProxy#method_missing` — a bind only ever carries `adapter`
(one string), `role`, `on`. No field for `root:`/`dir:`, no field for a
shell command template (`command:`, `args:`, `output_format:`, `timeout:`).
A comment elsewhere in the gem (`behaviour/hexagon.rb`'s `World` module)
references `persisted_by("Heki") do dir :default end` as if a block-form
existed, but grepping the whole gem for a `dir` DSL verb or a
command/args/timeout builder for a `:shell` adapter turns up nothing — no
such builder exists today. **These two storehouse shapes are not a
mechanical rename; they need either a new DSL surface (an options block on
a bind) or relocating the root-dir/shell-command configuration into the
`World` file** (`command_bus.bluebook`'s own comment already gestures at
this: "the world is the deployment").

## 3. The `interval` gap — confirmed as described, deeper picture on "closest working pattern"

Read `DrivingAdapterBuilder` in full and `Bluebook::Hexagon`'s IR (
`hexagon.rb`). The file's own header comment is unambiguous and answers the
task's question directly:

> THE DRIVING SIDE (not yet built here): `driving on cron "*/10 * * * *" do
> |clock| dispatch "..." end` — an external clock reaching IN. Its own
> grammar and runtime scheduler are a separate, still-pending unit; no
> `driving` method is defined on this builder, so writing one today raises
> NoMethodError rather than silently doing nothing.

**`driving` is not defined at all — cron and interval are equally unbuilt,
not "cron works but interval doesn't."** The observed `NoMethodError:
undefined method 'interval'` fires because Ruby evaluates `interval("2s")`
as an argument to `on(...)` before `driving(...)` itself is ever called —
so the trace never even reaches confirming whether `driving` itself would
work; the header comment states plainly it wouldn't. `hexagon.rb` carries
a `DrivingHandler = Struct.new(:adapter_name, :kind, :arg, :dispatch_command,
keyword_init: true)` — the wire/IR shape for both `"cron"` and `"interval"`
kinds already exists and is merged correctly across multi-file hecksagons —
but "this collection is always empty here… no DSL yet builds one," per the
struct's own comment.

**No `storehouse drive` CLI subcommand exists either** — grepped the whole
Rust `storehouse` crate and Ruby CLI, found zero `"drive"` matches. The
`agent_inbox.hecksagon` comment describing `storehouse drive --adapter
InboxPollClock` is aspirational documentation of the intended design, not a
description of something partially working. **This is a fully unbuilt
feature end to end: no DSL verb, no runtime scheduler, no CLI entry point.**

4 sites use `driving on interval`: `agent_inbox.hecksagon` (2s),
`event_sourcing.hecksagon` (2 handlers, 5s + 60s), plus the 2 parity
fixtures `cron_adapter.hecksagon` (`driving on cron`) and
`interval_adapter.hecksagon` (`driving on interval`) which exist
specifically to prove Ruby/Rust parity on this exact unbuilt grammar (both
fail identically today, which IS parity — they just don't validate).

### A no-gem-change alternative already lives in the corpus

`hecks_conception/bin/inbox_poll.mjs` is a real, currently-working
externally-scheduled poller — a Node script invoked by an outside
scheduler (cron/launchd, not `storehouse drive`) that does OAuth + delta
polling and drives real dispatches via the CLI door. It is *exactly* the
pattern `agent_inbox.hecksagon`'s own comment says `driving on interval`
was meant to REPLACE: "replacing the old `bin/agent_poll.sh` bash loop
(which cold-spawned `storehouse` ~30×/min)." In other words, the
"old-fashioned" alternative to `driving on interval` — an OS-level
scheduled process that calls `storehouse <root> Domain::Aggregate.Command`
directly on its own cadence — is already a proven, live pattern in this
exact codebase for a structurally identical problem (Gmail polling). It
sacrifices the "one warm in-process `storehouse drive`" efficiency goal
the agent_inbox comment explicitly wanted to move away from (cold-spawn
per tick instead of a persistent scheduler), but it requires zero gem
changes and could unblock `agent_inbox`/`event_sourcing` validation today
by moving their 4 `driving on interval` blocks out of the `.hecksagon`
entirely and back into an external script + crontab/launchd entry.

## 4. Design options

### `:memory` gap (tools, storehouse)

**(a) Domain-wide `persisted_by "Memory"` sugar + per-aggregate `Heki`
overrides for the 3 stateful exceptions.** Smallest fix: one bare line per
`.hecksagon` file (`persisted_by "Memory"` at the top, matching the gem's
own comment on what the old `adapter :memory` sugar used to do — verified
live to not crash), plus explicit `TaskTool.persisted_by("Heki")` /
`CronTool.persisted_by("Heki")` / `WorktreeTool.persisted_by("Heki")`
overrides for the 3 aggregates that need cross-restart durability. Does
NOT touch the `:fs, root:` / `:shell, command:/args:` crash sites — those
still need (b) or (c) below regardless.

**(b) Domain-wide `persisted_by "AppendLog"` instead of `"Memory"`,**
matching `ShellTool`/`FileTool`'s already-proven precedent and the
observed shape of 16/19 aggregates more precisely (invocation history,
not truly memory-only/ephemeral — `AppendLog` is durable, `Memory` is
not). Same TaskTool/CronTool/WorktreeTool exceptions apply. Slightly
stronger fit than (a) since it reuses the exact backend the file's own
comment already justifies for the two aggregates that DO have an explicit
bind, rather than reviving retired comment-text about `Memory`.

**(c) For the `:fs, root:` / `:shell, command:/args:/output_format:/
timeout:` shapes specifically (storehouse's real remaining problem, no
1-line fix available): extend the gem's `Bind`/DSL with an options block**
(e.g. `persisted_by("Heki") do dir "information" end`, `executed_by
("Shell") do command "storehouse" ; args [...] ; timeout 60 end`) —
real gem work, not mechanical. **Alternative that avoids a gem change:**
push `root`/shell-command-template configuration into the `World` file
(`command_bus.bluebook`'s own comment already gestures at this pattern:
"the world is the deployment"), if `World` already supports a settings
block for these two adapters (needs verification — not confirmed this
session; `World::for_binding`'s existing fallback-by-adapter machinery
looks like it may already be built for exactly this and just unused by
these 5 sites).

### `interval` gap (agent_inbox, event_sourcing)

**(a) Build `driving on cron`/`driving on interval` in the gem** — real
scope: a `driving(kind, &block)` method on `DrivingAdapterBuilder` (mirror
`driven`'s shape), `cron(schedule)`/`interval(duration)` sugar methods
that populate `DrivingHandler`'s existing `kind`/`arg` fields (the IR
already anticipates both), PLUS a genuinely new runtime piece with no
existing analog to mirror — an actual scheduler process and the
`storehouse drive` CLI verb that doesn't exist yet either. This is bigger
than i781/i782 characterized it (they treated it as "just build the DSL
verb"; the CLI entry point and scheduler loop are equally unbuilt and
would need building too, or `driving`'s dispatches would have nothing to
invoke them). Fork PR + Gemfile re-pin, same playbook as prior threads.

**(b) Move the 4 `driving on interval` blocks out of the bluebook entirely,
onto an external OS-scheduled poller** (cron/launchd) calling `storehouse
<root> Domain::Aggregate.Command` directly — the exact, already-proven
`bin/inbox_poll.mjs` pattern. Zero gem changes; unblocks validation today.
Trade-off: reintroduces the cold-spawn-per-tick cost `agent_inbox
.hecksagon`'s own comment explicitly wanted to retire (~30 spawns/min for
a 2s interval is the same order of magnitude the comment complains about
for the old `bin/agent_poll.sh`), and is a step backward from the "one
warm `storehouse drive` process" design goal on record. Reasonable as an
interim unblock, not obviously the final answer.

**(c) Hybrid — ship (b) now to get `agent_inbox`/`event_sourcing` back to
64/64, file (a) as the real fork-PR-scoped follow-up** once Chris confirms
the warm-process design goal is still wanted. Lets the sweep go green
without deciding the scheduler architecture under time pressure.
