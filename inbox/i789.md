# i789 — correction to i788 : the 4 "invalid" roots were a stale-gem artifact, not a real gap

*Continuation of i776 → ... → i788 (2026-08-18). Found while executing Chris's
"repin" instruction for the for_each fix (i787 thread 1, merged as
hecks-hecksagain#8). Read i788 first if you haven't -- this card narrows its
scope, doesn't replace its `interval`/`:fs`/`:shell` findings wholesale (see
below).*

## What happened

Re-pinning the Gemfile from `48d2210` to `main`'s HEAD (`1cce2d10`, the
for_each merge) broke the ENTIRE corpus (0/63 valid) -- but the break traced
to something totally unrelated to for_each: `main` has diverged from
`48d2210` (353 ahead / 59 behind per GitHub, not a simple ancestor
relationship) and its current HEAD dropped 2-positional-arg `aggregate`
support that the whole corpus depends on (`aggregate "Name", "description"
do ... end`). Backed out of pinning to raw `main`; a subagent instead
hand-ported the for_each fix's semantics onto the `48d2210` base directly
(straight `git cherry-pick` conflicted on 8/10 files -- the two lines use
different DSL grammars entirely, upstream's `dispatch(command, with: {},
for_each: nil)` vs this base's vendored `dispatch(command_fqn, **kwargs)`).
New commit: `f7db259e` on branch `fix/for-each-on-stable-base`, one commit
on top of `48d2210`.

**While verifying the re-pin, ran the same 64-root sweep i788 ran, and it
came back 63/63 valid -- including `tools`, `storehouse`, `agent_inbox`,
`event_sourcing` by name, confirmed genuinely swept and passing, not
silently excluded from the count.** This directly contradicts i788's
60/64-with-4-invalid finding, posted hours earlier the same session.

## Isolating the discrepancy

Ran the sweep three times to isolate what actually changed:

1. `f7db259e` (48d2210 + ported for_each fix): **63/63 valid**.
2. `48d2210` alone, freshly `bundle install`'d (no for_each changes at
   all): **also 63/63 valid**. This is the SAME commit i788 investigated.

**Conclusion: the for_each port did not fix the 4 roots -- they were
already passing on `48d2210` all along.** i788's investigation almost
certainly ran against a stale installed gem, not the Gemfile's actual
declared pin. Circumstantial evidence: at the start of this session (before
any fresh `bundle install` in this thread), `bundle show hecksagain`
reported `74ea7da` -- an OLDER commit than the Gemfile's own `ref: "48d2210"`
line -- and no `Gemfile.lock` existed to pin the resolution, meaning
`bundle exec` was silently running against whatever was last installed
locally, not what the Gemfile declared. `48d2210`'s own commit message
(dated 2026-08-15, predating this session) describes fixing exactly the
class of bug i788's `interval`/`:memory` framing would produce as a
symptom -- unresolved deep-namespaced dispatch strings on the driven side
-- via a `resolve_verb` unification. Plausible that this fix (or something
else between `74ea7da` and `48d2210`) is what actually closed the gap, and
i788 never saw it because its environment hadn't picked it up.

## What's retracted vs. what still stands from i788

**Retracted**: the claim that `tools`/`storehouse`/`agent_inbox`/
`event_sourcing` are currently invalid, and the "2-3 design options per
gap" proposing how to fix them -- there is nothing to fix right now, per
this live re-verification. Don't implement any of i788's options 2a-2c or
3a-3c against the current pin without re-confirming the gap actually exists
first.

**Still an open question, NOT re-verified either way by this card**:
whether `driving on interval` and the `:fs`/`:shell` adapter-kwargs shapes
are ACTUALLY built now (i.e. i788's characterization of them as unbuilt was
simply wrong), or whether they're still unbuilt but some other mechanism
(a fallback, a different code path) is making the 4 roots validate anyway
without those specific capabilities actually working end-to-end. `validate`
only proves the domain BOOTS -- i782 already established this exact trap
("validate green isn't proof a bind is real, check the compiled registry").
Whoever picks this up next should probably dispatch a real
`agent_inbox`/`event_sourcing` interval-driven event and confirm it
actually fires on a live clock, and confirm `tools`'s `:web_tool`/
`:fs`/`:shell` adapters genuinely execute, before trusting that these 4
roots are functionally complete just because they parse.

## The actual, unrelated, real finding from this session

`hecks-hecksagain`'s `main` branch is currently broken for this corpus (see
above) and has diverged from the commit (`48d2210`) actually in production
use here. Whoever next touches the Gemfile pin should NOT assume `main`'s
HEAD is safe to pin to without the same live-boot verification this card
did -- `validate` passing on the gem's own spec suite (as PR #8's 1606/0
and the ported branch's 1276/7-matching-baseline both did) does not catch
breakage in the CONSUMING corpus's actual DSL usage patterns.

## Do not

- Don't re-implement any of i788's :memory/interval fix options without
  first re-confirming the gap is real against a freshly `bundle install`'d
  gem -- this card found it may not exist.
- Don't pin the Gemfile to `hecks-hecksagain`'s raw `main` HEAD without a
  live boot check against real `hecks_conception` bluebooks first -- it is
  currently broken and diverged from the commit actually in use.
- Don't trust a "clean sweep" number from any card (including this one)
  without checking whether `Gemfile.lock` existed and was fresh at the time
  -- an absent or stale lockfile silently resolves against whatever gem
  happens to be cached locally, not what the Gemfile declares.
