# i791 — the door has never actually been smoke-tested; validate ≠ dispatch, still

*Follow-up to i790, filed same session immediately after merging i790's fix
to `hecks_playground` main (commit `d59310338`, 64/64 validate, confirmed no
regressions). Re-ran the smoke-test dispatch i789 originally asked for,
against the now-reconciled `main` — still fails, on a new, third shape of
error.*

## What's confirmed on the reconciled main

```
storehouse__dispatch aggregates_dir=hecks_playground_conception command=Tools::ShellTool.Bash
=> Hecksagain::Runtime::WiringError: unknown adapter "MainUpToDateCheck"
```

Traced to `aggregates/plan/bluebook/main_uptodate_check.hecksagon` —
notably NOT a `hecksagons/` sibling-folder file this time (it's in the
domain's own `bluebook/` dir), so this is not even the same file-set
discrepancy i790 diagnosed. It's a third, independent gap.

## The pattern across this whole arc, named explicitly

Every session in i776→i790 fixed ONE crash the door hit, declared some
flavor of "64/64" or "the gap is closed," and the NEXT session (or the
next few minutes of THIS session) found the door still didn't actually
dispatch — for a completely different reason each time:

1. `driving on interval` NoMethodError (i786-i789)
2. `adapter` kwargs-form ArgumentError (i788, same arc)
3. `driven` block's `event.method` NoMethodError — `instance_eval` binds
   the block param to the capture object, not a real event (i790, this
   session, also independently found+fixed by the parallel i787 session)
4. bare (non-`with:`) kwargs on a `driven` dispatch call — ArgumentError
   (i790, this session + i787's own sweep)
5. `unknown adapter "MainUpToDateCheck"` WiringError (THIS card, just now)

**`storehouse__validate` returning 64/64 has been treated as "the door
works" at least four separate times across this arc and has been wrong
every time.** It validates that each of 64 roots BOOTS in isolation ; it
has never validated that a command actually DISPATCHES through the full,
flattened, multi-root corpus the real door operates against.

## What this needs, not attempted here

1. **Chris's call from i790 section 6**, unchanged and still blocking:
   is a file `validate` never reaches (whether `hecksagons/` sibling
   folders or, per this card's new finding, possibly other categories too)
   supposed to be live? Everything below depends on the answer.
2. **A real run-to-exhaustion sweep of the DISPATCH path**, not another
   validate pass — pick a handful of representative commands (not just
   `Tools::ShellTool.Bash`) and dispatch each one repeatedly, fixing
   whatever crashes, until a dispatch actually completes clean. This
   card's own finding (a `bluebook/`-dir file failing, not just
   `hecksagons/` ones) suggests the discrepancy may be broader than i790
   scoped it — worth re-deriving what `stage_flat_corpus` actually stages
   vs. what each per-root `validate` call stages, precisely, rather than
   inferring it from crash sites one at a time.
3. Once a clean dispatch is achieved for real, add an actual smoke-test
   step to whatever session-end checklist currently ends on `validate`
   alone (this card's own restart-prompt lineage, i789's included) — the
   1-4 above is the direct evidence that validate-only is insufficient
   sign-off for "the door works."
